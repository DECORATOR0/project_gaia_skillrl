## 名词口径

### chunk

`chunk` 是 streaming/SSE 返回的增量片段。一个 chunk 可能包含：

- `delta.reasoning` 或旧名 `delta.reasoning_content`
- `delta.content`
- `finish_reason`
- usage 或其他元数据

在 vLLM 的 Qwen stream 场景里，`chunk_count` 常常接近 `completion_tokens`。它可以作为输出长度的近似观测，但严格含义仍然是 SSE 分片数。

### content 与 reasoning

vLLM 文档说明，Qwen3 系列使用 `qwen3` reasoning parser；reasoning 会被解析到 `reasoning` 字段，旧字段名是 `reasoning_content`。Qwen3 的 reasoning 默认开启；要关闭可传 `chat_template_kwargs={"enable_thinking": false}`。

Qwen 官方 quickstart 也说明，Qwen3 在 thinking mode 下会先生成 `<think>...</think>` thinking content，然后生成最终 response content。

因此，一个请求可能出现大量 reasoning chunk，但 `content_chunk_count=0`。对 GAIA executor 来说，这类 chunk 消耗时间和服务端 running slot，却不会产生可解析动作。

### max_context_chars

`max_context_chars=48000` 是 GAIA 侧构造 executor 输入时的字符裁剪上限。它控制输入 prompt 的大小。

它不控制模型输出长度，也不控制 thinking 长度。

### max_model_len / max_seq_len

这是 vLLM 服务端允许的总序列长度，近似等于：

`prompt tokens + completion tokens`

旧 8B 本地服务为 `40960`。远端 9B 当前 `/v1/models` 报 `max_model_len=262144`。

远端 9B 的输入没有变大太多，但服务端给输出留下了更大的空间。

### max_tokens

这是单次请求允许生成的新 token 上限。它包含 reasoning 和 content。

当前 9B baseline 没有显式设置 `max_tokens`，所以生成长度主要受服务端默认和 `max_model_len` 约束。

### thinking_token_budget

vLLM 新文档说明，部分模型包括 Qwen3 支持 `thinking_token_budget`。token 计数从 reasoning 起始标记开始；达到预算后，vLLM 会强制模型生成 reasoning 结束标记，从而终止 reasoning block。若不设置该参数，reasoning 没有额外上限，只受 `max_tokens` 等常规生成约束。

Qwen 官方 stable quickstart 对 thinking budget 的说明较保守：当时写的是开放框架里可用“两段生成 + early-stopping prompt”模拟；同时建议实践中 budget 不要低到 16，应该按可接受延迟调参，并高于 1024 才有意义。

Qwen3 技术报告在长上下文 thinking evaluation 中使用 `8192` thinking budget，用来缓解超长输入下的过度 verbose reasoning。

## 为什么 8B 长 chunk 没报，9B 长 chunk 报

8B 极端样本：

- 3.6 万 chunk 基本都是 content。
- 服务端到 `40960` 总 token 后返回 `finish_reason=length`。
- 客户端拿到了正文和结束信号。

9B timeout 样本：

- 8 万级 chunk 很多都没有 content。
- 很多 attempt 在 `1200s` 时仍然没有服务端结束信号。
- 客户端只能按 wall timeout 切断。

所以问题不在 chunk 多本身。问题在于长时间没有可用 content，并且没有正常 finish。

## 为什么 9B 更容易暴露

目前最可能的组合原因：

1. 9B 远端 `max_model_len=262144` 给 runaway thinking 留了很大空间。
2. 当前 executor 没有显式 `max_tokens`。
3. 当前没有 `thinking_token_budget`。
4. GAIA 某些 step 进入搜索失败、网页 404、Serper 400、证据不足或修复循环。
5. Qwen3.5-9B 的 thinking 行为可能比 Qwen3-8B 更倾向长 reasoning。

另外，当前远端 metrics 显示 `num_requests_waiting=0`，`num_requests_running=8`，所以这批异常更像 active decode 长跑。它们已经进了 engine，在持续生成 stream chunk。

## 初始预算建议

目标是保留 thinking，但防止 single step 在 reasoning 中跑成 8 万 chunk。

预算要同时覆盖三件事：

- 输入：`max_context_chars` 或 token 级 input limit，避免 prompt 过长。
- hidden reasoning：`thinking_token_budget`，避免正文被一直往后挤。
- 总输出：`max_tokens`，同时限制 reasoning 和正文，防止正文长跑。

建议先做小网格：

| 配置 | `max_model_len` | `max_tokens` | `thinking_token_budget` | 用途 |
| --- | ---: | ---: | ---: | --- |
| A | 40960 或 49152 | 4096 | 2048 | 最保守，先看空答和 timeout 是否消失 |
| B | 40960 或 49152 | 8192 | 4096 | 更接近 Qwen 官方建议下限以上 |
| C | 40960 或 49152 | 12288 | 8192 | 对齐 Qwen3 技术报告长上下文 budget |

如果远端服务暂时不能重启改 `max_model_len`，先只改请求侧：

- `NLRL_EXECUTOR_MAX_TOKENS=4096`
- 或 `NLRL_EXECUTOR_MAX_TOKENS=8192`
- 若远端 vLLM 支持 sampling 参数，额外传 `thinking_token_budget=2048/4096`。

当前代码只会把 `chat_template_kwargs={"enable_thinking": true}` 放进 payload，还没有传 `thinking_token_budget`。需要在 `gaia_skillrl/llm.py` 里加一个环境变量入口，例如：

- `NLRL_EXECUTOR_THINKING_TOKEN_BUDGET`
- `NLRL_LLM_THINKING_TOKEN_BUDGET`

同时保留 response metadata：

- `chunk_count`
- `reasoning_chunk_count`
- `content_chunk_count`
- `first_content_chunk_index`
- `finish_reason`
- `usage.completion_tokens`

但上游实现形式和 `project_skills-3.18dhc-19.40` 有差别：

- 上游主要走 LangGraph/LangChain `create_react_agent` 和 OpenAI tool calls。
- 上游 prompt 的最终答案格式是 `<Answer>Your choice<Answer>`。
- 上游没有使用 `project_skills` 这种显式 `<THOUGHT>/<CALL>/<ARGS>/<NEXT>/<ANSWER>` 标签协议。
- 上游日志会把 assistant 文本和 `tool_calls` 分开记录，外层过程主要来自 LangChain message/tool-call 轨迹。

上游并非只有最终 answer 会往下传。`scripts/langchain_qwen3_32B.py` 中 `agent.ainvoke({"messages": [...]})` 返回完整 `response["messages"]`，代码随后遍历所有 message：

- human message 进入 conversation log。
- AI message 的 `message.content` 被记录为可见文本，代码注释称为 `thinking content (text before tool calls)`。
- AI message 的 `additional_kwargs["tool_calls"]` 被记录为工具调用。
- tool message 被记录为工具结果。

因此，上游也有“可见过程文本 + tool call + tool result + final answer”的外层轨迹。只是它依赖 LangChain/OpenAI tool-call message 结构，没有强制每一步输出 `<THOUGHT>` 标签。

上游 Qwen3 相关配置：

- `agent/config_qwen3.json`：`generate_args={"enable_thinking": false}`
- `agent/config_qwen3_plus.json`：`generate_args={"enable_thinking": false}`
- `agent/config_qwen3_max.json`：`generate_args={"enable_thinking": false}`

上游本地/可部署模型配置没有发现：

- `thinking_token_budget`
- `chat_template_kwargs`
- `reasoning_content`
- `max_completion_tokens`

上游统一把 config 里的 `generate_args` 透传到 LangChain `ChatOpenAI(extra_body=...)`。因此如果将来要加 `thinking_token_budget`，上游这套结构理论上可以通过 `generate_args` 注入，但当前官方配置没有这么做。

和当前 GAIA 9B 的关键差异：

- 当前 GAIA 9B：`enable_thinking=true`，远端 `max_model_len=262144`，请求侧暂时没有 `max_tokens/thinking_token_budget`。
- 上游 Earth-Agent Qwen3：`enable_thinking=false`，也没有 thinking budget。
- `project_skills-3.18dhc-19.40`：`enable_thinking=true`，支持 `max_tokens` 配置/环境变量，但没有 thinking budget 入口。

### 论文是否说明 Qwen thinking 开关

检查论文：

- arXiv: https://arxiv.org/abs/2509.23141
- PDF 文本检索词：`Qwen`、`think`、`thinking`、`chain-of-thought`、`CoT`、`enable`、`thinking_token_budget`

论文明确写了 Earth-Agent 是 ReAct-style POMDP，并在每轮包含：

- Tool calling
- Memory update
- Think
- Action

论文还写到完整交互历史会保存在 memory stack 中，后续 reasoning 会基于更新后的 memory 和任务目标进行。实验部分报告了 Qwen3-Max、Qwen-Plus、Qwen3-32B 等 backbone。

但论文没有说明 Qwen3 的模型原生 thinking mode 是否开启，也没有说明 `enable_thinking`、`thinking_token_budget`、hidden reasoning stream 或 CoT 输出策略。因此，关于“官方上游 Qwen3 实际请求关了 thinking”的判断主要来自 GitHub 配置文件，而非论文正文。

### 本机 `Earth-Agent-origin` 的 shlab 配置

检查目录：

`/data/xsy/Earth-Agent-origin`

该目录 remote：

`https://github.com/opendatalab/Earth-Agent`

本机 HEAD 与远端 `main` 当前一致：

`ca1dfaef750654331308a434966d307f1728fd90`

本机存在：

`/data/xsy/Earth-Agent-origin/agent/config_qwen3_8b_shlab.json`

关键配置：

```json
"config_name": "qwen3-8b-shlab",
"model_name": "qwen3-8b",
"generate_args": {
  "enable_thinking": true
}
```

这个文件没有被 git 跟踪，且命中 `.gitignore`：

```text
.gitignore:14:agent/config_*.json
```

所以它不会出现在官方 GitHub 目录里。`git log --all -- agent/config_qwen3_8b_shlab.json` 没有历史记录；没有发现上游 commit 对该文件执行删除。

本机还有两个未跟踪脚本引用它：

- `/data/xsy/Earth-Agent-origin/scripts/run_qwen3_8b_formal60_parallel.sh`
- `/data/xsy/Earth-Agent-origin/scripts/langchain_qwen3_8b_autoplan.py`

其中 `langchain_qwen3_8b_autoplan.py` 对 Qwen3-8B 做了额外请求侧约束：

- `default_input_token_limit = 32768`
- `default_max_output_tokens = 8192`
- `request_timeout = 300`
- `streaming = True`
- `max_tokens = max_output_tokens`
- `extra_body = generate_args`

结论：本机 shlab 版本是“开 thinking + 输出最多 8192 + 输入估算 32768”的本地实验链路。官方当前 Qwen3 配置是“关 thinking + 无 thinking budget”。这解释了你看到的差异：`Earth-Agent-origin` 里的 shlab 文件属于本地保留/新增配置，不属于官方 main 的受跟踪文件。
