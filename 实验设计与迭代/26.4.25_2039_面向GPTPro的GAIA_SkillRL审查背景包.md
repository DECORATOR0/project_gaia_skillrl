## 1. 项目目标与基本假设

项目目标是用一套可训练的 skill 框架提升小 executor 模型在 GAIA 上的表现。

核心假设：

- GAIA 任务常需要局部文件读取、网页检索、结构化计算、格式核对和有限 repair。
- 小模型直接 ReAct 容易走偏、重复调用错误工具、过早给答案或缺少证据门禁。
- 把通用解题过程压缩成 phase graph，并逐 phase 注入 skill，可以降低执行时上下文负担。
- 强模型 critic / actor 可以从失败轨迹中抽取可迁移规则，再把这些规则写回 `SKILL.md`，让低成本 executor 得到行为增益。

当前主目标：

- 第一阶段：把 GAIA 本地 held-out `validation_test` 分数稳定拉高。
- 第二阶段：用相似框架迁移到 AgentBench DB/OS、WebShop text、tau retail 等工具型任务。

当前最大限制：

- executor 是 `qwen3-8b`，能力有限，prompt 不能太长。
- actor / critic 可用强模型，但 API 队列和额度曾多次中断，导致部分 run 需要干净重跑。
- 当前常规 actor 被限制在固定图里改文本，不能改 phase 数量、顺序和 `Next:` 目标集合。
- GAIA 官方 test 没有 gold，本地主要用 validation 切出的 `validation_test` 做 held-out 观察。

## 2. 数据与评估设置

本地使用 GAIA 2023 validation 作为可打分集合，共 165 题：

| split | 题数 | level 分布 | 用途 |
| --- | ---: | --- | --- |
| all validation | 165 | L1=53, L2=86, L3=26 | 原始可打分集合 |
| validation_dev | 83 | L1=27, L2=43, L3=13 | bootstrap、critic / actor 调参 |
| validation_test | 82 | L1=26, L2=43, L3=13 | 本地 held-out test |
| official test | 官方隐藏 | 无 gold | 最终提交方向 |

切分策略：按 level 分层，保留原始顺序，dev 使用向上取整。

打分方式：

- 每个任务最终只取 executor 输出的 `final_answer`。
- 与 gold answer 通过 GAIA scorer 判定 `task_success`。
- 每题保存完整 state，包括 tool trace、phase transition、action trace、outcome counts。
- 训练时看 dev，泛化判断主要看 `validation_test`。

## 3. 当前模型、工具与 runtime 配置

当前配置快照：

| 组件 | 设置 | 说明 |
| --- | --- | --- |
| executor | `qwen3-8b` | 真实执行任务的小模型，stream 模式 |
| actor | `gpt-5.2` | 当前配置；历史 run 多处用过 `gpt-5.4` |
| critic | `gpt-5.2` | 当前配置；历史 run 多处用过 `gpt-5.4` |
| executor temperature | 0.1 | 偏稳定执行 |
| actor / critic temperature | 0.2 | 偏稳定修改和诊断 |
| max executor steps | 24 | 部分旧实验试过 32 |
| max context chars | 48000 | executor 消息截断预算 |
| web search results | 5 | 默认搜索返回数 |
| web fetch char limit | 6000 | 默认网页文本截断 |
| task concurrency | 常用 c20，资源紧张用 c6 | 影响稳定性和队列压力 |

可用工具 16 个，按功能分组：

| 工具族 | 工具 |
| --- | --- |
| 本地文件 | `list_dir`、`read_file`、`read_json_file` |
| 文档 / 表格 | `extract_pdf_text`、`read_table`、`parse_docx`、`parse_pptx`、`extract_archive` |
| 多模态 | `image_metadata`、`ocr_image`、`image_qa`、`audio_transcribe` |
| Web | `web_search`、`fetch_url`、`html_extract` |
| 计算 | `run_python` |

关键工具语义：

- `read_table(path, max_rows)` 支持 CSV / XLSX / XLSM / XLS，返回 columns、row_count、preview。
- `web_search(query, max_results)` 使用 DuckDuckGo，失败时会走 HTML fallback。
- `fetch_url(url, max_chars)` 拉取网页并返回 title / cleaned text。
- `html_extract(url or path, max_chars)` 提取正文和最多 20 个 links。
- `run_python(code, input_json)` 在项目 Python 环境执行临时代码，返回 returncode、stdout、stderr、stdout_json。

已知工具问题：

- 有 case 中 `.xlsx` 表格解析失败，表现为 `read_table` unsupported 或环境依赖 / 文件兼容问题。
- 有 case 中 executor 连续用 `_raw` 作为 `run_python` 参数，被 schema 拒绝多次。
- Web 数据库类任务容易卡在入口页，缺少 site-specific helper 或 query template。
- 图片几何题只靠 OCR / image_qa 很难稳定得到可计算结构。

## 4. Executor 协议与逐 phase 注入机制

executor 必须使用三类标签：

```text
<CALL>tool_name</CALL><ARGS>{...}</ARGS>
<NEXT>PHASE_NAME</NEXT>
<ANSWER>short final answer</ANSWER>
```

runtime 每一步做以下检查：

1. 当前 phase 是否允许该工具。
2. `<NEXT>` 目标是否在当前 phase 的 `Next:` 集合里。
3. `<ANSWER>` 是否发生在 `CONCLUDE` phase。
4. 工具参数是否符合工具 schema。
5. step 是否达到 `max_executor_steps`。

逐 phase 注入：

- 初始 prompt 只包含 task 信息和 `INIT` phase。
- executor 发 `<NEXT>` 后，runtime 注入目标 phase 的内容。
- 当前 phase 之外的节点说明不会同时暴露给 executor。
- `Allowed tools:` 行和 phase 文本里的 `<CALL>` 示例会被解析成工具白名单。
- `Next:` 行会被解析成 transition graph。

错误反馈：

- 非法工具：反馈当前 phase 允许的工具。
- 非法转移：反馈当前 phase 允许的 next phase。
- 非 `CONCLUDE` phase 输出答案：记录 `invalid_answer_phase`，要求继续当前 phase。
- 无法解析动作：记录 `unrecognized_action`，提示只能 tool / next / answer。

低步数兜底：

- 当剩余步数很少，且当前 phase 允许去 `CONCLUDE`，runtime 会注入 fallback conclude prompt，要求停止采集并把已有证据映射成最终短答案。

这个设计提升了可控性，但也带来摩擦：如果 executor 在中间 phase 已经有答案并直接 `<ANSWER>`，runtime 会拒绝，统计上出现大量 `invalid_answer_phase`。

## 5. Skill 图结构

当前主力 skill 是 boot-v3 固定图，8 个 phase：

| phase | 职责 | 主要工具 |
| --- | --- | --- |
| `INIT` | 读任务、识别题型、记录答案约束、路由 | `list_dir`、`read_json_file`、`read_file` |
| `ATTACHMENT_PARSE` | 解析附件，生成本地证据或结构化数据 | 文件、表格、Office、图像、音频、archive、`run_python` |
| `WEB_RESEARCH` | 搜索、抓取、抽取网页证据 | `web_search`、`fetch_url`、`html_extract`、`run_python` |
| `DIRECT_REASON` | 自包含逻辑、字符串变换、规则推理 | `run_python` |
| `COMPUTE` | 计数、过滤、join、枚举、单位换算 | `run_python` 和少量读取工具 |
| `VERIFY` | 支撑性、完整性、格式、单位、字段检查 | 读取 / 抽取 / `run_python` |
| `REPAIR` | 对一个具体 blocker 做一次不同策略修复 | 全工具 |
| `CONCLUDE` | 只输出最终答案 | 无工具 |

当前图的边大致如下：

```text
INIT -> ATTACHMENT_PARSE / WEB_RESEARCH / DIRECT_REASON / COMPUTE / VERIFY / CONCLUDE
ATTACHMENT_PARSE -> COMPUTE / WEB_RESEARCH / VERIFY / REPAIR / CONCLUDE
WEB_RESEARCH -> COMPUTE / VERIFY / REPAIR / CONCLUDE
DIRECT_REASON -> ATTACHMENT_PARSE / WEB_RESEARCH / COMPUTE / VERIFY / REPAIR / CONCLUDE
COMPUTE -> VERIFY / REPAIR / CONCLUDE
VERIFY -> REPAIR / CONCLUDE
REPAIR -> ATTACHMENT_PARSE / WEB_RESEARCH / COMPUTE / VERIFY / CONCLUDE
CONCLUDE -> final answer
```

核心行为意图：

- 简单强证据题允许短路径。
- 多源、多表、多网页题应经过 `COMPUTE`。
- 非平凡计算、计数、比较、格式敏感题应经过 `VERIFY`。
- `REPAIR` 必须诊断一个具体 blocker，并做一次不同策略修复。
- `CONCLUDE` 是唯一合法最终答案出口。

当前 skill 的全局规则重点：

- 先捕获 exact answer contract：字段、类型、大小写、分隔符、排序、单位、舍入、日期/版本范围、全量/最小/最后一行等量词约束。
- 搜索结果摘要、标题、工具失败消息、blocked fetch、parser error、记忆事实都不能当最终证据。
- 进入 `CONCLUDE` 前必须有非空候选答案和支持来源。
- 支持来源应来自附件抽取、网页正文抽取、或确定性计算。
- schema / permission / blocked-search / path error 后最多做一次纠正重试，随后换策略或换 phase。
- 对计算和比较题，偏向先 `VERIFY` 再 `CONCLUDE`。

## 6. Bootstrap、Critic、Actor 的训练闭环

训练闭环：

1. 选取 dev tasks。
2. Bootstrapper 读取 runtime contract 和 batch task snapshot，生成初始 `gaia-general-skill/SKILL.md`。
3. executor 用当前 skill 跑一批题，保存 state。
4. critic 把每题压缩成 compact row，诊断失败族和节点级修改建议。
5. actor 根据 critic reward 改写 `SKILL.md`。
6. 保存 skill_before_actor、skill_after_actor、run_summary。
7. 用更新后的 skill 再评估 dev / validation_test。

bootstrap 输入：

- runtime contract。
- batch task snapshot。
- 约束：生成 common preface + phase-local instructions；图要表达 GAIA 可复用流程；`CONCLUDE` 路径合法；节点说明要足够短，适合 `qwen3-8b`。

critic 输入：

- compact execution rows。
- 当前 skill 全文。
- locked graph signature。
- 最近 history。

critic compact row 字段：

- `task_id`
- `level`
- `task_prompt`
- `file_list`
- `gold_answer`
- `final_answer`
- `success`
- `step_count`
- `empty_answer`
- `max_step_hit`
- `outcome_counts`
- `path`
- `tools`，包括 tool name、step、success、失败 error 截断。

critic 分族策略：

| family | 规则 |
| --- | --- |
| `success_anchor` | 成功题，作为要保护的行为 |
| `no_answer_or_timeout` | 空答案或达到 max steps |
| `protocol_friction` | `invalid_answer_phase`、非法转移、工具被拒、无法解析动作等 |
| `media_attachment_failure` | 图像、音频、PDF 等媒体相关失败 |
| `local_attachment_failure` | 表格、Office、archive、JSON、txt 等本地附件失败 |
| `web_retrieval_failure` | web_search / fetch_url / html_extract 相关失败 |
| `answer_synthesis_or_format_failure` | 有 final answer 但答案合成或格式错 |
| `other_failure` | 其他失败 |

full critic 与 sharded critic：

- full critic：一次吃全 batch，给一个整体 reward。
- sharded critic：按上述 family 分 shard，分别诊断后再 aggregate。

actor 权限：

- 可以改 common preface。
- 可以改每个 phase 的 Goal、Allowed tools、Rules、Exit handoff、Available actions。
- 可以澄清已有 `Next:` 边的使用条件。
- 可以收窄或放宽 phase-local tool permissions。

actor 边界：

- phase 名称固定。
- phase 顺序固定。
- `Next:` 目标集合固定。
- skill name 固定。
- 不写 task-specific 答案、task id、固定事实、固定 URL、假文件名、示例 HTML、dummy Python。
- 当前没有脚本资源生成权限，只改 `SKILL.md`。

## 7. 关键实验结果

目前最重要的分数表：

| run / skill | dev | validation_test | 观察 |
| --- | ---: | ---: | --- |
| direct qwen3-8b | - | `14/82` | 无 skill 直跑基线 |
| bootstrap v0.2 | `18/83` | `15/82` | 初始 skill 有轻微收益 |
| boot-v3 初始 skill | `18/83` | `14/82` | test 与 direct 持平 |
| A full critic iter2 | `21/83` | `11/82` | dev 涨，test 掉 |
| B sharded critic iter2 | `14/83` | `17/82` | test 短期最高，需干净重跑确认 |
| A full critic iter3 | `21/83` | `14/82` | 回到 baseline |
| B sharded critic iter3 | `21/83` | `13/82` | dev 追上，test 回落 |

初步结论：

- skill 文本可以改变 executor 行为，因为 dev 能从 `18/83` 涨到 `21/83`。
- test 没有稳定跟涨，说明当前 critic / actor 存在 dev 局部规则化风险。
- sharded critic 曾把 test 推到 `17/82`，说明按失败族诊断可能有效。
- 继续叠规则后 test 回落，说明 actor 可能把 skill 写得更重、更局部、更保守。
- 当前最优先要跑干净队列，隔离模型版本、并发、tail missing、API 中断等变量。

## 9. Case 观察

### 9.1 成功：强 anchor 单跳检索

任务：arXiv 2016 Physics and Society 文章里，哪个词描述 society 类型。  
gold / final：`egalitarian` / `egalitarian`。  
路径：`INIT > WEB_RESEARCH > CONCLUDE`。  
工具：`read_json_file`，`web_search`。  
观察：搜索结果的标题和摘要已经足够强，答案是单词级，格式简单。  
启示：强 anchor、单跳、答案字段明确的题，应保留短路径能力。

### 9.2 成功：网页多跳 + 计算

任务：2023-07-03 版本 Wikipedia 页面，从 The Lord of the Rings 到 A Song of Ice and Fire 最少点几次链接。  
gold / final：`2` / `2`。  
路径：`INIT > WEB_RESEARCH > COMPUTE > CONCLUDE`。  
工具：多次 `web_search`、`fetch_url`、`html_extract`。  
观察：开始有 404 / search 失败，但后续直接抓取 Wikipedia 页面，抽 links 后计算。  
启示：canonical URL fallback、版本页处理、抽链接后计算，是 web 复杂题有效模板。

### 9.3 失败：USGS NAS 数据库查询

任务：2000-2020 年 Florida 非本地 crocodiles 数量。  
gold / final：`6` / `Unable to retrieve...`。  
路径：`INIT > WEB_RESEARCH > COMPUTE > CONCLUDE`。  
工具：`web_search`、USGS 首页 `fetch_url`、`html_extract`、GBIF 403。  
失败点：只找到了 USGS NAS 查询入口，没有真正构造数据库查询；GBIF 403 后直接转 inability。  
疑似优化方向：site-specific query helper；`VERIFY` 拦截具体数值题里的 inability 文本。

### 9.4 失败：表格附件解析

任务：北美铁路博物馆 locomotives 表格，统计 steam locomotives 总轮数。  
gold / final：`60` / 空答案。  
文件：`.xlsx`。  
路径：`INIT > ATTACHMENT_PARSE > REPAIR > CONCLUDE`。  
工具失败：`read_table` unsupported，随后 `extract_archive`、`read_file`、`extract_pdf_text`、`ocr_image` 都失败。  
失败点：表格工具兼容性和 repair 工具选择都不稳，最后空答案。  
疑似优化方向：先修 `read_table` 对 xlsx/csv 的稳定性；repair 要按扩展名和工具契约选择修复动作。

### 9.5 失败：`run_python` schema 摩擦

任务：Caesar cipher 解密 picnic 位置。  
gold / final：`Picnic is in Ploybius Plaza.` / `Meet me at the park on Friday.`。  
路径：`INIT > COMPUTE > VERIFY > CONCLUDE`。  
工具失败：连续 9 次 `run_python` 使用 `_raw` 参数，被拒绝。  
失败点：executor 反复用错误 schema；repair 没把 schema 错误转成一次性纠正。  
疑似优化方向：工具层兼容 `_raw -> code`；prompt 层要求 schema 错误后改最小合法调用。

### 9.6 失败：附件 + 外部 denominator + 单位

任务：penguin csv 中一组企鹅占 2012 年 Wikipedia 上界总数的百分比，按指定精度输出。  
gold / final：`0.00033` / `98.76543`。  
文件：`.csv`。  
路径：`INIT > ATTACHMENT_PARSE > COMPUTE > CONCLUDE`。  
失败点：本地筛选、外部总量、百分比方向、单位和格式都要对；当前给出方向错误的大数。  
疑似优化方向：`COMPUTE` 强制写 inputs、denominator、unit、ratio direction；`VERIFY` 做数量级 sanity check。

### 9.7 失败：图片几何

任务：图片中绿色多边形面积，紫色数字为边长。  
gold / final：`39` / `2082.5`。  
文件：`.png`。  
路径：`INIT > ATTACHMENT_PARSE > COMPUTE > CONCLUDE`。  
工具：`ocr_image` 成功，但没有可靠几何结构。  
失败点：OCR 文本不足以推导形状面积；需要视觉几何 helper 或更明确的 `image_qa` 子问题。  
疑似优化方向：为 geometry image 题加 helper，把顶点 / 边长关系抽成结构，再用 `run_python` 计算。

## 10. 当前分析结论

已有结论按可信度排序：

1. 工具和协议摩擦是明显硬损耗。`run_python` schema 重复失败、表格解析失败、`invalid_answer_phase` 高发，都会直接浪费 step 和轨迹质量。
2. `VERIFY` 的实际门禁弱。很多复杂 web / compute 题直接 `CONCLUDE`，格式、单位、证据完整性、数量级错误没有被拦住。
3. critic 输入太压缩。compact row 只有 path、工具、outcome、final/gold，缺少关键 observation 摘要，critic 容易给泛化偏弱的建议。
4. actor 改写缺少 diff budget。每轮可能叠过多规则，导致 skill 冗长化、局部化，并损伤 test 泛化。
5. sharded critic 有信号，但需要更强的 success protection 和 minimal edit 约束。
6. Web 数据库 / 版本页 / 站点特化任务需要 helper 或 playbook，纯通用 prompt 收益有限。
7. 图片几何、多模态结构抽取是较难方向，优先级低于表格、Python schema、web helper。

仍需 GPT Pro 重点判断：

- P0 应该优先修 runtime 协议摩擦，还是先修 critic 输入和 actor diff 预算？
- `VERIFY` 应该变成更硬的必经门禁，还是只对计算 / 比较 / 多源任务硬化？
- `invalid_answer_phase` 应做 soft handoff，还是维持硬拒绝并加强 prompt？
- web helper 是优先做通用 direct-fetch ladder，还是先做几个 GAIA 高频站点 helper？
- boot-v3 8 phase 图是否已经足够，fixedprompt 9 phase 图是否值得独立重跑？

## 11. 已考虑的优化候选

这些是目前本地团队已经想到的候选，GPT Pro 可以重新排序、合并或反驳。

### 候选 A：`run_python` schema 兼容

现象：executor 会连续多次用 `_raw` 调 `run_python`，全部被拒。  
改法：工具层接受 `_raw` 作为 `code` 的兼容别名，或在 agent loop 里对该特例做自动转写并记录 outcome。  
收益假设：减少纯协议失败，改善 cipher、枚举、字符串变换、统计、计算题。  
风险：兼容过宽可能掩盖真正 malformed args，需要保留 trace 标记。

### 候选 B：`read_table` 稳定性

现象：xlsx case 中表格读取失败后，repair 乱试 OCR/PDF/Archive。  
改法：确认 pandas/openpyxl/xlrd 依赖；增加 sheet_name 支持；失败时返回可操作错误；repair prompt 中按扩展名选择工具。  
收益假设：表格题可直接救回，且能改善 local_attachment_failure family。  
风险：多 sheet 选择可能引入新决策点，需要 preview 更丰富。

### 候选 C：soft handoff for answer outside `CONCLUDE`

现象：`invalid_answer_phase=91`。  
改法：中间 phase 出现非空 `<ANSWER>` 时，不直接丢弃，可自动进入 `CONCLUDE` 并要求重发同一候选，或把候选保存为 pending answer 注入下一步。  
收益假设：减少协议摩擦，把已有正确候选转成可打分答案。  
风险：会放大 unsupported guess，需要 `VERIFY` 或 support check 配套。

### 候选 D：critic row 加 evidence exemplar

现象：critic 看不到关键 observation，难区分“证据已拿到但字段错”和“证据缺失”。  
改法：compact row 增加每题最多 2 条关键 observation 摘要、失败工具完整错误类型、最后候选答案来自哪个 phase、失败族 exemplar 的 action trace 片段。  
收益假设：critic 建议更具体，actor 改写更少且更准。  
风险：输入变长，critic 成本增加；需要摘要策略避免噪声。

### 候选 E：actor diff budget

现象：dev 涨、test 回落，疑似过多局部规则叠加。  
改法：actor 每轮限制 5-8 条规则级改动；输出 added / removed / modified 列表；要求保护 success_anchor 路径。  
收益假设：减少 skill 冗长化和过拟合。  
风险：单轮收益变慢，但结论更清晰。

### 候选 F：`VERIFY` 条件硬化

现象：复杂题大量绕过 `VERIFY`。  
改法：对计算、计数、比较、多源、附件+web、比例/单位题强制去 `VERIFY`；强证据单跳题仍允许短路径。  
收益假设：减少格式、单位、denominator、字段方向错误。  
风险：过度硬化会增加步数，使简单题超时或被噪声干扰。

### 候选 G：web helper / playbook

现象：USGS NAS、Wikipedia revision、DOI/Science、Census 等 web 题需要固定检索套路。  
改法：先做通用 direct-fetch ladder，再为少数高频源添加 helper 或 query template。  
收益假设：web_retrieval_failure 降低。  
风险：helper 过度特化会影响对外说法，需要按“通用站点模式”组织。

### 候选 H：图重修

现状：fixedprompt 曾生成 9 phase 图：`INIT -> ROUTE -> LOCAL_INVENTORY / EXTRACT_LOCAL / EXTRACT_WEB / COMPUTE / VERIFY / REPAIR / CONCLUDE`，但受 API 中断影响，没有可靠完整分数。  
问题：当前 8 phase 图里 `INIT` 分叉过宽，`VERIFY` 不够像门禁。  
建议 GPT Pro 判断：图重修是否值得当前就开，还是等 P1 工具和 critic 输入修完后再做。
