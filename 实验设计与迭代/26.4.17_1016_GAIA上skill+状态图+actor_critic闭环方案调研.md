# 26.4.17_GAIA上skill+状态图+actor_critic闭环方案调研

## 1. 这次调研想回答什么

这次调研聚焦一个具体方向：

- 让 agent 的运行过程从“自由文本 ReAct”进一步收紧到“`skill + state graph`”
- 图结构本身允许演化，维护者是 `actor + critic`
- 强化学习或类强化学习信号不只作用在最终答案，还作用在状态迁移、技能调用、回退、验证这些中间环节
- 最终目标是让 `GAIA` 这类长程、多工具、部分任务带附件的 benchmark 更稳定

你昨天讨论里提到的亮点，本质上可以整理成一句话：

**把 skill library 和显式状态图结合起来，让 actor/critic 学会维护一张会自我演化的部分策略图。**

这和早期 `FSM / HAM / Behavior Tree` 这条线有直接血缘关系，也和后来的 `options / hierarchical RL / skill library agent` 很接近。

对 `GAIA` 来说，这条线的最大价值在于：

- 能把“先看题面、再取证、再计算、再核对格式、再作答”写成硬结构

- 能把“乱跳阶段”和“重复抓网页”这类现象显式惩罚

- `option` 可以理解为带起始条件、内部策略、终止条件的宏动作

## 3. 对 `GAIA` 的数据形态做一个约束判断

参考 [GAIA 原始论文](/data/xsy/project_gaia_skillrl/实验设计与迭代/论文储存/04_Benchmark_与_GAIA/2023_GAIA_a_benchmark_for_General_AI_Assistants.pdf)，再结合本地对 `2023_all / validation` 的统计，这个 benchmark 对状态图设计有几个很明确的要求：

- `validation = 165`，其中 `L1/L2/L3 = 53/86/26`
- 附件占比随难度上升，`L1 = 20.8%`，`L2 = 23.3%`，`L3 = 26.9%`
- 各 level 最常见附件都是 `xlsx`
- 还会出现 `png / jpg / pdf / docx / pptx / mp3 / zip / csv / py / jsonld`

这说明两件事：

- `GAIA` 的主干流程仍然是 `题面解析 -> 取证 -> 计算/判断 -> 格式核对 -> 作答`
- 附件、多模态、复杂网页是增量分支，适合在主干图上再长分支

所以状态图的设计重点不该放在“每种附件一套独立主流程”，更适合放在：

- 主干状态稳定
- 分支技能可插拔
- 图复杂度随难度和失败簇逐步增长

## 4. 针对 `GAIA` 的四种可行方案

| 方案 | 核心思路 | actor 维护内容 | critic 维护内容 | 优点 | 风险 |
|---|---|---|---|---|---|
| A. 固定 phase graph + skill library | 图结构人工给定，技能持续写回 | 只改 skill，不改图 | 只评估 skill 质量 | 工程最稳，成本最低 | 图表达力有限，后期容易卡死 |
| B. FSM/HAM 式可编辑状态图 | 图是部分策略，actor 可以改节点和边 | split/merge state、改 guard、加 skill 节点 | 结构回归、死节点、无效迁移、路径效率 | 最符合你说的“复杂状态机亮点” | 图空间变大后容易失控 |
| C. Behavior Tree + progress constraints | 树形技能结构，强调子目标不回退 | 增删叶子技能、重排子树 | 监控 ACC/progress，防止破坏已完成子目标 | 很适合网页交互和多步取证 | 树在复杂回退场景下不如图灵活 |
| D. Option graph / hierarchical actor-critic | 高层选 option，低层执行 skill | 维护 option 定义、起止条件、状态映射 | option 级 reward、终止质量、跨层 credit | RL 味道最强，最系统 | 实现和训练成本最高 |

## 5. 我的判断：最适合当前项目的是一个混合版

我建议当前项目优先做：

**B + D 的混合版：显式状态图承载部分策略，节点内部用 skill/option 执行，actor 和 critic 共同维护图与技能。**

可以叫它：

- `Skill-State Graph`
- 或者 `Optionized Skill Graph`
- 或者 `Graph-Constrained Skill RL`

这个方案比纯 phase graph 更强，也比直接上 full hierarchical actor-critic 更稳。

### 5.1 结构定义

建议图里每个节点至少带这些字段：

- `state_id`
- `goal`
- `allowed_tools`
- `input_contract`
- `exit_conditions`
- `failure_signals`
- `linked_skills`
- `expected_outputs`
- `next_states`

边至少带这些字段：

- `from_state`
- `to_state`
- `guard`
- `cost`
- `retry_budget`
- `backtrack_flag`
- `critic_penalty_if_violated`

### 5.2 actor 负责什么

actor 不只改 `SKILL.md`，还应该能提出结构编辑动作：

- `add_state`
- `delete_state`
- `split_state`
- `merge_state`
- `add_edge`
- `remove_edge`
- `tighten_guard`
- `relax_guard`
- `promote_skill_to_state`
- `demote_state_to_skill`
- `attach_verifier`

直观理解就是：

- skill 负责局部动作知识
- state graph 负责全局运行约束
- actor 既能修局部，也能修整体结构

### 5.3 critic 负责什么

critic 应该维护的信号至少包括：

- 最终答案是否正确
- 是否使用了题目指定的 exact source / exact statistic
- 中间状态迁移是否合法
- 有没有在已经完成子目标后又把它破坏掉
- 工具调用是否有效
- 是否进入死循环、重复抓取、重复计算
- 最终答案格式、单位、尺度、舍入是否匹配
- token / step / tool cost

我建议把 critic 输出拆成两层：

- `task critic`：看单题是否完成
- `graph critic`：看结构是否健康

后者很关键，因为它直接决定“图要不要重构”。

## 6. 一个更贴近 `GAIA` 的图形态

### 6.1 建议的基础主干

我建议把当前最小主干升级成下面这种：

1. `INIT`
2. `TASK_PARSE`
3. `EVIDENCE_ROUTE`
4. `LOCAL_PARSE`
5. `WEB_RETRIEVE`
6. `CROSS_CHECK`
7. `COMPUTE_OR_COMPARE`
8. `FORMAT_VERIFY`
9. `ANSWER`
10. `BACKTRACK`

其中：

- `EVIDENCE_ROUTE` 决定走附件分支还是网页分支
- `CROSS_CHECK` 负责 exact source / exact statistic 校验
- `FORMAT_VERIFY` 负责单位、尺度、舍入、输出格式
- `BACKTRACK` 是显式状态，不要只靠自由文本反思

### 6.2 难度分层建议

建议把图复杂度和 `GAIA` 难度一起分层：

- `L1`：`6-7` 个状态，优先主干稳定
- `L2`：`8-10` 个状态，加入交叉验证、附件解析分支
- `L3`：`10-14` 个状态，加入多模态、多源对齐、回退和重试预算

这样做的好处是：

- 训练初期图空间可控
- 后面能把“图复杂度本身”当作一条研究变量
- 也更符合你提到的“phase 复杂程度可以成为亮点”

## 7. 为什么这个方向有研究亮点

我觉得这个方向至少有四个可以讲清楚的亮点。

### 7.1 图结构是显式可学习对象

很多 agent 工作在改 prompt、改 memory、改 skill。

这里可以把**状态图本身**定义成学习对象。

这比单纯改 prompt 更像“学会一套可解释运行策略”。

### 7.2 skill 和 graph 分工清楚

- graph 决定“什么时候做什么”
- skill 决定“这个状态内部怎么做”

这让复用和诊断都更容易。

### 7.3 critic 可以做结构监督

传统 critic 多数只给任务级反馈。

这里可以让 critic 明确指出：

- 哪条边经常把任务带歪
- 哪个状态太大，应该拆分
- 哪两个状态语义重复，应该合并
- 哪个 skill 该提升成独立状态

### 7.4 适合做 path dependence 的研究

你提到“通过强化学习形成运行路径依赖”，这个方向在这里很自然。

因为图结构一旦演化出来，后续 agent 的行为会越来越依赖：

- 哪些状态被保留
- 哪些边被强化
- 哪些 skill 被提升成高频 option

这本身就是一个可观测的路径依赖过程。

## 8. 当前项目最建议的落地顺序

我建议按下面的顺序推进。

### 8.1 第一阶段：先做“静态图 + 可编辑 skill”

目标：

- 让主干状态图稳定跑通
- 让 `actor` 继续只改 skill
- `critic` 开始记录状态级错误

这一阶段重点是把采样和日志打好。

### 8.2 第二阶段：让 actor 开始提结构编辑提案

目标：

- actor 能输出 `graph_patch.json`
- patch 先不过自动生效
- 先让 critic 审核，通过后再应用

这样可以避免图结构早期漂得太厉害。

### 8.3 第三阶段：引入 option 级 reward

目标：

- 给每个状态或 skill 估一个局部成功率
- reward 不只看 final answer，也看 transition quality
- 开始做 graph-level selection / pruning

这一阶段才真正开始接近你说的“状态机由 actor/critic 维护”的研究形态。

## 9. 对当前 `project_gaia_skillrl` 的具体建议

如果直接落到当前代码，我建议下一步补四个对象：

1. `graph_schema.json`
   - 定义状态图结构
2. `graph_actor.py`
   - 输出结构编辑提案
3. `graph_critic.py`
   - 输出状态级和边级评价
4. `transition_memory.jsonl`
   - 保存每一次状态迁移、工具结果、失败原因

另外建议把当前 `SkillEnvironment` 的 phase 机制逐步替换成：

- 图驱动状态迁移
- 每个状态有显式 allowed tools
- 每条边有 guard 和 retry budget

## 10. 我的结论

对于 `GAIA`，最值得试的方向是把 phase 升级成可维护的结构对象。

更具体地说：

- 把 phase 升级成显式状态图
- 把 skill 升级成节点内部的可复用执行单元
- 把 actor/critic 从“只改文本 skill”升级到“共同维护 graph + skill”

文献上，这条路线同时站得住三边：

- `HAM / FSC / Behavior Tree` 提供结构约束基础
- `Options / HRL / HAC / HIRO` 提供层级 credit assignment 基础
- `Voyager / ExpeL / SkillWeaver / SAGE / Agent Lightning` 提供 skill library 和自改进闭环基础

如果只选一个最适合当前项目的落地方向，我建议就是：

**先做 `Skill-State Graph`，从静态主干图起步，再让 actor/critic 逐步接管图的维护。**
