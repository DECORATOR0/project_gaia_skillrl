## 一页结论

这轮最新实验同时暴露了三类问题：

1. `missing` 有两层含义。整条 lane 未启动会造成整组 missing，例如 V5.1 的 `B_test` 全部 82 题缺失；单个 run 在低于队列 partial 阈值时崩溃，会造成剩余题缺失，例如 baseline 只写出 58/82、V4 只写出 54/83、V5 strict 只写出 59/82。
2. 很多 “80 多题只跑 50 多题” 属于远端执行器早期 fatal。直接原因是流式 LLM 调用反复出现 wall timeout、0 text fragments、empty content、server disconnected，子进程 returncode=1，队列拿不到足够 state 继续生成技能或进入下一段。
3. V5.1/V5.2 对 “空答” 的修复边界有限。V5.1 的 `any_phase` 和 V5.2 的 `no-CONCLUDE` 解决的是答案接收路径和阶段约束问题；这轮的空答主体是 24 步耗尽后的 `final_answer/final_choice_label` 为空。空答状态都有非空 `raw_executor_output`，并且全部走满 24 步，说明模型一直在搜索、修复、取证或工具失败循环里，没有交出可接收的最终答案。
4. 同一套提示词和状态机制在不同 executor 模型上仍存在明显泛化风险。8B 的 V5.2 no-CONCLUDE 历史轮次把空答压到低位，而 3.5-9B 远端这轮又大量出现 24 步空转后不交答案。后续跨模型比较时，需要把 “提示词/机制对模型行为的稳定性” 单独作为观察项，而不能只看单一模型上的修复收益。

因此，这轮 2026-05-03 数据不适合作为架构质量横向比较的主证据。它更适合作为远端 Qwen3.5-9B 高并发服务稳定性、队列 partial 策略、以及最终答案兜底机制的诊断样本。

## 为什么有 missing

`missing` 来自三种路径：

1. 整条 lane 没启动：V5.1 的 `B_test` 在队列退出前一直等待 free lane，最终 run 目录缺失，对应 82 个 missing。
2. 子进程 fatal 后剩余题未写 state：baseline、V4、V5 strict 的 50 多题现象都属于这一类。
3. 队列允许 partial tail：V5.2 每条 dev 保留 80/83、每条 test 保留 79/82，尾部 3 题按策略计入 missing。

队列脚本 `scripts/run_gaia_archv5_toolv4_direct_boot_ab_queue.py` 里的关键规则：

- `TAIL_THRESHOLD=3`
- `ALLOW_PARTIAL_TAIL=true`
- `min_required_states(total)=total-TAIL_THRESHOLD`
- dev 共 83 题，所以 required=80
- test 共 82 题，所以 required=79

因此，`80/83` 和 `79/82` 是当前 partial-tail 策略下的可接受收尾。`54/83`、`58/82`、`59/82`、`78/82` 属于失败或临界失败，队列拿不到 required state 时会退出。

## 为什么 80 多题只跑了 50 多题

这轮的 50 多题问题集中出现在高并发远端执行器阶段：

- baseline direct：58/82 后 returncode=1
- ARCH-V4 boot_dev：54/83 后 returncode=1
- ARCH-V5 strict boot_test：59/82 后 returncode=1，required=79

日志里的直接错误包括：

- `Streaming response exceeded wall timeout of 720.0s`
- `Streaming response produced empty content`
- `Server disconnected without sending a response`
- `0 text fragments`

这些错误发生在 LLM 流式调用层。每个子任务内部会重试，达到 6 次后抛出 RuntimeError，子进程退出，队列随之把该 run 判定为 failed 或无法满足 required state。

这轮同时跑了多个版本队列，单个远端 endpoint `http://127.0.0.1:18000/v1` 被多个 queue lane 共享，子任务并发为 `c20`。该配置对一个远端服务的压力非常高，符合日志中大量 stream timeout、断连、空流的表现。

## V5.1/V5.2 为什么仍然大量空答

先拆清两个指标：

- `empty final`：state 中最终答案字段为空，例如 `final_answer` 或 `final_choice_label` 没有可计分答案。
- `Streaming response produced empty content`：远端 LLM 某一次流式调用没有返回文本，属于执行器调用错误。

本轮 V5.1/V5.2 的空答主体是 `empty final`。统计结果显示：

- V5.1 的 227 个 empty final 全部有非空 `raw_executor_output`，并且全部走到 24 步。
- V5.2 的 276 个 empty final 全部有非空 `raw_executor_output`，并且全部走到 24 步。

这说明模型有输出、有轨迹、有工具调用，但最终没有形成可接收答案。主要卡点在取证和修复循环：

| 分组 | empty 最后阶段 Top |
| --- | --- |
| V5.1 | `REPAIR` 119，`WEB_EVIDENCE` 83，`COMPUTE` 12，`LOCAL_EVIDENCE` 7 |
| V5.2 | `REPAIR` 154，`WEB_EVIDENCE` 109，`COMPUTE_VERIFY` 5，`LOCAL_EVIDENCE` 5 |

empty 状态里的失败工具集中在：

| 分组 | 失败工具 Top |
| --- | --- |
| V5.1 | `web_search` 1642，`fetch_url` 597，`image_qa` 187，`run_python` 162 |
| V5.2 | `web_search` 1758，`fetch_url` 1245，`image_qa` 129，`extract_pdf_text` 79 |

empty 状态里的主要错误类型：

| 分组 | 错误类型 Top |
| --- | --- |
| V5.1 | `read_timeout` 1344，`not_found` 485，`403` 286，`web_search` 缺 query 210 |
| V5.2 | `read_timeout` 1642，`not_found` 951，`403` 399，Google sorry/429 33 |

V5.1 的 `any_phase` 和 V5.2 的 `no-CONCLUDE` 可以降低阶段约束导致的答案丢失风险，但它们不会自动解决以下问题：

- 模型在 24 步内持续搜索、抓取、修复，直到步数耗尽。
- 工具调用参数缺失，例如 `web_search` 缺 `query`、`fetch_url` 缺 `url`。
- 外部网页 timeout、403、404、Google sorry/429。
- 远端执行器流式调用超时、断连、空流。
- partial boot 产出的技能质量受污染，A/B 技能在不稳定执行器输出上继续放大空答。

V5.2 这轮完整跑到 477/495，但 empty final 达到 276，说明 `no-CONCLUDE` 让队列更顺利跑完，同时最终答案兜底仍然缺口很大。

## 5.1/5.2 修复点的边界

V5.1 重点是 `any_phase` 接收，核心价值是让答案可以在更多合法阶段被记录，减少 “答案出现过但因为阶段不对被丢掉”。

V5.2 重点是去掉强制 `CONCLUDE` 路径，核心价值是减少模型必须走到指定结束阶段的负担。

这两项修复都依赖一个前提：模型需要显式交出答案，或者轨迹里存在可提取的候选答案。本轮大量 empty final 的轨迹显示，模型经常在最后一步仍处于 `REPAIR` 或 `WEB_EVIDENCE`，最后动作多为失败的 `web_search` / `fetch_url`。在这种情况下，`any_phase` 和 `no-CONCLUDE` 都没有可接收的答案对象。

## 跨模型稳定性问题

这轮还暴露出一个需要单独记录的问题：同一套提示词、工具协议和状态机制，在不同 executor 模型上表现并不稳定。

历史 8B 轮次里，V5.2 no-CONCLUDE 对空答的缓解很明显。它处理的是 “模型已经有答案意图，但必须绕到 `CONCLUDE` 才能被接收” 这类问题；在搜索链路稳定时，empty 可以降到个位数。2026-04-30 两轮 V5.2 Serper 分别是 `7` 个 empty。

当前 3.5-9B 远端轮次里，V5.2 仍然允许提交答案，但大量样本的行为变成了 24 步内持续搜索、修复、重试工具，最后没有交出最终答案。这个现象说明，`no-CONCLUDE` 只放宽了答案接收路径，无法保证不同模型都会在合适时机主动收口。

因此，后续如果要做跨模型测试，需要把以下风险单列：

- 提示词在一个模型上能触发收口，在另一个模型上可能诱导持续检索或修复。
- ReAct baseline 的工具调用节奏相对更朴素，仍可能空答，但行为形态更接近按部就班执行；状态机 skill 的收益和风险更依赖模型是否理解 “何时停止、何时提交答案”。
- 架构比较不能只看 V5.2 在 8B 上的空答改善，还要看同机制迁移到 3.5-9B、远端 endpoint、高并发和不同搜索 provider 后是否仍能稳定交答案。
- 需要增加跨模型诊断指标，例如 `answer_submission_rate`、`steps_exhausted_without_answer`、`last_phase_when_empty`、`answer_candidate_seen_but_not_submitted`。

## 需要立刻改的地方

1. 把 2026-05-03 这轮标记为 infra-contaminated。架构优劣比较应先排除这轮，或只用于远端服务压力诊断。
2. 降低单 endpoint 压力后重跑 smoke：
   - `GAIA_QWEN35_MASTER_MAX_VERSION_QUEUES=1`
   - `GAIA_QWEN35_REMOTE_LANES_PER_QUEUE=1`
   - `GAIA_QWEN35_QUEUE_CONCURRENCY=4` 或 `8`
3. 增加队列健康守卫。若短时间内出现大量 `Streaming response exceeded wall timeout`、`0 text fragments`、`Server disconnected`，直接把队列标记为 `infra_failure`，避免继续消耗数小时后产生半截数据。
4. 增加子进程孤儿清理。V5.1 队列已经退出后，`B_dev` 仍继续写出部分 state，这会污染 “队列状态已经失败” 与 “run 目录后续补写” 的理解。
5. 指标拆分：
   - `missing_not_started`
   - `missing_fatal_below_threshold`
   - `missing_partial_tail`
   - `empty_final_answer`
   - `llm_empty_content_retry`
   - `llm_stream_fatal`
6. 增加最终答案兜底：
   - 最后 3 步禁止继续无界搜索，强制进入 answer-now。
   - 第 24 步仍无最终答案时，从轨迹中的候选答案、计算结果、最近一次非空结论里提取 best-effort final。
   - 没有候选答案时，写入明确诊断型 final，避免静默空字段。
7. 对 V5.2 继续保留 `no-CONCLUDE`，同时补一个显式 `answer_now` 动作或终止触发器。只放宽阶段约束不足以解决 “模型一直不提交答案”。
8. 增加跨模型稳定性验收。每次把同一套 skill/prompt 从 8B 迁移到 3.5-9B 或其他 executor 时，单独对比空答率、24 步耗尽率、最后阶段分布和候选答案提交率，避免把单模型上的修复收益直接外推到其他模型。

## 对三个问题的直接回答

第一，前面的 missing 主要来自 run 崩溃和 lane 未启动。baseline、V4、V5 strict 是远端执行器流式调用失败导致子进程提前退出；V5.1 的 `B_test` 是队列失败前一直没拿到 lane，整条 run 没启动。

第二，很多 80 多题只跑到 50 多题，原因是这些 run 在低于 required state 前 fatal。日志显示 LLM streaming 层反复 timeout、空流、断连，6 次重试耗尽后 returncode=1。`80/83`、`79/82` 属于队列 partial-tail 策略；`54/83`、`58/82`、`59/82` 属于异常提前死亡。

第三，5.1/5.2 修了答案接收路径，仍然会有几十到几百个 empty final，因为这轮模型经常走满 24 步还在搜索和修复。空答主要由工具失败循环、网页访问失败、协议参数错误、远端 stream 稳定性问题共同造成。后续需要加最终答案兜底和并发降压，单靠 `any_phase` / `no-CONCLUDE` 无法覆盖这类空答。
