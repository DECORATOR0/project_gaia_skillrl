## 结论

这次 `V5.2 no-CONCLUDE r2 c20` 的 `boot_dev` 是一个明确的外部检索异常点：`web_search` 150 次调用全部失败，失败形态全部是 `html.duckduckgo.com Read timed out`，影响 52/80 个已完成 state，占 65.0%。同一批 `boot_test` 也出现 168/168 全 timeout，影响 61/80 个 state。

按 `boot_dev` 同口径回看，V4 以来的大多数配置确实接近全成功：`V4 r6` 为 111/111，`V5 + TOOL-V4` 为 115/115，`V5 strict c5` 为 132/132，`V5 strict c10` 为 127/130 且无 timeout/403，`V5.1 any_phase` 为 113/114 且无 timeout/403。`V5 strict c20` 有 13/136 次 `403`，影响 5 个 state，但没有 timeout。

按完整配置聚合口径看，V5.2 这批全六路的外部检索影响为 201/480 个 state，占 41.9%。这个比例高于 V4 r6 的 16.9%、V5 strict c20 的 11.5%、V5 strict c10 的 3.1%、V5 + TOOL-V4 的 6.0%；低于 V5.1 全六路的 50.4%。差别在于 V5.1 的问题主要集中在下游 A/B 与 boot_test，V5.2 的异常直接打在 boot_dev/boot_test 的 bootstrap validation 上。

## 统计口径

- 数据源：各 run 的 `iteration_01/*/state.json`，读取 `env_result.tool_trajectory`。
- `states`：已落盘的 state 数，和 partial tail 后的完成数一致。
- `web_search succ/fail`：按 tool 调用次数统计。
- `外部检索题次`：某个 run state 中至少出现一次 `web_search` 的 `timeout`、`403`、连接错误或 botcheck，即计 1 次。相同 GAIA 题在不同 lane 中重复出现时按 run-state 计数。
- `fetch/html`：`fetch_url` 与 `html_extract` 的网页抓取层失败另列。这里包含目标站 403/404、页面不可达、timeout 等，不混入 `web_search` 主检索可用性判断。
- 本文的 `timeout calls` 仅统计 `web_search` 工具内部 DDG 搜索链路超时；本地 executor/vLLM 的 streaming wall timeout、empty content retry、队列等待和模型服务 readiness timeout 另属运行层问题，不计入本文表格。

### 403 归因边界

本文把 `web_search 403` 归入“外部检索题次”，含义是请求已经到达搜索上游或其防护层，但被 HTTP 403 拒绝。它不属于模型最终答案错误、invalid answer phase、JSON 解析失败这类本地执行错误。

但 `403` 也不能简单等同于“代理挂了”。它可能由多条链路共同触发：

- 代理/IP 信誉或出口地区被 DDG/Bing/防护层限流。
- c20 并发下，多个 lane 在短时间内打到相同搜索入口，触发反爬。
- 模型的检索策略更激进，产生更多重复搜索、宽泛搜索或连续失败后的重试。
- 工具实现只用 DDGS 与 DDG HTML fallback，没有 backoff、provider rotation、熔断与缓存。
- 对 `fetch_url/html_extract` 来说，403 还可能来自目标网站本身，例如新闻站、数据库站、图片站对非浏览器请求拒绝访问。

所以文档里的 `403` 更准确的标签是“搜索/网页上游拒绝请求”。它代表证据链受阻，但原因可能包括网络出口、上游限流、工具策略和模型调用模式。

### timeout 与 403 的分类边界

`timeout` 和 `403` 在本文中拆成两类外部信号：

- `timeout`：传输层、代理出口或搜索上游可达性事故信号。`web_search` 先走 DDGS 主路径，当前库默认 timeout 为 10s；主路径异常后走 `html.duckduckgo.com` fallback，代码里是 `requests.get(..., timeout=30)`。请求发出后，在这个窗口内没有读到响应，通常指向代理出口卡住、DDG HTML fallback 阶段性不可达、上游连接挂起、连接池或并发拥塞。V5.2 boot 段 `150/150` 与 `168/168` 全 timeout，且后续同代理复测能返回 HTTP 200，更符合阶段性网络或出口可用性异常。
- `web_search 403`：搜索上游拒绝请求信号。HTTP 已经返回明确状态码，说明请求大概率到达 DDG/Bing/防护层，但被反爬、限流、IP/地区信誉或请求形态拦截。它也会受模型检索强度、重复查询、并发和工具重试策略影响。
- `fetch_url/html_extract 403`：目标网站或网页抓取上游拒绝请求信号。这里的 403 可能来自新闻站、数据库站、图片站等目标站自身访问策略，诊断时应和 `web_search 403` 分开看。

因此，`timeout calls` 更适合作为 `transport_or_proxy_availability_incident`；`web_search 403` 更适合作为 `search_upstream_rejection`；`fetch/html 403` 更适合作为 `target_site_or_fetch_upstream_rejection`。三者都属于外部证据链受阻，但归因优先级不同。

## 工具与网络路径

`web_search` 的实现路径是：

1. 先调用 `DDGS().text(query, max_results=limit)`。
2. 一旦 DDGS 抛异常，回退到 `https://html.duckduckgo.com/html/?q=...`。
3. fallback 使用 `requests.get(..., timeout=30)`，然后 `raise_for_status()`。

## 对本次低分的解释

`boot_dev` 是直接从 dev bootstrap skill 后跑出来的验证段，理论上不应显著低于 V4/V5 历史 boot_dev。实际低分的直接原因是它的搜索证据入口在该时间窗口完全不可用：150 次 `web_search` 没有一次成功，52 个 state 被外部检索 timeout 影响。历史 boot_dev 的同口径数据支持这一点，因为 V4 r6、V5+TOOL-V4、V5 strict c5/c10、V5.1 boot_dev 都没有出现这种 timeout 面积。

因此，这批 V5.2 boot_dev 的 9/80 不适合直接拿来评价 prompt/skill 架构质量。更合理的处理是：

1. 将 `boot_dev` 与 `boot_test` 标记为 `web_search_timeout_incident`。
2. 复跑时换到稳定代理口径，例如本机 Clash `http://127.0.0.1:17890` / `socks5://127.0.0.1:17891`，或先做 3 次 `html.duckduckgo.com` 预检。
3. 在工具层保留 DDGS 原始异常并记录 fallback 目标、状态码、耗时，避免 run state 只看到 fallback 的最终异常。
4. 对 `web_search` 加最小健康检查：若连续 N 次 timeout，暂停队列或切换代理，防止整批任务用坏出口继续跑完。
