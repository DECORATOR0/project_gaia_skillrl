## 关键结论

1. `CONCLUDE` 单一答案出口太硬。50/51 个完成任务出现过提前 `<ANSWER>` 被拒，合计 186 次。很多题已经走到 `FORMAT_VERIFY` 或 `CROSS_CHECK`，却因为答案不在 `CONCLUDE` 输出而白白耗步。
2. 12 个硬 phase 对 24 步上限过重。一个正常 web 题至少要走 `INIT -> TASK_PARSE -> EVIDENCE_ROUTE -> WEB_RETRIEVE -> WEB_EXTRACT -> COMPUTE_OR_COMPARE -> CROSS_CHECK -> FORMAT_VERIFY -> CONCLUDE`，再加 3 到 6 次工具调用，很容易接近上限。
3. 无工具 phase 成本偏高。`TASK_PARSE`、`EVIDENCE_ROUTE`、`FORMAT_VERIFY` 这类阶段主要做判断，但每次都要消耗模型轮次；对于 L1 短题，这些阶段的收益低于步数成本。
4. `Next:` 图边过窄。模型常见行为是从 `COMPUTE_OR_COMPARE` 直接想去 `CONCLUDE`，或从 `WEB_EXTRACT` 回到 `WEB_RETRIEVE` 继续搜索；当前图把这类行为判成 invalid transition，最终造成循环。
5. web 任务失败率高。大量失败题在 `WEB_RETRIEVE` / `WEB_EXTRACT` 之间循环，工具错误和搜索噪声叠加后，最后空答案或错抽实体。
6. 本地/纯推理任务相对健康。成功题集中在简单 prompt 计算、局部文件读取、音频转写后计算、简单网页抽取。这说明状态图路线选择有价值，问题主要在硬状态执行成本。

## 建议的 v2 状态图

建议把 12 个硬 phase 压缩到 6 到 7 个硬 phase，子路线用 state memory 字段表达：

```text
INIT
  -> PARSE_ROUTE
  -> EVIDENCE
  -> SOLVE
  -> VERIFY_FORMAT
  -> CONCLUDE

optional:
  SOLVE -> EVIDENCE       # 证据不足时回查
  VERIFY_FORMAT -> SOLVE  # 计算或格式失败时修正
```

`EVIDENCE` 内部记录 `route=prompt|local|media|web|hybrid`，并把旧 `LOCAL_PARSE`、`MEDIA_PARSE`、`WEB_RETRIEVE`、`WEB_EXTRACT` 降级成本阶段内的 checklist。这样保留路由能力，同时减少模型必须显式跳转的次数。

## Runtime 改法

1. 允许 `VERIFY_FORMAT` 接收 `<ANSWER>`，runtime 可自动补一次虚拟 `CONCLUDE`。如果仍想保留 `CONCLUDE`，至少把非 `CONCLUDE` 的答案 rejection 改成提示模型立刻 `<NEXT>CONCLUDE</NEXT>`，并且不消耗额外工具路线。
2. 允许一组安全短边：`SOLVE -> CONCLUDE`、`VERIFY_FORMAT -> CONCLUDE`、`EVIDENCE -> SOLVE`、`SOLVE -> EVIDENCE`。当前 strict edge 对 8B 成本太高。
3. 增加 `state_memory` 槽：`route`、`evidence_found`、`candidate_answer`、`format_requirement`、`blocking_issue`。不同 phase 只展示相关字段，旧 phase 的冗长过程不继续堆在 prompt 里。
4. 对 `web_search` 增加重复 query 计数和失败后换策略提示。题 29 的 18 次工具失败说明仅靠模型自觉停止不够。
5. 若坚持强状态图，`max_executor_steps` 至少调到 32 或 36。当前 24 步对 12 hard phase 偏紧。

## Prompt 改法

Bootstrap prompt：

- 要求输出 `phases`、`edges`、`allowed_tools`、`phase_memory_schema` 四块。
- 明确约束：没有工具、没有独立观测价值的节点应合并进相邻 phase。
- 明确约束：答案可用性和最终出口必须兼容 executor runtime。
- 加一个 graph lint 自检：每条 route 从 INIT 到 CONCLUDE 的最短路径应小于等于 5 次状态迁移。

Critic prompt：

- 统计并惩罚 `invalid_answer_phase`、`invalid_phase_transition`、空答案、24 步打满、重复搜索。
- 要求把失败归因分成 graph defect、tool defect、reasoning defect、format defect。
- 对 graph defect 必须给出边修改、phase merge、answer gate 修改之一。

Actor prompt：

- 允许 actor 修改 `Next:`、`Allowed tools:`、phase 合并、phase 内 checklist。
- 优先修复协议摩擦：提前答案、非法跳转、无工具阶段过多。
- 每次修改必须保持 route 覆盖：prompt/local/media/web/hybrid 五类都要有可走路径。
- 对每个新 phase 写清楚进入条件、退出条件、可见 memory、可用工具。
