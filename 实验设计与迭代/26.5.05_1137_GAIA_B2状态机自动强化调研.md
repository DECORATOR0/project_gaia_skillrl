# 26.5.05 GAIA B2 状态机自动强化调研

记录时间：2026-05-05 11:37 +0800

目标：调研“已有状态机 / workflow 后，如何根据题目执行反馈自动优化状态、边、工具权限和节点规则”的路线，并给当前 GAIA BOOT-V3/V4 后续 B2 强化设计提供可执行借鉴。

本文件只做调研和方案设计，不改代码，不启动实验。

## 一页结论

用户提出的顺序更合理：**先调节点，再调边，再调工具 allowlist，最后调 rules**。

原因：

- 节点定义了状态空间和每个状态的职责边界。节点划分不稳时，后续边和工具权限都会被迫服务错误抽象。
- 边定义控制流和可回退范围。边太密会形成合法绕路，边太窄会形成非法收口和空答。
- 工具 allowlist 是每个节点的动作空间。它应依附于节点职责和边条件。
- rules 是最底层行为描述，用来细化节点内部策略，适合在结构稳定后用轨迹反思继续优化。

外部方法给出的共同信号是：把 agent workflow 当成可搜索的结构对象，使用真实执行反馈做候选选择；同时用受限 patch、lint、replay anchors、复杂度惩罚控制结构漂移。对 GAIA 来说，B2 最适合做成 **GraphSpec + 分层 graph patch + smoke 选择**，后续再渲染回当前 runtime 可读的 `SKILL.md`。

### 当前 critic 信号形态

当前 prompt 明确要求 fixed-graph：

- 禁止新增、删除、重命名、拆分、合并 phase。

- `natural_language_reward`

### 对 B2 的直接含义

当前 A_full 已经能让 critic 一次性看到全量环境摘要和完整 skill，但它有三个限制：

- 没有逐步 action_trace、tool observation、executor thought，只保留 path、工具名、成功失败和短 error。
- `path` 是压缩 phase path，无法直接看同一边重复次数和每个 phase dwell，需要从 action trace 或更细 compact feature 重新抽。
- prompt 和 schema 锁死 fixed graph，critic 缺少 node/edge/tool/rules 分层输出槽。

B2 可以先沿用 A_full 的“一跳 critic -> actor”形态，只改两件事：

1. critic 输入增加 graph-oriented trace features，例如 `phase_dwell`、`edge_counts`、`repeated_edges`、`tool_by_phase`、`invalid_next_by_phase`、`answer_phase`、`forced_answer_success`。
2. critic 输出从 node-local reward 扩展为两块：`graph_structure_signals` 与 `allowlist_rules_signals`。actor 随后一次性生成修改后的完整 skill。

## 外部路线

### 1. StateFlow：把过程控制和子任务求解拆开

来源：[StateFlow: Enhancing LLM Task-Solving through State-Driven Workflows](https://arxiv.org/abs/2403.11322)

StateFlow 把复杂任务求解建模为状态机，区分 process grounding 和 sub-task solving：状态与转移负责过程控制，状态内动作负责局部求解。论文报告在 InterCode SQL 和 ALFWorld 上，相比 ReAct 提高成功率并降低成本。

对 GAIA 的启发：

- `Phase` 应表达运行过程状态，避免退化成错误类型集合。
- 节点需要有输入、输出、完成条件和失败触发。
- R 阶段的 rules 优化应在状态和边稳定后进行。

### 2. MetaAgent：自动构建 FSM，并优化冗余状态

来源：[MetaAgent: Automatically Constructing Multi-Agent Systems Based on Finite State Machines](https://arxiv.org/abs/2507.22606)

MetaAgent 给定任务类型描述后，自动设计 agent、状态、转移条件和 condition verifier。部署时 FSM 控制 agent 动作和状态转移。它还用一个优化算法遍历状态对，让 LLM 判断是否可以合并冗余状态，以降低链路过长和信息传递复杂度。

对 GAIA 的启发最直接：

- 节点优先级应高于边和工具。状态数量、状态职责、状态合并/拆分先收敛。
- 每条边应有自然语言条件或 verifier，`Next:` 目标集合只表达可达性。
- `null-transition` 和 `traceback` 对应当前 GAIA 的“留在当前 phase 重试”和 `REPAIR` 回退；两者需要预算和退出条件。
- 状态合并是必要操作。自动优化不应只会加节点，也要能合并职责重叠的节点。

### 3. EvoFSM：显式演化 FSM，分离 Flow 和 Skill

来源：[EvoFSM: Controllable Self-Evolution for Deep Research with Finite State Machines](https://arxiv.org/abs/2601.09465)

EvoFSM 面向 deep research agent，把自进化限制在显式 FSM 上，并把优化空间分成 macroscopic Flow 和 microscopic Skill。Flow 管状态转移逻辑，Skill 管状态内行为。critic 通过少量受限操作修改 FSM，同时把成功轨迹蒸馏成 reusable priors，把失败模式蒸馏成约束。

对 GAIA 的启发：

- B2 应显式分成 Flow 层和 Skill 层。节点/边属于 Flow；工具权限介于 Flow 与 Skill；rules 属于 Skill。
- 每轮只开放少量 graph ops，配合 lint 和 replay，控制漂移。
- 成功样本适合变成结构先验，失败样本适合变成结构约束和 patch 证据。

### 4. AutoFlow：用执行 reward 迭代优化自然语言 workflow

来源：[AutoFlow: Automated Workflow Generation for Large Language Model Agents](https://arxiv.org/abs/2407.12821)

AutoFlow 把 workflow 表示成自然语言程序，包含 Process、Decision、Terminal 等步骤类型。生成器产生 workflow，解释器在任务集上执行，评估分数作为 reward；闭源模型场景下通过 in-context 反馈上一轮分数来生成新 workflow，开源模型场景下用 RL 更新生成器。

对 GAIA 的启发：

- B2 可以把 `GraphSpec` 当成自然语言/结构化 workflow 程序。
- 每轮 patch 都要有 reward，不靠人工感觉判断。
- GAIA 暂时不需要训练 workflow generator；用 in-context reward loop 加小样本 smoke 更现实。

### 5. AFlow：把 workflow graph 当搜索空间，用 MCTS 和执行反馈选候选

来源：[AFlow: Automating Agentic Workflow Generation](https://arxiv.org/abs/2410.10762)，[FoundationAgents/AFlow](https://github.com/FoundationAgents/AFlow)

AFlow 把 workflow 优化建模为代码表示的图搜索：节点是 LLM 调用或 operator，边表达依赖，优化器用 MCTS 选择、扩展、评估和更新 workflow。项目 README 也把组件分成 Node、Operator、Workflow、Optimizer、Evaluator。

对 GAIA 的启发：

- 不要每轮让 actor 只输出一个大改版。应保留多个候选 patch 或候选图。
- 每个候选图在固定 smoke/replay 上执行，用 evaluator 选择。
- 当前 B_sharded 的“critic 分片 + actor 全局一次改”可以升级成“候选 patch 搜索 + 自动评估选择”。

### 6. ADAS / EvoFlow：把 agent 架构当自动搜索对象

来源：[Automated Design of Agentic Systems](https://arxiv.org/abs/2408.08435)，[EvoFlow: Evolving Diverse Agentic Workflows On The Fly](https://arxiv.org/abs/2502.07373)

ADAS 把 agentic system 本身当成自动设计对象，由 meta-agent 在 archive 上持续发现更好的 agent 设计。EvoFlow 维护一组多样化 workflow，通过检索、交叉、变异和 niching selection 保持性能与多样性。

对 GAIA 的启发：

- B2 可以维护 `graph_candidate_archive`，保留多个候选技能图，而非只维护一条单链。
- 多样性有价值，尤其当前 dev/test 需要同时看；一个 candidate dev 高但 test 掉，另一个 candidate test 稳，可以保留为分支。
- 搜索空间需要受限。GAIA 目前更适合受限 GraphSpec patch，而非完全自由代码生成。

### 7. Agent Workflow Memory / ExpeL / GEPA：轨迹经验用于后层优化

来源：[Agent Workflow Memory](https://arxiv.org/abs/2409.07429)，[ExpeL](https://arxiv.org/abs/2308.10144)，[GEPA](https://arxiv.org/abs/2507.19457)

AWM 从历史轨迹诱导 reusable workflows。ExpeL 从训练任务经验抽取自然语言知识，在推理时检索使用。GEPA 从系统轨迹中反思，提出和测试 prompt updates，并合并 Pareto frontier 上互补经验。

对 GAIA 的启发：

- 这些方法更适合 rules / node-local skill 层，也适合从成功/失败轨迹提炼 priors 和 constraints。
- 它们支持“用少量 rollout 学到高层规则”，但不直接回答节点/边如何先验重构。
- B2 应先优化 Flow，再把 GEPA/ExpeL 风格反思放到最后一层 rules。

### 8. Workflow optimization survey：区分模板图、实际路径和执行轨迹

来源：[From Static Templates to Dynamic Runtime Graphs](https://arxiv.org/abs/2603.22386)

该调研把 agentic workflow 视为 computation graph，并区分 reusable workflow template、run-specific realized graph 和 execution trace。

对 GAIA 的启发：

- `SKILL.md` phase graph 是 reusable template。
- 单题走过的 phase path 是 realized graph。
- `state.json` 里的 tool call、NEXT、ANSWER、runtime feedback 是 execution trace。
- B2 必须先把 trace 聚合成结构证据，再改 template。单题路径不能直接变成全局边。

## 建议的 B2：FSM-RL / GraphPatch 自动强化

### 总体循环

```text
BOOT-V3 skill
  -> parse GraphSpec
  -> run dev trajectories / load existing state.json
  -> trace abstraction
  -> stage-1 node patch candidates
  -> lint + smoke + replay -> accept/reject
  -> stage-2 edge patch candidates
  -> lint + smoke + replay -> accept/reject
  -> stage-3 tool allowlist patch candidates
  -> lint + smoke + replay -> accept/reject
  -> stage-4 node rules patch candidates
  -> lint + smoke + replay -> accept/reject
  -> full dev/test eval
```

这里的 “RL” 是执行反馈驱动的黑盒优化，不训练模型权重。每个 patch 都有 reward、accept/reject、回滚和 replay。

### Stage 1：节点 / 状态本体

允许操作：

```json
{"op": "add_state", "state": "...", "reason": "..."}
{"op": "split_state", "target": "...", "new_states": ["...", "..."], "routing_rule": "..."}
{"op": "merge_state", "states": ["...", "..."], "merged_state": "..."}
{"op": "rename_state", "from": "...", "to": "..."}
{"op": "delete_state", "target": "...", "redirect_edges": []}
```

候选证据自动来自：

- 某节点驻留步数高、工具种类熵高、失败模式混杂。
- 某两个节点成功路径中的输入/输出/工具高度重叠。
- 某类任务持续被路由到错误节点，例如媒体题被塞进本地文档节点。
- 某节点几乎只作为中转，无有效工具调用和状态产物。

GAIA 的初始优先项：

- 是否单独拆 `ROUTE`。
- 是否单独拆 `MEDIA_EVIDENCE`。
- 是否把 `REPAIR` 缩成带预算的诊断节点。
- 是否合并过细但无收益的 prompt-only / compute / verify 变体。

### Stage 2：边 / 转移条件

允许操作：

```json
{"op": "add_edge", "from": "...", "to": "...", "condition": "..."}
{"op": "remove_edge", "from": "...", "to": "...", "reason": "..."}
{"op": "edit_edge_condition", "from": "...", "to": "...", "condition": "..."}
{"op": "add_edge_budget", "from": "...", "to": "...", "max_visits": 1}
```

候选证据自动来自：

- 频繁出现非法 `<NEXT>`，且目标阶段确实具备收口或修复价值。
- 合法循环多次发生，但工具返回无新增证据。
- 某边在成功样本中高频，在失败样本中低频，可强化条件。
- 某边在失败样本中高频，在成功样本中低频，可删除或加预算。

GAIA 的初始优先项：

- 处理 `REPAIR -> VERIFY / COMPUTE / evidence` 的预算。
- 处理 `WEB_EVIDENCE` 已有候选时的合法收口路径。
- 防止 `VERIFY -> WEB_EVIDENCE -> VERIFY` 无证据循环。
- 为低剩余步数的收口建立图级短路或运行时兜底。

### Stage 3：工具 allowlist

允许操作：

```json
{"op": "add_tool", "state": "...", "tool": "...", "condition": "..."}
{"op": "remove_tool", "state": "...", "tool": "...", "reason": "..."}
{"op": "move_tool", "tool": "...", "from": "...", "to": "..."}
```

候选证据自动来自：

- 某节点高频调用被拒工具，并且相邻节点拥有该工具导致绕路。
- 某工具在某节点高频失败或制造长循环。
- 成功样本中某工具几乎总在特定节点完成关键状态产物。
- `run_python`、`web_search`、`fetch_url` 等强工具在错误节点造成过度搜索或错误计算。

GAIA 的初始优先项：

- `INIT` 是否只保留 manifest/轻路由工具。
- `WEB_EVIDENCE` 是否拆分 search 与 fetch/html_extract，或通过 rules 控制。
- `VERIFY` 是否允许小范围 `fetch_url/html_extract/run_python`，并限制重新开大搜索。
- `LOCAL_EVIDENCE` 是否允许 `run_python` 作为格式/二进制/表格 fallback。

### Stage 4：rules / 节点内 skill

允许操作：

```json
{"op": "edit_node_goal", "state": "...", "text": "..."}
{"op": "edit_node_rules", "state": "...", "patch": "..."}
{"op": "edit_exit_handoff", "state": "...", "text": "..."}
{"op": "edit_answer_readiness", "state": "...", "text": "..."}
```

候选证据自动来自：

- 答案格式错、集合不完整、单位/舍入错。
- 证据链弱但路径结构正确。
- 成功样本和失败样本路径相同，差别主要在节点内部判断。
- false-answer 正确率低，说明 force 阶段缺少“已有证据下如何保守收口”的规则。

GAIA 的初始优先项：

- `VERIFY` 的 exact answer contract。
- `COMPUTE` 的 deterministic conversion 和 sanity check。
- `WEB_EVIDENCE` 的 source chain 与停止条件。
- `REPAIR` 的单次诊断和退出规则。

## 自动批次生成

B2 的 batch 不按人工错误类型切。每轮从 trace 里自动生成候选支持集：

```json
{
  "candidate_id": "edge_remove_VERIFY_to_WEB_EVIDENCE_001",
  "stage": "edge",
  "op": "remove_edge",
  "target": {"from": "VERIFY", "to": "WEB_EVIDENCE"},
  "supporting_failures": ["task_a", "task_b"],
  "protected_successes": ["task_c", "task_d"],
  "observed_signature": {
    "failure_path_pattern": "VERIFY->WEB_EVIDENCE->VERIFY repeated",
    "new_evidence_gain": "low",
    "max_step_hit_delta": "high"
  },
  "expected_effect": {
    "hit_max_step": "down",
    "wrong_final_risk": "medium",
    "test_generalization": "unknown"
  }
}
```

自动选择规则：

- `supporting_failures` 取所有暴露同一结构签名的失败样本。
- `protected_successes` 取经过同一节点/边/工具的成功样本。
- baseline 正确、skill 错误的样本权重最高。
- skill 正确、baseline 错误的样本作为保护先验。
- test 只作为 heldout，不进入 patch 证据。

## Lint 与 gate

每个 patch 先过静态 lint：

- phase id 唯一，入口可达。
- 每个非 terminal work phase 能到达可答阶段。
- 每个边目标存在。
- 每条边有 condition。
- `Allowed tools` 属于 runtime contract。
- 每个节点出边默认不超过 4。
- repair loop 有 `max_visits` 或明确预算。
- 图复杂度不能无证据增长。
- 节点拆分必须带来工具、输入、输出、退出条件之一的差异。

每个 patch 再过动态 gate：

```text
score =
  dev_accuracy
  - no_answer_penalty
  - invalid_action_penalty
  - max_step_penalty
  - graph_complexity_penalty
  - protected_success_regression_penalty
  + rare_family_recall_bonus
```

主线接受条件建议：

- full dev 或固定 dev sentinel 不低于上一版。
- protected success 回退数不超过 1。
- baseline-correct / skill-wrong 回退数下降或不升。
- test 只做观测；若 test 明显下降，该候选进入 archive，不作为主线。
- false-answer 正确率作为 safety 指标记录，辅助判断 force 收口质量。

## 对 B2 的具体建议

第一版自动化 B2 可以小做，不需要直接上完整搜索：

1. 从 BOOT-V3 skill 和 boot_dev `state.json` 生成 trace features。
2. 自动生成 Stage 1 节点候选：`ROUTE` / `MEDIA_EVIDENCE` / `REPAIR` 合并或拆分候选。
3. 每个节点候选渲染 1 个 skill，跑同一组 15-20 条 coverage smoke。
4. 选节点候选后，进入 Stage 2 边候选，重点处理收口边、坏循环边和 repair 预算。
5. 选边候选后，进入 Stage 3 工具权限，重点看高频 rejected tool 和强工具滥用。
6. 最后 Stage 4 用 GEPA/ExpeL 风格轨迹反思改 rules。
7. 每个 stage 保留 2-3 个候选到 archive，主线只接受 gate 通过的候选。

这个顺序和用户提出的一致：**节点 -> 边 -> 工具 -> rules**。每层都自动从轨迹选证据和保护样本，人工只看候选摘要和最终分数。

## 风险

- 节点层改动最容易改变所有路径，smoke 必须覆盖成功 anchor。
- 边层删除过猛会让模型无路可走，添加过猛会回到网状图。
- 工具层加入强工具可能提分，也可能扩大过度搜索和过度计算。
- rules 层如果过早介入，会把结构问题掩盖成提示词问题。
- test 参与 patch 决策会污染 heldout 信号，应保留为报告指标。
