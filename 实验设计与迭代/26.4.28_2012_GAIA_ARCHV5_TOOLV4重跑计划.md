# GAIA ARCH-V5.2 no-CONCLUDE + TOOL-V2 重跑计划

更新时间：2026-04-29 20:35 +0800

## 当前主线

`TOOL-GAIA-V4` 已废弃，后续实验工具面固定回到 `TOOL-GAIA-V2 / atomic_v2`。direct baseline 当前暂停，本轮只看 bootstrap skill 与后续 A/B skill 的变化。

当前主线版本为 `ARCH-V5.2`：

- bootstrap 生成的技能图不再包含 `CONCLUDE` 节点。
- bootstrap prompt 明确禁止 `CONCLUDE` 和其它 answer-only finalization phase。
- runtime 保持 `NLRL_RUNTIME_ANSWER_ACCEPTANCE_POLICY=any_phase`：任意 phase 输出非空 `<ANSWER>...</ANSWER>` 都会被接受并交给 evaluator。
- executor system prompt 不显式鼓励任意 phase 直接作答，只保留通用 action protocol 里的 `<ANSWER>` 格式。
- 后续 A/B actor 仍锁定 bootstrap 生成的 phase graph；由于图里没有 `CONCLUDE`，A/B 不会继续围绕 `CONCLUDE-only` 习惯做优化。

这个版本的目标是让技能图只表达“证据、计算、验证、修复”的流程，让答案出口回归通用 action 层，减少为进入 `CONCLUDE` 而产生的无意义跳转和 invalid loop。

## V5.2 改动范围

代码和 prompt 层：

- `prompts/bootstrap_skill_system.md`
  - 要求包含 `INIT`。
  - 禁止生成 `CONCLUDE`。
  - 禁止生成 answer-only finalization phase。
  - terminal work phase 可形成 verified candidate answer，但不需要跳到专门答案节点。
- `prompts/bootstrap_skill_user.md`
  - 删除 `CONCLUDE` edge 设计要求。
  - 改为限制 answer-ready terminal behavior，只在有完整支持和格式确定时发生。
- `prompts/executor_system.md`
  - 删除 “final answer only in CONCLUDE” 的硬规则。
  - 保留每轮一个 action：tool call / phase transition / supported final answer。
- `gaia_skillrl/bootstrap.py`
  - runtime contract 写成非空 `<ANSWER>` 会被 runtime 接受。
  - 明确 bootstrap skill 不创建 `CONCLUDE` 或 answer-only phase。
- `gaia_skillrl/environment.py`
  - 兼容没有 `CONCLUDE` 的技能图；只有图里存在 `CONCLUDE` 时才构造 conclude prompt。
- `gaia_skillrl/agent_loop.py`
  - `any_phase` 继续接受任意 phase 的非空答案。
  - 当技能图没有 `CONCLUDE` 时，tool follow-up 不再追加 “Do not answer yet.”。

保留的 V5.1 机制：

- 只把 accepted action 的 assistant 原始输出放回工作记忆。
- invalid / rejected 输出保留在 `action_trace.raw_output`，下一轮 executor 只看到 allowed-scope feedback。
- 空 `<ANSWER></ANSWER>` 继续被拒绝。

## 本轮关注指标口径

完整六路横向总表已单独落在 `26.4.29_2035_GAIA六路实验网络指标总表.md`，按开始时间精确到分钟区分版本、重跑与并发差异。

后续判断不只看 `success/accuracy`，还固定看三组健康指标：

| 指标组 | 字段 | 判读 |
| --- | --- | --- |
| 协议健康 | `invalid` / `invalid broad` | action protocol、phase guard、tool allowlist、动作解析相关摩擦。主要看总量、每 run 分布，以及 `invalid_answer_phase` 是否回潮。 |
| 答案出口健康 | `empty` / `empty_answer` | 最终没有交出非空答案，通常对应 max-step、空 `<ANSWER>`、被工具/搜索失败拖到无法收束。 |
| 外部证据链健康 | `web_search succ/fail`、`timeout calls/states`、`403 calls/states`、`fetch/html fail calls/states` | 判断搜索入口、网页抓取、目标站访问是否可用。该组指标异常时，低分要先按外部证据链受阻隔离。 |

网络相关指标沿用 `26.4.29_1838_GAIA_V4以来网络检索外部错误统计.md` 的口径：

- `web_search timeout`：更像传输层、代理出口、DDG HTML fallback 或并发拥塞事故。V5.2 r2 boot 段出现 `150/150`、`168/168` 全 timeout，应优先标成 `web_search_timeout_incident`。
- 这里的 `web_search timeout` 只指搜索工具内部 DDG 链路超时，典型文本是 `html.duckduckgo.com Read timed out (read timeout=30)`。它和 executor/vLLM 的 `Streaming response exceeded wall timeout`、`Streaming response produced empty content`、模型服务 readiness timeout 分开统计。
- `web_search 403`：搜索上游拒绝请求，通常和 DDG/Bing/防护层限流、出口信誉、并发和重复查询有关。
- `fetch_url/html_extract 403`：目标站或网页抓取层拒绝请求，要和 `web_search 403` 分开看。
- `外部检索题次`：同一个 run state 中出现至少一次 `web_search` 的 timeout、403、连接错误或 botcheck，即计 1 次。
- `fetch/html 外部题次`：同一个 run state 中 `fetch_url` 或 `html_extract` 失败另列，用来衡量证据抓取层受阻。

判读优先级：

1. 先看 `invalid` 与 `empty`。no-CONCLUDE 的核心收益应体现为 invalid loop 与空答案下降。
2. 再看 `web_search timeout/403` 与 `fetch/html fail`。如果这组异常成片出现，不能把该轮 accuracy 直接归因到 skill / 架构。
3. 最后看行为策略指标，例如 `read_json_file(task.json)` 覆盖、`web_search` 后是否 `fetch_url/html_extract`、`run_python` 覆盖、`REPAIR` 后是否恢复到有效证据链。

主因判断：

1. r2 boot 段存在明确 `web_search_timeout_incident`：`boot_dev 150/150` timeout，`boot_test 168/168` timeout。该异常直接切断外部证据入口。
2. `boot skill` 文本变得过于“可停止”。生成 skill 里 `<ANSWER>` 同时出现在 common rule、`INIT`、`COMPUTE`、`VERIFY`、`REPAIR`，再叠加 executor system 每步携带 “Final answering is a global stop condition”，实际效果接近每步都提醒可以停答。
3. 去掉 `CONCLUDE` 后缺少提交前缓冲层。no-CONCLUDE 抽象本身更自然，但当前实现没有补足“可见证据完全支撑、格式已校验、scope 已覆盖”的提交门槛，错误候选更早进入 evaluator。
4. bootstrap 重新生成了整张技能图，和 V5.1 / V4 的行为差异过大。V5.1 的 `INIT` 更强制读 `task.json`，REPAIR 也更愿意回流到 evidence / compute；V5.2 的 boot skill 更倾向一次取证或一次 repair 后直接提交。
5. A/B 段 timeout 消失后出现 `web_search 403`，说明外部证据链从“不可达/卡住”转为“上游拒绝/限流”。这会继续影响下游分数和 actor 学到的 repair 习惯。

AB 侧验证：

- A actor 在 skill 中加入了“取证失败后不凭记忆答”“第二次搜索超时后改用 canonical fetch / source-specific endpoint”“更严格读 task.json 和工作区”的规则，所以 `A_dev` 从 `boot_dev 9/80` 拉到 `18/80`。
- A/B 只能补一部分：`A_test 10/80`、`B_dev 13/81`、`B_test 11/79` 仍低，说明 boot skill 初始策略漂移已经影响后续优化上限。

结论：当前 V5.2 r2 同时测到两件事：no-CONCLUDE 能压低 invalid 和 empty；r2 boot 段遭遇搜索 timeout 事故，导致 accuracy 带有强外部干扰。它不能单独判定 no-CONCLUDE 抽象会拉低分数，也不能只归因到 bootstrap skill 策略漂移。

后续建议：

- 做一个 surgical V5-2：以 V5.1 的 `SKILL.md` 为基底，只机械移除 `CONCLUDE` 节点和 `CONCLUDE-only` 文本，保留 V5.1 的读任务、取证、repair 回流和计算习惯。
- runtime 继续 `NLRL_RUNTIME_ANSWER_ACCEPTANCE_POLICY=any_phase`。
- bootstrap prompt 暂停大幅重写 phase graph，先验证“同一技能图 + 去答案节点”这一单一变量。
- 所有复跑都必须同步落 `invalid/empty/web_search timeout/web_search 403/fetch-html fail` 五类指标；若 boot 段连续出现 `web_search timeout`，应暂停队列或切换代理后重跑。

## 当前判断

- V5.1 证明了“接受早答”能大幅削掉 invalid loop，并能显著提升 boot_dev。
- V5.2 r2 证明了 no-CONCLUDE 可以继续压低 invalid / empty，但重新 bootstrap 出来的技能图策略明显漂移，boot 分数大跌。
- 当前优先验证 surgical V5-2：保留 V5.1 skill 主体，只机械去掉 `CONCLUDE` 与 `CONCLUDE-only` 习惯。
- 如果 surgical V5-2 能接近 V5.1 boot_dev，同时改善 boot_test / A/B，再回头把 bootstrap prompt 收敛到这个形态。
- 本轮先看 `c20`，继续提高并发会加重 executor/vLLM streaming timeout 风险，暂不启动 `c40`。该运行层 timeout 不并入 `web_search timeout calls/states`。
