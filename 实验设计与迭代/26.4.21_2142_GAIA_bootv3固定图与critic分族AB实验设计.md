# GAIA boot-v3 固定图与 critic 分族 A/B 实验设计

## 目标

本轮目标是验证一条更清晰的 skill 训练边界：

- `bootstrap` 负责一次性设计状态图、状态名、连线和初始节点信息。
- 后续 `critic / actor` 保持图结构不变，只优化公共基础信息和节点内信息。
- 对比两种 critic 接入方式对性能的影响：全量 batch critic 与分族 shard critic。
- 实验优先看最终 `validation_dev` 与 `validation_test` 分数，性能优先于中间格式指标。

## boot-v3 设计

boot 输入保持轻量：

- `Runtime Contract`
- `Batch Task Snapshot`

boot prompt 只告诉强模型必要边界：

- executor 逐节点消费 skill。
- 公共基础信息会长期可见，节点局部信息只在进入该节点时接入。
- `## Phase: NAME` 是节点定义。
- `Next:` 行决定 phase graph。
- `Allowed tools:` 和节点内工具示例决定该节点工具权限。
- 每步只允许一个动作：`<CALL>`、`<NEXT>` 或 `<ANSWER>`。
- 最终答案只能从最终答案节点输出。
- 需要有限 repair path。
- 节点应具备局部价值，避免纯占位、纯思考、无观测收益的空节点。

boot 不显式要求模态 checklist。题型、附件、web/local/media/hybrid 覆盖由模型根据 batch snapshot 和工具边界自行归纳。

## skill 消费形态

skill 采用两层信息结构：

```text
Common Base Info
  - 运行协议
  - progressive node-local consumption
  - action tags
  - final answer rule
  - graph / tool extraction rule
  - step budget

Node-Local Info
  - Goal
  - Allowed tools
  - Rules
  - Exit handoff
  - Available actions
  - Next
```

executor 初始只看到任务信息和 `INIT` 节点。每次 `<NEXT>` 被接受后，runtime 只注入目标节点内容。因此每个节点必须局部自洽，能指导 executor 在该节点完成一个清晰子目标并交接到下一节点。

## 图锁边界

boot 之后，常规 actor 不改图。

允许 actor 修改：

- 公共基础信息的表达。
- 节点内 `Allowed tools`。
- 节点内 `Rules`。
- 节点内 `Exit handoff`。
- 节点内 `Available actions` 的说明。
- 已存在边的使用条件说明。

禁止 actor 修改：

- phase 名称。
- phase 顺序。
- phase header。
- 新增、删除、拆分、合并 phase。
- `Next:` 目标集合。

如果 critic 发现图结构硬伤，只输出 `graph_revision_needed`，本轮常规 actor 仍不改图。图重修需要单独开 graph-revision 实验。

## critic 输入重规划

critic 不再吃旧版冗余字段：

- `choices`
- `active_skill_name`
- `final_choice_label`
- `executor_summary`
- `evaluation.notes`
- `gold_tool_names`
- `gold_trajectory_summary`

每题 compact row 保留：

```json
{
  "task_id": "...",
  "level": 1,
  "task_prompt": "...",
  "file_list": ["task.json", "..."],
  "gold_answer": "...",
  "final_answer": "...",
  "success": false,
  "step_count": 8,
  "empty_answer": false,
  "max_step_hit": false,
  "outcome_counts": {
    "invalid_answer_phase": 0,
    "invalid_phase_transition": 0,
    "tool_call_failed": 0,
    "tool_call_rejected": 0,
    "unrecognized_action": 0
  },
  "path": ["INIT", "ROUTE", "GATHER", "SOLVE", "CONCLUDE"],
  "tools": [
    {"step": 1, "tool": "read_json_file", "success": true}
  ]
}
```

`action_trace`、tool observation、raw executor output 只在少量 exemplar 中给 critic。常规 compact rows 不携带大段原始输出。

## A/B critic 策略

### A. full critic

流程：

```text
全部 dev compact rows
  -> 单次 critic
  -> 单次 actor
```

优点是全局视野完整。风险是上下文较大，critic 容易输出平均化建议。

### B. family-sharded critic

流程：

```text
全部 dev compact rows
  -> 确定性分族
  -> 每族按 10-12 题切 shard
  -> shard critics
  -> aggregate critic
  -> 单次 actor
```

确定性分族优先级：

1. `success_anchor`
2. `no_answer_or_timeout`
3. `protocol_friction`
4. `media_attachment_failure`
5. `local_attachment_failure`
6. `web_retrieval_failure`
7. `answer_synthesis_or_format_failure`
8. `other_failure`

分族依据来自题目文件、工具轨迹、outcome counts、空答案、步数上限、成功状态。先不接额外 LLM 做自由分类，保持实验变量可控。

## 实验队列

本轮使用 `qwen3-8b` executor、`gpt-5.4` actor/critic、`c20`。

队列分阶段。关键约定是：A/B 两路强模型迭代必须复用同一份 `boot_v3_dev_iter1` 执行结果，不能为 A 或 B 在 actor 前额外重跑 executor。这样 A/B 的唯一变量才是 critic 接入策略。

1. `boot_v3_dev_iter1`
   - dev 切分 bootstrap。
   - `iterations_per_batch=0`。
   - 产出初始 skill，并在 dev 上得到 iter1 分数与 83 个 `state.json`。

2. `boot_v3_test_iter1`
   - 使用初始 skill 在 validation_test 上评估。
   - `iterations_per_batch=0`。
   - 这是初始 skill 的 test 分数。

3. `A_full_offline_actor_iter1`
   - 输入：`boot_v3_dev_iter1` 的 83 个 `state.json` 与初始 skill。
   - 不运行 executor。
   - critic 策略：`full`。
   - actor 在固定图内修改节点信息。
   - 产出 A 路 iter1 skill。

4. `B_sharded_offline_actor_iter1`
   - 输入：同一份 `boot_v3_dev_iter1` 的 83 个 `state.json` 与初始 skill。
   - 不运行 executor。
   - critic 策略：`sharded`。
   - actor 在固定图内修改节点信息。
   - 产出 B 路 iter1 skill。

5. `A_full_iter2_dev_eval`
   - 使用 A 路 iter1 skill 在 dev 切分上评估。
   - `iterations_per_batch=0`。
   - 得到 A 路 iter2 dev 分数。

6. `B_sharded_iter2_dev_eval`
   - 使用 B 路 iter1 skill 在 dev 切分上评估。
   - `iterations_per_batch=0`。
   - 得到 B 路 iter2 dev 分数。

7. `A_full_test`
   - 使用 A 路 iter1 skill 在 validation_test 上评估。

8. `B_sharded_test`
   - 使用 B 路 iter1 skill 在 validation_test 上评估。

最终比较三份 skill：

- 初始 boot skill：dev iter1 + validation_test。
- A 路 full critic skill：dev iter2 + validation_test。
- B 路 sharded critic skill：dev iter2 + validation_test。

## 长尾排队规则

采用轻量长尾触发，不实现全局槽位调度。

- 队列按依赖顺序启动。
- 当前依赖 run 进入当前 executor iteration 的最后 5% 时，允许启动下一个 run。
- 对 83 题 dev，剩余任务数 `<= 4` 视为长尾。
- 对 82 题 test，剩余任务数 `<= 4` 视为长尾。
- 如果下一个 run 依赖当前 run 的最终 skill，则必须同时满足 skill 文件已经存在。
- A/B offline actor 阶段不受 executor 长尾触发约束；它们直接复用 `boot_v3_dev_iter1` states。

这样可以减少长尾等待，同时避免引入复杂调度变量。

## 2026-04-22 当前 skill 复盘与后续演化方向

### 当前生成 skill 的形态

boot-v3 生成的初始 skill 是一个 8 节点固定图：

```text
INIT
  -> ATTACHMENT_PARSE
  -> WEB_RESEARCH
  -> DIRECT_REASON
  -> COMPUTE
  -> VERIFY
  -> REPAIR
  -> CONCLUDE
```

实际图中 `INIT` 可按任务类型跳到附件、网页、直接推理、计算、验证或结论；`ATTACHMENT_PARSE`、`WEB_RESEARCH`、`DIRECT_REASON`、`COMPUTE` 都可较快进入 `VERIFY` 或 `CONCLUDE`；`VERIFY` 和 `REPAIR` 构成有界纠错通道；最终答案只允许在 `CONCLUDE` 输出。

这个 skill 的主要特征：

- `Common Base Info` 很短，负责动作协议、answer-only phase、工作状态、工具/证据基本规则。
- 节点局部信息承担实际策略，每个 phase 都有 `Goal`、`Allowed tools`、`Rules`、`Exit handoff`、`Available actions`、`Next`。
- 工具权限按 phase 收敛：`WEB_RESEARCH` 只给 web 与 Python，`CONCLUDE` 无工具，附件节点集中处理本地文件、多模态和表格。
- actor 后续迭代没有改 phase 名、phase 顺序和 `Next:` 目标集合，主要改全局约束、节点规则、工具 schema 修复、证据门槛和验证要求。
- 当前 skill 已经从“粗路由 + 轻验证”演化为“先捕获 answer contract，再做证据/计算/格式硬检查”的形态。

A 路 full critic 的第二轮 actor 更偏向多跳拆解、source constraint、constraint table、日期/版本/集合运算检查。它把 `INIT`、`WEB_RESEARCH`、`COMPUTE`、`VERIFY` 写得更细，强调先拆 subquestion，再按每个 qualifier 做验证。

B 路 sharded critic 的第二轮 actor 更偏向硬证据门、工具 schema 修复、snippet 禁用、direct fetch fallback、无法访问时换源。它对“候选答案必须有支撑来源”管得更严，也更强调失败后换策略。

### 分数辨析

目前还没有形成稳定正收益。boot-v3 初始 skill 在 test 上与 direct `qwen3-8b` baseline 同为 14/82，略低于 bootstrap v0.2 的 15/82；A/B 后续 actor 能在 dev 局部涨分，但 test 上没有持续超过 17/82 的结果。

A iter2 的 dev 最高但 test 最弱，说明 full critic 容易把 dev failure 写成较宽的全局规则，短期修复 dev 局部题型，同时改变原本能中的路径。B iter2 的 test 最高但 dev 最低，说明分族 critic 的硬证据门对部分 test 题有益，但它也会让 executor 更保守，更多任务停在不完整证据或格式错误上。

到 iter3 时，两路 dev 都到 21/83，test 回落到 13-14/82。这个形态说明“继续自然语言加规则”已经进入边际收益很低的阶段。A/B 的正确题集合仍有明显错位，代表当前 score 变化更多来自 executor 采样、检索路径和局部规则相互作用，尚未学到一个可泛化的强策略。

从失败签名看，`protocol_friction` 是最大表层分类，但这个分类被 `invalid_answer_phase` 放大：很多任务先在非 `CONCLUDE` phase 输出 `<ANSWER>`，被 runtime 拒绝后还能恢复。关键数字如下：

- boot-v3 dev：`invalid_answer_phase=78`，tool failed 49，空答案 2。
- boot-v3 test：`invalid_answer_phase=139`，tool failed 37。
- A iter3 test：`invalid_answer_phase=117`，tool failed 58，不可解/无法访问类失败 11。
- B iter3 test：`invalid_answer_phase=91`，tool failed 64，unrecognized action 12，不可解/无法访问类失败 9。

因此协议摩擦确实消耗步数和注意力，但真正压分的主因是证据链没有拿全、网页/数据库检索失败、表格/附件抽取后未做正确 join/filter/format，以及多跳题过早把中间实体当成最终答案。

### 当前提示词与架构瓶颈

复盘时确认，最靠前的执行层漏项是 executor 系统提示词与固定图的一致性。`prompts/executor_system.md` 当时仍保留旧图规则：

```text
In INIT, inspect the task layout and then move to GATHER.
In GATHER and ANALYZE, do not output the final answer.
```

boot-v3 图里没有 `GATHER` / `ANALYZE`。虽然初始 prompt 同时展示了当前 phase graph 和 `INIT` 节点内容，旧规则仍会给 `qwen3-8b` 造成冲突。这个问题比继续打磨 actor 文案更靠前，因为它直接污染所有 skill 的消费方式，也会让 critic 看到大量协议类失败。

该漏项已在 2026-04-22 修复：`prompts/executor_system.md` 移除了 `GATHER` / `ANALYZE` 旧节点指令，改为只约束动态 `{phase_list}`、当前可见 phase、phase-local `Allowed tools` 与 `Next:` 目标。后续需要用同一份 skill 做修复前后 A/B，观察协议失败、平均步数、dev/test 分数和正确题集合变化。

第二个瓶颈是 critic compact row 的信息密度。当前 row 有 task、gold、final、path、tools、outcome_counts，但常规 compact rows 没有关键 observation、失败工具的上下文、候选答案生成依据和最后一段 reasoning。critic 因此容易把“检索没进正确页面”“网页只看了 snippet”“表格抽取后 filter 错”“计算单位错”都压成宽泛的 node edit。sharded 策略还会先按 protocol 分类，导致 recoverable 的 `invalid_answer_phase` 抢走更有价值的 web/local/media failure 诊断。

第三个瓶颈是自然语言 skill 承担了过多本该由工具和 runtime 承担的精确行为。USGS NAS、Wikipedia revision、网页快照、表格 join、图片棋盘/图表、音视频细节这些任务，靠继续给 `WEB_RESEARCH` 或 `VERIFY` 加规则很难稳定解决。需要把一部分高频失败源沉到工具层或 helper 层，例如特定站点 API、HTML 表格抽取、Wikipedia revision 查询、USGS 查询参数化、附件结构化摘要等。

第四个瓶颈是当前固定图只能表达粗任务族。8 phase 图本身可用，但 `WEB_RESEARCH` 同时承担“找候选页面、获取页面、抽取字段、跨页 join、快照验证”，`VERIFY` 同时承担格式、证据、计算、完整性审计。若前面三个无结构瓶颈解决后仍卡住，再开 graph revision，把网页检索/抽取/比较或格式审计拆成更明确的节点，会更有依据。

### 后续 A/B 演化方向

下一轮不应只继续比较 full critic 与 sharded critic。更有价值的 A/B 变量如下：

1. `executor_system` 对齐实验
   A 组使用修复前 `executor_system` 快照，B 组使用已移除 `GATHER` / `ANALYZE` 旧规则的新提示词。复用同一份 skill，直接看协议失败、平均步数、dev/test 分数变化。

2. fatal protocol vs recoverable protocol 分族实验
   当前只要有 `invalid_answer_phase` 就容易进入 `protocol_friction`。新分族应区分最终失败原因：如果任务最终有答案且工具证据链失败，应按 web/local/media/format 分族；只有 unknown phase、连续 rejected、最终空答或 action 无法恢复时才归入 protocol。

3. evidence-rich critic row 实验
   A 组继续 compact row；B 组每个 failure family 追加 2-3 个 exemplar，包含最后一次失败工具 observation、最后一个候选答案来源、关键 action_trace 片段。目标是让 critic 输出更像“修哪个行为”而非“加强验证”。

4. minimal actor diff vs rewrite actor 实验
   A 组要求 actor 每轮只改 5-8 条规则，优先保留工作路径；B 组允许大段重写。评估除分数外还看 skill token 长度、invalid action、tool_failed 和正确题集合保留率。

5. tool/helper augmentation 实验
   选择 2-3 个高频失败源先做工具层补强，例如 USGS NAS 查询、Wikipedia revision/page-history 查询、HTML table extraction。A 组纯 prompt，B 组同 skill 加工具能力，判断当前瓶颈有多少来自工具可达性和结构化抽取。

6. graph revision 实验
   仅在前几项完成后启动。候选方向是把 `WEB_RESEARCH` 拆出目标页获取与事实抽取，把 `VERIFY` 拆出格式审计，或增加 source-specific retrieval 节点。图改动需要单独实验，避免和 critic/actor 变量混在一起。

### 当前优先级判断

executor 系统提示词与动态 phase graph 的冲突已先修。下一优先级是修 critic 分族和 compact row 信息密度，再其次是补工具/helper。继续单纯给 `SKILL.md` 加更长的自然语言规则，短期可能还能改变少数题，但从 iter2 到 iter3 的 dev/test 形态看，泛化收益已经很弱。
