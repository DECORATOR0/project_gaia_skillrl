# GAIA boot-v3 固定图与 critic 分族 A/B 实验设计

时间：2026-04-21 21:42 +0800

## 目标

本轮目标是验证一条更清晰的 skill 训练边界：

- `bootstrap` 负责一次性设计状态图、状态名、连线和初始节点信息。
- 后续 `critic / actor` 保持图结构不变，只优化公共基础信息和节点内信息。
- 对比两种 critic 接入方式对性能的影响：全量 batch critic 与分族 shard critic。
- 实验优先看最终 `validation_dev` 与 `validation_test` 分数，性能优先于中间格式指标。

## 数据切分

所有设计、训练和选择都在 GAIA validation 内部完成。

- 开发切分：`data/converted/gaia_2023_all_validation_dev_tasks.json`
- 测试切分：`data/converted/gaia_2023_all_validation_test_tasks.json`
- 官方 `gaia_2023_all_test_tasks.json` 本轮不参与本地可打分实验。

## boot-v3 设计

boot 输入保持轻量：

- `Runtime Contract`
- `Batch Task Snapshot`

boot prompt 只告诉强模型必要边界：

- executor 逐节点消费 skill。
- 公共基础信息会长期可见，节点局部信息只在进入该节点时接入。
- `## Phase: NAME` 是节点定义。
- `Next:` 行决定 phase graph。
- `Allowed tools:` 和节点内工具示例决定该节点工具权限。
- 每步只允许一个动作：`<CALL>`、`<NEXT>` 或 `<ANSWER>`。
- 最终答案只能从最终答案节点输出。
- 需要有限 repair path。
- 节点应具备局部价值，避免纯占位、纯思考、无观测收益的空节点。

boot 不显式要求模态 checklist。题型、附件、web/local/media/hybrid 覆盖由模型根据 batch snapshot 和工具边界自行归纳。

## skill 消费形态

skill 采用两层信息结构：

```text
Common Base Info
  - 运行协议
  - progressive node-local consumption
  - action tags
  - final answer rule
  - graph / tool extraction rule
  - step budget

Node-Local Info
  - Goal
  - Allowed tools
  - Rules
  - Exit handoff
  - Available actions
  - Next
```

executor 初始只看到任务信息和 `INIT` 节点。每次 `<NEXT>` 被接受后，runtime 只注入目标节点内容。因此每个节点必须局部自洽，能指导 executor 在该节点完成一个清晰子目标并交接到下一节点。

## 图锁边界

boot 之后，常规 actor 不改图。

允许 actor 修改：

- 公共基础信息的表达。
- 节点内 `Allowed tools`。
- 节点内 `Rules`。
- 节点内 `Exit handoff`。
- 节点内 `Available actions` 的说明。
- 已存在边的使用条件说明。

禁止 actor 修改：

- phase 名称。
- phase 顺序。
- phase header。
- 新增、删除、拆分、合并 phase。
- `Next:` 目标集合。

如果 critic 发现图结构硬伤，只输出 `graph_revision_needed`，本轮常规 actor 仍不改图。图重修需要单独开 graph-revision 实验。

## critic 输入重规划

critic 不再吃旧版冗余字段：

- `choices`
- `active_skill_name`
- `final_choice_label`
- `executor_summary`
- `evaluation.notes`
- `gold_tool_names`
- `gold_trajectory_summary`

每题 compact row 保留：

```json
{
  "task_id": "...",
  "level": 1,
  "task_prompt": "...",
  "file_list": ["task.json", "..."],
  "gold_answer": "...",
  "final_answer": "...",
  "success": false,
  "step_count": 8,
  "empty_answer": false,
  "max_step_hit": false,
  "outcome_counts": {
    "invalid_answer_phase": 0,
    "invalid_phase_transition": 0,
    "tool_call_failed": 0,
    "tool_call_rejected": 0,
    "unrecognized_action": 0
  },
  "path": ["INIT", "ROUTE", "GATHER", "SOLVE", "CONCLUDE"],
  "tools": [
    {"step": 1, "tool": "read_json_file", "success": true}
  ]
}
```

`action_trace`、tool observation、raw executor output 只在少量 exemplar 中给 critic。常规 compact rows 不携带大段原始输出。

## A/B critic 策略

### A. full critic

流程：

```text
全部 dev compact rows
  -> 单次 critic
  -> 单次 actor
```

优点是全局视野完整。风险是上下文较大，critic 容易输出平均化建议。

### B. family-sharded critic

流程：

```text
全部 dev compact rows
  -> 确定性分族
  -> 每族按 10-12 题切 shard
  -> shard critics
  -> aggregate critic
  -> 单次 actor
```

确定性分族优先级：

1. `success_anchor`
2. `no_answer_or_timeout`
3. `protocol_friction`
4. `media_attachment_failure`
5. `local_attachment_failure`
6. `web_retrieval_failure`
7. `answer_synthesis_or_format_failure`
8. `other_failure`

分族依据来自题目文件、工具轨迹、outcome counts、空答案、步数上限、成功状态。先不接额外 LLM 做自由分类，保持实验变量可控。

## 实验队列

本轮使用 `qwen3-8b` executor、`gpt-5.4` actor/critic、`c20`。

队列分阶段：

1. `boot_v3_dev_iter1`
   - dev 切分 bootstrap。
   - `iterations_per_batch=0`。
   - 产出初始 skill，并在 dev 上得到 iter1 分数。

2. `boot_v3_test_iter1`
   - 使用初始 skill 在 validation_test 上评估。
   - `iterations_per_batch=0`。

3. `A_full_iter1`
   - 从初始 skill 出发。
   - dev 切分训练一轮。
   - critic 策略：`full`。
   - 产出 A 路 iter1 skill。

4. `B_sharded_iter1`
   - 从初始 skill 出发。
   - dev 切分训练一轮。
   - critic 策略：`sharded`。
   - 产出 B 路 iter1 skill。

5. `A_full_iter2`
   - 从 A 路 iter1 skill 出发。
   - dev 切分训练一轮。
   - critic 策略：`full`。
   - 产出 A 路 iter2 skill。

6. `B_sharded_iter2`
   - 从 B 路 iter1 skill 出发。
   - dev 切分训练一轮。
   - critic 策略：`sharded`。
   - 产出 B 路 iter2 skill。

7. `A_full_test`
   - 使用 A 路 iter2 skill 在 validation_test 上评估。

8. `B_sharded_test`
   - 使用 B 路 iter2 skill 在 validation_test 上评估。

## 长尾排队规则

采用轻量长尾触发，不实现全局槽位调度。

- 队列按依赖顺序启动。
- 当前依赖 run 进入当前 executor iteration 的最后 5% 时，允许启动下一个 run。
- 对 83 题 dev，剩余任务数 `<= 4` 视为长尾。
- 对 82 题 test，剩余任务数 `<= 4` 视为长尾。
- 如果下一个 run 依赖当前 run 的最终 skill，则必须同时满足 skill 文件已经存在。

这样可以减少长尾等待，同时避免引入复杂调度变量。

## 记录要求

- 所有后台实验用 `nohup` 和日志重定向启动。
- 每个后台进程写入 `/data/xsy/活的进程.csv`。
- 启动后监视 5 分钟，确认队列脚本仍在运行、首个 run 已创建、日志持续刷新。
