## 机制判断

### 8B / 9B step 差异

同一 p04 clean 配置下，8B 平均 step 低，主要来自早答、弱证据答、失败后直接答。9B 平均 step 高，来自更严格遵循证据充分、格式验证和继续取证约束。9B 的长链有时换来正确率，例如 9B boot_dev 明显高于 8B boot_dev；但它也更容易在 web/fetch/compute 中打满 step 后空 final 或 forced answer。

### 空答案与 forced answer

`any_phase` 修复后，主要问题从 `invalid_answer_phase` 转为 `empty final / hit 24 step / forced answer`。forced answer 子集正确率低：

- baseline_dev：`0/20`
- BOOT-V3 dev：`3/30`
- BOOT-V4 dev：`4/29`
- B2 test：`2/29`

这说明 max-step 后已经进入低胜率区间。提高 `max_executor_steps` 能减少强制答的数量，但需要配合早停和重复调用拦截。只给更多 step，9B 可能继续 search/fetch/verify，收益不稳定。

### token guard

token guard 是有效修复。`20260504_1611` 之后 7 行结果 `HTTP400=0`，解决了 char cap 与 vLLM token 上限不一致导致的 49153 token 边界问题。当前后续实验应继续沿用：

- `NLRL_RUNTIME_MAX_CONTEXT_CHARS=0`
- `NLRL_EXECUTOR_TOKENIZER_PATH=/data/xsy/codes/checkpoints/Qwen3.5-9B`
- `NLRL_EXECUTOR_MAX_MODEL_LEN=49152`
- `NLRL_EXECUTOR_TOKEN_GUARD_SAFETY_MARGIN=512`
- `NLRL_EXECUTOR_MAX_TOKENS=12288`

### BOOT-V3 / BOOT-V4

BOOT-V3 的主要贡献是把节点内字段和 stale phase prompt 隐藏机制理清，test 到 `36/82`。BOOT-V4 的 preprocess note 暂时没有证明能提高 seed skill，且 test forced 数更高。继续做 bootstrap 方向时，优先考虑结构化 profile 和 batch graph bootstrap，逐题短 note 只适合作为低优先级备选。

### B1 / B2

B1 可以近似理解成旧 B：按预制 failure family 分 shard，critic 分批审计，aggregate 后交给 actor，graph locked。

B2 的意图是让 critic 输出 `graph_structure_signals` 与 `allowlist_rules_signals`，actor 有权限改 phase graph、`Next:`、allowlist、rules。本轮实际 graph signature 未变，说明“权限放开”没有自动转化为“结构修改”。后续 B2 需要让 graph 信号更可执行，例如把 `add_edge/remove_edge/split_phase/edit_allowlist` 变成显式 patch 或操作建议，再由 actor 落地。

## 关键图结构

`INIT -> PROMPT_SOLVE -> LOCAL_EVIDENCE -> WEB_EVIDENCE -> COMPUTE -> VERIFY -> REPAIR`

- `LOCAL_EVIDENCE`: `WEB_EVIDENCE`, `COMPUTE`, `VERIFY`, `REPAIR`
- `WEB_EVIDENCE`: `LOCAL_EVIDENCE`, `COMPUTE`, `VERIFY`, `REPAIR`
- `COMPUTE`: `LOCAL_EVIDENCE`, `WEB_EVIDENCE`, `VERIFY`, `REPAIR`
- `VERIFY`: `LOCAL_EVIDENCE`, `WEB_EVIDENCE`, `COMPUTE`, `REPAIR`
