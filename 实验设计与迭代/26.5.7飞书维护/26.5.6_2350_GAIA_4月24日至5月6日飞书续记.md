## 2026-05-07 重要补记：FLOW-batch-V3 / 分层 critic 是目前更有希望的 SkillRL 方向

5 月 7 日在 B2 的基础上重新整理了一个更清晰、也更有意思的思路：当前的 `skill` 已经同时包含两类可优化对象：

- **内容层**：common preface、phase-local Rules、Allowed tools、Exit handoff、Available actions。
- **结构层**：phase 节点、`Next:` 边、routing 条件、REPAIR 收口方式、成功短路径保护。

因此，critic 更适合按层级拆开维护。不同性质的问题交给不同输入、不同职责的 critic：

- **Graph Critic** 专门看结构层。它接收去掉 per-phase `Rules:` 正文的 skill graph view、全题 compact path table、edge/phase value profile、loop profile、missing-transition profile，然后给出节点/边/routing/repair 的修改建议。
- **Rules/List Critics** 继续沿用 B1 的分桶方式。它们看各自 failure family 的轨迹、完整 skill、工具错误和失败类型，专门给 common text、phase Rules、Allowed tools、Exit handoff、已有边自然语言条件提出修改建议。
- **Aggregate Critic** 把 Graph Critic 和多个 Rules/List Critics 的建议统一合并，显式处理冲突，保留成功锚点，输出一个一致、可直接交给 actor 的明确 reward / patch 信号。
- **Actor** 按照 aggregate 后的信号，直接修改 `SKILL.md`，同时允许在证据足够时改 graph 和 phase 内容。

这个方向的意义在于：BOOT 不需要一次性生成一个非常完美的 skill。BOOT 只要生成一个可执行的 seed skill，后续 NLRL / SkillRL 闭环就可以通过轨迹统计、分层 critic 和 actor patch，持续优化 skill 的结构和内容。也就是说，后续优化的信心主要来自闭环本身：轨迹给出可量化反馈，critic 把反馈转成层级明确的修正建议，actor 把建议落到 skill。

一、4 月 25 日：先把 GAIA SkillRL 的早期状态盘清楚

4 月 25 日做了一份阶段性总盘点，把 GAIA 当前框架、数据切分、训练闭环和早期分数统一写下来。

当时的整体框架是：

- bootstrap 根据 dev task snapshot 和 runtime contract 生成一个 `gaia-general-skill/SKILL.md`。
- executor 带着 skill 逐题做 GAIA，按 `<CALL>`、`<NEXT>`、`<ANSWER>` 协议执行。
- critic 看 dev 轨迹和失败族，提出 skill 修改建议。
- actor 改 skill。
- 再用新 skill 跑 dev/test，观察分数、路径、工具和失败类型。

当时的关键分数是：

| run / skill            |       dev | validation_test | 当时理解            |
| ---------------------- | --------: | --------------: | ------------------- |
| direct qwen3-8b        |         - |       `14/82` | 8B 直跑基线         |
| bootstrap v0.2         | `18/83` |       `15/82` | 轻量 bootstrap 略高 |
| boot-v3 初始 skill     | `18/83` |       `14/82` | test 和 direct 持平 |
| A full critic iter2    | `21/83` |       `11/82` | dev 涨，test 掉     |
| B sharded critic iter2 | `14/83` |       `17/82` | 早期 test 短期最高  |
| A full critic iter3    | `21/83` |       `14/82` | 回到 baseline       |
| B sharded critic iter3 | `21/83` |       `13/82` | dev 追上，test 回落 |

当时已经能看到两个核心问题：

1. skill 能改变 executor 行为，dev 上能涨到 `21/83`。
2. test 没有稳定跟涨，critic / actor 很容易把 dev 错例修成局部规则。

同一天还整理了面向 GPT Pro 的审查背景包，方便让外部强模型审查当前 SkillRL 框架。后续方向包括：统一干净重跑、修 `run_python` schema、修 `read_table`、给 critic row 增加证据列、做 soft handoff 和 graph revision。

三、4 月 27 日：ARCH-V4、空答状态图和 A/B 分桶

4 月 27 日主要在研究有 skill 的状态图为什么会空答。

当时发现，bootstrap skill 的图里很多阶段没有直达 `CONCLUDE` 的边，尤其是：

- `REPAIR -> CONCLUDE`
- `WEB_EVIDENCE -> CONCLUDE`
- `LOCAL_EVIDENCE -> CONCLUDE`

模型经常已经有候选答案，却因为当前 phase 不能直接答、又走不到 `CONCLUDE`，最后 24 步耗尽变成空答。bootstrap dev/test 合计 22 个空答全部走满 24 步。

因此先做了 ARCH-V4 runtime 小修：invalid `<NEXT>` 反馈从泛泛提示改成更强的恢复指令，例如：

```text
CONCLUDE is illegal from REPAIR.
You must choose one of: LOCAL_EVIDENCE, WEB_EVIDENCE, COMPUTE, VERIFY.
```

随后跑了 fresh Codex 5.4 bootstrap + A/B 全链路，结果如下：

| run            |      分数 | 总分母口径 | 空答 |
| -------------- | --------: | ---------: | ---: |
| bootstrap dev  | `16/80` |  `16/83` |    7 |
| bootstrap test | `15/81` |  `15/82` |    8 |
| A_full dev     | `15/80` |  `15/83` |    6 |
| A_full test    | `20/79` |  `20/82` |    6 |
| B_sharded dev  | `15/81` |  `15/83` |   13 |
| B_sharded test | `16/79` |  `16/82` |    8 |

这里最有信号的是 A_full test `20/79`。它相对 bootstrap test 多了 5 个净正确，新增正确主要来自数值题、实体错配修正和访问失败恢复。与此同时，A_full dev 掉分，B_sharded 空答、tool fail 和 invalid next 都上升，说明 actor 规则变重后会带来 split 方差和协议噪声。

这一阶段形成了一个重要认识：状态图本身不一定要大改，真正要控制的是节点规则、VERIFY 门槛、REPAIR 行为和成功短路径保护。

四、4 月 28 日：公开基线、提前答摩擦和 ARCH-V5 方向

4 月 28 日先做了公开论文基线对齐。结论是，当前 `Qwen3-8B + fixed-tool ReAct agent + GAIA toolbox + scorer` 的 baseline 范式可以和 Reagent、ToolSelf、ARPO 等公开小模型 GAIA agent baseline 对齐。

同时也看到了本项目 `13/81` 低于公开小模型 GAIA baseline 的主要原因：工具后端差距很大。公开工作常用 Bing Search API、Jina Reader、强 VLM、Whisper 等；本项目那时主要是 DDG 免费栈、requests + BeautifulSoup、本地 OCR / image QA。

当时还试过 `TOOL-GAIA-V3 / reagent_facade_v3` 六工具复刻，把工具压成 Search、Browse、Python、File Reader、Image2Text、Audio2Text。结果 no-skill direct 只有 `9/82`，低于 atomic_v2 的 `13/81`，于是主线回到 `TOOL-GAIA-V2 / atomic_v2`。

同一天还追溯了有 skill 场景里的提前答摩擦。6 个有 skill run 合计 `invalid_answer_phase=1046`，其中 `ANSWER only` 是 `1031/1046`。这说明主要问题不是 parser 误判，而是模型在非 `CONCLUDE` phase 主动输出 `<ANSWER>`。

提前答集中在：

- `VERIFY`
- `COMPUTE`
- `WEB_EVIDENCE`
- `REPAIR`

于是提出了后续修复方向：

1. phase executor 模式下隐藏全局 `<ANSWER>` 模板。
2. 把 `VERIFY` 写成 route-only gate，通过后只输出 `<NEXT>CONCLUDE</NEXT>`。
3. invalid feedback 给明确动作模板。
4. parser 对合法 `NEXT+ANSWER` 做小容错。
5. 如果持续摩擦，就考虑合并 `CONCLUDE`，让 any-phase answer 成为主逻辑。

这条线后面发展成 V5.1 any_phase 和 V5.2 no-CONCLUDE。

六、5 月 3 日：Qwen3.5-9B、远端压力问题和 no-trunc budget matrix

5 月 3 日开始把 executor 从 8B 推到 Qwen3.5-9B。

先发起过一个远端 25 组实验：direct baseline + ARCH-V4 / V5 strict / V5.1 / V5.2 各六路。后来这轮被标记为 infra-contaminated。原因是单个远端 endpoint 被多个 c20 队列共享后，出现大量：

- streaming wall timeout
- 0 text fragments
- server disconnected
- empty content
- 子进程 fatal

很多 run 只跑到 50 多题，V5.1 还有整条 B_test 没启动。这轮更适合当远端服务压力诊断，不适合作为架构横向比较。

同一天还分析了 Qwen thinking chunk 与输出预算。9B 失败 attempt 里有大量 8 万级 chunk，很多是 0 text fragments，说明模型可能一直在 hidden reasoning，正文动作还没开始。结论是后续要同时管住：

- 输入长度
- hidden reasoning
- 总输出
- streaming wall timeout
- max step 和 forced answer

随后发起了 24 路 no-trunc budget matrix：

`2 model x 2 input cap x 2 thinking x 3 output cap`

几个重要观察：

- 8B 分数大多在 `12/82` 到 `16/82`，仍是低基线。
- 9B `cap49152 + think4k + out8k` 能到 `35/81`。
- 9B `nocap + think_unlimited + out8k` 临时能到 `36/82`，但出现大量 400、empty retry 和 stability 风险。
- `cap49152` 不是 token 上限，只是 GAIA 侧字符输入约束。9B request 高分位仍然会贴近服务端 token 限制。
- 无限 thinking 和无限输出会显著增加 KV cache 压力、wall timeout 和长尾。

七、5 月 4 日：p04 clean、token guard + forced answer，当前 best test 出现

5 月 4 日是当前 GAIA 最关键的一天。

先有一轮 `20260504_0110_abprio` 优先级队列，因为 answer gate 未对齐，AB 阶段全部 `success=0`，作为 dirty 样本保留。

然后修正 `any_phase` 后重跑 p04 clean：

| 配置             |      结果 |
| ---------------- | --------: |
| 8B baseline_test | `15/82` |
| 8B A_test        | `19/82` |
| 9B baseline_test | `32/82` |
| 9B boot_test     | `34/82` |
| 9B A_test        | `34/82` |
| 9B B_test        | `31/82` |

这轮发现 9B 虽然明显强于 8B，但也更容易长链、空 final、hit 24 step，并且在旧 char cap 下出现 HTTP400。

接着启用 token guard + forced answer：

- 关闭字符裁剪：`NLRL_RUNTIME_MAX_CONTEXT_CHARS=0`
- 使用 Qwen3.5-9B tokenizer
- `max_model_len=49152`
- `max_tokens=12288`
- token guard safety margin `512`
- max step 后追加 forced answer prompt

这轮把 HTTP400 压住了，并跑出当前最强 test：

| run              |      分数 |
| ---------------- | --------: |
| 9B baseline_test | `29/82` |
| 9B boot_test     | `35/82` |
| 9B B_dev         | `42/83` |
| 9B B_test        | `39/82` |

当前 best 就是：

`9B p04 token_guard + forced_answer + ARCH-V5.2 + BOOT-V3 + B_sharded`

这一阶段还分析了 9B 空答案提示词注入链路。9B 会更严格遵循 “sufficient / verified / fully supported” 这类取证要求，因此 skill 越强调证据完整，它越容易继续 search / fetch / verify，最后撞 max step。

九、5 月 5 日到 5 月 6 日：开始跳出 GAIA，准备换 benchmark

5 月 5 日晚上开始系统考虑换 benchmark。

一开始从本地资产角度看，SQLBench / AgentBench DB 最干净，tau2 第二。但随后做了 2025-2026 skill 论文 benchmark 调研，优先级发生变化。

调研后的主要判断：

1. 如果目标是和近期 skill 论文对齐，第一主线优先看 SkillsBench。
2. SkillFlow 很适合当前 B2 / critic-actor patch 方向。
3. SkillLearnBench 小而新，适合 automatic skill generation smoke。
4. WebShop / ALFWorld / ScienceWorld 是经典对齐组。
5. OfficeQA / SealQA / BrowseComp 适合展示搜索、证据和文档推理 skill。
6. SQLBench / AgentBench DB 继续适合 smoke 和机制调试，但不应作为唯一主战场。

5 月 6 日又盘点了本机已经落地的 benchmark 资产：

- `/data/xsy/project_agent_skillrl_transfer` 已有 AgentBench、tau2、Terminal-Bench、BrowserGym、SQLBench、WebShop、SealQA、OfficeQA、BrowseComp、SkillsBench。
- 已可全量端到端评分：SealQA、OfficeQA、BrowseComp、SQLBench SQLite 子集、GAIA、EO。

### 1. 汇报结论

这一阶段的核心目标，是在执行链路保持小模型闭环的前提下，让 agent 通过外部 skill 结构获得更稳定的工具使用、证据收集和答案收口能力。GAIA 在这里主要承担压力测试：它同时考验搜索、文件读取、多模态工具、上下文预算、状态图跳转和答案协议。

当前最强 test 记录来自 `Qwen3.5-9B + token guard + forced answer + ARCH-V5.2 + BOOT-V3 + B_sharded`，达到 `39/82`，对应 dev 为 `42/83`。后续 `ARCH-V5.3 + BOOT-V3/V4 + B1/B2` 把图结构做得更清楚，但 test 没有超过旧 best；这说明 GAIA 上的收益同时取决于图规范性和小模型在有限步数内短路径收尾的能力。

方法上，当前最值得继续推进的是 B-V3：把 critic 拆成 graph critic 和 content critic。graph critic 关注节点、边、跳转、loop、repair 出口等结构问题；content critic 按任务类别分 shard 审计失败样本；final critic 汇总两类信号后交给 actor 修改 graph、rules、allowlist 和 next。

### 2. 前置设计依据

相关 agent / skill learning 论文里，很多下游任务也采用 ReAct 或 ReAct-like 的推理-工具调用闭环。差别在于，一些工作会在 executor、critic、planner 或 tool router 中放入强模型。我们的主约束是执行阶段保持小模型闭环，强模型只用于离线生成、审计和修改 skill。因此 executor 继续采用 ReAct 范式，skill 作为外部结构化经验注入。

搜索链路从 DDG 迁到 Serper。原因很直接：GAIA 的 web-heavy 题对搜索后端非常敏感，DDG 免费链路会引入 timeout、403、web file、本地缓存页和代理波动。Serper 接入后，`ARCH-V5.2 no-CONCLUDE c20 + Serper` 的 `web_search` 外部 fail 压到 `0`，搜索噪声显著下降。DDG 保留为 fallback。

工具设计回到 `atomic_v2`。复合工具可以减少步骤数，但通常需要强模型承担中间理解和调度。当前全小模型 executor 更适合看到边界清楚的原子工具：搜索、网页读取、文件读取、表格、PDF、图片、音频、代码计算等都保持显式工具接口。

评测协议加入 forced answer。baseline 和 skill 方法都可能在 max-step 后仍没有提交答案；forced answer 让最后阶段必须输出候选答案，避免空提交把可比较样本变成协议失败。

### 4. 当前方法结构

实验配置按六个主轴描述：

```text
BOOT  ->  初始 skill 怎样生成
FLOW  ->  boot states 怎样进入 critic / actor / aggregate
ROLE  ->  bootstrap actor、offline critic、offline actor 使用什么模型和接口
EXEC  ->  executor 小模型、vLLM、tokenizer、窗口和端口
TOOL  ->  executor 可见工具集合
ARCH  ->  runtime 状态机、答案协议、phase guard、上下文披露方式
```

当前主线组合是：

```text
BOOT-V3 / BOOT-V4
FLOW-batch-V1 / V2 / V3
ROLE-GPT54-codex-V1
EXEC-QWEN8B-local-V2 或 QWEN9B-local
TOOL-GAIA-V2 atomic_v2
ARCH-V5.2 / V5.3
```

BOOT 直接生成 graph + skill，也就是一套可执行状态图和节点技能约束。每个 phase node 至少包含：

```text
phase node
  role:       这个阶段的职责
  rules:      阶段内经验、证据要求、工具选择、答案准备条件
  allowlist:  该阶段允许调用的工具
  actions:    该阶段允许输出的动作形式
  next:       合法后继阶段和跳转条件
```

整体形态是：

```text
BOOT actor
   |
   v
Graph + Skill
   |
   +-- INIT
   |     role / rules / allowlist / actions / next
   |
   +-- LOCAL_EVIDENCE
   |     role / rules / allowlist / actions / next
   |
   +-- WEB_EVIDENCE
   |     role / rules / allowlist / actions / next
   |
   +-- COMPUTE / VERIFY / REPAIR
         role / rules / allowlist / actions / next
```

`ARCH-V5.2` 稳定了 no-CONCLUDE 和 any-phase answer：答案出口从单独 `CONCLUDE` phase 上移到通用 action 层，只要任意阶段输出非空 `<ANSWER>` 就可以终止。`ARCH-V5.3` 在此基础上增加 stale phase prompt hiding：executor 只看到当前 phase 的完整披露，离开旧节点后旧节点内容变成 inactive marker，减少旧 phase 规则在上下文里干扰当前决策。

### 5. 旧 best 和新图的差异

旧 best `ARCH-V5.2 B_sharded` 的图是：

```text
INIT -> PROMPT_SOLVE / LOCAL_EVIDENCE / WEB_EVIDENCE
     -> COMPUTE / VERIFY / REPAIR
```

新 `ARCH-V5.3 B1/B2` 的图是：

```text
INIT -> LOCAL_EVIDENCE / WEB_EVIDENCE / MEDIA_EVIDENCE
     -> COMPUTE / VERIFY_AND_ANSWER / REPAIR
```

新图更清晰，代价也很明确：

- `PROMPT_SOLVE` 被移除后，prompt-only、符号变换和轻量推理题少了一条短路径。
- `LOCAL_EVIDENCE` 移除了 image/audio/run_python，图片、音频和复杂解析需要额外 phase hop。
- `VERIFY_AND_ANSWER` 移除了 PDF/table/image 复核工具，最终阶段遇到这类证据要回跳。
- `REPAIR` 工具面收窄，parser、archive、media blocker 需要绕回 evidence phase。
- 9B 容易过度遵循严格 evidence gate，在 `max_steps=24` 下更容易拖到 forced answer。

所以旧 B 的 `39/82` 更像是“phase 少跳 + VERIFY/REPAIR 工具宽 + prompt-only 快路径 + WEB 硬预算”的组合收益。新 B1/B2 的回落说明，graph 更整洁并不自动带来更高分；对小模型 executor，图结构还必须降低执行成本。

### 6. B1、B2、B3

B1 是 batch critic 版本：按 failure family / shard 分批审计，aggregate 后交给 actor，graph 锁住，主要修改 rules、allowlist 和 phase 内提示。结果为 `40/83`、`32/82`。

B2 允许 critic 输出 `graph_structure_signals` 和 `allowlist_rules_signals`，actor 有权限修改 phase graph、`Next:`、allowlist 和 rules。实际产物 graph signature 基本没变，主要变化仍落在 rules/allowlist。结果为 `41/83`、`31/82`。这个结果说明，放开改图权限不会自动产生结构修改，critic 信号需要变成更明确的 patch。

B3 的设计把“图结构评价”和“内容经验评价”拆开：

```text
executor trajectories
   |
   v
math profiler
   |-- edge / phase value profile
   |-- path / loop / missing-transition profile
   |-- compact task table
   |
   +------------------------+
   |                        |
   v                        v
Graph Critic          Rules / Content Critics
   |                        |
   |                        +-- shard by task family
   |                        +-- inspect rules / allowlist / exit handoff
   |                        +-- produce content-level fixes
   |
   +-----------+------------+
               v
        Aggregate / Final Critic
               |
               v
        graph + skill patch signal
               |
               v
        Graph-unlocked Actor
```

Graph Critic 使用压缩后的图统计输入，主要看 `skill_graph_view`、edge/phase value、loop、missing transition、path cost 和代表性失败边。它输出节点、边、routing、repair、answer exit 的结构建议。

Content Critic 关注题目内容和失败经验。GAIA dev 有 83 题，后续换更大训练集时无法一次性全塞给一个 critic，因此按预设任务类别分 shard：搜索证据、表格/文件、PDF/Office、多模态、计算、multi-hop 等。每个 shard 输出 rules、allowlist、handoff 和具体经验修正。

Final Critic 负责合并信号，去掉冲突和重复建议，最后给 actor 一个更像 patch 的指令。下一版 patch schema 应显式包含：

```text
op / target / evidence / expected_metric_effect / rollback_condition
```

### 7. 当前结论和下一步

GAIA 已经暴露了小模型 skill learning 的关键瓶颈：搜索后端、工具粒度、上下文预算、状态图跳转、答案协议和 forced answer 收口。它适合作为回归与失败分析环境，但继续只在 GAIA 上刷分的边际收益下降。

短期在 GAIA 上保留两条动作：

1. 完成 5 月 7 日 remain20 的 B1/B2/B3 评测，确认 B3 graph-value critic 是否真的改图、是否超过 `39/82` 旧 best。
2. 若 B3 继续回落，回到旧 B 的关键能力做小改：恢复 VERIFY/REPAIR 工具面，补 prompt-only 快路径，给 WEB 一主一备硬预算，并在剩余步数很少时强制收口。

中期把方法迁到更 skill-native 的 benchmark：

- `SkillsBench`：最贴近 `SKILL.md + scripts/references + verifier` 的工件形态。
- `SkillFlow`：最贴近 lifelong skill discovery / patch / transfer。
- `SkillLearnBench`：规模小，适合快速验证自动 skill generation。
- `OfficeQA / SealQA / BrowseComp`：适合验证搜索、证据和文档推理 skill。

组会主结论：当前分数最高的是旧 `ARCH-V5.2 B_sharded`，最新方法设计的价值在于把 skill 从文本规则推进到 graph + skill，再把 critic 从单一文本反馈推进到 graph critic + content critic 的结构化反馈。后续实验要验证 B3 能否把这种结构化反馈真正转化成可执行的 graph patch 和稳定分数提升。
