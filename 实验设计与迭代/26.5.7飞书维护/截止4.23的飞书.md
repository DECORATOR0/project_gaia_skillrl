二、读论文后，我目前比较确定的几点

1. SkillsBench：先确认skill机制有用，以及什么样的skill机制是有用的。

- 这篇回答 skill 本身能不能带来稳定收益。
- 它提示我：curated / high-quality skills 往往有效，但现场自动生成的 self-generated skills 很不稳定，甚至会引入噪声。
- 结论：必须把 skill 质量评估 和 skill 生成/更新机制 分开看，也就是skill质量很重要。
  
2. SkillCraft：skill如何创建——workflow的角度

- 关注 executable skill，也就是把成功的多步工具链沉淀成可复用 workflow，而不是只保留一段高层提示词。
- 和我现在的实验体验很一致：真正有用的 skill，往往不是一句抽象描述，而是对 工具顺序、输入选择、停止条件 的稳定先验。
- 提示我更关注 skill reuse、workflow abstraction 和 skill verification。
  
3. AutoSkill：维护可演化的 skill library

- 它把长期交互里的稳定经验抽成可复用 skill，且在测试交互时实时地更新skill库，或许是后续能够追加的一个trick或者说亮点
- memory 更偏“以前发生过什么”，skill 更偏“以后遇到类似任务该怎么做”。
  
4. EvoSkill：skill 更新里最关键的不是生成，而是验证和选择

- 这篇把 failure analysis -> propose -> build -> validate -> select 的闭环写得比较完整。
- 与前面不同，不仅关注“会不会生成新 skill”，还关注“生成之后怎样验证、怎样筛掉无效更新”。
- 和我们的工作流很像，我们现在的框架可以理解为在它上面的一些改进和深入。

3.2 这一段实验带来的两个核心认识

1. 当前 skill 在这个 benchmark 上的第一个价值，是约束工具包络。104 个工具全开放时，小模型面对的动作空间太大，上下文压力也更重。
2. 当前 skill 的第二个价值，是提供高层执行范式。小模型不只需要少一点工具，还需要知道这类题通常该怎样分步骤、先做什么、什么时候停。
  
所以 token 问题当前还没有解决完。即使带 skill，现有 skill 注入体积也依然偏大。tree 之所以还有继续做的价值，一个重要原因就是它更容易做细粒度约束；再往后看，更本质的方向还是渐进式披露，让同一条 skill 按需要逐步展开，避免在起点一次性把全部信息塞给 executor。

4.3 一个具体案例：task_08_44

如果只用一题来说明下游消费差异，task_08_44 很合适。这题是 ATI 月度变化题，三个形态在下游的差异比较清楚。

5. 接下来要做的事

1. Flat tree测试的错误分析
2. 继续调 critic 和 actor 的行为控制，提升 retained skill 的修改质量，并把聚合后的 guidance 做得更稳。
3. 继续往“单一总 skill + 内部多步路由”推进。当前多 skill 和 mode 的地位已经越来越接近，后续可以把外部 skill 数量继续收口，把内部层次统一放到一个总 skill 里管理。
4. 在 Earth-Bench 上把这条线调稳后，再迁移到更多任务和 benchmark 上验证泛化。
  
一句话版结论

这周期最重要的收获有四点：下游消费范式已经收口到单 executor；训练端可以从 gpt-5.4 切到 gpt-5.2 控制成本；token / 上下文问题已经确认是当前主要工程瓶颈；skill 在这个 benchmark 上的直接价值，主要体现在缩小工具包络和提供高层执行范式。
