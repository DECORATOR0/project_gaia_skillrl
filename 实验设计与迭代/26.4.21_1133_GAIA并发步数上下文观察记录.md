## 1. 结论摘要

这轮排查后，系统层面可以先固定三条结论：

1. 同一 LLM endpoint 上同时挂两条 `c20` 训练，稳定性不够。
   早期 `iteration_01` 没看到 429；后续两条恢复跑同时推进 `iteration_02` 时，executor 日志里出现了成批 `429 Too Many Requests`。这说明总并发打到 40 以后，服务余量偏紧，至少不适合作为默认配置。

2. `max_executor_steps` 不能只靠配置文件隐式继承。
   恢复跑脚本早期只覆写 `iterations_per_batch` 和 `task_concurrency`，步数会静默继承当时的 `system.json`。只要配置文件里的步数和原实验不同，恢复跑数据就会被污染。这个点已经补了显式参数和日志打印。

3. 历史配置 `max_context_chars=28000` 对 24 步 executor 偏紧。
   在 24 步的 `iteration_01` 里，`35.8%` 的题出现过显式 `[truncated]`，很多 request 的字符数贴着 28000 上限。当前 `system.json` 已经调到 `48000`，这个方向是对的，短期内不建议降回去。

## 3. 并发观察

### 3.1 直接证据

原始 `iteration_01` 两条日志里都没有 429：

| run | `429 Too Many Requests` | `Streaming attempt ... failed` |
|---|---:|---:|
| baseline `iteration_01` | 0 | 0 |
| step32 `iteration_01` | 0 | 0 |

后续两条恢复跑日志里，429 明显出现：

| run | `429 Too Many Requests` | `Streaming attempt ... failed` |
|---|---:|---:|
| baseline clean `iteration_02` | 9 | 10 |
| step32 clean `iteration_02` | 13 | 18 |

日志里的报错样式一致，来源都是 executor 模型接口：

```text
[executor] Streaming attempt 1/6 failed: Client error '429 Too Many Requests' for url 'http://35.220.164.252:3888/v1/chat/completions'
```

### 3.2 429 来源判断

这批 429 落在 executor LLM API 上，不在网页抓取工具上。

我把两条 clean `iteration_02` 的 `state.json` 里 web 相关调用重新扫了一遍：

| run | web 调用数 | 观测到的 HTTP 状态 | web 侧 429 |
|---|---:|---|---:|
| baseline clean `iteration_02` | 198 | `200 x 38` | 0 |
| step32 clean `iteration_02` | 186 | `200 x 28`, `202 x 1` | 0 |

结论：

- 这次“429”主要是 executor API 并发压力。
- 当前证据里，没有看到网页工具因为站点访问量而触发 429。
- 以后如果再抽查 state 里的 `429` 字样，先区分它是页面内容、搜索结果标题，还是 API 错误字符串。

### 3.3 对默认并发的建议

- 默认总 executor 并发先按 `20` 控。
- 同一台机、同一个 `http://35.220.164.252:3888/v1` endpoint 上，两个实验同时各跑 `c20`，建议排队或错峰。
- 如果必须并行，至少要把 429 计数、重试次数、单题完成率一起盯住，不能只看进程还活着。

### 4.3 恢复跑的步数坑

`resume_gaia_partial_run.py` 之前有两个容易污染实验的点：

1. 恢复跑时没有显式参数传 `max_executor_steps`
2. 日志里没有打印最终生效的 runtime

这样一来，只要 `system.json` 在恢复跑之前改过，恢复跑就可能悄悄用错步数。

当前脚本已经补上：

- `--max-executor-steps` 参数
- `Runtime: iterations_per_batch=... task_concurrency=... max_executor_steps=...` 日志

相关位置：
- `resume_gaia_partial_run.py:355`

### 4.4 对步数的操作建议

- 新实验启动时，`max_executor_steps` 用环境变量或命令行显式传。
- 恢复跑时，先看日志里的 `Runtime:` 行，再确认任务确实按预期步数继续。
- 做横向对比时，步数必须当成受控变量。24 步和 32 步不能混在一组里直接看胜负。

## 5. 上下文窗口观察

### 5.1 机制位置

executor 的消息裁剪发生在：

- `gaia_skillrl/agent_loop.py`
- `_prepare_messages_for_call(messages, max_context_chars)`
- `_TRUNCATION_MARKER = "\\n\\n[truncated]\\n"`

这里的 `max_context_chars` 是单次调用前的消息字符预算。它约束的是送进 executor LLM 的文本总长度。

### 5.2 历史配置 `28000` 的 24 步观测

这部分统计针对当时的旧值 `max_context_chars=28000`。

### 5.4 当前配置与建议

当前 `system.json` 已经是：

```json
"runtime": {
  "max_executor_steps": 24,
  "iterations_per_batch": 1,
  "max_context_chars": 48000,
  "search_results_limit": 5,
  "web_fetch_char_limit": 6000
}
```

建议：

- `max_context_chars=48000` 可以先保留。
- 24 步实验短期内不建议回到 28000。
- 32 步实验如果后面继续拉长尾，可以在 `48000` 到 `64000` 区间观察一次，前提是同时监控 token 成本。

附带观察：

- `web_fetch_char_limit=6000` 只是工具默认值。
- executor 如果显式传更大的 `max_chars`，网页结果仍然可能放大上下文。
- 后面如果还想进一步稳住上下文，工具层可以考虑加硬上限。

## 6. 建议作为默认操作规范的事项

1. 同一 endpoint 上，默认只开一条 `c20`。第二条实验排队或错峰。
2. 所有启动和恢复命令都显式传 `max_executor_steps`。
3. 恢复跑必须检查日志里的 `Runtime:` 行。
4. `max_context_chars` 暂时保留 `48000`，后续只做向上微调，不做回退。
5. 做系统层对比实验时，把并发、步数、上下文窗口都视为主变量，避免多项同时变化。

## 7. 当前可接受的系统基线

如果目标是先把系统层面定住，当前比较稳的基线是：

- executor 总并发：`20`
- baseline 步数：`24`
- 上下文字符预算：`48000`
- 恢复跑：显式传步数并校验 runtime 日志

这套基线已经覆盖了本轮最容易污染实验判断的几个系统问题。后面再改，应尽量一次只动一个主变量。
