# GAIA bootstrap / critic / actor 提示词与 skill 架构设计

时间：2026-04-21 10:52 +0800  
背景分析样本：`/data/xsy/project_gaia_skillrl/实验设计与迭代/26.4.20_2105_GAIA_stategraph_seed_iter01_partial逐题分析.md`  
相关 prompt：`/data/xsy/project_gaia_skillrl/prompts/bootstrap_skill_system.md`、`critic_system.md`、`actor_system.md`

## 1. 目标

本项目的核心目标是训练一套能自动生成并优化 GAIA 通用 skill 的机制：

- bootstrap prompt 引导强模型生成初始 `SKILL.md`。
- executor 用较小模型执行 skill，产出 batch traces。
- critic 从 traces 中提炼 skill-level 缺陷。
- actor 按 critic 反馈修改 skill。
- 多轮迭代后，skill 的泛化执行质量提升。

当前这份人工 state-graph seed skill 的主要价值是诊断机制缺口。它看起来完整，route 覆盖也合理，但运行后暴露出执行成本、硬状态边界、答案出口、渐进式披露这些约束没有被 bootstrap 明确编码。

## 2. 现有信号

2026-04-20 的 iteration_01 部分结果显示：

| 指标 | 数值 |
|---|---:|
| 已完成题数 | 51 |
| 成功题数 | 15 |
| 未完成题数 | 2 |
| `invalid_answer_phase` | 186 |
| `invalid_phase_transition` | 119 |
| 打满 24 步 | 21 |
| 步数 >= 22 | 29 |

这些指标说明，失败的主因大量来自 skill 和 runtime 协议的摩擦：

- executor 经常已经形成候选答案，却在非 `CONCLUDE` phase 输出 `<ANSWER>`，随后被拒绝。
- hard phase 数量多，prompt/local/web/media 这些类型被编码成控制流节点，导致每道题都要支付多次 `<NEXT>` 成本。
- repair edge 过窄，web 检索、计算、校验之间的自然回跳经常被判非法。
- web 失败有工具噪声和网页波动，但 traces 中更明显的问题是重复搜索、证据未固化、候选答案未进入账本。

结论：下一步应改 bootstrap / critic / actor 的提示词设计，让强模型生成更适合 executor 执行和被 actor 优化的 skill 结构。

## 3. 核心架构

建议把 skill 拆成两层：

```text
Hard phase layer:
INIT -> PARSE_ROUTE -> EVIDENCE -> SOLVE -> VERIFY_FORMAT -> CONCLUDE

Soft route layer:
prompt / local / media / web / hybrid

Memory layer:
route
subroute
artifact_type
answer_shape
format_constraints
evidence_ledger
candidate_answer
verification_status
blocking_issue
```

hard phase 表达任务生命周期。soft route 表达任务类型和证据类型。memory layer 承接跨 phase 的少量结构化状态。

这样做的收益：

- phase 数减少，executor 的 `<NEXT>` 成本下降。
- 任务类型仍然清晰，类型差异由 `route` 和 route card 表达。
- critic 和 actor 有稳定的修改对象：phase、edge、answer gate、route card、memory schema、stop condition。
- skill 更容易被强模型生成，也更容易被 actor 局部修改。

这里没有 local/media/prompt 的大段说明，也没有整个 skill 的全部内容。runtime 负责把上下文压缩成这一小块。

## 4. 渐进式披露如何实现

### 4.1 prompt-only 版本

当前 runtime 也能支持一个轻量版本。`SKILL.md` 中保留所有 route card，但要求 executor 在每个 phase 只使用当前 `route` 对应的小节。

示例：

```markdown
## Phase: EVIDENCE

Visible memory: route, attachments, answer_shape, evidence_ledger, blocking_issue.

Goal: collect the smallest sufficient evidence for the selected route.

If route=prompt:
- Do not call tools unless arithmetic or enumeration benefits from run_python.
- Convert prompt constraints into evidence_ledger rows.

If route=local:
- Inspect only relevant attachments.
- Record file path, row/cell/slide/page/line when available.

If route=web:
- Search one hop at a time.
- Record source_url, source_title, source_sentence, extracted_fact.
- Stop searching once candidate_answer is source-backed.

If route=media:
- Use OCR/audio/image tools only for the requested visual or audio facts.
- Convert raw media output into compact structured facts.

If route=hybrid:
- Execute route_plan in order, such as local -> compute or web -> compute.
```

这个版本的渐进式披露依赖 prompt discipline。所有内容仍在 skill 里，但 executor 有明确选择规则。

### 4.2 runtime-supported 版本

更强的版本需要 runtime 按 `route` 注入 route card。skill 生成结构可以像这样：

```yaml
phases:
  - INIT
  - PARSE_ROUTE
  - EVIDENCE
  - SOLVE
  - VERIFY_FORMAT
  - CONCLUDE

route_cards:
  prompt:
    evidence: ...
    solve: ...
    verify: ...
  local:
    evidence: ...
    solve: ...
    verify: ...
  web:
    evidence: ...
    solve: ...
    verify: ...
  media:
    evidence: ...
    solve: ...
    verify: ...
  hybrid:
    evidence: ...
    solve: ...
    verify: ...

memory_schema:
  route: prompt|local|web|media|hybrid
  route_plan: []
  answer_shape: ""
  format_constraints: []
  evidence_ledger: []
  candidate_answer: ""
  blocking_issue: ""
```

runtime 在 `PARSE_ROUTE` 后保存 `route`，进入 `EVIDENCE` 时只注入：

```text
Current phase: EVIDENCE
Current route: web
Visible route card: route_cards.web.evidence
Visible memory: answer_shape, format_constraints, evidence_ledger, blocking_issue
```

这个版本能真正减少上下文噪声。实现复杂度更高，可以作为第二阶段。

## 5. 预期生成的 SKILL.md 架构

bootstrap 应要求强模型生成一份结构化、可 lint 的 skill。建议目标格式如下：

```markdown

  - parse_pptx
  - extract_archive
  - web_search
  - fetch_url
  - html_extract
  - run_python

  benchmark: GAIA
  version: boot-v2
  entry_phase: INIT
  answer_phases:
    - VERIFY_FORMAT
    - CONCLUDE
---

## Skill Contract

...

## Memory Schema

...

## Route Cards

### route=prompt
...

### route=local
...

### route=web
...

### route=media
...

### route=hybrid
...

## Phase: INIT
...

## Phase: PARSE_ROUTE
...

## Phase: EVIDENCE
...

## Phase: SOLVE
...

## Phase: VERIFY_FORMAT
...

## Phase: CONCLUDE
...

```

关键设计点：

- `answer_phases` 至少允许 `VERIFY_FORMAT` 和 `CONCLUDE`。如果 runtime 暂时只允许 `CONCLUDE`，skill 必须强制 `VERIFY_FORMAT -> CONCLUDE` 的单步出口。
- route card 放在 phase 前面，phase 内只引用 route card，避免把所有类型逻辑写进 hard phase 控制流。
- `EVIDENCE` 负责证据采集，`SOLVE` 负责从证据推出候选答案，`VERIFY_FORMAT` 负责答案形态。
- `CONCLUDE` 只做最后输出。

## 6. Bootstrap prompt 设计

### 6.1 bootstrap 的输入

bootstrap 可以看见：

- 当前 skill library snapshot。
- 选定 batch 的任务摘要。
- 训练阶段可用的 gold answer、gold trajectory、reference process。
- 工具列表和 executor 约束。
- runtime 约束，如 `qwen3-8b`、`max_executor_steps`、`task_concurrency`、工具可用性。

训练阶段的 bootstrap 可以利用 gold 信号做 skill induction。输出 `SKILL.md` 时，仍应把这些信号蒸馏成 reusable workflow，避免把题目专属答案、固定实体链、固定 URL 结论直接写进 skill。

### 6.2 bootstrap 的设计要求

建议在 `bootstrap_skill_system.md` 中加入这些硬约束：

```text
Design a general GAIA skill for a qwen3-8b phase executor.

The skill must use 5-7 hard phases only.
Hard phases must describe task lifecycle, not evidence modality.

Use soft routes to represent task types:
prompt, local, web, media, hybrid.

Generate:
1. YAML frontmatter.
2. Skill Contract.
3. Memory Schema.
4. Route Cards.
5. Phase definitions.
6. Answer Gate.
7. Graph Lint.

Each route card must define:
- when to choose the route
- useful tools
- evidence ledger rows to record
- stop condition
- repair condition
- verification focus

Each phase must define:
- visible memory
- goal
- allowed tools
- entry condition
- exit condition
- available actions

Graph lint must check:
- INIT can reach CONCLUDE.
- Every route reaches VERIFY_FORMAT in at most 5 phase transitions after PARSE_ROUTE.
- There is at least one repair path from SOLVE or VERIFY_FORMAT back to EVIDENCE.
- No phase requires a tool unavailable in allowed-tools.
- The answer gate is compatible with the executor protocol.
```

### 6.3 bootstrap user prompt 重点

`bootstrap_skill_user.md` 应从“这批题有什么类型”转成“请从这批题归纳 route coverage 和 execution constraints”。

建议补充：

```text
Use the selected batch only to infer reusable route coverage.
You may read gold answers and reference trajectories during training-time induction.
Do not emit task IDs, task-specific answers, fixed named entities, fixed URLs, or one-off facts into the final skill.

Optimize for execution by qwen3-8b:
- minimize hard phase count
- avoid long mandatory phase chains
- define explicit answer gates
- avoid forcing web use when local or prompt evidence is enough
- preserve exact short-answer formatting

Prefer route cards over modality-specific hard phases.
```

## 7. Critic prompt 设计

critic 的职责是把 rollout traces 变成 skill-level reward。它不应停留在“哪些题错了”，应输出可以被 actor 操作的缺陷对象。

### 7.1 critic 诊断维度

建议固定这些维度：

| 维度 | 关注点 | 典型指标 |
|---|---|---|
| graph_friction | phase 结构和边导致的摩擦 | `invalid_answer_phase`、`invalid_phase_transition`、max-step hit |
| route_selection | route 选错或 hybrid plan 缺失 | 先 web 后发现应本地、prompt 题误搜索 |
| evidence_ledger | 证据没有固化 | 重复搜索、source sentence 缺失、候选答案漂移 |
| solve_policy | 推理、计算、枚举、比较策略 | 计算错、过滤过宽、实体链断裂 |
| format_policy | final answer 形态 | 单位、精度、大小写、列表顺序、答案粒度 |
| tool_noise | 工具或网页波动 | 403、空结果、解析失败、stream retry |
| skill_edit_priority | actor 应先改哪里 | phase、edge、answer gate、route card、memory schema |

### 7.2 critic 输出格式

建议让 critic 返回结构化 JSON：

```json
{
  "natural_language_reward": "...",
  "batch_metrics": {
    "success_count": 0,
    "invalid_answer_phase": 0,
    "invalid_phase_transition": 0,
    "max_step_hits": 0,
    "empty_answer_count": 0
  },
  "failure_modes": [
    {
      "name": "answer_gate_too_strict",
      "severity": "high",
      "evidence": "many tasks produced candidate answers before CONCLUDE",
      "affected_routes": ["prompt", "web", "local"],
      "recommended_edit_target": "answer_gate"
    }
  ],
  "edit_priorities": [
    {
      "target": "answer_gate",
      "change": "allow VERIFY_FORMAT to answer or force one-step transition to CONCLUDE",
      "expected_effect": "reduce invalid_answer_phase and max-step hits"
    }
  ],
  "guardrails": [
    "Do not add task-specific facts.",
    "Preserve all working routes."
  ],
  "summary": "..."
}
```

### 7.3 critic 的行为约束

critic 应遵守：

- 优先给 skill-level 缺陷，少做单题叙事。
- 先看跨题重复出现的 failure signature。
- 对工具失败降权，只有稳定复现的工具问题才提升优先级。
- 每条建议都必须映射到 actor 可修改对象。
- 给出预期指标变化，如减少 illegal transition 或减少 max-step hit。

## 8. Actor prompt 设计

actor 的职责是把 critic reward 转成最小、可执行、可审计的 skill 修改。

### 8.1 actor 可修改对象

建议把修改对象限制在这些类别：

```text
phase:
  add, remove, merge, rename, rewrite entry/exit condition

edge:
  add safe transition, remove loop, add repair path

answer_gate:
  allow answer phase, require one-step conclude, define final answer string contract

route_card:
  update route choice, tool policy, stop condition, repair condition

memory_schema:
  add or simplify route memory fields

format_policy:
  exact short answer rules, units, rounding, list order, answer grain

evidence_policy:
  source ledger, candidate source selection, repeated query limit
```

### 8.2 actor 输出格式

建议 actor 返回：

```json
{
  "summary": "short modification summary",
  "target_skill_name": "gaia-general-skill",
  "edit_plan": [
    {
      "target": "answer_gate",
      "operation": "rewrite",
      "reason": "invalid_answer_phase dominated failures",
      "expected_metric_effect": "lower invalid_answer_phase"
    }
  ],
  "files_to_write": {
    "SKILL.md": "full updated skill"
  },
  "files_to_delete": [],
  "experience_entry": {
    "failure_signature": "answer_gate_too_strict + overlong hard graph",
    "action_type": "modify_skill",
    "affected_skills": ["gaia-general-skill"],
    "modification_summary": "..."
  }
}
```

### 8.3 actor 的硬约束

actor prompt 应明确：

- 保留 YAML frontmatter 中的工具列表，禁止发明工具。
- 保留 route coverage：prompt、local、web、media、hybrid 都要有可走路径。
- 禁止加入任务 ID、具体答案、具体实体、具体 URL。
- 每轮最多做 1 到 3 类结构修改，避免整份 skill 漂移。
- 修改后必须更新 `Graph Lint`。
- 如果 critic 指向 graph friction，优先改 edge 或 answer gate，少加长 checklist。
- 如果 critic 指向 evidence strategy，优先改 route card 和 evidence ledger，少改 phase graph。

## 9. 预期效果

### 9.1 bootstrap 预期效果

新的 bootstrap 应生成：

- phase 数更少的 skill。
- route 表征更清晰的 skill。
- 有明确 memory schema 的 skill。
- 带 answer gate 和 graph lint 的 skill。
- 能被 critic/actor 稳定局部修改的 skill。

### 9.2 critic 预期效果

新的 critic 应输出：

- 更少单题流水账。
- 更明确的 failure signature。
- 更容易被 actor 执行的 edit target。
- 更稳定的跨轮经验条目。

### 9.3 actor 预期效果

新的 actor 应产生：

- 更小的 skill diff。
- 更少 prompt 膨胀。
- 更少无序重写。
- 更强的 route coverage 保持能力。
- 更清晰的“改了什么、为什么改、预期指标怎么变”。

### 9.4 rollout 指标预期

第一轮不只看成功数。建议优先观察这些指标：

| 指标 | 预期方向 |
|---|---|
| success_count | 不低于旧 seed 的自然波动区间 |
| `invalid_answer_phase` | 大幅下降 |
| `invalid_phase_transition` | 明显下降 |
| max-step hit | 明显下降 |
| empty answer | 下降 |
| repeated web query | 下降 |
| successful routes 覆盖 | prompt/local/web/media 都保留 |

如果协议指标明显改善，成功数仍在 15 到 19 附近，这个 bootstrap 方向仍然健康。下一步再专门改 route cards 和 critic/actor 的 evidence policy。

## 10. 推荐实施顺序

### 第一步：只改 bootstrap prompt

改 `bootstrap_skill_system.md` 和 `bootstrap_skill_user.md`，让强模型按上述结构生成新 seed skill。

验证：

- 生成的 `SKILL.md` 是否满足 5 到 7 hard phases。
- 是否包含 route cards。
- 是否包含 memory schema。
- 是否包含 answer gate。
- 是否包含 graph lint。
- 是否覆盖 prompt/local/web/media/hybrid。

### 第二步：用新 bootstrap seed 跑一次 iteration_01 smoke

保持工具、runtime、模型、并发、题集一致。先不让 actor 介入复杂优化。

记录：

- success count。
- outcome 统计。
- phase transition 数。
- route 使用分布。
- max-step hit。
- 空答案。

### 第三步：改 critic prompt

让 critic 输出 failure_modes、edit_priorities、guardrails。先让 critic 读新 seed 的 iteration_01 traces，检查它是否能提出结构化修改建议。

### 第四步：改 actor prompt

让 actor 根据 critic reward 修改 skill，但限制 diff 尺度和修改对象。检查 actor 是否遵守：

- 无任务特化内容。
- 无工具发明。
- route coverage 保持。
- graph lint 更新。
- 修改理由和预期指标清楚。

### 第五步：跑两轮训练

在 bootstrap、critic、actor 都结构化后，再跑完整两轮训练。评估关注均值和稳定性，减少对单次总分波动的解释。

## 11. 对当前人工 seed 的使用方式

当前人工 seed 可以保留为对照组和 failure corpus：

- 用它的 traces 校准 critic prompt。
