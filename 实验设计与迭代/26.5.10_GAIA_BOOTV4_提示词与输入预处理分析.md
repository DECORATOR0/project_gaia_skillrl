## 结论摘要

当前 `BOOT-V4` 是“bootstrap 生成 hard phase graph”的版本：先用 `gpt-5.4/codex_cli` 对 83 道 `validation_dev` 题做轻量预处理，给每题追加 `preprocess_note`；再把 runtime contract、完整题目快照、gold answer、附件摘要和 preprocess notes 一起交给 bootstrap skill architect，生成一个 `gaia-general-skill/SKILL.md`。

本轮实际生成的 skill 是 6 phase 图：

`INIT -> LOCAL_EVIDENCE / WEB_EVIDENCE / COMPUTE / VERIFY / REPAIR`

具体 phase 为：`INIT`、`LOCAL_EVIDENCE`、`WEB_EVIDENCE`、`COMPUTE`、`VERIFY`、`REPAIR`。没有 `CONCLUDE` phase，也没有专门 answer-only phase；最终回答是任意 phase 内满足证据和格式条件后的全局 stop action。

## 两段提示词链路

### 1. 题目预处理 prompt

预处理由 `SkillBootstrapper._preprocess_batch_payload()` 触发，条件是：

- `NLRL_RUNTIME_BOOTSTRAP_TASK_PREPROCESS=1`
- `NLRL_RUNTIME_BOOTSTRAP_PREPROCESS_NOTE_CHAR_CAP=700`

输入给 actor 的内容：

- runtime contract
- raw batch task snapshot
- note 字符预算

输出要求：

- 只能返回一个 JSON object
- 顶层必须有 `items`
- `items` 内每个对象必须包含 `task_id` 和 `preprocess_note`
- 每题一条 note
- note 是训练期提示，只写工作流、工具顺序、确定性处理、验证和格式压力
- 可以看 gold answer 来推断答案形状、单位或格式压力
- 禁止复制 gold answer、固定事实、固定 URL、题目专属最终值

运行时校验：

- 如果 `items` 不是 list，直接报错
- 如果任意 input task 没有对应 `task_id` 的 note，直接报错
- note 会经过 `_cap_preprocess_note()` 再写回 task row
- 本轮 `missing_count=0`

### 2. skill 生成 prompt

skill 生成由 `SkillBootstrapper.bootstrap()` 触发。它读取：

- `bootstrap_skill_system.md`
- `bootstrap_skill_user.md`
- runtime contract
- 预处理后的 batch snapshot

输出要求：

- 只能返回一个 JSON object
- 顶层必须包含 `summary`、`target_skill_name`、`files_to_write`
- `target_skill_name` 固定为 `gaia-general-skill`
- `files_to_write` 必须包含非空 `SKILL.md`
- 禁止创建 `scripts/` 文件
- 可选 reference files 原则上避免

`SKILL.md` 的强约束：

- 必须以 YAML frontmatter 开头
- frontmatter 必须包含 `name`、`description`、`allowed-tools`、紧凑 `metadata`
- 只能使用 runtime contract 中的工具
- phase header 格式为 `## Phase: NAME`
- 必须包含 `INIT`
- 禁止 `CONCLUDE`
- 禁止专门 answer-only finalization phase
- 每个 phase 必须有显式 `Next:`，供 runtime 推断 graph
- 每个 phase 应含 `Goal`、`Allowed tools`、`Rules`、`Exit handoff`、`Available actions`、`Next`
- `Allowed tools` 是 phase 级硬工具白名单
- 每步只能输出一个动作：`<CALL>`、`<NEXT>` 或 `<ANSWER>`
- final answering 是全局 stop action，phase 名本身不能成为 answer gate
- evidence / computation / verification / repair phase 的规则可以写得较密，模板建议主要工作 phase 约 250-600 words

主要行为：

- `INIT` 负责读 `task.json`、识别题型和答案格式，尽早路由。
- `LOCAL_EVIDENCE` 负责附件和 workspace 文件，强调优先 native parser，必要时用 `run_python` 处理样式、坐标、公式、科学文件和复杂表格。

- `COMPUTE` 只允许 `run_python`，负责确定性转换：算术、单位、排序、去重、图/网格、日期、约束求解等。

## 对提示词设计的判断

优点：

- BOOT-V4 把 hard graph 设计集中在 bootstrap 阶段，后续 B/A/B3 可以在同一图上做 actor 修改或锁图修改，版本边界清晰。
- task preprocess 给 bootstrap architect 提供了题型密度、工具顺序、格式压力，能把局部经验沉淀成通用 phase rules。
- `Allowed tools` 和 `Next` 都显式，符合 runtime 的 progressive disclosure 机制。
- 无 `CONCLUDE`，配合 `any_phase`，避免小模型被迫多走一个 answer-only phase。
- `LOCAL_EVIDENCE` 和 `VERIFY/REPAIR` 的全工具/半全工具设计覆盖附件题、网页题、计算题和多模态题。

风险与可调点：

- bootstrap 输入包含 `gold_answer`。prompt 禁止复制最终答案，但这仍会让 skill 学到 dev 集答案形状和格式压力；这是训练期 bootstrap 的设计选择，调优时要明确是否接受。
- preprocess note 里对无附件 web 题直接提工具名较少，更多是 workflow 描述；如果希望强化 search/fetch/html 的阶段选择，可以改 preprocess prompt，让 note 固定输出 `likely_route` 或 `tool_order` 字段。
- 当前 skill 的 `VERIFY` 和 `REPAIR` 都允许全工具。覆盖面强，但也可能让模型在后段重新发散搜索。若后续要降步数，可以让 VERIFY 更窄，只允许最常见的确认工具，REPAIR 保留全工具。
- `COMPUTE` 只允许 `run_python`，很干净；但如果进入 COMPUTE 后发现缺事实，只能转 VERIFY/REPAIR，不能直接回 LOCAL/WEB。当前路径依赖 REPAIR 中转，步数会增加。
- prompt 模板里的 `qwen3-8b` 历史措辞与当前 `Qwen3.5-9B-local` 不一致。建议下次 BOOT-V4+ 改成“small executor model”或直接从 runtime contract 注入 executor model，避免版本混淆。
- skill body 中每个主 phase 很长，适合低歧义执行，但会增加 phase 注入 token。当前 no-trunc + token guard 能支撑；若未来 max_model_len 收紧，要考虑压缩 Rules。

## 如果要继续调 BOOT-V4

优先看这几处：

1. 把 preprocess 输出从单个 `preprocess_note` 升级成结构化字段：`likely_route`、`tool_order`、`format_pressure`、`risk_check`。这样 bootstrap skill architect 更容易稳定生成图和 phase rules。
2. 修正 `bootstrap_skill_user.md` 里的 executor 模型措辞，避免 `qwen3-8b` 历史残留。
3. 给 bootstrap prompt 增加“VERIFY 不要 broad search，REPAIR 才允许 broad repair”的更硬约束，减少后段发散。
4. 让 `COMPUTE` 的 Next 增加 `LOCAL_EVIDENCE` / `WEB_EVIDENCE`，或者在 COMPUTE rules 里更明确“缺事实时走 REPAIR”的判断，二者选一保持图语义一致。
5. 对 attachment-heavy 题，把 preprocess prompt 强制要求 mention primary tool，尤其 `.xlsx/.png/.zip/.pdf/.docx/.pptx/.mp3`，降低 INIT 路由不稳定。
