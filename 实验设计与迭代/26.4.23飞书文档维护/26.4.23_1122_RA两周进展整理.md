# RA-熊思远两周进展整理

时间范围：2026.4.10-2026.4.23

## 一页总结

这两周的主线经历了从 `EarthBench / EO Bench` 到 `GAIA` 的切换。

前半段主要继续沿用学长后面设想的 `skill 渐进式披露` 方向，在 EarthBench 上把 V6 prompt、单 executor、strict-state、actor / critic prompt、工具契约、gold 覆盖和 data align 都做了一轮系统排查。结论是：这条线在工程上已经能跑，但 benchmark 本身存在较重的数据、工具、gold trajectory 和训练/测试划分问题；同时任务范式偏简单，主要是工具选择和参数传递，继续投入大量调参不一定能充分验证 SkillRL 架构。

后半段主线切到 GAIA。先完成独立项目初始化、GAIA 数据接入、工具链、本地官方 scorer、executor / critic / actor / skill writeback 闭环；随后在 validation level1 53 题上做了多轮基线、训练、逐题复盘和强状态图实验；再进一步把 validation 按 dev / test 切分，开始用 `bootstrap 定图 + critic/actor 改节点细节` 的方式做固定图 A/B 实验。目前 boot-v3 在 dev 上能有局部涨分，但 test 收益还不稳定，后续重点应转向错例拆解，判断瓶颈落在图行为、证据指导、工具能力，还是 evaluator / API 噪声。

当前资源侧也有变化：上海 AI Lab 额度已经见底，`gpt-5.4` 和原 executor endpoint 都出现过 quota / 403 问题；临时可用方案是保留 `SSSAI gpt-5.2` 做强模型侧 actor / critic，并用自己开的硅基流动 qwen3-8b 号支撑小并发执行。

## 1. EarthBench 线：把问题从 skill 调参推到 benchmark 诊断

### 1.1 V6 接入和执行框架修正

4 月 10 日之后，我主要先把之前 EarthBench 的 skill 方向继续往下推。具体做了这些事：

- 把对方传来的 `V6 prompt snapshot` 接进本地 batch single-skill 训练链路。
- 将下游执行形态继续收口到单 executor，避免 planner / worker / selector 多角色拆分带来的额外不稳定。
- 把 skill 组织成 phase-based 结构，并用 strict-state 约束 phase 跳转。
- 将 `<ANSWER>` 收口到 `CONCLUDE` 阶段，减少中途乱答和空答案。
- 调整 actor / critic 输入，让 critic 能看到完整 skill、完整题干和 choices，让 actor 从 append-only 改成可做局部 `ADD / REPLACE / DELETE`。

这一阶段的结果大致稳定在 `17/30` 到 `18/30` 附近。前期有一部分做对题属于工具失败后靠猜测命中；随着 success 判定、路径契约和 strict-state 收紧，这类脆弱成功被暴露出来，分数没有继续上升，但结果更接近真实能力。

### 1.2 数据、工具和 gold 问题被系统暴露

这几天集中确认了 EarthBench 的几个关键问题：

- `248` 题 gold answer 扫描中，有 `24` 题高置信金标异常，另有 `5` 题记录不完整。
- `248` 题里存在 `63/248` 的 gold batch 写法和当前 runtime tool contract 冲突，典型表现是 gold 把一次 list 调用当成抽象 step，但工具实际不能稳定吃 batch 参数。
- 题面、选项、评测文本和真实数据目录不一致的题有 `26` 题，其中 `19` 题是高置信硬错配。
- strict gold replay 在 30 题上只有 `1/30` 完整跑通，说明大量 gold trajectory 在当前 runtime、数据目录和工具实现上无法顺序执行到底。
- `gpt-5.2 no-skill` 直接跑 30 题只到 `14/30`，强模型也会遇到类似的路径、工具、gold 和猜答问题。

工具层面也做了一轮修补，包括 perception lookup、semantic failure 判定、`SAM2 / ChangeOS` 产物路径、batch 参数双态接口、dataalignv1 题面覆盖等。这些修正把环境噪声压低了，但也进一步说明当前瓶颈主要来自 benchmark 质量和任务范式。

### 1.3 当前对 EarthBench 的判断

EarthBench 目前的价值更适合保留为诊断集和回归集。它能暴露工具契约、路径、gold、strict-state 和 executor 早答等问题；但继续在这条线上调 SkillRL 架构，风险在于：

- 没有明确训练集，后续如果继续在测试集上训练 skill，最终分数意义会被削弱。
- 任务主干多是工具选择、参数传递和结果读取，较少体现复杂推理、长程策略和可迁移 skill 演化。
- 数据、工具、答案和 gold trajectory 同时存在问题，reward 信号容易混入脏监督。

4 月 21 日学长提到那边数据已经修好，所以代码侧已经可以 git 交付和同步；但训练集划分问题仍需要解决，否则在测试集上训练出来的 skill 难以说明泛化价值。

## 2. GAIA 线：从项目搭建到 boot-v3 固定图 A/B

### 2.1 独立项目和最小闭环落地

4 月 17 日开始，主实验切到 `/data/xsy/project_gaia_skillrl`。已完成的底层工作包括：

- 初始化独立 git 项目和目录结构。
- 接入 Hugging Face gated GAIA 数据，先落地 `2023_level1 / validation` 的 53 题。
- 去掉 executor 输入里的 `Annotator Metadata`，避免开发阶段数据泄漏。
- 接入基础工具：本地文件、JSON、PDF、表格、图片元信息、网页搜索、网页抓取、Python 计算。
- 后续补齐多模态和结构化工具：`audio_transcribe`、`ocr_image`、`image_qa`、`parse_docx`、`parse_pptx`、`extract_archive`、`html_extract`。
- 接入官方 GAIA scorer，并对历史 run 做重打分，后续正式分数按 leaderboard-aligned scorer 口径看。

最早单题 smoke 已经跑通 `executor -> critic -> actor -> skill writeback -> final eval`。第一题能答对，但也暴露出 phase 越权、网页证据抽取不稳、没有稳定调用 `run_python` 的问题。

### 2.2 Level1 53 题训练和复盘

4 月 18 日在 level1 53 题上做了几组 qwen3-8b executor + gpt-5.4 actor / critic 的训练和复盘。

代表结果：

| run | iteration_01 | iteration_02 | 官方口径补充 |
| --- | ---: | ---: | --- |
| direct qwen3-8b baseline | - | - | `11/53` |
| train2 c20 | `13/53` | `11/53` | 最终验证重打分 `14/53` |
| train2 c20G | `10/53` | `12/53` | 最终验证重打分 `9/53` |

这几轮给出的主要观察：

- skill 能改善一部分流程完成率，但最终答案准确率提升有限。
- 早答问题很突出，`invalid_answer_phase` 在很多题中大量出现。
- 附件题是明显短板，docx、pptx、mp3、图片棋盘、复杂 xlsx 都需要更强工具或 helper。
- 错误逐渐从“走不完 phase”转向“走完后答错”，包括取错实体、格式不合规、网页证据不完整、表格 join / filter 错、数值题未做程序化验证。

### 2.3 强状态图设计与问题

4 月 20 日基于 53 题扫描，我先人工设计了一版更复杂的强状态图，把原来的 `INIT -> GATHER -> ANALYZE -> CONCLUDE` 拆成：

`INIT -> TASK_PARSE -> EVIDENCE_ROUTE -> PROMPT_SOLVE / LOCAL_PARSE / MEDIA_PARSE / WEB_RETRIEVE -> WEB_EXTRACT -> COMPUTE_OR_COMPARE -> CROSS_CHECK -> FORMAT_VERIFY -> ANSWER / BACKTRACK`

这版图结构的好处是任务族划分清楚，能把 prompt、本地附件、媒体、网页、多跳和格式校验区分出来。部分运行结果也显示状态图可以驱动 8B 做任务路由，`LOCAL_PARSE`、`MEDIA_PARSE`、`WEB_RETRIEVE`、`COMPUTE_OR_COMPARE` 等节点都被真实使用。

但 4 月 20 日的 partial run 也暴露出硬状态图代价很高：

- `15/51` 有效成功，2 题中止未完成。
- `invalid_answer_phase = 186`。
- `invalid_phase_transition = 119`。
- `21` 题打满 24 步，`29` 题步数达到 22 以上。

核心问题是节点太多、无工具 phase 成本高、`CONCLUDE` 单一答案出口过硬、边过窄。很多题已经有候选答案，却因为不在合法节点输出而被拒，最终消耗步数。这个结果促使后续从人工强图回到更轻的 boot / critic / actor 自动机制。

### 2.4 回到 boot / critic / actor：让 boot 定图，RL 轮次改细节

后续架构调整成更清晰的两层边界：

- `bootstrap`：一次性设计状态图、状态名、连线和初始节点信息。
- `critic / actor`：保持图结构不变，只改公共基础信息、节点内 allowed tools、规则、exit handoff、已存在边的使用条件说明。

这样做的目的，是让图结构先由强模型根据任务分布生成，后续 RL 轮次聚焦节点内策略和证据规则，避免每一轮 actor 都大改图导致对照变量混乱。

在 GAIA validation 内部，我把数据切成：

- `validation_dev`：83 题，用于 boot、训练和选择。
- `validation_test`：82 题，用于本地可打分测试。

官方 test 不参与本轮本地可打分实验。

boot-v3 生成的固定图是 8 节点：

`INIT -> ATTACHMENT_PARSE -> WEB_RESEARCH -> DIRECT_REASON -> COMPUTE -> VERIFY -> REPAIR -> CONCLUDE`

随后做了 A/B：

- A 路：full critic，看全量 dev compact rows 后一次 actor。
- B 路：family-sharded critic，先按失败族分 shard，再 aggregate 后 actor。

当前分数按官方 scorer 口径整理如下：

| skill / run | validation_dev | validation_test |
| --- | ---: | ---: |
| direct qwen3-8b baseline | - | `14/82` |
| bootstrap v0.2 | `18/83` | `15/82` |
| boot-v3 初始 skill | `18/83` | `14/82` |
| A full critic iter2 | `21/83` | `11/82` |
| B sharded critic iter2 | `14/83` | `17/82` |
| A full critic iter3 | `21/83` | `14/82` |
| B sharded critic iter3 | `21/83` | `13/82` |

这组结果说明：critic / actor 能在 dev 上局部涨分，但 test 上还没有稳定泛化。A full critic 容易把 dev failure 写成更宽的全局规则，dev 涨分但 test 下降；B sharded critic 的硬证据门一度让 test 到 `17/82`，但后续也回落。到 iter3 时，两路 dev 都到 `21/83`，test 回到 `13-14/82`，说明继续单纯加自然语言规则的边际收益已经很低。

### 2.5 当前已经发现的 GAIA 架构瓶颈

目前比较明确的瓶颈有四类：

1. executor system prompt 和动态 phase graph 曾经不一致。旧 prompt 还写着 `GATHER / ANALYZE`，boot-v3 图里已经没有这两个节点。这个问题已经在 4 月 22 日修掉，后续需要做修复前后对照。
2. critic compact row 信息密度不够。只给 task、gold、final、path、tools、outcome_counts，缺少关键 observation、失败工具上下文、候选答案来源和最后 reasoning，导致 critic 容易输出宽泛规则。
3. 自然语言 skill 承担了过多精确行为。USGS、Wikipedia revision、HTML 表格、附件结构化摘要、多跳网页证据等问题，需要工具或 helper 承接一部分。
4. 固定图只能表达粗任务族。`WEB_RESEARCH` 和 `VERIFY` 负担过重，等前面的问题处理后，可以再考虑 graph revision，把网页目标页获取、事实抽取和格式审计拆得更细。

## 3. 方法调研和思路沉淀

这两周也持续用 AI 辅助查了一些和自动机、图结构、层级 RL、skill library 相关的方向，主要是为了回答“怎样压缩 agent 的执行空间”：

- 有限状态控制器、behavior tree、hierarchical machines、option / skill 等层级 RL 思路。
- AutoSkill、EvoSkill、EvoSkills、ExpeL、Voyager、SkillWeaver 等 LLM agent skill 自改进路线。
- SkillsBench、OfficeQA、SealQA、BrowseComp、HotpotQA、WebShop、ALFWorld 等 benchmark 的交互范式和 skill 适配性。

当前对我们最有参考价值的点是：skill 的关键不仅在生成，也在验证、选择、可复用结构和上下文消费方式。GAIA 上的 boot-v3 固定图实验已经体现出这一点：人工或 boot 设计图可以短期带来结构化行为，但后续能否提升，要看 critic 能否定位真实失败、actor 能否做小而稳定的修复、runtime 能否把节点局部信息渐进式披露给 executor。

## 4. 当前状态和下一步

当前工程状态：

- EarthBench 线已经完成一轮系统诊断和代码交付，等待数据修复后的训练集划分方案。
- GAIA 线已经具备独立项目、工具链、官方 scorer、dev/test 切分、bootstrap、critic、actor、固定图 A/B 和逐题复盘能力。
- boot-v3 方向有一定结构化价值，但当前还没有稳定超过 direct baseline 的 test 收益。
- 上海 AI Lab 额度不足，后续实验需要切到可用 API，控制 qwen3-8b 小并发。

下一步建议：

1. 优先看 GAIA `validation_test` 错例，把错误拆成图行为问题、证据指导问题、工具能力问题和 executor 能力问题。
2. 做 executor system prompt 修复前后 A/B，确认协议摩擦、平均步数、空答案和分数变化。
3. 改 critic 输入，让每个 failure family 带少量 evidence-rich exemplar，避免只依赖 compact row。
4. 做 minimal actor diff 实验，限制每轮只改少量规则，观察正确题保留率和 test 泛化。
5. 选 2-3 个高频失败源做工具/helper augmentation，例如 HTML 表格抽取、Wikipedia revision 查询、USGS / NASA 类精确检索。
6. 如果前面仍无法改善，再开 graph revision，把 `WEB_RESEARCH`、`VERIFY` 这类重节点拆开。
