# GAIA 有 skill 场景提前答摩擦追溯

记录时间：2026-04-28 12:03 +0800

## 背景

这份记录整理 2026-04-28 对 `invalid_answer_phase` 的追溯过程。问题来自 ARCH-V4 fresh bootstrap + A/B run：executor 明确收到 phase graph、合法 next 和 `CONCLUDE` 出答案规则，实际仍大量在非 `CONCLUDE` phase 输出 `<ANSWER>`。

追溯目标：

- 明确 no-skill direct 是否走同一套 `CONCLUDE` 规则。
- 判断提前答来自解析误判，还是 executor 主动选择结束。
- 统计提前答集中在哪些 phase，尤其 `VERIFY` 占比。
- 找出提示词和 runtime 上的摩擦来源。
- 给出下一步修复建议。

关键代码和产物：

- phase executor prompt：`prompts/executor_system.md`
- direct executor prompt：`prompts/direct_executor_system.md`
- 通用 XML 协议：`prompts/tool_agent_protocol.md`
- phase executor loop：`gaia_skillrl/agent_loop.py`
- direct/skill environment：`gaia_skillrl/environment.py`
- bootstrap skill：`runs/2026/4/2026-4-27/20260427_114226_codex54_fresh_bootstrap_ab_archv4_r6_fresh_bootv3_boot_dev_c20/bootstrap/skill_after_bootstrap/gaia-general-skill/SKILL.md`

## 1. no-skill direct 的入口确认

先确认了一个容易混淆的点：no-skill direct baseline 没有 `CONCLUDE` phase。

代码路径：

- `DirectEnvironment.run()` 加载 `prompts/direct_executor_system.md`。
- `DirectExecutorAgent` 只接受 `<CALL>` 或 `<ANSWER>`；如果模型输出 `<NEXT>`，runtime 会反馈 phase transitions unavailable。
- direct run 写入 state 时 `phase_transitions=[]`，`active_skill_name="direct-baseline"`。

所以 `executor_system.md` 里的规则：

```text
Give the final answer only in the CONCLUDE phase.
```

只作用于有 skill 的 phase executor。no-skill direct 使用 `direct_executor_system.md`，规则是 evidence sufficient 后直接 `<ANSWER>`。

这个结论很重要：本轮提前答摩擦只分析有 skill 的 phase protocol，不能拿 no-skill direct 的 direct answer 行为混在一起。

## 2. 解析器是否误判

`parse_executor_tags()` 当前逻辑是：只要输出里含 `<ANSWER>`，就把 action type 判成 `answer`，优先级高于 `<CALL>` 和 `<NEXT>`。

这确实可能放大少量 “同一步多动作” 的摩擦。但批量统计显示，本轮主体来自模型原始输出直接选择 `<ANSWER>`。

| run | invalid total | ANSWER only | NEXT+ANSWER | CALL+ANSWER | short candidate | inability | empty | long |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| boot_dev | 147 | 147 | 0 | 0 | 133 | 10 | 2 | 2 |
| boot_test | 171 | 171 | 0 | 0 | 152 | 13 | 0 | 6 |
| A_dev | 233 | 218 | 15 | 0 | 193 | 35 | 2 | 3 |
| A_test | 197 | 197 | 0 | 0 | 176 | 18 | 0 | 3 |
| B_dev | 146 | 146 | 0 | 0 | 117 | 24 | 0 | 5 |
| B_test | 152 | 152 | 0 | 0 | 127 | 21 | 2 | 2 |
| 合计 | 1046 | 1031 | 15 | 0 | 898 | 121 | 6 | 21 |

读法：

- 1031/1046 = 98.6% 是纯 `<THOUGHT>...<ANSWER>...</ANSWER>`。
- 只有 A_dev 里有 15 次 `NEXT+ANSWER` 混合输出，解析器优先 `ANSWER` 会把这 15 次记成提前答。
- 主体行为是 executor 认为任务已经可以结束，直接报答案。
- 解析器容错仍值得改，但它解释不了这一轮的大量摩擦。

典型样本，`boot_dev/00d579ea` 在 `VERIFY` phase 第 4 步：

```xml
<THOUGHT>The verification confirms that Saul Fingerman is the writer of the 1968 film "The Thinking Machine," which directly addresses the development of thinking machines as described in the task. The answer matches the required format and historical context.</THOUGHT>
<ANSWER>Saul Fingerman</ANSWER>
```

runtime 期望的动作是先 `<NEXT>CONCLUDE</NEXT>`，进入 `CONCLUDE` 后再 `<ANSWER>`。

## 4. 为什么明规则仍然摩擦大

### 4.1 全局协议每步都暴露 `<ANSWER>`

`tool_agent_protocol.md` 被拼到 system prompt，所有 phase 都能看到：

```text
To answer:
<THOUGHT>why the evidence supports this exact answer</THOUGHT>
<ANSWER>short final answer</ANSWER>
```

同时 current phase 的 user message 才告诉它 `Available actions` 和 `Next`。对小模型来说，全局 “To answer” 模板很强，尤其当 thought 已经写出 “verification confirms / computation complete / no further evidence needed” 时，它会自然接 `<ANSWER>`。

### 4.2 `VERIFY` 的语义像 final answer 阶段

当前 bootstrap skill 的 `VERIFY`：

- Goal：确认 support 并 enforce exact output shape。
- Rules：检查 current candidate 是否回答真实问题、格式是否正确。
- Exit handoff：传递 final answer string 和确认信息。
- Available actions：`<NEXT>CONCLUDE</NEXT>` 或 `<NEXT>REPAIR</NEXT>`。

这套语义对模型的自然动作是直接输出 final string。runtime 的形式约束要求多走一步 `CONCLUDE`，形成二段式协议摩擦。

`boot_dev/00d579ea` 的 step 4 request 里，模型看到 `VERIFY` phase 内容，里面写：

```text
If the answer is exact and fully supported, move to `CONCLUDE`.
Available actions
- <NEXT>CONCLUDE</NEXT>
- <NEXT>REPAIR</NEXT>
```

模型输出仍是 `<ANSWER>Saul Fingerman</ANSWER>`。这说明它理解了“答案已验证”，但没有执行 phase-level next tag。

### 4.3 `COMPUTE/WEB_EVIDENCE` 中 candidate 语言太强

bootstrap skill 的 common rules 写：

```text
Move to `VERIFY` as soon as one concrete candidate is supported.
```

`COMPUTE` 又写：

```text
Keep intermediate reasoning minimal and target a single concrete candidate answer.
When computation is complete, move to `VERIFY`.
```

这些规则本意是压缩路径。对 8B executor，它们会让 `COMPUTE` 成功或 `WEB_EVIDENCE` 找到候选后直接 `<ANSWER>`。本轮合并统计里，`COMPUTE` 提前答 336 次，接近 `VERIFY` 的 370 次。

### 4.4 两步收口协议本身有额外负担

phase executor 的合法链路是：

```text
VERIFY -> <NEXT>CONCLUDE</NEXT> -> CONCLUDE -> <ANSWER>...</ANSWER>
```

对小模型，`VERIFY` 已经承载“确认答案”的语义，再要求它通过 `NEXT` 进入一个只输出答案的 phase，是额外协议负担。这个负担在强模型上可能可控，在 Qwen3-8B-local 上会频繁转成提前 `<ANSWER>`。

### 4.5 invalid feedback 可操作性不足

当前 `_invalid_answer_feedback()` 只返回：

```text
Invalid answer output.
Current phase: VERIFY
Answer is only allowed in CONCLUDE.
```

它指出了规则，但没有给出下一步模板。连续提前答样本里，模型收到反馈后仍继续 `<ANSWER>`，直到后来才输出 `<NEXT>CONCLUDE</NEXT>`。

更有效的反馈应该直接给动作：

```text
You are in VERIFY. Do not emit <ANSWER>.
If checks passed, emit exactly <NEXT>CONCLUDE</NEXT>.
If a gap remains, emit exactly <NEXT>REPAIR</NEXT>.
```

## 5. 代表性链路

### boot_dev/00d579ea

路径：

```text
INIT -> WEB_EVIDENCE -> VERIFY
```

第 4 步在 `VERIFY` 提前答：

```xml
<THOUGHT>The verification confirms ... The answer matches the required format and historical context.</THOUGHT>
<ANSWER>Saul Fingerman</ANSWER>
```

问题：

- 模型执行了“验证完成”的语义。
- 模型跳过了 `VERIFY -> CONCLUDE` 的形式动作。
- 这类样本是 `VERIFY` 提前答的标准形态。

### boot_dev/05407167

局部链路：

```text
WEB_EVIDENCE -> VERIFY -> REPAIR -> WEB_EVIDENCE -> VERIFY
```

第 15、16 步连续在 `VERIFY` 输出 `<ANSWER>Format Document</ANSWER>`，收到 invalid feedback 后仍重复。第 17 步才输出 `<NEXT>CONCLUDE</NEXT>`，第 18 步正式 final answer。

这说明 feedback 对小模型的修正力有限。它知道要“conclude”，但仍用 `<ANSWER>` 表达 conclude。

## 6. 当前判断

当前提前答摩擦由三层叠加：

| 层级 | 现象 | 影响 |
| --- | --- | --- |
| prompt protocol | 全局 system 一直展示 `<ANSWER>` 模板 | 非 `CONCLUDE` phase 也会触发 final answer habit |
| skill phase semantics | `VERIFY/COMPUTE/WEB` 反复强调 candidate/final answer/string | 模型把候选完成理解成可以答 |
| runtime parser/feedback | `<ANSWER>` 优先解析；invalid feedback 没有直接给合法下一步 | 少量混合输出被计入 invalid；重复提前答恢复慢 |

其中主因是前两层。解析器只解释 A_dev 的 15 次 `NEXT+ANSWER` 小头，主体 1031 次 `ANSWER only` 来自模型主动直答。

## 7. 修复建议

### P0：phase 模式下隐藏全局 answer 模板

给 phase executor 使用一个不含 “To answer” 的 protocol，或在 `tool_agent_protocol.md` 模板里按 mode 渲染：

- 非 `CONCLUDE` phase：只展示 `<CALL>` 和 `<NEXT>`。
- `CONCLUDE` phase：单独注入 `<ANSWER>` 格式。

这能直接减少非 `CONCLUDE` phase 对 `<ANSWER>` 的可见诱导。

### P0：改 `VERIFY` 为 route-only gate

把 `VERIFY` 从“最终答案确认”改成“路由 gate”：

```text
VERIFY does not output the final answer.
If all checks pass, emit exactly <NEXT>CONCLUDE</NEXT>.
If any support, scope, or format gap remains, emit exactly <NEXT>REPAIR</NEXT>.
Never emit <ANSWER> in VERIFY.
```

同时减少 `final answer string` 这类词，改为 `candidate string` 和 `decision`。

### P1：改 invalid feedback 为动作模板

按 current phase 生成反馈：

- 当前 phase 有 `CONCLUDE` next：提示 `emit exactly <NEXT>CONCLUDE</NEXT>`。
- 当前 phase 没有 `CONCLUDE` next：提示合法 next 列表或一个 tool call。
- 明确 `Do not repeat <ANSWER> until CONCLUDE is entered.`

### P1：parser 做小容错

对非 `CONCLUDE` phase 的 `NEXT+ANSWER` 输出，如果 `<NEXT>` 合法，可以优先执行 `<NEXT>`，并记录 `salvaged_next_with_extra_answer`。

这只能修小头，但能避免 A_dev 这类 15 次混合输出被全部记成 invalid answer。

### P2：弱化 candidate 触发语

bootstrap skill 和 actor skill 里避免：

- `as soon as one concrete candidate is supported`
- `final answer string` 出现在非 `CONCLUDE`
- `No further evidence is needed` 这类未绑定直接 evidence 的表达

替换成：

- `when direct support, exact field, scope, and format checks pass`
- `candidate string`
- `route to VERIFY for the pass/fail decision`

### P2：重新考虑二段式收口

如果后续仍持续摩擦，可以让 `VERIFY` 直接允许 `<ANSWER>`，并把 `CONCLUDE` 合并掉或只保留 runtime 内部 finalization。代价是 graph 语义会更短，critic/actor 对 “final phase only” 的约束需要一起更新。

## 8. 下一步实验建议

建议先做一个最小补丁实验：

1. phase executor protocol 隐藏 `<ANSWER>` 模板。
2. `VERIFY` 明确 route-only。
3. invalid feedback 给 `<NEXT>CONCLUDE</NEXT>` 模板。
4. 保持 graph 不变，避免和 skill graph 改动混淆。

验收指标：

- `invalid_answer_phase` 总量至少下降 50%。
- `VERIFY` 提前答题数从 boot/A 的 60+ 题降到 20 题以内。
- 空答不增加。
- A_full test 9 个新增正确和 4 个丢失样本作为 regression slice。

如果这个补丁有效，再考虑 parser salvage 和 bootstrap prompt 文案的系统性调整。
