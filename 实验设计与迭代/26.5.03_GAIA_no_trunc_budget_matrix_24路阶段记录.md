分数统计口径：优先读取各 `state.json` 的 `env_result.evaluation.task_success`。`state.json` 顶层没有 `score` 字段，不能用顶层 `score` 统计。运行中的组如果 launch log 比 state 多打一条 progress，则在备注里保留 log 进度。

错误统计口径：`400 / empty / exhausted / timeout` 是 LLM 请求或重试 attempt 级别的日志计数，不能直接理解成题目数。一次题目执行会有多步 LLM 调用，每次调用最多会重试 6 次；其中某次 attempt 可能 empty，随后重试成功，最终题目仍然可能答对。题目级别只看 `states`、`score` 和 `env_result.final_answer`。

术语解释：

- `400`：vLLM HTTP 400 次数。常见原因是 `prompt tokens + max_tokens` 的服务端预留超过 `max_model_len`。
- `empty`：某次 streaming attempt 没有产生可见 content，代码抛出 `Streaming response produced empty content.` 并进入重试。它是 attempt 计数。
- `exhausted`：某次 LLM 调用重试耗尽后仍失败，通常是 6 次 attempt 后抛出 `Streaming LLM call failed after 6 attempts`。
- `timeout`：streaming 超过 `NLRL_LLM_STREAM_WALL_TIMEOUT_SECONDS` 的次数。
- `final_answer_empty`：题目级最终空答，需要单独从 `state.json -> env_result.final_answer` 统计，和 `empty` 不是同一个指标。

例子：`20260503_203208_notrunc_9b_cap49152_think_unlimited_out_unlimited_c20_gpu1_9b` 这一行有 `score=32/82`、`empty=30`、`exhausted=4`、`timeout=4`。核对 state 后，实际是 `81 states`、`32` 题成功、`49` 题失败；最终 `final_answer` 为空的是 `19` 题。`empty=30` 表示全 run 的 streaming empty attempt 发生 30 次，不表示 30 道题空答。

## 阶段观察

1. `think4k` 的 reasoning 分布按预期被压住：已完成的 8B think4k 组里，reasoning P99/P99.9 基本稳定在 4096。这个约束直接降低了无限 thinking 带来的 vLLM KV 压力。
2. 8B `cap49152 + think4k + out8k/out12k` 分数目前相同，都是 12/82；`out8k` 用时略短，KV 峰值更低。`out_unlimited` 得到 14/82，但 wall time 从 6.5-8.0m 拉到 17.0m，可见输出 P99/P99.9 明显放大。
3. 8B `nocap + think4k + out12k` 已完成 14/82，时间 8.0m，未出现 400。这个组合当前看起来是 8B 里速度和分数最平衡的一组。
4. 8B `nocap + think4k + out8k/out_unlimited` 都异常退出，日志里有 400 与 streaming exhausted。结合 vLLM 400 语义，固定输出上限会被 vLLM 预留；当 prompt tokens + max_tokens 超过 `max_model_len=40960` 时，请求会直接失败。这个组合需要在最终表里保留为“配置代价”。
5. 8B `cap49152 + think_unlimited + out12k` 在 81 个 state code=1，临时 15/82，分数看起来有增益；代价也很明确，reasoning P99 到 7397，P99.9 到 11817，KV 峰值到 90.8%，并出现 15 次 empty-content retry 和 1 次 exhausted。
6. 8B `cap49152 + think_unlimited + out8k` 已 code=1，停在 80 states、14/82；压力明显低于 `out12k/out_unlimited`，但 empty-content retry 已到 33 次，最终仍由 streaming exhausted 收尾。
7. 8B `cap49152 + think_unlimited + out_unlimited` 最终 code=1，停在 79 states、12/82；wall time 102.1m，KV cache 峰值到 100%，出现 waiting、9 次 wall timeout 和多次 exhausted。这个组已经足够说明无限输出对本地 vLLM 压力过高。
8. 8B `nocap + think_unlimited + out12k` 已 code=1，停在 80 states、15/82，400 计数到 16。`nocap` 搭配固定输出预留依然有明显 context 风险。

10. 9B `nocap + think4k + out8k/out12k` 的 state 口径都到 32/82，但都出现大量 400。`out12k` 子进程仍存活但已长时间不产 state，GPU3 utilization 为 0。两个组的 request chars P99 均超过 90K，prompt tokens P99 超过 32K，再叠加固定输出预留后很容易撞 `max_model_len=49152`。

## 阶段 low 分析

- 目前已经能看到一个比较稳定的配置边界：`nocap` 对 8B 可能带来少量收益；9B `nocap` 虽然有 32/82 的临时分数，但 400 数量快速上升，稳定性风险很高。
- `cap49152` 的含义更接近“把输入字符维持在可控范围”，它并不等同于服务端 token 上限；9B cap 组 request chars 高分位贴边，说明这个 cap 已经频繁生效。
- `out8k/out12k/out_unlimited` 的收益已能看到方向：9B `cap49152 + think4k + out8k` 的最佳重复为 35/81，高于 `out12k` 的 29/82 和 `out_unlimited` 的 32/82；但它不是完整 82 states，最终选择 AB 主线时还要把退出原因和缺失题纳入风险。
- `think_unlimited` 可能提升局部分数，不过它会快速推高 hidden reasoning、KV 使用率和 wall timeout。后续若要选主线配置，优先等 `cap49152 + think_unlimited + out12k` 和 `cap49152 + think4k + out12k` 的完整对比。
