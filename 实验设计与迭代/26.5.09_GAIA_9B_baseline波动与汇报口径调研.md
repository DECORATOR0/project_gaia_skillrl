# GAIA 9B Baseline 波动与论文汇报口径调研

时间：2026-05-09  
目的：确认 `Qwen3.5-9B-local` direct baseline 同配置复跑的波动，并给出后续调参和论文汇报口径。

## 结论

1. 当前 9B direct baseline 的单次分数波动已经足够大，dev 上同配置至少出现 `43/83 -> 35/83 -> 35/83 partial`，test 上同配置已出现 `29/82 -> 32/82 -> 33/82`。dev 的 `8` 题波动约 `9.6` 个百分点，已经超过很多候选 skill 的预期增益。
2. 完全消掉随机性不现实。主要来源不是一个开关，而是模型采样、vLLM 动态 batching/数值非确定性、搜索结果时效、网页/文件工具、生成代码工具长尾、并发调度共同叠加。
3. 可以在尽量不牺牲性能的前提下降低一部分波动：固定服务与版本、降低或固定 sampling、固定搜索与网页缓存、限制 tool snippet 超时、减少动态 batching 变化、用同一套任务级对照表做 paired comparison。
4. 后续实验选择不要看 1 次 dev 增益。小于 `4-5` 题的 dev/test 单次差异先视为噪声区间；候选方法只有在 test 或 dev 多次复跑仍超过 baseline range 时才算有说服力。
5. 论文/文档里建议同时报告两种口径：`Pass@1 mean ± range/std over N runs` 作为可靠性口径，另列 `best run` 作为对齐 GAIA/HF leaderboard 的口径。若采用多尝试/投票/自一致性，明确标成 `Pass@K` 或 `test-time scaling`，不要和单次 Pass@1 混在一个数里。

### `43/83` 异常点复核

2026-05-09 晚上复核了 `43/83` 与后续 `35/83` runs 的配置和成功集合。

结论：

1. 从 eval-critical 配置看，`43/83` 没有发现明显偷跑项：executor 都是 `Qwen3.5-9B-local`、`chat_completions`、`temperature=0.1`、`max_tokens=12288`、`max_model_len=49152`、`thinking_token_budget=null`、`answer_acceptance_policy=any_phase`、`tool_profile=atomic_v2`、`task_concurrency=20`、`max_executor_steps=24`、`bootstrap_initial_skill=false`、`initial_skill_path=""`。
2. `config_snapshot.json` 不是 bit-identical。`43/83` 当时 endpoint 是 `http://127.0.0.1:8110/v1`；后续复跑主要是 `http://127.0.0.1:8610/v1`。actor/critic 默认项也有差异，例如 SSSAI `gpt-5.2` vs Codex `gpt-5.4`，但 direct baseline 不走 bootstrap actor/critic，所以这些字段不应直接影响执行分数。
3. 成功集合不是稳定包含关系。相对 `20260508_000942...35/83`，`43/83` 有 `14` 个 only-orig success，同时后者也有 `6` 个 only-rerun success。相对本轮 r1 的 `35/83`，`43/83` 有 `11` 个 only-orig success，r1 有 `3` 个 only-rerun success。相对本轮 r2 partial，`43/83` 有 `13` 个 only-orig success，r2 有 `5` 个 only-rerun success。
4. 这说明 `43/83` 更像一次高尾 agent rollout：搜索结果、工具路径、模型采样、并发调度和 vLLM 服务状态叠加后，某些题走到了更好路径，同时也丢了另一批题。它不像一个稳定配置优势，也不应作为后续候选方法必须超过的唯一 baseline。

后续口径：`43/83` 保留在 baseline range 里，作为 best/high-tail reference；调参筛选主要看是否超过当前稳定中心 `35/83` 和 test best `33/82`，并用 task-level paired diff 判断新增答对是否集中在目标能力上。

## `validation_dev/test` 切分与模态覆盖

### 当前切法

当前内部 `validation_dev83 / validation_test82` 来自官方 GAIA validation `165` 题。切分 manifest 是：

- `split_strategy=stratified_by_level_preserve_original_order_ceil_to_dev`
- Level 1：`53` 题，dev 取该 level 原顺序前 `27`，test 取后 `26`
- Level 2：`86` 题，dev 取该 level 原顺序前 `43`，test 取后 `43`
- Level 3：`26` 题，dev 取该 level 原顺序前 `13`，test 取后 `13`

它不是全局前 `83` / 后 `82`。它是在每个 level 内做前后切，再按原 validation 全局顺序过滤输出。

### 能否当作随机

谨慎口径：不能严格说是随机 split。原因是没有 shuffle，也没有按除 level 以外的字段做随机抽样。它能保证 level 分布对齐，不能保证题目主题、来源网站、文件类型、创建批次、annotator 风格都对齐。

但从当前可见字段看，这个 split 没有明显把“有文件题”集中到一边：

| split | 总数 | 无附件 | 有附件 |
| --- | ---: | ---: | ---: |
| validation_dev | `83` | `64` | `19` |
| validation_test | `82` | `63` | `19` |

按粗略附件类型看：

| 类型 | dev | test | 备注 |
| --- | ---: | ---: | --- |
| no attachment / web-text | `64` | `63` | 主体很平衡 |
| spreadsheet/table (`xlsx/csv`) | `5` | `9` | test 稍多 |
| image (`png/jpg`) | `4` | `6` | test 稍多 |
| audio (`mp3`) | `1` | `2` | 数量太小 |
| document (`pdf/docx/txt/pptx`) | `5` | `1` | dev 偏多 |
| archive/bundle (`zip`) | `2` | `0` | 只在 dev |
| code (`py`) | `0` | `1` | 只在 test |
| structured data (`pdb/jsonld`) | `2` | `0` | 只在 dev |

结论：这个 split 对“难度”和“有没有附件”基本可用；对细模态/文件类型只能算弱平衡。小样本下，某些稀有类型天然会只落在一边。若论文主张“从 dev 学到泛化 skill”，最好不要把它描述成 random stratified split；建议写成 `level-stratified, original-order holdout split`。

### GAIA 是否有官方任务类别

官方公开数据主要字段是 `task_id`、`Question`、`Level`、`Final answer`、`file_name`、`file_path`、`Annotator Metadata`。当前项目转换后的 JSON 保留了 `level/file_name/file_path/dataset_index`，`gold_tool_names/gold_trajectory` 为空，所以本地不能直接按官方 annotator 工具类别做 per-task stratification。

GAIA 原论文给了能力大类，但作者明确说明这不是完美 typology，因为同一道题可以用不同能力路径解：

- web browsing：搜索和浏览网页
- multi-modality：音频、视频、图像、OCR、Street View 等
- coding：Python、计算器、脚本、编译器等
- diverse filetype reading：PDF、Excel、PowerPoint、CSV、txt 等
- N/A：不需要增强工具或当前 LLM 可直接处理的任务

Magentic-One 论文进一步把 GAIA annotator 工具映射成 `web browsing / coding / file handling / none` 四类，用于 ablation 分析。这说明“按能力类别看 GAIA”是合理的，但这不是官方公开 leaderboard 的强制 split 口径；它更像分析维度。

### 训练型/学习型论文怎么处理 split

调研到的模式大致有四类：

1. 官方 GAIA：公开 validation 用于开发和调试，私有 test 用于 leaderboard。官方只按 level 暴露配置，没有提供 train split。
2. 工程 agent 论文：通常在 GAIA validation 做 ablation，在 GAIA test 或 leaderboard 报最终数。Magentic-One 就是这个模式：GAIA/AssistantBench 报 test；GAIA validation 用来做 ablation，并按 level/capability 展示。
3. 训练型 web agent：主训练数据通常另建，不直接把 GAIA validation 当唯一训练集。WebDancer 明说 GAIA 只有 validation/test 且规模小，不足以有效训练；它用自动合成 QA 和轨迹数据训练，再在 GAIA text-only validation `103` 题上报 `Pass@1/Pass@3/Cons@3`。它还做过一个 memorization stress test：用 GAIA dev 中 `69` 条正确轨迹 fine-tune 10 epochs 后在同集合评估，greedy 也只有 `37.4%`，这个实验是为了说明开放域 agent 任务难稳定，并非主训练/测试 split。
4. 大规模 learning-from-practice：AWorld training recipe 用 GAIA 展示 rollout scale 和 RL 训练价值。它在完整 `165` 题 validation 上画 pass@k 曲线，SFT 用 `886` 条 Claude 3.7 成功轨迹，RL 每题 `32` rollouts，最终报 GAIA test pass@1，并用 xbench-DeepSearch 无直接训练样本结果支撑泛化。论文没有给出一个可直接复用的 `GAIA validation train/dev/test` 子切分。

OpenAI Deep Research 和 DeepResearcher 这类 deep research 训练工作更偏向“在跨领域 hard browsing/reasoning 或 NQ/TQ/HotpotQA/2Wiki 等开放问答数据上训练，再用真实 web/外部 benchmark 检验”。DeepResearcher 还专门做 contamination filtering：对候选训练题让 base model pass@10，无搜索能答对的题剔除。这对我们有启发：如果 skill 真的从 GAIA dev 学，最好避免直接记答案或题号，训练信号应抽象到路径、工具选择、错误类型和答案格式。

### 对当前项目的建议

1. 保留现在的 `dev83/test82` 作为内部开发/holdout 是可接受的，因为 level 和是否有附件基本平衡。
2. 文档表述建议写：`level-stratified original-order split over public GAIA validation`。避免写 `random split`。
3. 如果后续需要更强泛化论证，可以额外生成一个固定 seed 的 `level + attachment category` stratified split，或者做 3-fold cross validation over validation。当前资源紧张时，先不用重切，直接在现有 split 上加 per-task diff 和附件类型 breakdown。
4. Skill 学习阶段尽量只用 dev 的失败模式、工具路径、答案格式错误和能力标签，避免把 dev 题号、答案、具体搜索结果写进 skill。这样 test82 更能说明“学到方法”。
5. 最终汇报时把 test82 说成 internal holdout，不等同于官方 hidden test。若有机会提交官方 leaderboard，再把官方 test 结果作为主泛化证据。

## 如何减少随机性

优先级按“能减少波动且大概率不伤性能”排序。

1. 给工具执行加硬超时和进程组清理。  
   本轮 r1 dev 的长尾来自 generated `tool_snippet.py` 枚举 `256^3` RGB 并逐色扫图。这类问题会把分数变成调度/超时问题。建议对 `run_python` 或 generated snippet 设置单次 60-120s wall timeout，超时后返回工具失败并继续 agent，而不是让整条 eval 卡死。

2. 固定搜索与网页输入。  
   对 GAIA，搜索 provider、代理、搜索时间、网页内容变化会影响路径。建议正式对比时固定 `search_runtime.json`、代理、搜索 key 轮转策略，并把 search result / fetched page 做 per-run cache。性能优先时仍可用 Serper，但必须记录缓存命中和 provider fallback。

3. 降低 sampling 随机性，但保留一个性能对照。  
   当前 executor `temperature=0.1`，本身会引入采样波动。可以补一组 `temperature=0`、固定 seed 的小规模对照，看是否掉分。如果 `temperature=0` 不明显掉分，后续稳定性实验用 0；如果掉分，则保留 0.1 作为性能口径，同时在文档里承认随机性。

4. 控制 vLLM 动态 batching 变化。  
   并发 `20` 有利于吞吐，但会改变同一请求处在 batch 中的位置与邻居请求。严格复现实验可用 `concurrency=1/5` 小样本估计方差；性能实验继续 c20，但不要把 c20 单次结果当确定值。更激进的确定性需要 batch-invariant kernels 或固定 serving 调度，当前环境不具备。

5. 固定服务端和环境元数据。  
   每个可引用分数都记录 vLLM 版本、GPU、endpoint、`max_model_len`、`max_num_seqs`、prefix caching、模型权重路径、tokenizer、runtime git diff、搜索配置、工具 API。后续比较时先排除配置漂移。

6. 用 task-level paired comparison。  
   只看总分会把噪声放大。对候选 skill，记录“相对同配置 baseline 新增答对、丢失答对、共同答对、共同失败”。如果总分 +2 但换题严重，可信度低；如果总分 +5 且新增答对集中在 skill 目标能力上，可信度高。

7. 最终选择用多次 run 或 pass@k，而不是单次撞运气。  
   资源允许时，每个最终候选至少 `N=3` 次 Pass@1；如果目标是实用性能，可以再报告 `Pass@3/majority/any-pass`，但要与 Pass@1 分开。

### 归纳

1. GAIA 没有一个全社区统一口径。官方榜单偏 `best run`，部分论文报单次 `Pass@1`，近期高分/训练/稳定性论文越来越多地补 `Pass@3`、`Cons@3`、三次均值和 std。
2. “冷不丁抱一个分”在 leaderboard 语境里很常见。HF 官方页面直接写了 leaderboard 只报 best run；当前高分榜单也只有一个平均分和提交日期，很多条目没有公开均值/std。
3. 论文里直接只放一个分数也存在，尤其是早期 agent 论文、工程系统 blog、商业系统新闻稿、资源受限的 subset 评测。风险在于小幅提升很难说服审稿人。
4. 高分如果来自多次尝试、投票、self-consistency、best-of-N、critic 反复修正，就应标成 `Pass@K`、`Cons@K`、`best-of-K` 或 `test-time scaling`。OAgents 已经专门指出 Pass@1/3/5 混用会影响公平比较。
5. 当前项目想要“性能优先”时，可以接受单次 test 分数作为筛选依据；正式写法要把它命名为 `single-run Pass@1` 或 `leaderboard-style best run`。

### 对当前项目的最低证据包

在没时间反复跑的条件下，我建议采用这个口径：

1. baseline 固定为一个噪声带：dev 记录 `[43, 35, 35]`，test 记录 `[29, 32, 33]`，这就是当前 9B p04 baseline 的自然波动背景。
2. 每个候选 skill 先跑一次 test，算 `single-run Pass@1`。如果只比 baseline best 高 `1-3` 题，标成“未能超过噪声带”；如果超过 baseline best `>=4` 题，进入候选池。
3. 如果一个候选只在 dev 高、test 平，先不作为主结论；如果 test 高且 task-level 新增答对集中在 skill 目标能力上，可以保留。
4. 最终只有一个候选时，资源允许再补一次同配置 test；资源紧张时，主表写 `single-run Pass@1`，附录列 baseline 三次分数、候选 run_dir、配置快照和 per-task diff。
5. 多尝试策略只作为“上限”单独列，例如 `Pass@3/Best-of-3`。这个分数可以展示潜力，但不要和 direct baseline 的 `Pass@1` 放在同一列比较。

## 给当前项目的执行建议

1. 把 9B p04 baseline 稳定性记录成事实：dev 自然波动已见 `8` 题，test 自然波动已见 `4` 题。
2. 后续调 skill 时，把 `+1/+2/+3` 当噪声区间处理。单次 test 至少超过 baseline best `4` 题，才值得占用后续复跑资源。
3. 现在最省时间、最有说服力的方式是“baseline 噪声带 + 候选单次 test + task-level paired diff”。这比机械给每个候选都跑 `N=3` 更适合当前资源。
4. 论文里可以写两套口径：正文主结论用 `single-run Pass@1` 和噪声带说明；附录补 best run / raw runs。若最终方法用了多尝试，显式写成 `Pass@K`。
5. 当前性能优先的调参路线：继续用 p04 baseline 作为噪声底线，优先比较 `9B BOOT-V4 B2/B3` 这类已经高于 baseline range 的组合；图理论叙事可以降级为方法解释，不作为调参目标。
