## 1. 当前定位

bootstrap 的职责是生成第一份可运行的初始 `SKILL.md`。

它只负责给强模型一个清晰的起点：

- 看见 runtime 边界。
- 看见 dev 开发切分里的任务分布。
- 生成一份大致符合预期的通用 GAIA skill。
- 保持 lifecycle phase 简洁。
- 保持 route 意识，但不提前展开复杂状态图。

后续路由细化、状态修补、证据策略、格式策略、web 重试策略、phase 边调整，留给 critic 和 actor 处理。

## 2. 输入约定

当前 bootstrap 只使用两块输入。

### 2.1 Runtime Contract

由 `SkillBootstrapper._runtime_contract()` 生成，表达 executor 的硬边界。

字段：

```json
{
  "executor_model": "qwen3-8b",
  "max_executor_steps": 24,
  "answer_rule": "Only the CONCLUDE phase may emit <ANSWER>...</ANSWER>.",
  "phase_header_format": "## Phase: NAME",
  "action_tags": {
    "tool_call": "<CALL>tool_name</CALL><ARGS>{...}</ARGS>",
    "phase_transition": "<NEXT>PHASE_NAME</NEXT>",
    "final_answer": "<ANSWER>short final answer</ANSWER>"
  },
  "available_tools": [
    "list_dir",
    "read_file",
    "read_json_file",
    "extract_pdf_text",
    "read_table",
    "image_metadata",
    "audio_transcribe",
    "ocr_image",
    "image_qa",
    "parse_docx",
    "parse_pptx",
    "extract_archive",
    "web_search",
    "fetch_url",
    "html_extract",
    "run_python"
  ],
  "environment_limits": [
    "Browser automation is unavailable.",
    "Task workspaces contain task.json and any materialized attachments."
  ]
}
```

这块输入决定初始 skill 的执行协议、工具边界、phase 输出边界。

### 2.2 Batch Task Snapshot

由 `_batch_payload()` 生成，表达 dev 开发切分里的任务分布。

顶层字段：

```json
{
  "task_count": 83,
  "levels": [1, 2, 3],
  "attachment_suffix_histogram": {},
  "tasks": []
}
```

每题字段：

```json
{
  "task_id": "...",
  "level": 2,
  "split": "validation_dev",
  "question": "...",
  "gold_answer": "...",
  "attachments": [
    {
      "name": "...",
      "suffix": ".xlsx"
    }
  ],
  "file_list": ["...", "task.json"]
}
```

`gold_answer` 只用于让 bootstrap 归纳答案形态和格式习惯。prompt 明确禁止把具体答案、具体实体、固定 URL、任务 ID 写进 `SKILL.md`。

## 3. 当前不输入的内容

为了保持 bootstrap 原生、轻量，当前不额外喂这些信息：

- 旧版完整 seed skill。
- 历史逐题失败长分析。
- critic 输出格式。
- actor 可编辑对象 taxonomy。
- `answer_shape_examples` 之类额外手工聚合字段。
- `route_hint_counts` 之类启发式路由统计。
- 复杂 memory schema。
- Graph lint 大段规则。
- gold trajectory，当前数据里基本为空。

这些内容会提高 prompt 约束密度，也容易让初始 skill 过早继承上一版状态图的复杂度。

## 4. Prompt 约束

当前 system prompt 的约束只保留必要部分。

### 4.1 输出协议

bootstrap 必须返回一个 JSON object：

```json
{
  "summary": "...",
  "target_skill_name": "gaia-general-skill",
  "files_to_write": {
    "SKILL.md": "..."
  }
}
```

约束：

- `target_skill_name` 固定为 `gaia-general-skill`。
- `files_to_write` 必须包含 `SKILL.md`。
- 禁止创建 `scripts/` 文件。
- 可选 reference 文件默认不需要。

### 4.2 Skill 形态

初始 skill 建议使用简洁生命周期：

```text
INIT -> ROUTE -> GATHER -> SOLVE -> CONCLUDE
```

硬 phase 的角色：

- `INIT`：读取 `task.json` 和工作区文件列表，确认题目、附件、格式要求。
- `ROUTE`：选择最小证据路径。
- `GATHER`：按路径收集证据。
- `SOLVE`：把证据变成最终答案字符串。
- `CONCLUDE`：只输出 `<ANSWER>...</ANSWER>`。

route 类型写在 phase 内部规则里：

- prompt
- local
- media
- web
- hybrid

route 当前不生成独立硬 phase，避免初始 skill 直接膨胀成多节点状态图。

### 4.3 答案出口

runtime 目前只接受 `CONCLUDE` 中的 `<ANSWER>`。

因此 prompt 要求：

- `CONCLUDE` 是唯一答案输出 phase。
- `GATHER` 和 `SOLVE` 在答案字符串已准备好时可以跳到 `CONCLUDE`。
- 非 `CONCLUDE` phase 不输出 `<ANSWER>`。

### 4.4 每个 phase 的格式

每个 phase 建议包含：

- `Goal`
- `Allowed tools`
- `Rules`
- `Exit handoff`
- `Available actions`
- `Next: ...`

`Next:` 行很重要，runtime 会用它推断 phase transition graph。

### 4.5 Tool-call 示例约束

这条是启动实验后补上的必要约束。

`INIT` 中允许写真实固定调用：

```text
<CALL>list_dir</CALL><ARGS>{"path":"."}</ARGS>
<CALL>read_json_file</CALL><ARGS>{"path":"task.json"}</ARGS>
```

非 `INIT` phase 中，工具选择尽量写在 `Rules` 里，`Available actions` 主要列 `<NEXT>`。

禁止在 tool-call 示例中写：

- 假文件名。
- 假 URL。
- 示例 HTML。
- dummy Python 代码。
- 复制自某道题的具体路径。

原因是 executor 容易复制这些示例参数，导致无效工具调用。附件路径和 URL 应来自当前任务或工具结果。

## 8. 当前生成 skill 的架构特征

这份初始 skill 的结构已经稳定收敛到一个轻量 lifecycle：

```text
INIT -> ROUTE -> GATHER -> SOLVE -> CONCLUDE
```

当前架构的几个特点：

- `INIT` 负责读取 `task.json`、识别附件和答案格式，并允许 prompt-only 题直接走 `SOLVE`。
- `ROUTE` 是软路由节点，负责选择 `prompt / local / media / web / hybrid`，这些 route 写在规则里，没有展开成独立硬 phase。
- `GATHER` 负责取证，允许在证据已经充分时直接跳 `CONCLUDE`。
- `SOLVE` 负责计算、筛选、格式压缩和最后答案串生成。
- `CONCLUDE` 负责唯一合法答案出口。

从当前生成结果看，这个架构有两个优点：

- phase 成本低。dev 平均步数 `9.73`，test 平均步数 `10.50`，都远低于此前重状态图版本。
- phase graph 比较顺。`max_step_hits` 很低，dev 只有 2 题，test 只有 1 题。

但也有明显缺口：

- skill 里还没有显式 evidence ledger。
- skill 里还没有候选答案冻结机制。
- skill 里还没有显式“证据支持后再 conclude”的约束对象。
- `ROUTE` 的规则仍然偏粗，local/media/web 的区分还不够强。

也就是说，这份 skill 现在更像一份轻量执行骨架，生命周期清楚，但中间状态还偏松。

## 10. 当前最需要调优的点

### 10.1 第一优先级：答案出口摩擦

`invalid_answer_phase` 仍然很高：

- dev：123
- test：168

这说明虽然 phase 数已经降下来了，executor 还是经常在 `GATHER` 或 `SOLVE` 想直接答。

下一步可以优先考虑：

- 在 `GATHER` 和 `SOLVE` 里更强地写清“答案串 ready 时先 `<NEXT>CONCLUDE</NEXT>`”。
- runtime 侧考虑更温和的 answer gate 修正，例如把非 `CONCLUDE` 的提前 `<ANSWER>` 反馈成强制跳转提示。

### 10.2 第二优先级：web 路由偏重

test 上 `web_search=107`，明显高于 dev。

这说明当前 skill 在 test 上更容易走 web 路线。问题在于：

- 一旦过早走 web，噪声会上升。
- local/media 题会付出额外搜索成本。
- web 找到弱证据后，模型容易直接 conclude。

下一步更适合补：

- `ROUTE` 中更强的 attachment-first 约束。
- `GATHER` 中更明确的 local/media 优先规则。
- 只有题目明确要求外部来源时才优先 web。

### 10.3 第三优先级：证据到答案的收束机制

当前 skill 里没有 evidence ledger，也没有 candidate answer 冻结机制。

这会导致：

- 找到部分线索后直接跳 conclude。
- 多候选时没有一个清楚的筛选步骤。
- 格式、粒度、单位、实体名之间容易漂。

下一步适合补的是轻量版本的中间约束：

- 在 `GATHER` 中要求记录“最后要用到的关键事实”。
- 在 `SOLVE` 中要求先形成唯一 candidate answer，再做 conclude。
- 对 web 题要求答案至少对应一个明确来源句或来源页。

### 10.4 第四优先级：格式与粒度

当前失败里有不少题已经给了一个像样的答案，但因为粒度、格式或表述不对而失败。

这个问题当前更适合放在 `SOLVE` 内部修，不需要再加新 phase：

- 明确数字精度、单位换算、日期格式、列表分隔符。
- 明确名称粒度，例如 full title、first name only、city only、exact phrase。
- 明确不要输出 “Unable to determine” 这类无帮助兜底，除非题面真的允许。

### 10.5 第五优先级：tool 失败与 web 噪声

当前两边都有将近 47 到 48 次 `tool_call_failed`。

这部分有环境噪声，也有策略噪声：

- 搜索命中不稳定。
- 页面抽取有波动。
- 多次 web 回跳仍然存在。

这部分更适合后续由 critic/actor 处理，不建议再塞回 bootstrap prompt。

## 11. 当前判断

这版 bootstrap prompt 已经达到一个比较清楚的阶段目标：

- 输入约定足够简单。
- 初始 skill 形态稳定。
- phase 成本低。
- 和 qwen3 direct baseline 相比，在 `validation_test82` 上已有小幅收益。

接下来更值得做的不是继续给 bootstrap 增加很多历史经验，而是沿着这份轻量 skill 往下做：

1. 让 critic 更准确地抓“提前答案”“web 偏重”“证据不足 conclude”“格式粒度错”这几类失败。
2. 让 actor 在不增加很多 phase 的前提下，给 `ROUTE / GATHER / SOLVE` 增加更精确的局部规则。
3. 尽量保持这份 lifecycle 骨架稳定，不急着回到复杂状态图。
