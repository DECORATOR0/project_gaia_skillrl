# GAIA 四路 Web Search 后端对比与 Codex Search 发现

记录时间：2026-04-29 23:32 +0800

## 背景

本记录承接两份已有实验记录：

- `26.4.28_0843_GAIA小模型工具Agent范式与本地13分差异证据.md`
- `26.4.29_2035_GAIA六路实验网络指标总表.md`

已有结论很集中：当前 `Qwen3-8B-local + TOOL-GAIA-V2 / atomic_v2` 的 agent 范式本身可以和公开小模型 GAIA baseline 对齐，主要短板落在 search / browse 后端。`13/81` direct run 中，web-related 题为 `5/46 = 10.9%`，明显低于 non-web 的 `8/35 = 22.9%`。后续多轮六路实验也显示，DDG HTML fallback 的 timeout / 403 会直接影响最终分数。

这次新增一个搜索后端选型记录，覆盖目前讨论到的四路：

1. `DDG / DDGS`：当前默认免费搜索栈。
2. `Serper`：Google SERP API。
3. `Brave Search API`：Brave 自有索引，当前代码里已有 raw Search provider 分支。
4. `Codex CLI --search`：Codex 原生 live web search 开关，属于之前未纳入实验设计的发现项。

## 快速结论

对 GAIA web-heavy 任务，下一步最有价值的诊断是 `Serper raw` 与 `Serper + reader`。Serper 的核心价值是便宜、快、接近 Google SERP，对官方站点、人物事实、多跳检索的 top-k 召回预期最好。

Brave 已经在本项目 `tools.py` 里有 provider 分支，接入成本低。它的优势是自有索引、AI/agent 场景上下文、额外 snippets、合规和稳定供应链。缺点是官方 Search 价格为 `$5 / 1k requests`，比 Serper Starter 的 `$1 / 1k` 高很多。

DDG / DDGS 继续保留为免费 fallback 和对照组。它适合低成本 smoke test，难以支撑高可信 GAIA 主线结论。现有 timeout / 403 统计已经说明免费栈会把外部网络波动注入实验分数。

Codex CLI `--search` 适合做人工研究、错题诊断、外部 oracle、文档补证。把它放进 GAIA in-loop 工具要非常谨慎，因为它返回的是模型加工后的搜索结果，query 过程、召回列表、计费边界和可复现实验日志都更难控制。

## 本项目代码现状

当前搜索工具定义在：

- `gaia_skillrl/tools.py`

关键事实：

- `web_search` 工具描述为 lightweight web search，返回 top results。
- 默认 provider 走 `duckduckgo_search.DDGS()`。
- DDGS 异常后，代码会请求 `https://html.duckduckgo.com/html/?q=...`，用 BeautifulSoup 抽取 `a.result__a` 和 `.result__snippet`。
- Brave raw Search 已有实现：
  - endpoint 默认 `https://api.search.brave.com/res/v1/web/search`
  - provider 环境变量：`NLRL_WEB_SEARCH_PROVIDER=brave`
  - key 环境变量：`NLRL_BRAVE_SEARCH_API_KEY` 或 `BRAVE_SEARCH_API_KEY`
  - 可选：`NLRL_BRAVE_SEARCH_ENDPOINT`、`NLRL_BRAVE_SEARCH_TIMEOUT_SECONDS`、`NLRL_BRAVE_SEARCH_SAFESEARCH`、`NLRL_BRAVE_SEARCH_COUNTRY`
- Serper 当前没有 provider 分支。若设置 `NLRL_WEB_SEARCH_PROVIDER=serper`，现有代码会报 unsupported provider。

因此，最小实现路线是：

1. 先用已有 Brave provider 做小切片 probe。
2. 新增 Serper provider，保持 `title / href / body` 输出结构不变。
3. 在日志里加入 `search_backend`、`search_latency_ms`、`search_result_count`、`search_status`、`search_error_type`。
4. 同一批 web-heavy wrong tasks 下跑 `ddg`、`serper`、`brave` 三组，Codex Search 只做旁路诊断。

## Codex Search 发现

本机 `codex --help` 顶层选项里有：

```text
--search
  Enable live web search. When enabled, the native Responses `web_search` tool is available to the model (no per-call approval)
```

这个开关容易漏掉，因为 `codex exec --help` 的子命令帮助里没有单独列出 `--search`。正确使用时应把它放在顶层选项位置：

```bash
codex --search -C /data/xsy
codex --search exec -C /data/xsy "查找某个事实，并输出答案、引用链接、检索关键词"
codex --search exec --json -C /data/xsy "对某个 GAIA 错题做 web 诊断，输出 JSON"
```

它可以提供一个新的诊断手段：

- 对 web-heavy wrong tasks 做强搜索复盘，判断题目是否因 search 召回失败、browse 抽取失败、agent 不继续探索、最终答案格式错误而失分。
- 让 Codex 输出候选 query、关键 URL、答案证据，再把这些 evidence 回填到本地错题分析。
- 用 `--output-schema` 要求 Codex 输出固定 JSON，降低复盘成本。

把 Codex Search 直接包进 `Qwen3-8B` executor 会改变实验含义。那时 `web_search` 工具已经包含强模型搜索策略与总结能力，分数不能再解释为 `Qwen3-8B + fixed lightweight search`。若后续确实要测试，可以单独命名为 `codex_search_oracle_tool`，并在报告里单列。

## 成本粗估

这里只按 search request 估算，不含网页读取、Jina/reader、Brave Answers token、Qwen/Codex 推理成本。

以 `ARCH-V5.2 no-CONCLUDE r3 c20` 六路快照为例，聚合 `web succ/fail = 637/66`，总搜索调用约 `703` 次：

| 后端 | 单价口径 | 703 次约成本 |
| --- | ---: | ---: |
| DDG | 免费 | 0 |
| Serper Starter | `$1 / 1k` | `$0.70` |
| Brave Search | `$5 / 1k` | `$3.52` |

以网络事故更重的 `ARCH-V5.1 any_phase c20` 为例，聚合 `web succ/fail = 326/1006`，总搜索调用约 `1332` 次：

| 后端 | 单价口径 | 1332 次约成本 |
| --- | ---: | ---: |
| DDG | 免费 | 0 |
| Serper Starter | `$1 / 1k` | `$1.33` |
| Brave Search | `$5 / 1k` | `$6.66` |

如果实际账单显示人民币或其他币种，以账户结算为准。相对比例仍可参考：Brave raw Search 约为 Serper Starter 的 5 倍。

## 质量预期

### DDG / DDGS

DDG 的价值是成本和可用性，不适合继续承担主解释变量。当前实验已经看到：

- DDGS 正常时可以跑出若干有效题。
- HTML fallback 会遇到 timeout / 403 窗口。
- fail 成片时，skill 或 prompt 的真实差异会被外部搜索噪声覆盖。

DDG 后续应作为 `free_search_control`。当 DDG 成绩偏低时，不能直接归因到 agent/prompt/skill。

### Serper

Serper 是最值得先接入的 P0。理由：

- 它提供实时 Google SERP，适合 GAIA 中大量事实查找题。
- 官方页面显示一般响应 `1-2s`，Starter 为 `$1 / 1k`，50 QPS。
- 输出结构适合直接映射到现有 `title / href / body`。

Serper 的不足也清楚：

- 它解决 search 召回，不自动解决网页正文抽取。
- 对复杂题，仍需要 `fetch_url`、`html_extract`、Jina Reader 或 browser extraction。
- 如果只替换 search，不替换 browse，提升可能被正文读取失败抵消。

因此推荐两组并行诊断：

| 条件 | Search | Browse |
| --- | --- | --- |
| `serper_raw` | Serper | 现有 `requests + BeautifulSoup / trafilatura` |
| `serper_reader` | Serper | Jina Reader 或更强 browser extraction |

### Brave Search API

Brave 的独特价值是 agent-friendly 和供应链稳定。官方说明 Brave Search API 使用自有独立 Web index，Search plan 包括 URLs、text、news、images 和面向 AI 的 LLM context，还支持 extra snippets、schema metadata、Goggles reranking。

对本项目来说，Brave 有三个用法：

1. raw Search：沿用当前 `_brave_web_search`，低改动即可和 DDG A/B。
2. raw Search + extra snippets：增加每个 result 的上下文，减少小模型凭短 snippet 猜答案。
3. AI Grounding / Answers：把 Brave 作为外部深搜工具，输出 citations 和 grounded answer。

第 3 种能力更强，也会改变工具边界。建议先跑 raw Search，再考虑 AI Grounding 单列为 `brave_grounding_oracle`。

### Codex CLI Search

Codex Search 的意义在于把“无限 Codex CLI”变成实验辅助能力：

- 快速复盘错题。
- 自动找证据链接。
- 生成候选 query。
- 对比 Serper/Brave/DDG 是否漏召回。
- 给 web-heavy wrong tasks 建 evidence cache。

它的局限也要写清楚：

- 它返回的是 Codex agent 搜索后的结果，天然带有模型总结。
- raw SERP、rank、snippet、query 改写过程难以完全观察。
- 若让 `Qwen3-8B` 调用 Codex Search，等价于给小模型接了一个强搜索代理。

所以 Codex Search 最适合两类工作：

1. 人工/半自动研究：帮助我们理解题目、找证据、改工具。
2. 上限参考：估计“如果 search/browse 足够强，这题是否可被解决”。

## 推荐实验矩阵

短期只抽 15-20 个 web-heavy wrong tasks，保持同一模型、同一 prompt、同一 `TOOL-GAIA-V2 / atomic_v2` executor。

| 记录名 | Search backend | Browse backend | 是否进入正式对比 | 目的 |
| --- | --- | --- | --- | --- |
| `v2_ddg_default` | DDG / DDGS | 当前 fetch/html | 是，作为当前 baseline | 复现免费栈噪声 |
| `v2_serper_raw` | Serper | 当前 fetch/html | 是 | 分离 search 召回收益 |
| `v2_serper_reader` | Serper | Jina/browser extraction | 是 | 分离 search + browse 总收益 |
| `v2_brave_raw` | Brave raw Search | 当前 fetch/html | 是 | 低改动验证 Brave |
| `v2_brave_context` | Brave extra snippets 或 LLM context | 当前或 reader | 视成本决定 | 验证 LLM-friendly snippet |
| `codex_search_probe` | Codex `--search` | Codex 自行搜索/总结 | 否，旁路 | 错题证据和上限诊断 |

每题记录至少包含：

- `task_id`
- `search_backend`
- `search_query_count`
- `search_result_count`
- `top_domains`
- `search_error_type`
- `fetch_status_code`
- `fetch_content_type`
- `reader_backend`
- `final_answer`
- `score_pass`
- `manual_note`

## 执行建议

优先级建议：

1. 接 Serper provider，输出结构保持现有 `title / href / body`。
2. 用已有 Brave provider 跑同一小切片。
3. 对小切片加 search cache，避免同一题多轮重复付费。
4. 用 Codex `--search` 对错题做旁路复盘，生成 evidence cache。
5. 如果 `serper_raw` 明显提升，再补 `serper_reader`；如果 raw search 无明显提升，优先查 agent query 生成和继续探索策略。

预期解释口径：

```text
DDG -> Serper/Brave 的提升，主要解释 search backend 质量。
raw search -> reader 的提升，主要解释 browse / extraction 质量。
Codex Search probe 的成功题，说明题目在强搜索辅助下可解，不能直接计入 Qwen3-8B 工具 baseline。
```
