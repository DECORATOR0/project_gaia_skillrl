核心结论：

- 如果目标是和近期 Agent Skills / skill learning 论文对齐，第一主线优先看 `SkillsBench`，它直接评估 `SKILL.md + 资源 + deterministic verifier` 对 agent performance 的增益，且官方覆盖 `Codex CLI + GPT-5.2`、`Claude Code`、`Gemini CLI`。
- 第二主线优先看 `SkillFlow`，它的 family-local lifelong skill patch 协议和当前 critic/actor skill 改写框架最接近。
- `SkillLearnBench` 很新、规模小，适合做 automatic skill generation smoke。
- `WebShop / ALFWorld / ScienceWorld` 虽然早，但 2025-2026 的 `SkillNet`、`SkillRL`、ICRL/self-generated examples 等仍在跑，适合作为经典对齐组。
- `WebArena / OfficeQA / SealQA / BrowseComp` 适合后续展示搜索、证据和文档推理 skill，优先级建议放在 SkillsBench/SkillFlow 之后。
- `SQLBench / AgentBench DB` 继续适合作为干净 smoke 和状态机调试集；它们的近期 skill 论文对齐价值低于上面几组。

## 当前背景

这段时间主线在 `/data/xsy/project_gaia_skillrl` 上做 GAIA SkillRL：

- 9B executor 从 ARCH5.2、BOOTV2 继续推到 BOOTV3 / BOOTV4、ARCH5.3。
- 跑过 baseline、boot-only、B1/B2 sharded offline actor、Codex 5.5 manual skill、旧 ARCH5.2 B_sharded 复跑。
- 重点观察过 dev/test 分数、平均 step、forced answer、missing answer、max step hit、false/forced answer 正确率等指标。
- 旧 ARCH5.2 B_sharded 曾出现较高 test 分数 `39/82`，但复跑后同 skill 同配置仍有明显波动，说明 GAIA 的结果随机性和环境扰动较大。
- 新 ARCH5.3 B1/B2 和 Codex 5.5 手写 skill 没有稳定超过 baseline，skill 变复杂后还会增加 max step hit 和 forced answer。

当前比较明确的困境：

- GAIA 任务太灵活，web/search/file/media/tool 混在一起，噪声和偶然性很强。
- 9B executor 容易过度推理、过度遵循、反复走流程，skill 越复杂越容易把步数耗满。
- force answer / missing / search 波动会干扰真实 skill 效果判断。
- 手工增强 skill、B1/B2 actor 改 skill、旧 skill 复跑都没有形成稳定上升趋势。
- 继续在 GAIA 上刷分收益变低，难以判断方法本身是否有效。

因此现在想跳出 GAIA，换一个更适合展示 skill 框架优势的 benchmark。

## 用户新的目标

下一步先别急着开实验。需要做一份更系统的外部调研：

调研范围：

- 时间重点限定在最近一两年，大致 `2025-2026`。
- 主题限定在涉及 skill 框架、skill library、skill discovery、skill evolution、experience-to-skill、agent skill learning、自动强化 skill 的论文。
- 关注这些论文实际跑了哪些 benchmark，尤其是多个论文反复使用、方便和别人对齐刷分的 benchmark。

调研目的：

- 找出“大家都在跑”的 benchmark，避免只按本地已有 adapter 决定。
- 判断哪些 benchmark 更适合当前 SkillRL / 状态机 / critic-actor skill 改写框架迁移。
- 避免继续陷在 GAIA 这种噪声过大的任务里。

## 目标文档需要包含什么

建议新开文档，例如：

`/data/xsy/project_gaia_skillrl/实验设计与迭代/26.5.xx_GAIA换benchmark_2025_2026_skill论文benchmark调研.md`

每个 benchmark block 至少包含：

1. Benchmark 名称和基本定位
   - QA / web browsing / shopping / text game / embodied / DB / coding / multi-file work / memory / tool-use 等。

2. 哪些 skill 相关论文跑过它
   - 论文名、年份、方法名。
   - 尽量标出是否是主实验、迁移实验、消融实验或补充实验。

3. 论文里用的模型
   - 例如 GPT-5.2 / GPT-4.x / Claude / Qwen / Llama / DeepSeek 等。
   - 大概模型规模：如 7B、8B、9B、70B、API frontier model。
   - 如果论文没写清楚，要标注“未明确”。

4. 普通 agent 做一题时的正常工作流
   - 不要按我们当前 GAIA phase 硬套。
   - 用 benchmark 本身的自然流程描述，例如：
     - 读题 / 读环境
     - 搜索或查看状态
     - 调工具 / 执行动作
     - 验证中间结果
     - 输出答案或完成环境目标
   - 这个部分用于判断我们的 skill/状态机框架能不能迁移。

5. 训练集、验证集、测试集规模
   - train/dev/test 分别多少题。
   - 如果 benchmark 没有固定 train/dev/test，要写清官方划分方式或常用协议。
   - 如果公开 benchmark 有 hidden test，也要说明。

6. 评分方式
   - exact match、execution accuracy、success rate、reward、pass@k、LLM judge、official verifier 等。

7. 迁移适配判断
   - 适合当前框架的点。
   - 主要阻塞，例如环境复杂、需要 Docker、需要浏览器服务、需要 LLM judge、数据许可、测试集隐藏、太简单或太开放。

## 当前倾向但需要调研验证

当前直觉：

- `AgentBench DB` 可能太简单，只适合 smoke。
- `SQLBench / BIRD / Spider` 更干净，但可能偏 text-to-SQL，是否属于 skill 框架论文常用 benchmark 需要确认。
- `WebShop / ALFWorld / HotpotQA` 在经验学习和 skill discovery 论文里出现较多，可能更适合对齐公开工作。
- `SkillsBench` 最贴近“显式 skill 工件”评测，若能拿到并跑通，可能很值得做。
- `Terminal-Bench` 与真实工作任务很贴，但环境成本和 checker 权限要先确认。

下一步调研完成后，要给出一个优先级排序：

1. 最适合快速迁移并出结果的 benchmark。
2. 最适合和近期 skill 论文对齐的 benchmark。
3. 最适合长期展示 SkillRL 框架优势的 benchmark。

## 当前不要做的事
