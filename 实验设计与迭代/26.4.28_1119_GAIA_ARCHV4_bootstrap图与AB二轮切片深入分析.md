## 1. Bootstrap 生成的图

bootstrap 只生成了一个 skill：`gaia-general-skill`。`bootstrap_skill_decision.json` 里的摘要是固定 GAIA executor skill，路由经过 local、media、web、compute、verify、bounded repair，最后输出精确 final answer。输入任务数是 83。

图结构是 8 个 phase，29 条有向边，A/B actor 后 graph lock 检查确认节点和边完全保持一致：

| phase | 允许转移 |
| --- | --- |
| `INIT` | `LOCAL_EVIDENCE`, `MEDIA_EVIDENCE`, `WEB_EVIDENCE`, `COMPUTE` |
| `LOCAL_EVIDENCE` | `MEDIA_EVIDENCE`, `WEB_EVIDENCE`, `COMPUTE`, `VERIFY`, `REPAIR` |
| `MEDIA_EVIDENCE` | `WEB_EVIDENCE`, `COMPUTE`, `VERIFY`, `REPAIR` |
| `WEB_EVIDENCE` | `COMPUTE`, `VERIFY`, `REPAIR`, `LOCAL_EVIDENCE` |
| `COMPUTE` | `VERIFY`, `LOCAL_EVIDENCE`, `WEB_EVIDENCE`, `MEDIA_EVIDENCE`, `REPAIR` |
| `VERIFY` | `CONCLUDE`, `REPAIR` |
| `REPAIR` | `LOCAL_EVIDENCE`, `MEDIA_EVIDENCE`, `WEB_EVIDENCE`, `COMPUTE`, `VERIFY` |
| `CONCLUDE` | 无 |

bootstrap skill 在每个节点附加了五类信息：

- `Goal`：节点目标，例如 `WEB_EVIDENCE` 是收集时间正确的网页证据，`VERIFY` 是确认 support 和输出形态。
- `Allowed tools`：节点工具白名单，例如 `WEB_EVIDENCE` 只有 `web_search/fetch_url/html_extract`，`VERIFY` 只有 `run_python`，`CONCLUDE` 无工具。
- `Rules`：节点内行为规则，例如 INIT 按 dominant need 路由，WEB 优先 primary/official/archived 页面，COMPUTE 使用 `run_python` 处理算术、排序、模拟等。
- `Exit handoff`：离开节点时要带给下一节点的信息，例如证据来源、候选答案、未解决字段、格式约束。
- `Available actions` 和 `Next`：当前 phase 合法动作和合法下一跳。

这个图的核心价值是把小模型限制在一个可检查的状态机里。当前主要问题来自节点内规则的强弱、工具调用细节、VERIFY 门槛和 REPAIR 行为，图的 phase/edge 本身在 A/B critic 里都被判定可保留。

## 3. Critic 对第一轮行为的分析

### A_full critic

A critic 是 full 口径，看完 80 个 first-round rows 后输出一个整体 reward。它的核心判断：

- 主失败模式是 premature closure。
- `WEB_EVIDENCE` 经常把 search impression 或偏题页面当作足够证据。
- `VERIFY` 放过了 unsupported 或语义错位 candidate。
- `LOCAL_EVIDENCE` 与 `COMPUTE` 在 schema 未检视、直觉计算上出错。
- graph 无需改，应该加固已有节点。

按 node edit 的证据 task id 估算：

| phase | 点名 unique id | 失败 id | 成功 id | phase/tool 对齐 |
| --- | ---: | ---: | ---: | ---: |
| `WEB_EVIDENCE` | 9 | 9 | 0 | 9/9 |
| `VERIFY` | 9 | 9 | 0 | 9/9 |
| `LOCAL_EVIDENCE` | 9 | 8 | 1 | 9/9 |
| `COMPUTE` | 8 | 8 | 0 | 8/8 |
| `REPAIR` | 6 | 6 | 0 | 6/6 |
| unique 合计 | 37 | 36 | 1 | 37/37 |

结论：

- 失败证据精度：36/37 = 97.3%。
- 失败覆盖率：36/64 = 56.3%。
- 唯一成功样本是 `32102e3e`，它虽然最终正确，但路径里有大量 parser/tool failure。这个样本可作为“成功但高摩擦”的保护样本，放在失败证据表里会带来一点噪声。

A critic 的强项是覆盖面较大，尤其抓到了 WEB、VERIFY、LOCAL schema、COMPUTE formalization、REPAIR diffuse loop 五个主面。弱项是对“加规则会增加协议摩擦”的副作用估计不足，A actor 后 invalid action 和 tool failure 明显上升。

### B_sharded critic

B critic 是 sharded 口径，先按 family 分片，再 aggregate。它的核心判断：

- graph held up。
- 主损失来自 phase 内 instruction quality。
- 最大收益集中在 `WEB_EVIDENCE`、`VERIFY`、`REPAIR`、`LOCAL_EVIDENCE`、`COMPUTE`。
- 特别强调 action legality、工具参数合法性、失败工具结果零证据、raw URL 不得交给 local parser。

按 node edit 的证据 task id 估算：

| phase | 点名 unique id | 失败 id | 成功 id | phase/tool 对齐 |
| --- | ---: | ---: | ---: | ---: |
| `INIT` | 4 | 2 | 2 | 4/4 |
| `LOCAL_EVIDENCE` | 4 | 4 | 0 | 4/4 |
| `WEB_EVIDENCE` | 5 | 5 | 0 | 5/5 |
| `COMPUTE` | 4 | 4 | 0 | 4/4 |
| `VERIFY` | 5 | 5 | 0 | 5/5 |
| `REPAIR` | 4 | 4 | 0 | 4/4 |
| unique 合计 | 24 | 22 | 2 | 24/24 |

结论：

- 失败证据精度：22/24 = 91.7%。
- 失败覆盖率：22/64 = 34.4%。
- 两个成功样本主要来自 success anchor 设计，其中 `32102e3e` 和 `a3fbeb63` 也被用于提示“要保留能成功的快路径/混合路径”。

B critic 的强项是更早指出协议合法性、raw URL/local parser、失败工具零证据这类 runtime 摩擦。弱项是失败覆盖更窄，且 success anchor 的保护意图没有被 actor 稳定落实；B dev 反而丢了 `32102e3e`、`a3fbeb63` 等原本正确样本。

### A+B 合并视角

A 和 B 点名的 unique evidence id 合并后有 45 个，其中 43 个是失败样本，覆盖 43/64 = 67.2% 的第一轮失败。整体判断比较可靠：

- graph 保留，这点和 actor graph lock 结果一致。
- WEB/VERIFY/REPAIR 是主改动面。
- LOCAL schema 和 COMPUTE 绑定输入是第二优先级。
- 协议摩擦需要和准确率一起管控，B critic 看到了这一点，A/B eval 进一步放大了这一点。

剩余 21 个未被 evidence 直接点名的失败不能忽略。它们大概率包含 media、格式粒度、实体错配、集合题、以及少量 tail/长步数问题。下一轮 critic 如果只跟着点名样本走，会继续过拟合 WEB/VERIFY。

## 4. Actor 对 skill 的节点级行为

A/B actor 都是 `modify_skill`，都只写 `SKILL.md`，没有删文件。两边 `actor_graph_lock_check.json` 都显示：

- `graph_unchanged: true`
- phase order 一致。
- edge list 一致。

### A_full actor 加了什么

A 的摘要是：加强 source grounding、verification gates、schema-aware local parsing、executable computation、single-blocker repair。

节点级改动：

| 位置 | A actor 主要新增约束 |
| --- | --- |
| Common rules | 携带 asked field、answer type、source qualifier、time/version scope；候选必须有具体 file/URL 和 row/field/quote/cell/calculation 支持后才进 `VERIFY`；access/quota/path/parser/empty extraction 作为 unresolved blocker；`according to/as of/before/latest 2022 version/without adjusting for stock split` 作为强约束 |
| `INIT` | handoff 增加 source qualifiers；路由描述更聚焦 dominant evidence need |
| `LOCAL_EVIDENCE` | allowed tools 增加 `run_python`；用 Python 检查 sheet/header/type/nested structure；离开前记录 filename、sheet/section、columns、row filters、joins、units、type conversions |
| `MEDIA_EVIDENCE` | 只有答案已由 media facts 支持且输出形态清楚才进 `VERIFY` |
| `WEB_EVIDENCE` | search/snippet 只做线索；必须 fetch 目标页并 extract 字段/日期/table/revision；source qualifier 和历史 snapshot 强绑定；blocked/off-domain 后找同源 direct/archive URL |
| `COMPUTE` | 非平凡计算默认 `run_python`；代码编码 prompt semantics 和 output scale；缺 operand/schema/constraint 时回证据节点 |
| `VERIFY` | 检查 exact field、answer type、entity、time/version scope、direct support、format；拒绝 blank、inability prose、snippet/neighbor heading 支持 |
| `REPAIR` | 一个明确 blocker，一个窄 remedy；避免泛化搜索和 `VERIFY<->REPAIR` 空转；single-use 倾向更强 |

A 的行为倾向是“证据门槛更严、计算更可执行、schema 更显式”。这解释了 test 上数值/实体题的新增正确，也解释了 dev 上工具失败和 invalid action 的上升。

### B_sharded actor 加了什么

B 的摘要是：加强 legality 和 support gates，让 evidence phase 更 path/source-aware，约束 computation retry，使 repair blocker-specific。

节点级改动：

| 位置 | B actor 主要新增约束 |
| --- | --- |
| Common rules | CONCLUDE 前不得输出 answer text；工具参数必须 schema-valid；snippet、guessed path、failed parse、failed code、403/404/quota/no-such-file/unsupported/syntax error 全部零证据；raw URL 不得传给 local parser；进入 `VERIFY` 前必须有 exact candidate 且 filter/relation/entity/role/time/version 全部 resolved |
| `INIT` | `read_json_file task.json` 作为默认第一动作；附件/ZIP/JSON bundle/table/PDF/local file 提示下，filename 未确认时先 `list_dir`；混合 local+web 任务优先 local grounding |
| `LOCAL_EVIDENCE` | confirmed workspace paths only；extension-aware parser；archive 先解包；一次 type mismatch/dependency/unsupported 后停止尝试无关 parser；最多一次小型 `run_python` fallback；输出 named blocker |
| `MEDIA_EVIDENCE` | 关注 file identity、rotation、multi-image order；OCR/image_qa 只在具体 ambiguity 下组合；失败带 named blocker |
| `WEB_EVIDENCE` | `web_search` 只做 lead generation；fetch+html_extract 后才能 claim support；DOI/Wayback/Wikipedia history/paper/PDF/image 用 source-native/revision-specific URL；exclusion 题先枚举候选集再消元；raw URL 不能交给 local |
| `COMPUTE` | run_python 前绑定每个变量到 source value；raw executable Python only；输出 compact witness；一到两次 syntax/runtime failure 后停止 retry 并回证据节点或 REPAIR |
| `VERIFY` | 通过则只发 `<NEXT>CONCLUDE</NEXT>`；失败则只发 `<NEXT>REPAIR</NEXT>` 并命名一个 blocker |
| `REPAIR` | blocker label 显式枚举：`blocked_source/wrong_path_or_artifact/parse_failure/missing_operand/scope_conflict/ocr_ambiguity/format_gap`；同一 broad search、wrong parser、malformed Python 不重复 |

B 的行为倾向是“协议合法性和工具失败处理更硬”。这对某些访问失败、集合候选消元、local path 错误有帮助，但也会把更多题推到高步数、空答或无法收口。

## 6. 对 AB 第二轮 dev 切片的串通分析

### 6.1 可保留信号

A/B 共同 gained 的 5 题是第二轮最稳的正样本。它们说明“更严格的 support gate、WEB source binding、LOCAL/COMPUTE 输入绑定”确实能把部分第一轮错误拉回来。

A test 的 9 个新增正确也支持这个判断。上一份文档已列出这些 test 新增正确以数值题、实体错配修正、访问失败恢复为主。A 的修改方向对 test split 是有效信号。

B-only gained 的 `7dd30055`、`e1fc63a2` 值得单独复核，因为它们可能来自 B 的 protocol/path/source-aware 规则；这类规则可以合并到下一版，但需要压缩表述和降低空答风险。

### 6.2 需要保护的成功路径

A/B 共同 lost 的 6 题是必须加入 regression slice 的保护样本。它们代表“第一轮已经能靠短路径答对，A/B 加规则后反而被拖慢、过度验证或改错”的风险。

B-specific lost 里的 `32102e3e` 和 `a3fbeb63` 特别重要。B critic 原本把 success anchor 纳入 shard，但 B actor 后仍丢掉这些成功样本，说明“保留成功路径”的文字约束没有转化成稳定执行行为。下一轮 actor 需要把保护写成更具体的低步数策略：

- self-contained `COMPUTE` 成功路径保留短链路。
- local file 已经 parsed 并得到 exact candidate 时，直接进 `VERIFY`，不要额外找 web 或换 parser。
- `VERIFY` 在 support 和格式满足时快速 `CONCLUDE`，不要再走 REPAIR。

### 6.3 A 的收益和副作用

A 的收益：

- A_test 从 15/81 到 20/79，common set 净增 +5。
- test 上 WEB 首跳正确数从 7 提到 10，LOCAL 从 5 提到 6。
- A 的新增规则直接命中 critic 所说的 WEB snippet closure、VERIFY loose gate、LOCAL schema、COMPUTE formalization。

A 的副作用：

- A_dev 从 16/80 到 15/80，common set 净 -1。
- invalid next 从 67 到 109，invalid answer phase 从 147 到 233，tool failure 从 81 到 122。
- WEB dev 首跳正确从 8/55 到 6/53。

判断：A 适合作为下一版主干，但要做“摩擦瘦身”。尤其是 common rules 与 VERIFY 文案太重，小模型容易多发非法 answer 或在支持不完美时反复绕路。

### 6.4 B 的收益和副作用

B 的收益：

- B_dev WEB 首跳正确达到 10/55，高于 bootstrap 的 8/55。
- B_test 相对 bootstrap common set 净 +1。
- B 明确打击 raw URL/local parser、失败工具零证据、schema-valid action、同一错误重试，这些都是实际 runtime 噪声点。

B 的副作用：

- B_dev 空答从 7 涨到 13，steps >= 24 从 5 涨到 14，tool failure 从 81 涨到 162，invalid next 从 67 涨到 165。
- B_dev LOCAL 首跳正确从 3/12 降到 2/15，COMPUTE 从 5/8 降到 3/6。
- B_test 列表/集合错误在上一份文档里上升，说明“候选集枚举”写进去了，但集合校验和最终输出形态仍弱。

判断：B 更像 protocol hardening patch。它适合拆出少量高价值规则合并到 A 主干，例如“raw URL 不交 local parser”“failed tool zero evidence”“run_python raw executable”“一到两次失败后停止 retry”。B 的整体严格度会放大空答和长尾。

## 8. 下一版 skill/actor 建议

建议从 A 主干出发，吸收 B 的少量硬规则，形成一个 C 候选：

1. 保留 A 的 `WEB_EVIDENCE` source binding 和 `VERIFY` direct-support gate，但压缩成更短、更可执行的 checklist。
2. 合并 B 的协议硬规则：CONCLUDE 前不输出 answer text；failed tool/403/404/quota/no-such-file/unsupported/syntax error 零证据；raw URL 不交 local parser；`run_python` 必须 raw executable。
3. 给 `VERIFY` 增加成功快车道：如果 exact candidate 已有 direct support 且格式满足，下一步只能 `CONCLUDE`。
4. 给 `REPAIR` 增加低步数收口策略：REPAIR 只能一次；若 REPAIR 后仍缺证据，但已有非空候选，回 `VERIFY` 做支持/格式检查，避免空答或 hypothetical number。
5. 给 `LOCAL_EVIDENCE` 限制 fallback：默认 parser 成功后不再换 parser；parser 失败后最多一次 `run_python` schema fallback；fallback 必须打印 sheet/header/row witness。
6. 给 `COMPUTE` 增加“输入绑定”但保留 self-contained 快路径：prompt 已给全量 operands 的逻辑/算术题，直接 `COMPUTE->VERIFY->CONCLUDE`，不要引入 web。
7. 给集合题补最终校验：元素数、去重、排序、大小写、分隔符、是否需要 all/both/which one exclusion。
8. 单独补 MEDIA：image/audio 题需要先抽取 observable facts，再决定 compute/web；当前 A/B 对 MEDIA 首跳仍是 0/5。

## 9. 总结判断

bootstrap 生成的图是合理的固定状态机，当前不需要改 phase/edge。第一轮失败主要集中在 WEB 证据不足、VERIFY 门控弱、LOCAL schema 和 COMPUTE 输入绑定不牢、REPAIR 扩散。A critic 对这些问题的证据精度高、覆盖中等偏高；B critic 覆盖较窄，但抓到了协议和工具失败语义。

A actor 的方向更接近下一版主干，test 净增明显；它的规则负载会带来 invalid action 和 tool failure 上升。B actor 的 protocol hardening 有价值，但整体太硬，dev 空答、长步数、tool failure 都明显恶化。下一轮应该用 dev slice 保护共同 gain 和共同 loss，把 A 的 evidence gate 与 B 的少量 runtime 硬规则合并，并把成功快车道、REPAIR 单次收口、LOCAL fallback 限制写得更具体。
