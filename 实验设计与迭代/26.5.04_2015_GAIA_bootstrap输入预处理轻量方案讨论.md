## 背景判断

当前 `bootstrap_input.json` 的结构比较原始：前半部分是 `runtime_contract`，后半部分把 83 道题的 `question / gold_answer / attachments / file_list` 基本全量放进 `batch_task_snapshot.tasks`。这对 83 题还能接受，但 bootstrap 模型需要在长 prompt 内自己完成分类、归纳、抽象和图设计，质量受注意力分配影响较大。

bootstrap 的核心任务是生成初始固定图 skill。它需要看到任务能力分布、工具覆盖、答案格式和常见风险；逐题完整答案只应作为训练期统计信号，直接全量暴露会增加 token、过拟合和噪声。

本轮文件统计：

- `bootstrap_input.json`：约 54 KB，1093 行。
- `o200k_base` 近似口径：`bootstrap_input.json` 约 14.8k tokens，实际 Codex bootstrap prompt 约 16.1k tokens。
- Qwen3.5-9B tokenizer：`bootstrap_input.json` 约 17.4k tokens，实际 Codex bootstrap prompt 约 18.7k tokens。
- 83 题平均每题 row 约 170 `o200k_base` tokens / 199 Qwen tokens。几百题会线性涨到 50k-100k+ token。

## 目标

预处理只做轻量、通用、跨任务的抽象，服务两个目标：

- 提升 bootstrap 生成的固定图和节点规则质量。
- 控制输入 token，避免几百题场景里把 prompt 消耗在重复 JSON 行上。

本阶段不追求复杂自动课程学习，也不做针对某道题的定制标签。预处理结果应该能复用于 GAIA 以外的“多工具问答任务集合”。

## 推荐输入形态

把当前输入从“全量题目清单”改成三层：

```json
{
  "runtime_contract": {},
  "batch_profile": {},
  "representative_examples": []
}
```

`runtime_contract` 继续保留完整内容，因为它是执行硬约束。

`batch_profile` 放全量任务的统计摘要，例如：

```json
{
  "task_count": 83,
  "level_histogram": {"1": 27, "2": 43, "3": 13},
  "modality_histogram": {},
  "operation_histogram": {},
  "answer_shape_histogram": {},
  "attachment_suffix_histogram": {},
  "risk_flag_histogram": {},
  "modality_answer_shape_cross": {}
}
```

`representative_examples` 放少量代表题。每条只保留通用标签、简短题目片段和答案形状：

```json
{
  "level": 2,
  "modality": "web_lookup",
  "operation_tags": ["entity_linking", "temporal_or_version_check", "comparison_selection"],
  "implied_tool_groups": ["web", "compute_optional"],
  "answer_shape": "short_text",
  "format_constraints": ["exact_string"],
  "risk_flags": ["multi_hop", "source_date_sensitive"],
  "question_excerpt": "A paper about AI regulation that was originally submitted to arXiv..."
}
```

`task_id` 可以写进审计文件，默认不放进最终 boot prompt。`gold_answer` 默认转成 `answer_shape` 和 `format_constraints`，只有在少数格式样例里保留脱敏或截断后的形状说明。

## 轻量标签设计

### Modality

用于告诉 bootstrap “信息主要从哪里来”：

- `prompt_only_or_ambiguous`
- `web_lookup`
- `local_table`
- `local_document`
- `local_image`
- `local_audio`
- `local_archive`
- `local_structured_or_code`
- `mixed_local_web`

这组标签直接影响 phase 图是否需要本地证据、网页证据、计算、验证、修复路径。

### Operation Tags

用于告诉 bootstrap “题目通常要做什么操作”：

- `entity_linking`
- `temporal_or_version_check`
- `comparison_selection`
- `aggregation_counting`
- `numeric_compute`
- `table_filter_join`
- `document_extraction`
- `ocr_or_visual_reasoning`
- `audio_transcription`
- `archive_traversal`
- `format_sensitive_answer`
- `multi_hop_reasoning`

标签数量需要控制。每题 1-4 个足够，避免把分类体系做成另一个复杂任务。

### Answer Shape

用于指导最终答案格式：

- `integer`
- `decimal_or_number`
- `date_or_year`
- `short_text`
- `phrase_or_sentence`
- `comma_list`
- `boolean_or_yes_no`
- `code_or_formula`
- `coordinate_or_move`

这比直接给完整 gold answer 更稳。它保留答案格式信号，同时降低 boot skill 过拟合具体答案的风险。

### Risk Flags

用于指导 `VERIFY` 和 `REPAIR` 节点：

- `exact_format_required`
- `source_date_sensitive`
- `version_sensitive`
- `multi_source_conflict_possible`
- `long_context_source`
- `attachment_extraction_risk`
- `requires_python_for_exactness`
- `visual_extraction_uncertain`

这些风险标签不需要特别精细。bootstrap 只要知道哪类风险常见，就能写出更有用的验证和修复规则。

## 代表样本抽样

建议默认最多 60-100 条样本进入 bootstrap prompt。样本选择规则：

- 稀有 modality 必保留，例如 audio、archive、PDB/structured、少量 image。
- 每个常见 modality 至少覆盖 2-5 条。
- 优先覆盖 `modality × answer_shape` 的主要交叉格子。
- level 1/2/3 都要出现，level 3 样本优先保留多步、混合证据、长题。
- 长题保留 excerpt 和标签，完整题目放审计文件。
- 普通 web lookup 不需要全量塞入；保留能代表 entity linking、temporal check、comparison、counting 的样本。

这样能让 bootstrap 看到能力覆盖，同时把 prompt 控制在稳定范围内。

## 当前 83 题的粗分类示例

按轻量规则粗分，本轮任务大致是：

```text
web_lookup: 34
prompt_only_or_ambiguous: 17
compute_or_reasoning: 13
local_table: 5
local_document: 6
local_image: 4
local_archive: 2
local_audio: 1
local_other/PDB: 1
```

答案形状大致是：

```text
short_name_or_term: 30
integer: 28
phrase_or_long_text: 10
list: 8
number: 7
```

这类摘要比全量题目更直接地告诉 bootstrap：图里需要稳定覆盖 web evidence、local extraction、compute、verify、repair；答案规则要重视短实体、整数、列表、精确格式和少量长短语。

## 最小可行实现

第一版可以只做规则预处理，不引入额外 LLM：

1. 在 `gaia_skillrl/bootstrap.py` 增加 `_task_features(task)`。
2. 从 prompt 文本、附件 suffix、gold answer 字符串推导 `modality / operation_tags / answer_shape / risk_flags`。
3. 增加 `_batch_profile(tasks)`，输出 histogram 和 cross table。
4. 增加 `_representative_examples(tasks, features, cap=80)`，按 modality 和稀有类型抽样。
5. 新增日志文件：
   - `bootstrap_raw_batch_input.json`：保留当前全量原始输入，便于审计。
   - `bootstrap_profile_input.json`：新的模型输入主体。
   - `bootstrap_preprocess_report.json`：记录每题特征、抽样原因、token 估计。
6. 修改 `bootstrap_skill_user.md`，让模型主要消费 `batch_profile_json` 和 `representative_examples_json`。

原来的 `bootstrap_batch_input.json` 可以保留为兼容审计文件，但不再默认进入完整 prompt。

## 可选增强

第二版可以引入一个很小的 LLM/classifier 步骤，只处理规则不确定的题：

- 输入单题 question、附件 suffix、answer shape。
- 输出 3-5 个标签，不输出推理过程。
- 只用于修正规则分类，不参与最终答案。

这一步要设置硬预算和缓存。分类结果写入 `bootstrap_preprocess_report.json`，相同 task_id 和 question hash 命中缓存后复用。

大批量任务场景可以做 shard summarize：

1. 每 50-80 题生成一个 shard profile。
2. 聚合 shard profile 成全局 profile。
3. final bootstrap 只读全局 profile、shard 摘要、代表样本。

这个方式适合几百到上千题，能避免 final architect 读完整题集。

## 对 skill 图设计的影响

预处理后，bootstrap prompt 可以更明确地要求：

- 图必须覆盖 `prompt_only / web / local / compute / verify / repair` 这些能力族。
- 本地文件节点需要按附件类型写工具选择规则。
- web 节点需要写 source/date/version 验证规则。
- compute 节点需要明确什么时候使用 Python。
- verify 节点需要覆盖 answer shape 和 format constraints。
- repair 节点需要针对 extraction、source conflict、calculation drift、format mismatch 给出单次聚焦修复。

这样生成的图仍然通用，后续 R 阶段继续只改文本和节点内规则。

## 当前结论

建议先做规则版 MVP。它改动小，性能成本低，能直接减少 prompt token 和过拟合风险，也能让 bootstrap 的输入从“题目堆叠”变成“任务分布画像 + 代表样本”。

下一步若实现，优先改 `bootstrap.py` 和 `bootstrap_skill_user.md`，并在一轮 boot-only smoke 中比较：

- boot prompt tokens
- 生成图是否稳定
- boot skill 的 phase 规则是否覆盖稀有 modality
- boot_dev 成功率和失败类型是否改善

## 外部方法调研补充

调研时间：2026-05-04 20:30 +0800

问题：类似“把题目/训练集转成可消费材料、经验、提示词或 skill”的论文一般怎么接入训练集？

### 相关方法线索

1. **ExpeL：训练任务 -> 经验池 -> 抽象洞察 + 检索示例**

   ExpeL 从一组训练任务中收集成功/失败轨迹，把轨迹存入 experience pool，再用 LLM 从成功/失败对和成功轨迹集合中抽取自然语言 insights。推理时，它把抽取出的 insights 加到任务说明里，并按任务相似度检索成功轨迹作为 few-shot 示例。论文还设计了 `ADD / EDIT / UPVOTE / DOWNVOTE` 这类操作来维护 insight 集合，降低单条轨迹误导的风险。

   对我们的启发：bootstrap 的输入最好先变成 `batch_profile` 和少量代表样本。真实 trajectory 产生后，再让 R/critic/actor 消费“成功/失败对”和“跨任务洞察”。bootstrap 阶段只拿静态题面，不适合伪造经验轨迹。

   来源：[ExpeL: LLM Agents Are Experiential Learners](https://arxiv.org/abs/2308.10144)，HTML 版方法段落：[ar5iv](https://ar5iv.labs.arxiv.org/html/2308.10144v3)

2. **Reflexion：反馈信号 -> verbal reflection -> episodic memory**

   Reflexion 把任务反馈转成自然语言反思，放进 episodic memory，后续 trial 用这些反思改善决策。它的重点在“反馈后的文本记忆”，不更新模型参数。

   对我们的启发：bootstrap 之前没有执行反馈，所以不该把题面强行转成“失败经验”。R 阶段已有 boot_dev state，适合做 Reflexion/ExpeL 式失败模式总结。

   来源：[Reflexion: Language Agents with Verbal Reinforcement Learning](https://arxiv.org/abs/2303.11366)

3. **APE / OPRO：训练样例 -> 候选指令 -> 指标筛选**

   APE 把 instruction 看作 program，用 LLM 生成候选 instruction，再用训练样例上的分数筛选。OPRO 把优化过程放进自然语言 prompt，每轮把历史候选及其分数提供给 optimizer LLM，让它提出新候选，再评估回填。

   对我们的启发：固定图 bootstrap 可以从 one-shot 生成升级为轻量候选筛选：同一份 `batch_profile` 生成 2-3 个 seed skill，跑小规模 stratified boot smoke，选择更好的图作为锁图。这个是可选增强，成本比全量多轮 R 小。

   来源：[Large Language Models Are Human-Level Prompt Engineers / APE](https://arxiv.org/abs/2211.01910)，[Large Language Models as Optimizers / OPRO](https://arxiv.org/abs/2309.03409)

4. **DSPy / MIPROv2：dataset summary + bootstrapped demos + instruction candidates**

   DSPy 把 LM pipeline 抽象成可优化模块。MIPROv2 同时优化 instruction 和 few-shot examples：先从训练集采样并运行程序，输出正确的样例才保留为候选 demo；然后用训练集属性摘要、程序摘要、候选 demos 和随机 generation tip 来提出 instruction candidates；最后用 Bayesian optimization 在验证集上选择组合。

   对我们的启发：它的训练集接入并不是“全量样例常驻 prompt”。更像是三件事：数据集属性摘要、通过结果验证的候选示例、指标驱动的候选选择。我们当前的 `batch_profile + representative_examples` 正好对应前两件；第三件可以用小样本 smoke 做。

   来源：[DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines](https://arxiv.org/abs/2310.03714)，[MIPROv2 docs](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/api/optimizers/MIPROv2.md)

5. **Coverage-based ICL selection：代表性优先，避免相似样本冗余**

   Coverage-based Example Selection 指出，单独按相似度选 examples 容易选到冗余样本，漏掉重要 reasoning pattern；set-level coverage 对组合任务更有效。

   对我们的启发：`representative_examples` 应按 coverage 选，不按原数据顺序或单纯题面相似度选。最实用的 coverage 维度是 `modality × operation_tags × answer_shape × level`，稀有 modality 必保留。

   来源：[Coverage-based Example Selection for In-Context Learning](https://aclanthology.org/2023.findings-emnlp.930/)

6. **Dataset distillation / data selection：大训练集先压成小而有代表性的材料**

   Dataset Distillation/Condensation 的目标是把大训练集压成小的 synthetic/representative set，使小集合仍保留训练效果。LLM instruction tuning 的 data selection 调研也反复强调质量、覆盖和冗余控制，数据数量本身不是唯一目标。

   对我们的启发：对 bootstrap prompt 来说，目标不是“让模型看见每道题”，而是让它看见足够覆盖的任务分布和代表样本。由于我们不训练权重，采用规则 profile + coverage 抽样比真正 synthetic sample 优化更合适。

   来源：[Dataset Distillation: A Comprehensive Review](https://arxiv.org/abs/2301.07014)，[A Survey on Data Selection for LLM Instruction Tuning](https://arxiv.org/abs/2402.05123)

7. **SkillAct / SkillsBench：skill 要抽象成可复用过程，且需要评估约束**

   SkillAct 说明 LLM agent 可以从 few-shot demonstrations 中学习 reusable skill abstractions。SkillsBench 进一步提示：curated skills 平均有明显收益，但效果因领域而异；self-generated skills 平均收益不稳定；聚焦的少模块 skills 往往优于全面文档式 skills。

   对我们的启发：bootstrap 生成的 skill 应保持聚焦，phase 规则服务可复用过程，避免把训练集知识写成大而全说明书。锁图前最好有小规模验证，避免 self-generated graph 直接变成全局约束。

   来源：[SkillAct: Using Skill Abstractions Improves LLM Agents](https://openreview.net/pdf/bfff2c8e4152f4eb2eadcad6a5a347c364cb32c9.pdf)，[SkillsBench](https://arxiv.org/abs/2602.12670)

8. **GEPA / textual prompt evolution：trajectory 级反思更适合优化阶段**

   GEPA 从系统 trajectories 中做自然语言反思，诊断问题、提出 prompt updates，并组合互补经验。它强调用少量 rollout 获得较大 prompt 质量收益。

   对我们的启发：这更适合 R 阶段。bootstrap 阶段用题面 profile 生成初始图；boot_dev 跑完后，再用 trajectory 反思来改节点文本和局部规则。

   来源：[GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning](https://arxiv.org/abs/2507.19457)

9. **STaR：从题目生成 rationale，但只保留验证正确的材料**

   STaR 用少量 rationale examples 引导模型为大量题目生成 rationale；答错时给正确答案再生成 hindsight rationale；最终只把能导向正确答案的 rationale 用于下一轮。

   对我们的启发：如果以后想把题面转成“解题策略材料”，需要验证过滤。bootstrap 当前还没有 executor rollout，先不要生成伪 rationale 当 skill 依据。

   来源：[STaR: Self-Taught Reasoner](https://research.google/pubs/star-self-taught-reasoner-bootstrapping-reasoning-with-reasoning/)

### 调研后的修正建议

基于这些方法，当前轻量方案可以小幅修正为：

1. **静态题集阶段只做 task profile**

   输入题面、附件、gold answer 形状，输出 `batch_profile`、coverage examples 和审计文件。不要在这里写“失败经验”或“成功经验”。

2. **代表样本按 coverage 选**

   第一版不用 embedding。按 `modality × operation_tags × answer_shape × level` 分层抽样，稀有类型强制覆盖，普通 web lookup 限额。

3. **gold answer 默认只转 shape**

   保留 `integer / short_text / comma_list / decimal / date_or_year` 等 answer shape。具体答案放审计文件，进入 prompt 的样本只保留必要的格式特征。

4. **可选做小规模候选筛选**

   若成本允许，同一 profile 生成 2-3 个 seed skill，跑 10-20 条 coverage smoke，按成功率、平均步数、无答案率、图合法性选择锁图。这个借鉴 APE/OPRO/MIPRO，能减少单次生成运气成分。

5. **trajectory 经验留给 R 阶段**

   boot_dev 产生 state 后，再做 ExpeL/Reflexion/GEPA 风格的 failure family、success/failure 对比、节点内规则更新。这样训练材料来自真实运行结果。

6. **skill 文本保持短而聚焦**

   SkillsBench 对全面文档式 skill 的收益并不乐观。我们的 bootstrap 目标应是清晰 phase control 和关键工具规则，不追求把所有任务知识写进 skill。

### 对当前 MVP 的影响

MVP 仍然建议先实现规则版预处理：

- `bootstrap_profile_input.json` 替代全量题目进入 prompt。
- `bootstrap_raw_batch_input.json` 保留全量原始题目审计。
- `bootstrap_preprocess_report.json` 记录每题标签和抽样理由。
- `bootstrap_skill_user.md` 明确要求模型基于 profile 设计图，不要复制样本事实。

后续增强按优先级排序：

1. coverage smoke 选择 seed skill；
2. boot_dev trajectory insight extraction；
3. 题量很大时的 shard profile 聚合；
4. 仅对规则不确定样本调用小 LLM classifier。
