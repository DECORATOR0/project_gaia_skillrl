# GAIA SkillRL 换 Bench 快速迁移盘点

时间：2026-05-05 20:39 +0800

## 一页结论

当前最适合快速迁移的是 `SQLBench / AgentBench DB` 这一类结构化 DB 任务。理由很直接：本机已有 adapter、数据、manifest、smoke 结果，评分可程序化，任务 family 清楚，能把 skill 的价值落在“读 schema、抽约束、写查询、执行验证、错误修复”这些可总结的经验上。

第二优先级是 `tau2 retail / airline`。它比 SQL 更像 agent：有 policy、工具、用户状态、数据库状态和 reward。迁移成本比 SQL 高，但更能体现状态机和 skill 对工具顺序、政策遵循、状态更新的帮助。

`WebShop / BrowserGym MiniWoB / Terminal-Bench` 都能接，但当前更适合作为后续扩展。`Terminal-Bench` 思路最像真实工作任务，当前本机 Docker/Harbor 权限阻塞；`BrowserGym MiniWoB` 已可跑，任务偏轻；`WebShop` 当前是 offline small text env，正式原生环境依赖重。

`/data/xsy/project_gaia_skillrl` 当前分支仍适合保留为 GAIA 主线和 actor/critic/skill graph 参考。通用 bench adapter 的资产主要在 `/data/xsy/project_agent_skillrl_transfer`，建议下一步开一个迁移分支，把 DBBench/SQLBench 先接成正式 baseline vs skill 小实验。

## 当前分支判断

- `project_gaia_skillrl/codex/gaia-archv4-runtime-queue`：适合作为当前 actor/critic、skill graph、后台队列和评测框架参考。若在 GAIA repo 内迁移新 bench，建议从这个分支新开 `codex/bench-transfer-sqlbench`。
- `project_gaia_skillrl/main`：比当前分支旧一点，可以作为干净对照，不建议作为迁移起点。
- `project_gaia_skillrl/codex/gaia-bootv3-ab`：保留 bootv3 A/B 固定图实验历史，迁移通用 bench 的价值较低。
- `project_skills-3.18dhc-19.40/batch_method-xsy-26.4.11`：适合作为 EO 旧系统参考，不适合作为新 bench 主线，因为它绑定 Earth-Bench 工具和历史数据修复链路。
- `project_agent_skillrl_transfer`：建议把它初始化成独立 git 项目，或者把其中 adapter 层复制到 GAIA 新分支。它是目前迁移成本最低的实际代码来源。

## Benchmark 候选排序

### 1. SQLBench / AgentBench DB

推荐作为第一迁移目标。

现状：

- `SQLBenchAdapter` 已实现：Spider + BIRD Mini-Dev。
- 数据已落本地：Spider dev `1034` 题，BIRD Mini-Dev SQLite `500` 题。
- smoke 已跑通：`5/5` execution accuracy。
- `AgentBenchAdapter` 已实现 DBBench：`db_dev=60`，`db_standard=300`，`db_out_new=4803`。
- AgentBench DB smoke 已跑通：`3/3`。

适配价值：

- 稳定、离线、可复现，能显著降低 GAIA 里 web/search/test 波动带来的噪声。
- 错误类型可聚类：schema 读错、join path 错、filter 漏、aggregation 错、排序/limit 错、SQL 执行错误。
- skill 可总结成清晰经验：先读 schema 和 sample，再写候选 SQL，执行后用 row shape/answer constraints 验证，失败时只修一个具体错误。
- 适合做 `baseline / boot skill / critic-actor skill` 的小规模快速对照。

迁移工作量：

- 接一个 executor，让模型从 `build_initial_prompt()` 生成 SQL。
- 复用 adapter 的 `score_task()` / `run_task(sql=...)` 做 execution accuracy。
- 先跑 `20` 题 smoke+dev 子集，再跑 `100` 题，最后扩到 Spider dev 或 BIRD Mini-Dev。

主要风险：

- 任务会偏 text-to-SQL，工具调用复杂度低于 GAIA。
- 这类任务依然能体现“结构化经验”和“验证-修复”价值，第一轮足够干净。

### 2. tau2 retail / airline

推荐作为第二迁移目标。

现状：

- `TauBenchAdapter` 已实现。
- 本地 splits：retail `base=114/train=74/test=40`，airline `base=50/train=30/test=20`。
- adapter smoke 已跑通：retail `1/1`，airline `1/1`，通过官方 expected actions replay。

适配价值：

- 比 SQL 更像真正的 agent 环境：有 policy、工具、数据库状态和 reward。
- 很适合测 skill 的“流程经验”：读 policy、确认用户身份、查订单/预订、选择合法工具、写入状态、最后 communication。
- 可分 train/test，适合做 skill 学习和泛化。

迁移工作量：

- 把 tau tools 暴露给当前 executor，或写一个轻量 text tool wrapper。
- 接真实 agent action 解析，再用 upstream tau evaluator 评分。
- 先跑 retail 10 题 + airline 10 题，确认 action JSON 和工具调用稳定性。

主要风险：

- 真实 user simulator / NL assertion 可能需要 LLM judge，成本和稳定性需要单独控。
- 工具调用协议比 SQL 多一层，首轮调通时间更长。

### 3. WebShop text mode

推荐作为中期候选。

现状：

- `WebShopAdapter` 已实现 offline small text env。
- 本地 small 数据：human_small `13`，attr_small `415`，smoke `3`。
- adapter smoke 已跑通：`3/3`。

适配价值：

- 状态-动作闭环明确：search、click、select、buy now。
- skill 可总结成“约束解析、候选筛选、属性核对、购买前验证”。
- 和公开经验学习/skill discovery 文献有交集。

主要风险：

- 当前是 offline small text env；正式 WebShop 原生环境需要重依赖、索引和更多数据准备。
- small 子集太小，第一阶段容易变成 adapter smoke。

### 4. BrowserGym MiniWoB

推荐作为 UI/action smoke 和回归集。

现状：

- `BrowserGymAdapter` 已实现 MiniWoB。
- `.venvs/browsergym` 可用，Chromium/Playwright 已装。
- smoke 已跑通：`5/5`。

适配价值：

- reset/step/reward 很干净。
- 可快速验证状态机 action parser、observation 压缩、step 预算。

主要风险：

- 当前 5 个 MiniWoB 任务太轻，难以体现复杂 skill 经验。
- 更像工程回归集，主论文实验支撑偏弱。

### 5. Terminal-Bench

推荐作为后续高价值候选。

现状：

- `TerminalBenchAdapter` 已实现 metadata 和 workspace dry-run。
- 任务集 `89` 个，smoke 5 题 dry-run 已跑通。
- 真实 checker 当前阻塞：本机 Docker socket permission denied，Harbor command not found。

适配价值：

- 最接近真实多文件、多命令、多验证任务。
- skill 的价值空间很大：读任务、定位文件、写代码/脚本、运行测试、修复失败。

主要风险：

- 环境成本最高。
- Docker/Harbor 权限先解决，才能做正式评测。

### 6. Earth-Bench / EO Bench

推荐保留为诊断集和历史对照。

现状：

- 旧项目有 `248` 题、严格状态机、critic/actor、大量运行记录。
- 已确认 gold/data/tool contract 问题很多。

适配价值：

- 适合验证 tool contract、状态机纪律和历史修复是否回归。

主要风险：

- 数据和工具噪声会持续吞掉 skill 迭代信号。
- 当前已不适合作为下一阶段主力提分 bench。

## 建议执行路线

### 阶段 0：保留 GAIA，另起迁移线

- 新建分支建议：`codex/bench-transfer-sqlbench`。
- 代码来源：从 `/data/xsy/project_agent_skillrl_transfer` 复制 adapter 思路，或直接让该目录成为独立迁移项目。
- 当前 GAIA 结果继续作为负例经验：web 波动、answer policy、step forced、skill 过约束，都写进新 bench 的设计约束。

### 阶段 1：SQLBench 先跑通 baseline vs skill

最小实验：

- Split：`sqlbench smoke + spider_dev 前 20 + bird_mini_dev_sqlite 前 20`。
- 模型：先用当前稳定 executor。
- Skill：写一个 DB 专用 skill，不做复杂图迭代。
- 评分：execution accuracy。
- 记录：正确率、SQL 执行错误率、空答案率、平均 step、repair 次数。

目标：

- 先确认 skill 对 execution accuracy 有正收益。
- 用错误类型给 critic 生成信号：schema、join、filter、aggregation、sort/limit、format。

### 阶段 2：AgentBench DB 做泛化

最小实验：

- `db_dev=60` 全跑，`db_standard` 抽 `100`。
- 用 SQLBench 生成的 DB skill 零样本迁移。
- 再让 critic/actor 针对 AgentBench DB 修一轮，看是否继续增益。

目标：

- 验证 DB skill 不是只贴 Spider/BIRD 题型。
- 对比“同一 skill 跨 DB bench”的迁移信号。

### 阶段 3：tau2 做 agent 化验证

最小实验：

- retail train 抽 `10`，airline train 抽 `10`。
- baseline：无 skill 直接做。
- skill：读 policy、确定目标状态、按工具类型分 read/write、写入前复核 policy。

目标：

- 验证 skill 在工具顺序和 policy 遵循上的收益。
- 这里比 SQL 更能体现状态机优势。

## 推荐结论

下一步建议直接做 `SQLBench + AgentBench DB`。这条线最干净、最快，能把现在 GAIA 里很难分辨的波动降下来；一旦 DB 线上出现稳定收益，再迁到 `tau2 retail/airline` 做更像 agent 的状态-工具闭环。

如果只选一个 branch 起步：从 `/data/xsy/project_gaia_skillrl` 的 `codex/gaia-archv4-runtime-queue` 新开 `codex/bench-transfer-sqlbench`，并把 `/data/xsy/project_agent_skillrl_transfer` 的 adapter 和 manifest 作为第一批迁移源。
