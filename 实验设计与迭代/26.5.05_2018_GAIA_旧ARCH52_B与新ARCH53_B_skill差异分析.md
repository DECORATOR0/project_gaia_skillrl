## 结论

这几份 skill 不是同一图上的小改动。旧 B 属于 ARCH5.2 图：`PROMPT_SOLVE` 独立，`LOCAL_EVIDENCE / VERIFY / REPAIR` 工具权限更宽。新 B1/B2 属于 ARCH5.3 图：新增 `MEDIA_EVIDENCE`，把 `VERIFY` 改成 `VERIFY_AND_ANSWER`，同时明显收窄 `LOCAL_EVIDENCE`、`VERIFY_AND_ANSWER`、`REPAIR` 的工具 allowlist。

这组差异足够解释 test 回落：9B 本来容易长链，新图更强调严格分工和 evidence gate，phase 跳转次数增加，很多旧 B 能在当前 phase 内解决的 parser/media/repair 动作，新 B 必须跳到另一个 phase；在 `max_steps=24 + forced answer` 下，这会提高 forced 占比并压低 forced 子集正确率。

## 规则风格差异

旧 B 全局规则偏短路径：

- 强调“当前 phase 已有足够 support 就 `<ANSWER>`”。
- 对 derived result 要求先 gather raw facts 再去 `COMPUTE/VERIFY`。
- WEB 阶段预算更硬：每个缺失 fact 一个 primary query，加一个 focused alternate。
- REPAIR 允许“一次不同 recovery move”，工具面宽。

新 B1/B2 全局规则偏严格 evidence gate：

- 强调搜索不能替代 evidence，final support 必须来自 extracted source text 或 deterministic computation。
- 强调 repeated failure / no-progress 后切 phase。
- `VERIFY_AND_ANSWER` 进入条件更高：需要 concrete candidate + provenance。
- B2 比 B1 更强调 allowlist literal、native tool parameters、wrapper key 禁止、exact phase ownership。

这些规则本身更干净，但对 9B executor 不一定更好。9B 容易过度遵循，严格 gate 会让它把本可收尾的题继续转相位或补证据，最终撞到 24 步 forced answer。

## B1 与 B2 的差异

B1 和 B2 的 graph signature 基本相同，B2 没有真正改图。B2 的变化集中在文案和规则收束：

- B2 顶层更强调 `<CALL>/<NEXT>/<ANSWER>` 单动作和 literal allowlist。
- B2 `INIT` 用 bullet rules，比 B1 更硬性限制直接回答。
- B2 `WEB_EVIDENCE` 增加 remote video/web-hosted media 的文本证据路径。
- B2 `COMPUTE` 更强调 native `code` 字段、closed-world、不要在计算阶段重开 broad search。
- B2 `REPAIR` 更强调“一次 narrow diagnostic”。

这解释了 B2 dev 略稳一点、test 仍回落：它减少了一些长路径和 token guard，但没有恢复旧 B 的宽 repair/verify 能力，也没有真正改变 graph。

## 对分数的解释

旧 B test `39/82` 的优势，可能来自三点组合：

- `LOCAL/VERIFY/REPAIR` 工具权限宽，减少 phase-scope 错误和跳转。
- `PROMPT_SOLVE` 让 prompt-only/变换类任务先短路径解决。
- WEB 和 REPAIR 预算更直接，避免 9B 围绕证据门槛过度补证。

新 B1/B2 test `32/82`、`31/82` 的回落，主要风险来自：

- media/local/verify 拆分过细，增加平均 step 和 forced answer。
- final verify 工具面过窄，PDF/table/image 候选不能在 final phase 快速复核。
- repair 工具面过窄，parser 和 media blocker 需要回跳。
- 严格 evidence gate 对强模型更规范，对 9B executor 会放大过度谨慎。

## 建议

下一轮不要直接沿用 ARCH5.3 B1/B2 的 allowlist 设计。更合理的 B3 可以保留 ARCH5.3 的清晰 phase 名，但恢复旧 B 的几个关键能力：

- `VERIFY_AND_ANSWER` 加回 `extract_pdf_text/read_table/ocr_image/image_qa`。
- `REPAIR` 加回 local parser、archive、media 工具，至少允许一次 parser/media repair。
- 给 `COMPUTE` 保留 `run_python`，同时允许 LOCAL 在 parser fallback 时直接用一次 `run_python`。
- 保留 `PROMPT_SOLVE` 或在 `INIT -> COMPUTE` 上明确 prompt-only 快速路径，限制最多一次 compute 后进 final。
- 对 WEB 阶段设硬预算：一主一备后必须 `COMPUTE/VERIFY/REPAIR`，减少搜索循环。

核心判断：旧 B 的高 test 分更像“phase 少跳 + repair/verify 工具宽 + 短路径收尾”的收益，新 B 的回落更像“结构更优雅但 9B 执行成本更高”的代价。
