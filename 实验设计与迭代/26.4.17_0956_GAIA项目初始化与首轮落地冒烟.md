# 26.4.17_GAIA项目初始化与首轮落地冒烟

## 1. 背景与本轮目标

`Earth Bench` 线当前先冻结，后续实验主线切到 `GAIA`。本轮的目标很明确：

- 在独立目录 `/data/xsy/project_gaia_skillrl` 下完成新项目初始化。
- 先把单 downstream executor 跑通，确保本地文件、联网检索、基础数值计算都能工作。
- 在此基础上接上 `critic -> actor -> skill writeback -> final eval` 这条最小训练闭环。
- 控制模型消耗，本轮只做单题 level1 冒烟，不做大规模试跑。

另外，当前项目已经单独初始化为一个独立 git 目录，便于后续维护。

## 3. 单题冒烟结果

本轮固定使用同一道 level1 题，控制成本并提高对比可读性。

- 任务 ID：`e1fc63a2-da7a-432f-be78-7c4a95598703`
- 题目核心：从 Wikipedia 取 Moon 的最小 perigee，结合 Eliud Kipchoge 的配速，回答“多少 thousand hours”
- 标准答案：`17`

### 3.1 第一轮：`seqfix`

run 目录：

- `runs/2026/4/2026-4-17/20260417_gaia_smoke_level1_task1_seqfix`

结果：

- `run_summary.json` 结果为 `success_count = 1`
- iteration 和 final eval 都给出了正确答案 `17`

这一轮确认了几件事：

- 整个闭环已经能跑完：`executor -> critic -> actor -> final eval`
- actor 的 skill 修改和写回流程正常
- “thousand hours” 这类尺度词在提示加强后可以被修回来

这一轮也暴露了一个明显问题：

- executor 虽然答对了，phase 行为还不够干净
- 它在 `INIT` 里已经开始做 web retrieval
- 它在 `CONCLUDE` 前还有提前给答案的冲动，只是被 runtime feedback 拉回来了

所以这轮可以视为“答案闭环已通”，还不能当成“executor 行为已经稳定”。

### 3.2 第二轮：`phaseguard`

run 目录：

- `runs/2026/4/2026-4-17/20260417_gaia_smoke_level1_task1_phaseguard`

这一轮的新增改动：

- phase graph 收紧为 `INIT -> GATHER -> ANALYZE -> CONCLUDE`
- 增加 phase-level tool gate
- `INIT` 只允许 `list_dir` 和 `read_json_file`
- `CONCLUDE` 禁止再调工具

结果：

- `run_summary.json` 结果为 `success_count = 0`
- final eval 没有产出最终答案，`max steps reached`

这一轮带来的正面信号：

- `INIT` 的工具约束已经生效
- executor 在 `INIT` 里一旦尝试 `web_search / fetch_url`，会被 runtime 拦下
- phase 语义比第一轮更接近我们想要的形式

这一轮的失败点也很清楚：

- executor 在 `GATHER` 阶段反复抓取 Wikipedia 页面
- 抓取目标不稳定，在 `Moon` 页和 `Lunar distance` 页之间来回
- 没有稳定抽到“题目指定的 exact statistic”
- 没有稳定进入 `run_python` 数值计算
- 最后直接耗尽步数

所以第二轮可以视为“phase 约束更干净”，同时说明当前网页证据抽取能力还不够稳。

## 4. 当前判断

到 2026-04-17 这一刻，可以下的结论有四条：

### 4.1 已经明确打通的部分

- 独立项目目录已经建好
- 独立 git 目录已经初始化
- Hugging Face gated 数据接入已打通
- 单题 GAIA 数据 materialization 已打通
- executor / critic / actor / skill writeback / final eval 闭环已打通
- 本地文件读取、联网搜索、网页抓取、Python 计算这几类基础能力已接通

### 4.2 已经确认有效的约束

- 去掉 `Annotator Metadata` 是必要的，而且已经生效
- phase graph 串行约束是必要的
- `INIT` 的 phase-level tool gate 是必要的，而且已经看到明显效果

### 4.3 当前最主要的短板

- 网页抓取后缺少“定点抽取”能力，容易整页抓、整页绕
- executor 还不够稳定地选择“题目要求的 exact statistic”
- 多步数值题虽然有 `run_python`，模型还没有稳定用起来
- final answer 的形成仍然过度依赖 prompt 约束，缺少更硬的执行辅助

### 4.4 这版项目当前应当怎么定性

我对这版的定性是：

- 工程骨架已经落地
- executor 的最小可运行形态已经有了
- actor / critic 训练闭环已经接上
- 当前还不适合直接扩大任务量
- 下一步先补 executor 的证据抽取和数值收束能力，再进小批量 smoke

## 5. 当前环境还缺的东西

如果只看“最小 GAIA text/web smoke”，当前环境已经够用。

如果看更完整的 GAIA 覆盖，当前还缺这些能力：

- 真正的浏览器自动化能力：当前没有 `playwright / chromium / node`
- 更强的页面内定点抽取能力：当前 `fetch_url` 还是偏整页抓取
- `docx / pptx / 音频 / 视频` 的专用解析工具还没接
- 动态网页、登录态网页、复杂交互网页当前没有覆盖

另外，后面如果要接 gate 相关逻辑，按当前约定继续参考那个 `decorator` 仓库，并沿用当前账户。

## 6. 下一步建议

建议按下面的顺序推进：

1. 先补一个“网页文本内定点抽取”工具，减少整页抓取后反复打转。
2. 把 `run_python` 在多步数值题上的使用再做硬约束，尽量从 prompt 级建议提升到默认动作。
3. 选 `3-5` 道 level1 的纯 text/web 题做小批量 smoke，先看 executor 的稳定性。
4. 等 executor 稳下来，再开始扩到 actor / critic 的真正迭代观察。
