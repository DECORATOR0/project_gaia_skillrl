## forced answer 与 max-step 观察

forced answer 子集的正确率明显低于总体正确率。baseline_dev 的 forced 子集是 `0/20`；BOOT-V3 dev 是 `3/30`；BOOT-V4 dev 是 `4/29`。这说明 max-step 后强制收口确实是低胜率区间，skill 版本里 forced 数量增加，会直接拖低总分。

BOOT skill 让 hit 24 step 变多，主要来自三类成本叠加：

- 阶段路由成本：BOOT-V3 dev 有 `142` 次 `phase_transition`，约 `1.71` step/题；BOOT-V4 dev 有 `135` 次，约 `1.67` step/题。baseline 没有这一项。
- 阶段 allowlist 误用成本：BOOT-V3 dev 有 `116` 次 `tool_call_rejected`、约 `1.40` 次/题；BOOT-V4 dev 有 `111` 次、约 `1.37` 次/题。常见错误是当前阶段不允许 `run_python`、`web_search`、`list_dir`、`read_table`、`extract_pdf_text`，模型仍先调用工具再被 runtime 拒绝。
- 过度取证成本：BOOT-V3 dev 工具调用约 `13.65` 次/题，baseline_dev 约 `10.72` 次/题；BOOT-V4 dev 约 `13.37` 次/题。skill 的“先证据、再验证、再答案”对 9B 会放大保守倾向，尤其在 web 题和图像/表格题上继续 search/fetch/OCR，已有候选的提交被推迟。

同一 dev 集合上，BOOT-V3 相比 baseline 新增 `12` 道 hit 24 step，其中 `5` 道是 baseline 已答对但 skill forced 后答错；BOOT-V4 也新增 `12` 道 hit 24 step，其中 `3` 道是 baseline 已答对但 skill forced 后答错。典型回归包括：

- `2a649bb1-795f-4a01-b3be-9a01868dae73`：baseline `15` step 答对 EC number；BOOT-V3 `25` step forced 后答错，BOOT-V4 `25` step forced 但答对。原因是 web 搜索链过长，V3 没及时收口。
- `2b3ef98c-cc05-450b-a719-711aee40ac65`：baseline `7` step 答对 anagram；BOOT-V3 `25` step forced 后答错，且有 `17` 次阶段拒绝。原因是 prompt-only/compute 题被带进不合适的工具阶段。
- `544b7f0c-173a-4377-8d56-57b36eb26ddf`：baseline `9` step 答对；BOOT-V4 `25` step forced 后答错，且有 `15` 次阶段拒绝。原因是 local/web 路由和工具 allowlist 反复不匹配。
- `08cae58d-4084-4616-b6dd-dd6534e4825b`：baseline `10` step 答对；BOOT-V3 `25` step forced 仍答对，BOOT-V4 `25` step forced 答错。原因是简单 web/finance 题被过度搜索，延迟到 max-step。

对 “把 max_executor_steps 拉到 32 或 40 能否反超 baseline” 的判断：只调大步数有机会减少 forced answer 数，但按现有 trace 看，反超 baseline 不稳。BOOT-V3/BOOT-V4 dev 当前都是 `40/83`，要超过 baseline_dev 的 `43/83` 至少需要净增 `4` 题。V3 的 forced wrong 有 `27` 题，其中 `5` 题是 baseline 已答对的回归；V4 的 forced wrong 有 `25` 题，其中 `3` 题是 baseline 已答对的回归。若只是把 24 放宽到 32/40，必须让这些 forced wrong 中至少 `15%` 左右稳定转正，同时不能让原本 forced 已答对或非 forced 已答对的题继续拖错。当前 forced 子集正确率只有 `10.0%` 到 `13.8%`（dev），说明纯加步数的收益大概率不足以稳定反超。

更可取的下一版实验是同时做两件事：把 `max_executor_steps` 提到 `32` 作为 A/B 小试；再给 skill/runtime 增加早停和降拒绝约束，例如 prompt-only/compute 明显可解时直接进 `COMPUTE/PROMPT_SOLVE`，阶段拒绝后强制转入允许该工具的 phase，连续 web/fetch 失败或已有候选时进入 VERIFY 并允许提交答案。这样能保留长题的额外预算，同时压住 9B 的过度遵循和过度取证。

## baseline_dev 平均步数拆解

baseline_dev 的 `avg step = 12.0` 主要由长尾 forced 题抬高。`81` 道落盘题的 step 分布是：中位数 `8`，最小 `1`，最大 `25`；非 forced 的 `61` 题平均 `7.70` step，答对题平均 `7.47` step，错题平均 `17.08` step。`20` 道 forced 题全部走到 `25` 个 trace step，且 forced 子集正确率为 `0/20`。

step 直方图：

```text
1:2, 2:6, 3:8, 4:6, 5:6, 6:6, 7:5, 8:4, 9:1, 10:2,
11:3, 12:2, 13:1, 15:1, 17:1, 18:3, 20:1, 23:2, 24:1, 25:20
```

baseline 的慢题集中在失败长尾。forced 题的主导工具分布是：`web_search` 主导 `9` 题、`fetch_url` 主导 `6` 题、`run_python` 主导 `3` 题、`read_file/list_dir` 主导 `2` 题。forced 子集内工具调用合计为 `web_search 214`、`fetch_url 123`、`run_python 51`，说明长尾主要集中在 web 取证和少数计算/本地文件循环。

典型异常和低效模式：

- `05407167-39ec-4d3a-a234-73a9120c325d`：`22` 次 `web_search`、`2` 次 `fetch_url`，一直围绕 Replit/VSCode blog 改 query，最终 forced 答 `Ctrl+H`，gold 是 `Format Document`。这是检索无收敛停止条件。
- `33d8ea3b-6c6b-4ff1-803d-7e270dea8a57`：`21` 次 `fetch_url`，反复拉取同一个 Wayback/Wikipedia 页面并逐步加 `max_chars`，最终 forced 答 `1`，gold 是 `2`。这是 fetch 截断/页面链接解析没有转入结构化解析。
- `56db2318-640f-477a-a82f-bc93ad13e882`：`24` 次 `run_python`，多次改公式假设，最终 forced 答 `5, 3`，gold 是 `7,9`。这是计算题缺少“穷举失败后停止并系统重建约束”的机制。
- `7dd30055-0198-452e-8c25-f73dbe27dcb8`：反复在绝对路径和相对路径之间读 PDB，`read_file` 失败 `7` 次，最终 forced 答 `150`，gold 是 `1.456`。这是本地文件路径错误没有被 runtime 记忆为禁用路径。
- `9b54f9d9-35ee-4a14-b62f-d130ea00317f`：第 `4` 到 `24` 步都是 `unrecognized_action`，模型已有中间信息但连续没有输出合法 `<CALL>` 或 `<ANSWER>`，最终 forced 答错。这是 tag/parser 恢复失败。

当前 baseline 的“12 步”可以理解为两层问题：正常路径约 `8` 步，失败路径会被 `max_executor_steps=24` 截断后追加一次 forced answer，形成 `25` step 记录。若要压低平均步数并提高分数，优先处理长尾停止条件和重复调用拦截：同 query/同 URL 重复阈值、fetch 截断后改用结构化抽取或 Python 解析、同一工具连续失败后强制换策略、`remaining_steps<=4` 时禁止继续 broad search 并要求提交候选。
