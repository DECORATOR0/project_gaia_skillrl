## 1. 当前结论

OfficeQA 对小模型的主要压力可以拆成五条轴：

1. 数据 split：`full=246`，`pro=133`。`pro` 是 `hard` 子集；`full` 包含 `hard=133` 和 `easy=113`。
2. 评分容错：`exact/0%`、`0.1%`、`1%`、`5%`、`10%`，以及 EvoSkill/OfficeQA 风格的 `multi_tolerance`。
3. 材料形态：原始 PDF、parsed JSON、transformed TXT。
4. 证据访问：只给 full corpus、给候选 docs/top-k、直接给 oracle source files/pages。
5. harness/model/tools：Claude Code/Codex/Gemini CLI 等 coding-agent harness，与本地小模型 ReAct wrapper 的能力差别很大。

我们 remote132 c8 的 `Qwen3.5-9B ReAct` 结果是：

- 口径：`full / exact0 / transformed TXT / evoskill_corpus / Qwen3.5-9B-local ReAct`
- 结果：`8/246 = 3.25%`
- 运行完成：8 个 shard summary 总计 `task_count=246`，`success_count=8`，`solver_error_count=4`，`missing_prediction_count=0`
- 结果文件：`/data/xsy/project_agent_skillrl_transfer/runs/benchmarks/officeqa/qwen35_9b_evoskill_react_exact0_full_shard{0..7}_20260506_1957_remote132_c8.json`

这个 3.25% 主要说明小模型在 `evoskill_corpus` 口径下承担了完整证据定位压力。当前 ReAct wrapper 的检索和读表能力弱，导致大量题在定位文件、定位表格、定位月份/口径时已经偏离。它不能直接代表“方法本身无效”。

## 2. OfficeQA 数据规模

本地 corpus metadata：

- 文件：`/data/xsy/project_agent_skillrl_transfer/data/benchmarks/officeqa/corpus/corpus_metadata.json`
- transformed TXT 数量：`697`
- transformed TXT 总大小：`383,162,413 bytes`
- 官方 README 同时提供原始 PDF、parsed JSON、transformed TXT 三种材料：
  - PDF：约 `696` 个，约 `20GB`
  - parsed JSON：约 `600MB`
  - transformed TXT：LLM/agent consumption 更友好

任务规模：

- `officeqa_full.csv`：246 题
  - hard：133
  - easy：113
- `officeqa_pro.csv`：133 题
  - 全部 hard

每题实际需要的 gold source files 数量：

```text
full 246:
  1 file : 126 tasks
  2 files: 68 tasks
  3 files: 31 tasks
  4 files: 13 tasks
  5 files: 7 tasks
  12 files: 1 task
  avg=1.846, median=1, max=12

pro 133:
  1 file : 68 tasks
  2 files: 38 tasks
  3 files: 14 tasks
  4 files: 9 tasks
  5 files: 4 tasks
  avg=1.820, median=1, max=5
```

所以路由问题的核心规模是：从 `697` 个 TXT 中找到通常 `1-2` 个真正需要的 bulletin 文件，然后在这些文件中找到表格、行列、月份、修订口径。

## 3. 路由标签与几种证据访问方式

OfficeQA CSV schema 中包含：

- `source_docs`：FRASER/Treasury Bulletin 原始页面 URL
- `source_files`：对应 parsed/transformed 文件名，例如 `treasury_bulletin_1941_01.txt`

这些字段是 gold evidence / gold route 标签。它们可以用于分析、诊断和 oracle setting。

建议固定以下术语：

1. `full corpus`
   - 只给问题和 corpus 目录。
   - agent 需要自己用 file search、vector search、bash/read 等工具找证据。
   - 原版 OfficeQA agent headline 更接近这一档。

2. `soft routing / candidate docs / retrieval_topk`
   - 系统先做检索，从 697 个 TXT 中给出 top-k 候选文件或候选窗口。
   - 模型再从候选中读表和计算。
   - 适合小模型，因为可以把“文档路由”和“表格推理”拆开测。

3. `oracle_source_files / oracle pages`
   - 直接把每题的 gold source file、source snippet、PDF page 或 parsed page 给模型。
   - 主要测读表、计算和答案格式。
   - 这是诊断上界，不适合作为与 full-corpus headline 的直接比较。

## 4. 原版 OfficeQA 是怎么搞的

OfficeQA 官方技术报告把任务定义为 end-to-end grounded reasoning：文档解析、信息检索、定量分析都算在内。

官方 README 明确数据集列包含 `source_docs` 和 `source_files`，但 agent baseline 并不总是把这些 gold 标签作为输入。技术报告中同时报告以下 setting：

1. LLM baselines
   - `Prompt Only`：只给问题。
   - `Web Search Enabled`：允许模型用 web search 找 Treasury Bulletin 信息。
   - `Oracle PDF Page(s) + Web Search`：直接给需要的 oracle PDF page(s)。
   - `Oracle Parsed Page(s) + Web Search`：直接给 oracle parsed page(s)。

2. Agent baselines
   - `Full Corpus` vs `Oracle Page(s)`：用于隔离 retrieval bottleneck。
   - `PDF` vs `Parsed Documents`：用于隔离 document parsing bottleneck。
   - Agent prompt 要求使用 `../officeqa_corpus/` 下的 Treasury docs，并用 file system search 查找，不要直接读完整文件。

3. Search tool ablation
   - file search：`grep/sed/cat/ls` 或 `fs_search/fs_read`
   - vector search
   - contextual vector search
   - file search + contextual vector search

技术报告结论之一是：search/retrieval 是关键瓶颈；对弱一些的模型，retrieval 质量的影响更大。

## 5. EvoSkill 的 OfficeQA 口径

EvoSkill 论文中的 OfficeQA 配置：

- dataset：OfficeQA full 246
- model/harness：Claude Code + Opus 4.5
- train sizes：12 / 24 / 36
- validation：17
- test：剩余 held-out
- evolution：1.5 epochs
- scorer：OfficeQA fuzzy / multi-tolerance，同时报告 exact 结果
- baseline exact：约 60.6%
- skill 后 exact：约 67.9%

EvoSkill repo 的 `examples/officeqa` 是 demo：

- `data/officeqa_sample.csv`：10 题
- `data/treasury_bulletins/`：9 个 source documents
- example config 当前展示 `harness.name = "claude"`，`model = "anthropic/claude-sonnet-4-6"`，`data_dirs = ["data/treasury_bulletins"]`

需要区分：

- 论文实验：full OfficeQA + Claude Code/Opus 4.5。
- 仓库 demo：10 题、9 文档，用于演示 EvoSkill 流程。

EvoSkill 对齐口径的核心是：agent 拿到 `question + data_dirs/corpus`，没有每题 oracle `source_files/source_docs/source_text`。强模型和 coding-agent harness 能自己用读文件、搜索、脚本计算完成证据定位。

## 6. 我们 remote132 c8 为什么会低

我们 remote132 c8 的配置与 EvoSkill 对齐了一部分：

- `input_mode=evoskill_corpus`
- 隐藏 `source_files/source_docs/source_text`
- 使用 transformed TXT corpus
- 使用 official exact scorer，`tolerance=0.0`
- split 使用 `full=246`

但它没有对齐 EvoSkill/OfficeQA 原版强 agent harness：

- 模型：`Qwen3.5-9B-local`
- solver：`scripts/solver_officeqa_evoskill_react.py`
- 工具：`smart_search/read/calc`
- 轮数：`OFFICEQA_REACT_MAX_ROUNDS=8`
- tool 输出截断：`OFFICEQA_REACT_TOOL_MAX_CHARS=18000`
- 候选文件 cap：`OFFICEQA_RETRIEVAL_MAX_CANDIDATE_DOCS=30`
- 最终给模型的片段：`OFFICEQA_RETRIEVAL_TOP_CHUNKS=8`，`WINDOW_LINES=24`，`PER_DOC_WINDOWS=4`

实际含义：

- 检索先从 697 个 TXT 中最多保留 30 个 candidate docs。
- 再从这些候选中抽 top 8 个窗口/chunks 给模型。
- 模型看到的是有限截断片段，不是 30 个完整文件。
- 小模型还要自行决定读哪个文件、读哪个窗口、怎么加总、怎么归一化单位。

因此 8/246 更像是“source-hiding + 小模型粗检索 ReAct”的失败结果。它对我们有价值，因为它暴露了小模型直接扛 full corpus routing 时的瓶颈。

## 7. 后续合理实验路线

当前目标是证明“我们的方法能让小模型在这个 bench 上生效”。合理做法是先冻结可解释的 OfficeQA 小模型环境，再接方法。

建议分三档 baseline：

1. `oracle_source_files + small model`
   - 直接给 gold source file/snippet。
   - 目标：测证据已定位后，小模型读表、计算、输出格式能到什么水平。
   - 如果这一档很低，先补读表、计算和 answer normalization。

2. `retrieval_topk + small model`
   - 不给 gold source，但由确定性 retrieval 给候选文件/窗口。
   - 目标：测 routing recall 和 table locator。
   - 核心指标：gold source file 是否进入 top-k，例如 top5/top10/top30 recall。

3. `evoskill_corpus + small model agent`
   - 最终对齐口径。
   - 只给 corpus 目录，agent 自己找。
   - 这档用于最终报告，但不适合一开始直接拿来判断方法有效性。

建议再固定报告格式：

```text
split / scorer+tolerance / material_format / evidence_access / harness+model+tools
```

例如：

```text
full / exact0 / TXT / evoskill_corpus / Qwen3.5-9B ReAct
pro / multi_tolerance / TXT / retrieval_top30 / Qwen3.5-9B ReAct
full / exact0 / TXT / oracle_source_files / Qwen3.5-9B
```

## 8. 小模型环境适配建议

可以增强工具，但要保证 test 时不读取 gold `source_files`。合理的工具包括：

1. corpus/file router
   - 从问题抽年份、月份、财政年度、部门/表名/指标。
   - 返回候选 bulletin 文件和理由。
   - 输出 top-k 候选时记录 recall 指标。

2. table locator
   - 对候选文件建立 page/section/table title/line index。
   - 返回表标题、页码、行号窗口、列名候选。

3. read window
   - 稳定读取 `file + start_line + num_lines`。
   - 保留源文件名、行号、表名或 section。

4. calc/python
   - 做 sum、mean、geometric mean、regression、percent change、standard deviation、rounding。
   - 让模型把数据抽取和计算分开。

5. answer normalizer
   - 处理 comma、million/billion、percent、bracket/list、Unicode minus、rounding。
   - 输出 scorer-friendly final answer。

这些工具相当于把 Claude Code/Codex 原生 shell/file/python 能力显式工具化给小模型。只要不使用每题 gold `source_files` 作为输入，就仍然保留 full-corpus/soft-routing 口径。

## 9. 建议的近期验收指标

近期先不要直接追 EvoSkill Claude 的 60%+。更合理的阶段目标：

1. `oracle_source_files + Qwen3.5-9B`
   - 验证证据已定位后的读表/计算上限。
   - 输出 easy/hard/pro split。

2. `retrieval_topk` recall
   - 统计 top5/top10/top30 是否覆盖 gold source_files。
   - 如果 top30 recall 不高，先改 retrieval。

3. `retrieval_topk + Qwen3.5-9B`
   - 目标从 3.25% 提到一个可解释 baseline，例如 10-20%。
   - 同时记录错误类别：路由错、表格错、月份/口径错、计算错、格式错、timeout。

4. 方法接入
   - 在同一套工具和 scorer 下比较：
     - base small model
     - base + 手写 OfficeQA skill
     - 我们的方法生成/演化 skill
     - 可选强模型 reference

最终对外报告时，headline 建议用 `full=246`，同时给 `pro=133` 和 easy/hard breakdown。`pro` 适合作为 hard subset 诊断。
