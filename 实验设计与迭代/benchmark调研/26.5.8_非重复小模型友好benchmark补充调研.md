## 2. 直接结论

### 第一批新增优先池

1. `InterCode SQL/Bash/Python`
2. `FinQA / TAT-QA / DROP`
3. `ToolQA`
4. `DS-1000`
5. `HotpotQA + FEVER`

这五类和上一份候选错开程度较高，同时能承接当前方法。它们的共同点是：输入规模可控、评分清楚、训练/验证切分成熟、工具面可以压成有限集合。`InterCode` 和 `ToolQA` 最像 tool/agent；`FinQA/TAT-QA/DROP` 最像 OfficeQA 的轻量替代，没有 697 文件路由瓶颈；`DS-1000` 是代码执行/repair 方向的干净候选；`HotpotQA/FEVER` 可直接复用 ReAct 传统设置，适合解释“skill 改善检索-推理-验证流程”。

### 第二批补位池

`MuSiQue / 2WikiMultiHopQA / IIRC`、`API-Bank`、`LiveCodeBench lite/self-repair`、`HumanEval/MBPP`、`GSM8K/SVAMP/TabMWP/MATH500`、`ProofWriter/PrOntoQA/FOLIO`、`TabFact` 都能保留。它们有一个共同问题：要么方法形态弱一些，要么小模型 frozen 记录需要本机 smoke 验证，要么太容易被质疑为常规 benchmark 或污染风险高。

### 暂缓

`FanOutQA`、大型开放域 RAG、ParseBench/EnterpriseRAG 一类企业级长文档 benchmark 暂缓。它们能体现检索能力，但容易把主要风险放到索引、长上下文、证据路由和 judge 上，和 OfficeQA full corpus 的小模型风险相似。

## 3. 详细分析

### 3.1 InterCode SQL/Bash/Python

**Benchmark 在做什么**

InterCode 是交互式代码 benchmark。题目给自然语言目标，agent 需要和软件系统交互，例如用 SQL 查数据库、用 Bash 操作文件/命令、用 Python 解释器写代码并观察执行反馈。官方项目页写明它包含 `IC-Bash`、`IC-CTF`、`IC-Python`、`IC-SQL`、`IC-SWE` 五类环境，主指标是 success rate。

**哪些论文或系统跑过**

- `InterCode: Standardizing and Benchmarking Interactive Coding with Execution Feedback`，2023，NeurIPS Datasets & Benchmarks，原始 benchmark。
- `StateFlow: Enhancing LLM Task-Solving through State-Driven Workflows`，2024，在 InterCode SQL 和 ALFWorld 上比较 ReAct，报告 StateFlow 相比 ReAct 有更高成功率和更低 cost。这个和当前方法里的“状态图/skill 控制流程”很贴。
- Lemur、CodeLlama、StarChat、Vicuna 等模型也出现在 InterCode leaderboard。官方页能看到 Vicuna-13B、StarChat-16B 在 Bash/SQL 上都有非零结果。

**普通 agent 工作流**

1. 读任务目标。
2. Inspect 数据库 schema、当前目录、文件内容或 Python 对象。
3. 生成 SQL / shell command / Python snippet。
4. 执行并读 stdout/stderr。
5. 根据错误或输出 shape 做修复。
6. 提交最终 answer 或完成环境目标。

**适配当前方法**

适配度很高。当前 skill 可以写成：

- SQL：先读 schema/sample，再写 SQL，执行后检查 row shape、单位、排序和 limit。
- Bash：先 `ls/find/head/wc`，再构造命令，避免大范围 destructive 操作，最后用目标输出验证。
- Python：先复现输入输出，再写最小函数，运行测试，按 traceback 修复。

critic 很容易把错误归到 syntax、wrong file/schema、wrong command、wrong output format、premature submit 等类别。

**小模型可行性**

R4 评为 `Y/P`。公开 leaderboard 有 13B/16B 开源模型非零，且 9B thinking 搭配执行反馈有机会获得可调 baseline。它的任务比 SWE-bench 和 Terminal-Bench 更短，环境也轻很多。

**复现难度**

中低。`IC-SQL` 和 `IC-Bash` 最适合先跑；`IC-SWE` 暂时放后面，因为会接近 SWE-bench 的长 repo 风险。

**建议用法**

第一轮只跑 `IC-SQL 20 + IC-Bash 20`。若 baseline 非零，再做 boot skill；`IC-Python` 可以作为第二轮加进来。

### 3.2 FinQA / TAT-QA / DROP：OfficeQA 的轻量替代

**Benchmark 在做什么**

这三类都属于“给定局部上下文，做数值/离散推理”的 QA：

- `FinQA`：给金融报告中的文本和表格，回答需要数值推理的问题。官方页说明它有约 2.8k financial reports、8k QA pairs、reasoning programs 和 supporting facts。
- `TAT-QA`：表格+文本混合金融 QA，GitHub README 写明包含 16,552 questions、2,757 hybrid contexts。
- `DROP`：段落阅读理解中的离散推理，AWS Open Data 页写明有 96k QA、6.7k paragraphs，train/dev/hidden test 切分清楚。

**哪些论文或系统跑过**

- `FinQA: A Dataset of Numerical Reasoning over Financial Data`，EMNLP 2021。
- `TAT-QA: A Question Answering Benchmark on a Hybrid of Tabular and Textual Content in Finance`，ACL 2021。
- `DROP: A Reading Comprehension Benchmark Requiring Discrete Reasoning Over Paragraphs`，NAACL 2019。
- 后续大量 numerate QA、program-of-thought、calculator-augmented reasoning、table reasoning 工作会把这几类作为标准测试集。

**普通 agent 工作流**

1. 读问题，抽目标指标、年份、实体、单位。
2. 从给定 context/table 中找相关数字。
3. 调 calculator/python 做加减乘除、百分比、排序、计数。
4. 检查单位、rounding、符号和答案格式。
5. 输出短答案。

**适配当前方法**

适配度高。它们可以直接承接当前 GAIA/OfficeQA 里的“读表、抽数、算数、短答案格式”skill，但去掉了 OfficeQA full corpus 的全局路由问题。也就是说，若 OfficeQA 卡在从 697 文档中找文件，这一组能单独验证“找到证据以后，9B 是否能稳定读表和计算”。

**小模型可行性**

R4 评为 `Y/P`。上下文通常是单段或单表，冻结 9B thinking + python/calc 应该能非零，且错误可调。`DROP` 更容易，`FinQA/TAT-QA` 更贴近 OfficeQA 的金融表格形态。

**复现难度**

低到中。数据和 scorer 都成熟，依赖主要是 JSON 读取和答案归一化。TAT-QA 官方环境偏旧，但可只复用 dataset 和 metric。

**建议用法**

优先顺序：`DROP smoke 100` 验证 pipeline，`FinQA 100` 验证金融数值推理，`TAT-QA 100` 验证表格+文本混合。若三者都跑，文中可以把它们统一成“local numeric QA suite”。

### 3.3 ToolQA

**Benchmark 在做什么**

ToolQA 是专门测 LLM 是否能用外部工具回答问题的 QA benchmark。项目页说明它提供 13 个 specialized tools，并尽量减少 benchmark data 和模型预训练数据重叠。每题包含 question、answer、reference corpora 和工具列表。

**哪些论文或系统跑过**

- `ToolQA: A Dataset for LLM Question Answering with External Tools`，NeurIPS 2023 Datasets and Benchmarks。
- 后续 tool-use、RAG、program-of-thought 类工作经常把 ToolQA 作为工具使用能力测试。

**普通 agent 工作流**

1. 读问题，判断需要哪类工具。
2. 对 corpus/database/graph 调相应工具。
3. 多步组合工具输出。
4. 最终生成短答案。

**适配当前方法**

适配度很高。当前方法本身就是 skill 注入到 tool executor，ToolQA 可以直接测 skill 是否会改进工具选择、调用顺序和验证规则。skill 内容可以写得很具体：先分类问题类型，再调用工具，工具结果必须被引用到最终答案。

**小模型可行性**

R4 评为 `P`。它理论上比 AppWorld/API-Bank 更小、更 QA 化，9B 有希望。但公开 small frozen 9B 记录需要本机 smoke 验证。这个 benchmark 的关键在于“能否在工具列表和 corpus schema 中选对路径”，大规划压力相对小。

**复现难度**

中。数据和工具需要统一包装，但远低于真实 APP/API 服务。若工具全本地化，成本可控。

**建议用法**

先跑 `easy 50 + hard 50`，只开放最小工具集合。若 baseline 有 20%-40% 量级信号，就非常适合做 boot/actor skill。

### 3.4 DS-1000

**Benchmark 在做什么**

DS-1000 是数据科学代码生成 benchmark。官方页说明它有 1000 个来自 StackOverflow 改写的数据科学问题，覆盖 NumPy、SciPy、Pandas、TensorFlow、PyTorch、Scikit-learn、Matplotlib 七个库，并用 test cases 与 API/关键词约束做可靠自动评估。

**哪些论文或系统跑过**

- `DS-1000: A Natural and Reliable Benchmark for Data Science Code Generation`，2022/ICML 2023 相关。
- 后续数据科学 code generation、program repair、code-agent 工作常用它作为比 HumanEval/MBPP 更实际的代码 benchmark。

**普通 agent 工作流**

1. 读题和给定代码上下文。
2. 判断需要的库/API。
3. 生成插入代码。
4. 运行测试。
5. 根据 traceback、shape mismatch、数值误差修复。

**适配当前方法**

适配度高。它天然适合 ReAct + code execution + repair。skill 可以按库拆分：Pandas 的 index/groupby/merge 检查，NumPy 的 shape/broadcast 检查，Matplotlib 的 object/axis 检查，Scikit-learn 的 fit/transform 检查。

**小模型可行性**

R4 评为 `Y/P`。7B/9B 普通模型在泛数据科学库上可能吃力，但 Qwen3.5-9B thinking 加执行反馈会有非零。若换 Qwen Coder 7B/14B 则更稳；本项目当前约束是 executor 不改参数量、不微调，所以建议先用 9B thinking 做小子集 smoke。

**复现难度**

中。主要成本来自 Python scientific deps 和 sandbox 稳定性。比 SWE-bench 轻很多，评分更清楚。

**建议用法**

先按库各抽 10 题，共 70 题。只看 pass@1 和 repair-after-error 成功率。若 Pandas/NumPy 子集有增益，就保留 DS-1000 作为代码方向主线。

### 3.5 HotpotQA + FEVER

**Benchmark 在做什么**

`HotpotQA` 是多跳 QA，问题需要跨多个 Wikipedia paragraph 找支持事实。`FEVER` 是事实核验，输入 claim，系统需要找 evidence 并判断 Supported / Refuted / NotEnoughInfo。

**哪些论文或系统跑过**

- `HotpotQA: A Dataset for Diverse, Explainable Multi-hop Question Answering`，EMNLP 2018。
- `FEVER: a large-scale dataset for Fact Extraction and VERification`，NAACL 2018。
- `ReAct: Synergizing Reasoning and Acting in Language Models`，ICLR 2023，同时跑 HotpotQA 和 FEVER，并用 simple Wikipedia API 做 action-observation 交互。

**普通 agent 工作流**

1. 读问题或 claim。
2. 拆成实体和子问题。
3. 调 Wikipedia search / lookup / retrieval。
4. 累积 evidence。
5. 做短答案或三分类。
6. 输出 answer/label 和 supporting facts。

**适配当前方法**

适配度高。当前 GAIA 搜索/验证经验可以直接迁移。skill 能约束模型先找实体页、再找桥接实体、最后用证据验证答案，避免凭常识答。FEVER 还可以要求“没有证据时输出 NEI”，这对 skill 的保守性有价值。

**小模型可行性**

R4 评为 `P/Y`。如果给本地 retrieval 或简单 wiki API，9B 能有非零；若开放网页搜索并要求复杂多跳，稳定性会下降。它的问题比 OfficeQA full corpus 更干净，且 ReAct 已经提供传统工作流参照。

**复现难度**

中。难点在 Wikipedia 索引和 evidence scorer。若只做 HotpotQA distractor setting 或提供 candidate paragraphs，复现很快；open-domain 版本更耗检索工程。

**建议用法**

先跑 `HotpotQA distractor dev 200` 和 `FEVER dev 200`。避免先上全开放搜索。主分数用 EM/F1 或 FEVER score，辅助记录 supporting fact 命中。

### 3.6 MuSiQue / 2WikiMultiHopQA / IIRC

**Benchmark 在做什么**

这一组是更系统的多跳 QA：

- `MuSiQue` 用 single-hop question composition 构造多跳问题，强调连接推理。
- `2WikiMultiHopQA` 用 Wikipedia/Wikidata 构造多跳 QA，并提供 reasoning steps。
- `IIRC` 要求模型识别原始段落信息不够，再去找补充上下文。

**哪些论文或系统跑过**

- `MuSiQue: Multi-hop Questions via Single-hop Question Composition`，TACL 2022。
- `Constructing A Multi-hop QA Dataset for Comprehensive Evaluation of Reasoning Steps`，COLING 2020，即 2WikiMultiHopQA。
- IIRC 是 EMNLP 2020。
- retrieval/decomposition、self-ask、graph-RAG、multi-hop reranking 论文经常使用这些数据。

**适配当前方法**

适配度中高。skill 可控制“问题分解 -> 子问题检索 -> 证据合并 -> 最终答案”的流程。它比 HotpotQA 更能测 multi-hop discipline，也更容易暴露 9B 的链式推理弱点。

**小模型可行性**

R4 评为 `P`。这一组比 HotpotQA/FEVER 更难，适合作第二批。若先给 gold paragraphs 或 top-k retrieval，9B 有希望；open-domain 版本很可能变成检索瓶颈。

**复现难度**

中。数据和 scorer 可拿，但检索策略要明确。建议不要一开始跑 fan-out 或 4+ hop。

**建议用法**

先用 `2-hop / answerable / gold-context` 子集做 100-200 题，再切 top-k retrieval。用它验证 skill 是否真的能约束分解和证据合并。

### 3.7 API-Bank

**Benchmark 在做什么**

API-Bank 是 tool-augmented LLM benchmark。arXiv 摘要说明它有 runnable evaluation system、73 个 API tools、314 个 tool-use dialogues、753 个 API calls，用于测 planning、retrieval、API calling。

**哪些论文或系统跑过**

- `API-Bank: A Comprehensive Benchmark for Tool-Augmented LLMs`，EMNLP 2023。
- 原论文训练了 Lynx，比较 Alpaca/GPT 系列工具使用能力。

**适配当前方法**

适配度高。它的形态就是工具选择、API 参数、调用顺序和对话状态。skill 能写入 API selection、参数校验、调用前后状态核对、错误重试。

**小模型可行性**

R4 评为 `P/Y`。它不像 AppWorld 那样有大量 app 状态和代码执行复杂度，API 数量也比 BFCL-v4 的完整函数调用评测更小。问题在于部分结果来自训练型工具模型，training-free 9B 仍要先 smoke。

**复现难度**

中。需要确认官方 runnable API 是否全本地可用，以及评分里人工评价占比。如果主分数依赖人工/LLM judge，要拆出自动子集作为首轮。

**建议用法**

只跑自动评分子集，先做 50 dialogue smoke。若 API search/selection 分数可拆解，就进入 skill 迭代。

### 3.8 LiveCodeBench lite / HumanEval / MBPP

**Benchmark 在做什么**

这一组是代码生成与代码修复：

- `LiveCodeBench` 官方 GitHub 说明它持续收集 LeetCode、AtCoder、CodeForces 新题，包含 code generation、code execution、test output prediction、自修复等场景，release_v6 有 1055 problems。
- `HumanEval` 和 `MBPP` 是更老、更小的代码生成基准。

**哪些论文或系统跑过**

- `LiveCodeBench: Holistic and Contamination Free Evaluation of Large Language Models for Code`，2024。
- `Evaluating Large Language Models Trained on Code`，2021，HumanEval。
- MBPP 是 Google Research 的 Mostly Basic Python Problems。

**适配当前方法**

适配度高，但叙事上偏 coding benchmark。skill 可以控制“先读题 -> 写函数 -> 运行样例/隐藏测试近似 -> repair traceback”。LiveCodeBench 的 self-repair 场景尤其贴合当前 actor/critic 的修复逻辑。

**小模型可行性**

R4：`HumanEval/MBPP` 为 `Y`，`LiveCodeBench` 为 `P`。Qwen3.5-9B thinking 普通 coding 题可打，但 LiveCodeBench 最新题和竞赛题难度高，应先跑 lite/easy 子集。

**复现难度**

HumanEval/MBPP 低，LiveCodeBench 中。LiveCodeBench 的环境更现代，污染风险更低；HumanEval/MBPP 容易被质疑过熟。

**建议用法**

若需要代码方向 benchmark，优先 `LiveCodeBench code_generation_lite easy subset`，再用 HumanEval/MBPP 作为回归 smoke。

### 3.9 GSM8K / SVAMP / TabMWP / MATH500

**Benchmark 在做什么**

数学和表格数学推理。GSM8K 官方 README 写明它有 8.5K grade school math word problems，7.5K train、1K test，答案最终数值在 `####` 后；官方还提供 calculator annotation 思路。

**适配当前方法**

R1 只是 `P/Y`。这些任务可以接 calculator/python tool，也能注入 skill，但 agent 形态弱。它们适合作低成本回归，验证 skill 是否能改善“拆题、计算、格式化答案”。

**小模型可行性**

R4 为 `Y`。9B thinking 能打，且工具化后更稳。

**主要风险**

太常规、太窄，论文叙事不够 agent。适合补充，不适合当三个主 benchmark 之一，除非主线急需一个低成本稳定提分点。

### 3.10 ProofWriter / PrOntoQA / FOLIO

**Benchmark 在做什么**

逻辑推理 benchmark。输入自然语言规则和事实，输出结论是否成立，或给出证明路径。`FOLIO` 提供自然语言和一阶逻辑公式，`PrOntoQA` 是合成演绎推理，`ProofWriter` 有规则、事实和 proof tree。

**哪些论文或系统跑过**

- `FOLIO: Natural Language Reasoning with First-Order Logic`。
- `Language Models can be Deductive Solvers`、`Logic-LM`、`ProofSketch` 等都把这类 benchmark 用于“LLM + symbolic solver”评测。

**适配当前方法**

适配度中。skill 可以指导模型把自然语言转成 Prolog/Z3/FOL，再调用 solver，最后把 solver 结果映射回 label。这个能展示 tool discipline，但工程上需要写 formalization wrapper。

**小模型可行性**

R4 为 `P`。如果要求 9B 自己纯自然语言推理，稳定性一般；如果把主要推理交给 Z3/Prolog，9B 只做翻译和验证，成功率可能有可调空间。

**建议用法**

只作为第二批。先做 `ProofWriter depth<=2/3` 或 `PrOntoQA easy`，避免一开始做复杂 formal proof。

## 4. 本轮不建议新增为首批的项

| 候选 | 暂缓原因 |
|---|---|
| `FanOutQA` | 多文档 fan-out 检索对小模型和检索系统压力大，容易复刻 OfficeQA full corpus 的路由风险。 |
| `Natural Questions / TriviaQA / PopQA / SimpleQA` | 小模型可打，但方法接入弱，容易变成普通 RAG/短答评测；适合做检索回归，不适合主提分实验。 |
| `ToolBench / StableToolBench` | 工具数量和 API 模拟复杂度较高，且常和训练型 ToolLLaMA 绑定；若要用，优先 API-Bank/ToolQA。 |
| `MiniHack / Jericho / TextWorld games` | 任务很 agent，但动作空间和环境调参会吞时间；上一份已有 ALFWorld/ScienceWorld 后，这类文本游戏增量价值较低。 |
| `ParseBench / EnterpriseRAG-Bench` | 近期且真实，但核心难点是文档解析/大规模检索，和当前 small frozen executor 的硬门槛冲突。 |

## 5. 建议的新增 smoke 顺序

### Smoke 0：InterCode

- `IC-SQL 20`：先测 schema inspect、SQL generation、execution repair。
- `IC-Bash 20`：测 shell 命令规划、文件检查、stdout 验证。
- Headline：success rate。
- 进入条件：baseline 至少非零，with-skill 能减少 syntax/runtime/format 错误。

### Smoke 1：数值 QA suite

- `DROP 100`
- `FinQA 100`
- `TAT-QA 100`
- Headline：EM/F1 或 numeric exact/tolerance。
- 进入条件：9B + calculator/python 能稳定做局部证据读取和计算。

### Smoke 2：ToolQA

- `easy 50 + hard 50`
- Headline：answer accuracy，辅助看 tool selection accuracy。
- 进入条件：工具调用失败和错选工具可归因，skill 有明显可写规则。

### Smoke 3：DS-1000

- 七个库各 10 题，共 70。
- Headline：execution accuracy。
- 进入条件：至少 Pandas/NumPy/Scikit-learn 子集 baseline 非零，repair trace 可读。

### Smoke 4：HotpotQA + FEVER

- HotpotQA distractor dev 200。
- FEVER dev 200。
- Headline：HotpotQA EM/F1，FEVER score。
- 进入条件：retrieval API/本地 index 稳定，skill 能减少 hallucination 和 unsupported answer。

## 6. 会议用推荐口径

如果需要和上一份主候选互补，我建议新增候选这样排：

1. `InterCode SQL/Bash`：最像当前方法，接入完整，评分清楚，StateFlow 已证明状态化流程对它有价值。
2. `FinQA/TAT-QA/DROP`：OfficeQA 的轻量替代，去掉海量文件路由，专测读表/抽数/计算/格式化。
3. `ToolQA`：方法最贴，工具增强 QA，适合证明 skill 改善工具选择和工具链。
4. `DS-1000`：代码执行和 repair 方向，评分清楚，比 SWE-bench 轻。
5. `HotpotQA/FEVER`：经典 ReAct 对齐，适合做检索-推理-验证流程的可解释提分。

这批和上一份的 WebShop、SQLBench、tau2、OfficeQA staged、AppWorld 等形成互补。若接下来要凑三个 benchmark，新增池里最稳的组合是：

`InterCode + FinQA/TAT-QA/DROP + ToolQA/DS-1000`

如果更想保留 agent/tool 叙事：

`InterCode + ToolQA + API-Bank`

如果更想降低环境成本并快速看到分数：

`DROP/FinQA + DS-1000 small + HumanEval/MBPP/GSM8K 回归`
