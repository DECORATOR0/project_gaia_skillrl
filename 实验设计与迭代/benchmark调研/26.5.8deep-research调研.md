# Agent Skill Learning 基准调研报告

## 一页结论

- **如果只看“2025–2026 skill 论文里出现最多、同时又适合横向对比分数”的 benchmark，第一梯队是 ALFWorld、SkillsBench、AppWorld。**  
  ALFWorld 在 2026 这波 skill / memory / continual-skill 论文里出现频率最高，覆盖 Skill-Pro、SkillRL、Skill0、GoS、GraSP、MemSkill、AutoRefine、ProactAgent 等多条路线；SkillsBench 则是 2026 年最明确把 “skill 作为一等工件” 来评测的公共 benchmark；AppWorld 虽然出现次数不如 ALFWorld，但在现代 agent benchmark 里更贴近真实工具调用、函数/API 流与稳定 verifier。citeturn12view1turn6search6turn12view0turn17view1turn17view2turn17view0turn9view0turn8view2turn31search12turn37search1turn13view0

- **如果只看“最贴近显式 skill 工件 / skill library / skill patch”的 benchmark，首选是 SkillsBench，其次是 SkillLearnBench、SkillFlow、SkillCraft。**  
  SkillsBench 直接把 `SKILL.md` / skill package、curated skill、self-generated skill、deterministic verifier 放到同一框架里；SkillLearnBench 进一步把 skill 生成单独拿出来，分成 skill 质量、轨迹行为、任务结果三级评估；SkillFlow 则几乎是把“顺序 family + 显式 skill patch + 持续演化”写进 benchmark 协议；SkillCraft 的目标就是评估“高阶 tool composition skill 的形成与复用”。citeturn34view0turn34view4turn22view1turn32view5turn33view0turn33view4turn30search0turn30search2

- **如果只看“最适合你当前 SkillRL / 状态机 / critic-actor skill 修改框架快速迁移”，我建议优先看 SkillsBench、AppWorld、ALFWorld。**  
  SkillsBench 最适合外部 skill 文件、rules、tool allow list、answer policy 的直接 A/B；AppWorld 最适合你当前“graph + node rule + repair policy + verifier 信号”的闭环，因为它有函数/API 交互、状态可测、评分相对稳定；ALFWorld 则是最低工程成本的快速迁移位点，可以很快验证 “skill graph 是否真的提升 success / 降 step / 减 forced answer”。citeturn31search12turn34view4turn37search3turn13view0turn12view0turn9view0

- **最适合做“论文主表分数”的，不一定就是最适合做“方法叙事”的。**  
  ALFWorld 和 SkillsBench 更适合公共横向对比；SkillFlow 和 SkillLearnBench 更适合讲“critic 从失败轨迹产出 patch，actor 继续改 skill”的方法故事；AppWorld 适合做两者中间层：既不像 GAIA 那么开放漂移，也不像 ALFWorld 那么 toy。citeturn33view4turn22view1turn31search12turn37search3

- **你当前方法和 SkillFlow 的范式耦合度非常高，但 SkillFlow 还不是社区主战场。**  
  它的核心协议就是 family 内顺序做题、从轨迹与 rubric 外化 skill patch、持续带着 skill library 向后做题；这和你的 “critic/actor 改 graph、node、edge、rule、allow list” 几乎天然对齐。问题在于：到 2026-05 为止，它基本还是 benchmark 官方论文自己在跑，横向生态还没形成。citeturn33view0turn33view4turn33view2

- **热门但会很麻烦的 benchmark，我会明确点名：GAIA、WebArena、WindowsAgentArena / OSWorld、内部企业数据 benchmark。**  
  GAIA 天然开放、答案隐藏、网页/检索噪声大，容易把“skill 是否有效”与“环境随机性/网页变化/答案格式”混在一起；WebArena 需要真实网站式浏览器环境，工程比 ALFWorld / AppWorld 重；WindowsAgentArena / OSWorld 这类 GUI/OS 基准更重、更贵，也更容易把 skill 问题和 perception / GUI 操作误差混在一起；SkillForge、AgentFactory 这类内部或自造任务则不适合做主线横比。citeturn16search0turn28search0turn4search3turn3search13turn21search0turn27view0

- **如果你想证明“critic 能否从失败轨迹里产生有用修改信号”，AppWorld、SkillFlow、SkillsBench 比 GAIA 更干净。**  
  AppWorld 有 scenario/test protocol 和 outcome-based/unit-test 式评估；SkillFlow 明确把 skill patch 写进生命周期；SkillsBench 对每条任务都有 deterministic verifier，且 paper 直接比较 no-skills / curated / self-generated 三个条件。citeturn37search3turn13view3turn33view4turn34view3turn34view4

- **如果你想证明“actor 改 graph 结构、rules、tool allow list 后能不能迁移”，AppWorld 和 ALFWorld 的性价比要高于 WebArena / GUI benchmark。**  
  前两者都在 2025–2026 技术线里被多次复用，评分更稳定、环境更容易本地控制；WebArena / GUI benchmark 虽然更真实，但你会花很多实验预算在 infra、浏览器、截图和环境维护上。citeturn37search1turn13view0turn12view0turn17view2turn28search0turn4search3turn3search13

- **如果只选 1 个主线 benchmark 和 1 个备用 benchmark，我建议：主线选 SkillsBench，备用选 AppWorld。**  
  SkillsBench 的优势是：它最直接评 skill 文件本身、复现门槛可控、judge 不是主 evaluator、2026 年已有多篇 skill 论文围绕它做 benchmark / retrieval / routing；AppWorld 的优势是：它更像真实 agent 工作流，适合承接你现在的 state graph / verification / repair policy 研究。citeturn31search12turn34view4turn22view1turn17view1turn35search3turn37search1turn13view0

- **如果你的目标是“先快速跑出可解释信号，再逐步扩展”，最稳妥的组合不是单 benchmark，而是“三层组合”：SkillsBench 主线 + AppWorld 现实对齐 + ALFWorld 低成本回归组。**  
  这样既能和 2026 新 skill 生态对齐，又能保留一个传统但出现频率最高的轻量基准，避免方法只在单一新 benchmark 上成立。citeturn31search12turn37search1turn12view0turn17view2turn17view1

## Benchmark 详细分析

### B01. ALFWorld

#### 基本定位

ALFWorld 是 2025–2026 这波 skill / memory / continual learning 论文里**出现频率最高**的轻量 text environment。它测的是：能否把自然语言目标转成多步交互式行动，并在探索、状态变换、顺序约束和终止判断上保持稳定。它不是“显式 skill benchmark”，但恰恰因为环境轻、评分硬、轨迹易分析，成了 skill 论文最常见的实验场。citeturn10view1turn12view1turn17view2turn9view0turn8view2

#### 哪些论文跑过

P04 Skill-Pro（主实验、cross-task/cross-agent）；P05 MemSkill（主实验之一）；P06 SkillRL（主实验）；P07 Skill0（主实验）；P14 GoS（主实验）；P15 GraSP（主实验）；P20 AutoRefine（主实验）；P21 ProactAgent（主实验）。citeturn12view1turn17view0turn6search6turn12view0turn17view1turn17view2turn9view0turn8view2

#### 模型与规模

这里覆盖很广：Gemma-3-4B、Qwen3-32B、Llama-3.3-70B、Qwen2.5-VL 3B/7B、Claude Sonnet 4、GPT-4-turbo、GPT-4.1、Claude 4 Sonnet、Gemini 2.5 Pro、o4 Mini、Qwen3-235B、Kimi-K2.5 等。换句话说，它同时服务于**小模型 skill 学习**和**前沿 API 模型 orchestration**两类研究。citeturn12view1turn12view0turn9view0turn17view2

#### 普通 agent 做一题的 workflow

典型流程很自然：先读目标；再做定位与探索；拿到目标物；完成必须的状态变换，比如 clean / heat / cool / look-at-light；验证目标条件是否满足；最后放置并结束。如果失败，最常见的可解释失败点就是**漏探索、错误顺序、过早放置、遗漏状态变换**。citeturn10view1turn9view0

#### 数据规模与 split

从 Skill0 引用的 benchmark 描述看，ALFWorld 含 **3,827 task instances**、**6 类家居任务**；但 2025–2026 不同论文的具体评测协议并不完全统一：AutoRefine 明写用了 **validation unseen set 134 tasks**，GoS 又写到 **full 140-episode split**。所以它很适合作为主线 compare，但**论文里必须把 split 协议钉死**，否则会造成“同叫 ALFWorld，分数口径不一样”的问题。citeturn10view1turn9view0turn17view1

#### 评分方式

主流是 success rate、average reward、average environment steps。不同论文对 reward 还是 success 的主指标有所区别，但 evaluator 总体偏 deterministic。citeturn12view1turn17view2turn9view0

#### 为什么适合或不适合我的 SkillRL

它非常适合你的方法做**快速、干净、可解释**的闭环验证。skill 很容易写成 reusable workflow；跨 task family 的迁移空间真实存在；verifier/reward 相对稳定；baseline 成本很低；critic 很容易从失败轨迹里产出“该改探索规则、状态顺序、终止条件还是 repair 策略”的信号；actor 也很容易把 patch 写进 skill 文件、graph 节点、rules 或 tool allow list。  
它不够好的地方也很明确：它偏 toy，工具空间窄，最终很可能不能单独支撑一篇“通用 agent skill learning”论文，只适合做强 baseline 和 smoke 主战场之一。citeturn10view1turn12view1turn17view2turn8view2

#### 工程落地风险

风险很低。主要风险反而不是 infra，而是**split 口径**与**论文间指标不一致**。你需要在论文里显式写：到底用 unseen val、140 episodes、还是别的 protocol。citeturn9view0turn17view1

#### 初步优先级

**P0。**  
如果你要先证明“外部 skill 工件 + critic/actor 改 rules/graph”这件事在可控环境里能成立，ALFWorld 是最该先跑通的一站。

### B02. SkillsBench

#### 基本定位

SkillsBench 是目前最明确把“**skill 作为一等工件**”纳入评测的公共 benchmark。它不是泛泛测 agent，而是直接测：给 skill、不给 skill、让模型自己生成 skill，三者到底有什么差别。对你的项目而言，它天然就是“skill 文件是否真的有用”的主线 benchmark。citeturn34view0turn34view4turn34view5

#### 哪些论文跑过

P10 SkillsBench（benchmark 提出）；P11 SkillLearnBench（17 个任务从它改造而来）；P13 Wild Skill Usage（在更真实 skill retrieval 场景下重评）；P14 GoS（把 skill routing/structural retrieval 跑在 SkillsBench 上）。citeturn34view0turn32view1turn35search3turn17view1

#### 模型与规模

官方 paper 跑了 7 个 harness-model 配置：Claude Opus 4.5/4.6、Sonnet 4.5、Haiku 4.5、Gemini 3 Pro、Gemini 3 Flash、GPT-5.2 Codex。Wild Skill Usage 又加了 Kimi K2.5 与 Qwen3.5-397B。GoS 再加了 MiniMax。生态非常新，但模型覆盖已经够宽。citeturn34view2turn35search3turn17view1

#### 普通 agent 做一题的 workflow

单题 workflow 通常是：读 instruction；如果有 skills 先判断要不要加载；执行真实任务；调用 verifier；根据 pass/fail 记录轨迹。和普通 benchmark 最大的差别是：**skill 本身就是显式输入变量**，不是只在 prompt 里隐式存在。citeturn34view4turn34view3

#### 数据规模与 split

paper 版写的是 **86 tasks / 11 domains**，其中 **84 tasks 实际纳入评测**；当前官方 docs 已写到 **92 tasks**。也就是说，这个 benchmark **还在演化**，你如果要对齐论文，必须锁 paper 版；如果要做最新复现，必须锁 release 版本。这个细节非常重要。citeturn34view0turn34view7turn31search15

#### 评分方式

核心是 deterministic pytest verifier 下的 pass/fail，再统计 pass rate、normalized gain。不是 LLM judge 主导。citeturn34view3turn34view2

#### 为什么适合或不适合我的 SkillRL

它几乎是为你的方法量身定制的：  
skill 能直接作为外部工件；no-skill / curated / self-gen 的 setting 天然支持 ablation；skill 数量与复杂度还能单独分析；你可以直接把 graph、node rules、tool allow list、answer policy 写进 skill，并测试 patch 是否带来稳定提升。  
缺点是它**不是 lifelong benchmark**。如果你只跑 SkillsBench，很容易把论文写成“skill artifact 好不好用”，而不是“critic-actor 如何持续演化”。所以它非常适合做**主表 benchmark**，但最好配一个 lifelong 或现实 workflow benchmark 做补充。citeturn34view4turn34view6turn22view1turn35search3

#### 工程落地风险

可控，但不如 ALFWorld 轻。你要处理 BenchFlow/Harbor runtime、任务时长、极少数 GPU/timeout 任务，以及 paper 版和 current docs 的版本漂移。citeturn31search15turn34view7

#### 初步优先级

**P0。**  
如果你的论文核心叙事是“显式 skill 工件是否有价值”，我会把它放在首页主表。

### B03. AppWorld

#### 基本定位

AppWorld 是更现代、也更接近生产式 agent workflow 的函数/API 生态 benchmark。它不像 ALFWorld 那样是纯 text env，也不像 GAIA 那样开放且噪声大，而是围绕应用状态、API 文档、逻辑调用和 verifier 组织任务。对你的 state graph / repair policy 方法来说，它是最像“真实工具 agent”的场地。citeturn37search3turn13view3

#### 哪些论文跑过

P02 SAGE 在 AppWorld 上做主实验；P17 SkillX 也把 AppWorld 作为三大主 benchmark 之一。citeturn37search1turn37search3turn13view0turn13view3

#### 模型与规模

SAGE 在 AppWorld 上用 Qwen2.5-32B + RL/GRPO 技线；SkillX 则覆盖 Qwen3-32B、Kimi-K2-Instruct-0905、GLM-4.6。这个 benchmark 既能接 frontier API，也能接较强开源模型。citeturn37search1turn13view0

#### 普通 agent 做一题的 workflow

读任务与约束；查 API 文档；决定调用序列；用 API/逻辑程序改写应用状态；验证 scenario 是否完成。这里极其适合显式 graph，例如把“读题 / 查文档 / 调 API / 验证 / repair”做成节点化流程。citeturn37search3turn13view3

#### 数据规模与 split

在 SkillX 的复现实验设置里，AppWorld 明确有 **90 training instances**，测试用 **Test Normal**；SAGE 用的是官方 **Scenario Goal Completion** 协议。更细的 test 条数，本次主证据未最终核实。citeturn13view0turn13view3turn37search3

#### 评分方式

论文里主要看到两种：Task Goal Completion，与更严格的 Scenario Goal Completion。后者要求一个 scenario 内三道相近任务都成功。citeturn13view3turn37search3

#### 为什么适合或不适合我的 SkillRL

非常适合。  
skill 可以表现为流程模板、API 选择策略、参数校验规则、验证节点和修复节点；critic 可以从 API 调错、顺序错、状态错、验证失败里提炼明确信号；actor 修改 graph、rules、allow list 的收益也容易通过 verifier 观察。  
相较之下，它唯一的短板是：skill 论文生态还没有 ALFWorld 那么密集，因此你需要自己承担一部分“把这个 benchmark 变成 skill 论文主线”的叙事工作。citeturn37search3turn13view0

#### 工程落地风险

中等。环境比 ALFWorld 重，但远比 WebArena / OS GUI 轻；比 GAIA 可控得多。主要工作是熟悉 API 生态、scenario 协议与本地 runner。citeturn37search3turn13view3

#### 初步优先级

**P0。**  
如果你想找一个能取代 GAIA 的“现实但不太脏”的主线 benchmark，AppWorld 是我最推荐的备选主线。

### B04. SkillFlow

#### 基本定位

SkillFlow 不是泛化 agent benchmark，而是**专门为 lifelong skill discovery / evolution 设计**的 benchmark。它把任务组织成 20 个 family，每个 family 内按难度顺序做题，并要求 agent 在做完一道后把经验 externalize 成 skill patch，带到下一题。这个协议与你现在的方法闭环非常接近。citeturn33view0turn33view4turn33view6

#### 哪些论文跑过

到本次检索为止，主要还是 P12 SkillFlow 官方论文自身在跑。citeturn33view0turn33view2

#### 模型与规模

官方主实验覆盖 11 个 agent-model 变体：Claude Sonnet/Opus 4.5/4.6、MiniMax M2.5/M2.7、GPT-5.4、GPT-5.3 Codex、Qwen-Coder-Next、Qwen3-Coder-480B、Kimi K2.5。它不是“小 benchmark only”。citeturn33view2

#### 普通 agent 做一题的 workflow

family 内顺序选题；执行当前任务；收集 trajectory 与 rubric feedback；把 lesson externalize 成显式 skill patch；修补 library；继续下一题。对你当前“critic 读真实执行结果 → actor 改 skill 图结构/边/规则/tool allow list”的框架来说，这个 workflow 几乎是天然对齐。citeturn33view4turn33view6

#### 数据规模与 split

**166 tasks / 20 families / 5 domains**，每个 family 8–9 题，family 内有固定难度顺序。这里最关键的不是 train/test，而是**within-family sequential protocol**。citeturn33view0turn33view4

#### 评分方式

completion、turns、cost、output tokens，并比较 vanilla vs skills evolve。官方 paper 也专门做了一个“只把完整历史拼进 context”的控制组，结果明显低于 full protocol。citeturn33view2turn33view5

#### 为什么适合或不适合我的 SkillRL

如果你想证明“critic-actor 改 skill patch 真的能在后续 family 里迁移收益”，它是**范式最贴脸**的 benchmark。  
问题只有一个：截至 2026-05，它还是“新 benchmark + 单论文生态”。所以它更适合做**方法叙事位**，不适合单独承担“横向对比分数”的全部责任。citeturn33view4turn33view2

#### 工程落地风险

中等。不是 GUI 那种重 infra，但你要实现 sequential rollout、skill patch 管理和 family-level bookkeeping。更大的风险是**社区对齐弱**。citeturn33view0turn33view4

#### 初步优先级

**P1。**  
非常值得做，但更适合作为“第三个展示 benchmark”而不是唯一主线。

### B05. SkillLearnBench

#### 基本定位

SkillLearnBench 的目标不是测“会不会做题”，而是拆成三层看：**生成的 skill 本身好不好、执行轨迹是否更合理、最后任务结果有没有改善**。对于你这种有 critic 和 actor 的方法，这是非常有价值的中间诊断层。citeturn22view1turn32view4

#### 哪些论文跑过

目前主要是 P11 SkillLearnBench 官方论文。citeturn22view1

#### 模型与规模

它评了多种 skill generation LLM：Claude Haiku 4.5、Sonnet 4.6、Opus 4.6、Gemini 3.1 Flash Lite、Gemini 3 Flash、Gemini 3.1 Pro。换句话说，它已经不是单一模型 benchmark。citeturn32view6turn32view5

#### 普通 agent 做一题的 workflow

先在 seed instance 上生成 1–5 个 skill 文档；用这些 skill 解题；把 skill 带到该 task 的其他 instance；看 skill 质量、轨迹 keypoints 与 task outcome 的变化。这个 workflow 很适合显式研究“skill 是否 overfit 种子实例”。citeturn32view5turn32view2

#### 数据规模与 split

**20 tasks / 15 sub-domains / 100 instances**；其中 **17 个 task** 改自 SkillsBench，**3 个新 task** 用来补类别。它更像“可控实验台”，不是超大规模 leaderboard。citeturn22view1turn32view1

#### 评分方式

Level 1 用 LLM judge 评 skill quality；Level 2 评 execution order / trajectory keypoints / completeness；Level 3 看 task outcome。也就是说，它不是纯 deterministic benchmark，而是**diagnostic benchmark**。citeturn32view4turn32view6

#### 为什么适合或不适合我的 SkillRL

非常适合做“critic 信号质量”研究。你的方法可以天然对接 Level 1–3：critic 改写 skill artifact，actor 输出新版本，再看 skill quality 是否先涨、轨迹是否更像 oracle、最终结果是否再涨。  
不适合拿来做唯一主线的理由也很明确：L1/L2 含 LLM judge，横向对比分数不如 SkillsBench / AppWorld 硬。citeturn32view4turn32view6

#### 工程落地风险

中等。任务规模不大，但要管理 judge 成本与稳定性。论文里最有价值的其实不是单个分数，而是三级分析面板。citeturn32view4turn32view6

#### 初步优先级

**P1。**  
如果你要写“critic 真的给出了有用 patch”这一段，它比只跑 success rate 更有说服力。

### B06. ScienceWorld

#### 基本定位

ScienceWorld 是长程 scientific lab text environment。相比 ALFWorld，它更强调实验步骤、对象关系与中间验证，因此更适合体现阶段约束、验证节点和 repair。citeturn17view2turn9view0turn8view2

#### 哪些论文跑过

P15 GraSP、P20 AutoRefine、P21 ProactAgent。citeturn17view2turn9view0turn8view2

#### 模型与规模

从已找到论文看，既有 Claude Sonnet 4 / GPT-4-turbo 这类 API 模型，也有 GraSP 用的一整组 frontier model。citeturn17view2turn9view0

#### 普通 agent 做一题的 workflow

读实验目标；探索实验环境；收集与组合对象；执行实验步骤；检查中间状态；完成并收尾。相较 ALFWorld，它更容易暴露“步骤顺序对了但验证错了”这类 critic-able failure。citeturn17view2turn9view0

#### 数据规模与 split

GraSP 明写 **30 task types**；更细的 split 数量在本次主证据中未查到。citeturn17view2

#### 评分方式

常见是 average reward、success、steps。citeturn17view2turn9view0

#### 为什么适合或不适合我的 SkillRL

它很适合把 skill graph 写成实验流程图：准备、操作、观测、验证、修复。critic 也更容易指出“失误发生在物料准备、步骤顺序还是终态验证”。  
不如 AppWorld 的地方在于：它仍是 text env，和真实工具/文件/浏览器 workstyle 不是一类问题。citeturn17view2turn9view0turn8view2

#### 工程落地风险

低到中。比 WebArena / GUI 轻得多，但比 ALFWorld 更复杂。主要风险在于任务类型多、轨迹长、调参更费时间。citeturn17view2turn8view2

#### 初步优先级

**P1。**  
适合做 ALFWorld 之后的第二个 text env 补点，但不是你最优先的替代主线。

### B07. WebShop

#### 基本定位

WebShop 是经典的 web shopping benchmark。它不直接测 skill 文件，但很适合测 search / filter / compare / verify 这一类高复用 workflow skill。citeturn17view2turn6search6

#### 哪些论文跑过

P06 SkillRL、P15 GraSP。citeturn6search6turn17view2

#### 模型与规模

SkillRL 和 GraSP 都把它纳入主实验；GraSP 还用多种 frontier model 跑了横向表。citeturn6search6turn17view2

#### 普通 agent 做一题的 workflow

读购物要求；检索候选；按属性过滤；查看商品详情；比较多个候选；提交选择。这个结构非常天然地支撑 search/verify 类 skill。citeturn17view2

#### 数据规模与 split

GraSP 主文中给出 **500 sessions**；更细 split 未查到。citeturn17view2

#### 评分方式

常见是 average reward 与 steps。citeturn17view2

#### 为什么适合或不适合我的 SkillRL

如果你想测“有限工具集下的状态机是否能避免过度搜索/过早提交”，它很适合。skill 可以表现为筛选策略、验证规则和 submit 前收敛条件。  
但它的任务分布单域，不能单独代表通用 skill learning。citeturn17view2turn6search6

#### 工程落地风险

低。老 benchmark，环境成熟。风险主要是“任务面太窄，论文故事不够大”。citeturn17view2

#### 初步优先级

**P1。**  
适合作为 legacy 对齐组的一员，不建议单独做主线。

### B08. SkillCraft

#### 基本定位

SkillCraft 是 2026 新出的 benchmark，目标非常直接：测 agent 能不能从 atomic tools 中抽象出更高阶、可缓存、可跨题复用的 skill composition。你现在的方法虽然更偏“显式外部 skill 工件”，但 graph/patch/allow list 的中心思想和它非常接近。citeturn30search0turn30search2

#### 哪些论文跑过

目前主要是 P03 SkillCraft 官方论文本身。citeturn30search0turn30search2

#### 模型与规模

官方摘要明确说评估了 state-of-the-art agents，但本次主证据没有完整主表模型列表；官方代码和 OpenReview 已公开。citeturn30search0turn30search2turn30search6

#### 普通 agent 做一题的 workflow

先用已有 atomic tools 解子问题；把常见组合抽象成 skill；将 skill 缓存；在后续任务中重用；比较成功率和 token 成本。它其实非常像一个“在线 skill compilation”协议。citeturn30search0turn30search6

#### 数据规模与 split

摘要没有给出明确题数；只说明 benchmark 沿 quantitative scaling 与 structural scaling 两条轴线增长。精确任务数、本地 release 协议与 split，本次未查到。citeturn30search0

#### 评分方式

成功率 + 效率协议，尤其强调 token usage 和 skill cache/reuse 带来的收益。citeturn30search0

#### 为什么适合或不适合我的 SkillRL

它非常适合你讲“skill graph / node composition / reusable patch”的方法叙事，因为 benchmark 本身就在测这个能力。  
但问题是：它太新，横向论文还不够多，所以适合做**新范式对齐**，不适合现在就作为唯一主战场。citeturn30search0turn30search6

#### 工程落地风险

中等。代码已开源，但生态尚早，论文复现实战经验还不多。citeturn30search6

#### 初步优先级

**P2。**  
很值得关注；更适合在主线结果稳定后做“方法亮点展示”。

### B09. Terminal-Bench 2.0

#### 基本定位

Terminal-Bench 2.0 不是显式 skill benchmark，但 Wild Skill Usage 论文拿它来证明：即便 benchmark 本身没配 curated skills，skill retrieval + refinement 仍然能提升 pass rate。这对于你的工作很重要，因为这说明“外部 skill 工件”不一定只能在 skill-native benchmark 上工作。citeturn36view0turn35search3

#### 哪些论文跑过

P13 Wild Skill Usage。citeturn35search3turn36view0

#### 模型与规模

论文具体报告了 Claude Opus 4.6 在 Terminal-Bench 2.0 上从 57.7% 提到 65.5%。citeturn35search3turn36view0

#### 普通 agent 做一题的 workflow

读终端任务；检查文件系统与环境；写命令或脚本；执行并看反馈；必要时修复；通过 verifier/pass 条件。它很适合强调“修复策略”和“tool-use procedure” skill。citeturn36view0

#### 数据规模与 split

本次主证据未查到精确题数与官方 split。citeturn35search3turn36view0

#### 评分方式

pass rate。citeturn35search3turn36view0

#### 为什么适合或不适合我的 SkillRL

它适合作为“外部 skill 对通用 agent benchmark 也能起作用”的补充证据。特别适合研究 repair policy、脚本执行失败后的 critic 信号。  
不适合作为第一主线的原因是：它更偏 terminal/coding/ops，和你当前 GAIA 上那种多模态综合题并不完全同类。citeturn36view0

#### 工程落地风险

中等。需要 terminal/container 环境，但整体比 browser/GUI benchmark 干净。citeturn35search1turn36view0

#### 初步优先级

**P2。**  
适合做一个“第三组证明外推性”的 benchmark，不建议先上。

### B10. WebArena

#### 基本定位

WebArena 是 web agent 经典 benchmark。SkillWeaver 把“website-specific APIs / skills”明确跑在了 WebArena 上，因此它仍然是 skill 研究的重要公共对照位。citeturn28search0turn28search1

#### 哪些论文跑过

P01 SkillWeaver。citeturn28search0turn28search1

#### 模型与规模

SkillWeaver 摘要没有在本次主证据里完整列出模型规模，但明确报告 WebArena 上相对成功率提升 31.8%。citeturn28search0

#### 普通 agent 做一题的 workflow

读网页任务；浏览网站；搜索点击表单；维护网页状态；达成任务目标。这一类任务中，skill 很容易表现为网站级 SOP、表单填写模板、错误恢复策略。citeturn28search0turn28search1

#### 数据规模与 split

官方 benchmark 有 seen/unseen 网站协议，但本次严格主证据未核到精确题数，因此这里写 **未查到**。citeturn28search0

#### 评分方式

通常是 success rate。citeturn28search0

#### 为什么适合或不适合我的 SkillRL

它对“website-specific reusable skill”很自然，也适合 actor patch SOP；但对你当前项目不友好的地方在于：web page 变化、browser infra、等待策略、页面状态和 skill 设计会深度耦合，让你很难分清收益到底来自 skill 还是来自浏览器工程。citeturn28search0turn28search1

#### 工程落地风险

高于 AppWorld、ScienceWorld、ALFWorld。真实浏览器环境会显著放大实验方差和维护成本。citeturn28search0turn28search1

**P2。**  
适合做对外对齐，不适合你现在第一批迁移实验。

## 三个排序

### 最适合横向对比分数的 benchmark

排序依据：**多篇论文使用、主指标直观、数据/代码公开、baseline 多、社区已经形成可比口径**。

1. **ALFWorld** —— 出现最多，复现最成熟，但要锁 split。citeturn10view1turn17view1  
2. **SkillsBench** —— 2026 skill 生态里最标准的“显式 skill benchmark”。citeturn34view0turn34view3  
3. **AppWorld** —— 现代 agent benchmark，中间地带最佳。citeturn37search3turn13view3  
4. **ScienceWorld** —— 老 benchmark 但 2026 仍在被 skill 论文持续使用。citeturn17view2turn9view0  
5. **WebShop** —— 老 benchmark，依旧在 skill graph / RL 论文中出现。citeturn17view2turn6search6  
6. **WebArena** —— 公共影响力大，但工程方差更高。citeturn28search0turn28search1  
7. **Terminal-Bench 2.0** —— 新但开始被“skills in the wild”拿来做泛化对照。citeturn35search3turn36view0  
8. **InterCode** —— 单域但 verifier 硬，适合做 graph/repair 对照。citeturn17view2

### 最贴近显式 skill 工件 / skill library 的 benchmark

排序依据：**能不能直接评 skill 文件/skill package/skill patch，能不能清楚观测 skill reuse。**

1. **SkillsBench** —— 直接比较 no-skills / curated / self-generated skills。citeturn34view4turn34view5  
2. **SkillLearnBench** —— 直接看 skill 质量、轨迹影响、结果提升。citeturn22view1turn32view4  
3. **SkillFlow** —— 明确要求沿 family 顺序外化并维护 skill patch。citeturn33view4  
4. **SkillCraft** —— benchmark 本身就在测高阶 tool composition skill。citeturn30search0  
5. **WindowsAgentArena** —— 在 CUA-Skill 里被明确图结构化为 skill graph。citeturn4search3  
6. **AppWorld** —— 可直接把 skill 写成 API workflow / rules / validation policy。citeturn37search3turn13view3  
7. **ALFWorld** —— skill 能表现成明确可复用阶段规则，但 benchmark 本身不是 skill-native。citeturn12view1turn10view1  
8. **WebArena** —— website-specific API/skill 复用自然，但 infra 更脏。citeturn28search0turn28search1

### 最适合从 GAIA 迁移并快速跑出结果的 benchmark

排序依据：**工程环境可控、评分稳定、划分清楚、能体现状态机/critic-actor 修改 skill 的价值。**

1. **AppWorld** —— 最像真实 agent workflow，同时不太脏。citeturn37search3turn13view3  
2. **SkillsBench** —— 工件最对口，verifier 硬，适合直接做 skill patch。citeturn34view4turn34view3

## 最终建议

**第一主线 benchmark：SkillsBench。**  
理由很直接：它和你的工件设计最对口，skill 是显式文件而不是隐式提示；有 no-skill / curated / self-generated 三组天然对照；verifier 是 deterministic；2026 年已经形成了围绕它的 benchmark、retrieval、routing、realistic skill usage 多篇论文生态。用它做主表，你最容易把“外部 skill 工件是否真有用”写清楚。citeturn31search12turn34view4turn35search3turn17view1

**备用 benchmark：AppWorld。**  
理由是它最适合承接你当前的 state graph / node rule / repair policy / tool allow list 研究。相比 GAIA，它更可控；相比 ALFWorld，它更现实；相比 WebArena / GUI benchmark，它更容易把收益归因到 skill 与执行策略，而不是归因到浏览器或 GUI 感知。citeturn37search3turn13view0turn13view3

**经典对齐组建议保留：ALFWorld + ScienceWorld + WebShop。**  
这三者能让你和 2025–2026 skill / memory / self-evolving agent 论文有最稳定的 legacy 对齐：ALFWorld 是出现次数王者；ScienceWorld 把阶段化实验流程补齐；WebShop 把 search/filter/submit 流程补齐。citeturn12view1turn17view2turn9view0turn6search6

**只适合 smoke 或方法展示的 benchmark：SkillFlow、SkillLearnBench、SkillCraft。**  
它们非常适合展示你的方法独特价值，但还不适合单独承担“社区主战场”的职责。最佳用法是：在主表 benchmark 结果稳定之后，再用它们展示“critic-actor 持续演化 / skill patch / graph rewrite”的独特性。citeturn33view4turn22view1turn30search0

**暂时不建议碰的主线：GAIA、WebArena、WindowsAgentArena / OSWorld、内部企业 benchmark。**
