下面是我按“自己独立调研”做出来的版本。你的原始文件我只把它当作研究目标和判断偏好：要为 **外部 skill 工件 + 状态机/图结构约束 + critic/actor 修改 skill + re-eval** 找比 GAIA 更干净、更能看出迁移收益的 benchmark，而不是照着提示词机械填表。

# 0. 一页结论

1. **真正最贴近你当前 SkillRL 闭环的不是 GAIA，也不是 WebArena，而是 SkillLearnBench / SkillFlow / SkillsBench / SkillCraft 这一组 2026 年 skill-native benchmark。** SkillLearnBench 直接评估“从 agent 经验持续生成 skill”，20 个 verified skill-dependent tasks、100 个 instances、三层评估框架；SkillFlow 明确是 lifelong skill discovery/evolution，166 tasks、20 families、trajectory/rubric-driven skill patches；SkillsBench 则是目前最核心的“skill 有无效果”基准。([arXiv][1])
2. **最适合快速迁移的是 SkillLearnBench。** 它比 GAIA 更窄、更干净，目标正好是“skill 生成方法是否从经验中学到可复用 procedure”，并且不是只看最终答案，还看 skill quality、trajectory alignment、task outcome。它的缺点是部分中间指标涉及 LLM judge，最终 outcome/verifier 仍需先做 smoke。([CXCSCMU][2])
3. **最适合做静态 skill 效果对照的是 SkillsBench。** 它有 86 个任务、11 个 domain、curated Skills 和 deterministic verifiers；论文里实际评估时排除 2 个任务，最终用 84 个任务。No Skill 平均 24.3%，Curated Skills 40.6%，Self-generated Skills 21.0%，说明“好 skill 有用，但随便自生成 skill 可能反而没用”。([arXiv][3])
4. **最像你“critic 读失败轨迹、actor 修改 graph/rules/tool allow list”的是 SkillFlow。** 它的协议就是 agent 从无 skill 开始，在 task family 内按固定顺序做题，之后用 trajectory/rubric-driven patches 更新外部 skill library；Claude Opus 4.6 从 62.65% 提到 71.08%，但同时发现高 skill usage 不等于高 utility。([arXiv][4])
5. **SkillCraft 是非常值得补充的 tool-composition skill benchmark。** 它有 126 tasks、21 task families、6 domains，显式测 agent 是否能把 atomic tools 组合成可缓存、可复用的 executable skills；项目页给出的结果显示多个模型在 Skill Mode 下成功率提高且 token/cost 大幅下降，GPT-5.2 token 降幅约 79%。([arXiv][5])
6. **ALFWorld / WebShop 仍是横向对比最稳的经典组。** SkillRL、SkillNet、ProcMEM、MemSkill、AutoRefine 等都继续用 ALFWorld；SkillRL 和 SkillNet 继续用 WebShop。它们不是 skill-native，但论文生态成熟、success/reward 指标常见、历史 baseline 多。([arXiv][6])
7. **WebArena / Mind2Web / AppWorld / BFCL-v3 / τ²-Bench 更适合“workflow/tool-use skill”叙事，但工程和随机性更重。** WebArena 被 ASI、SkillWeaver、AWM 等 web skill/workflow 论文使用，但需要 browser service、自托管网站、账号/状态管理；AppWorld 有 750 tasks、105/60/168/417 split 和程序化 state evaluator，很适合 sequential skill reuse，但更偏 API/code execution agent。([arXiv][7])
8. **SWE-Skills-Bench 和 Terminal-Bench 2.0 很适合做 deterministic verifier 的工程型补充。** SWE-Skills-Bench 有 49 public SWE skills、约 565 task instances、fixed commit、pytest/Docker verifier，但论文结论反而很克制：39/49 skills 零提升，平均收益约 +1.2%，token overhead 最高 451%。Terminal-Bench 2.0 是 89 个 terminal tasks；“realistic skill usage”论文用它验证 skill retrieval/refinement，把 Claude Opus 4.6 pass rate 从 57.7% 提到 65.5%。([arXiv][8])
9. **暂时不建议把 WebArena 或 WindowsAgentArena 作为第一主线。** 它们叙事上很强，但和 GAIA 一样容易引入 browser/GUI/environment stochasticity；WindowsAgentArena/CUA-Skill 更接近真实 GUI skill graph，但 Windows GUI 工程成本高，不适合快速判断 skill graph 是否有效。([arXiv][9])
10. **如果只选 1 个主线 + 1 个备用：主线 SkillLearnBench，备用 SkillsBench。** SkillLearnBench 用来验证“critic/actor 从失败轨迹改 skill 是否带来 held-out instance 收益”；SkillsBench 用来做静态 skill/no-skill/curated/self-generated 对照。SkillFlow 很适合写方法故事，但最好等 repo/runner smoke 后再决定是否升为主线。

# 3. Benchmark 详细 Block：Top 10

## B01. SkillLearnBench

### 基本定位

SkillLearnBench 是目前最直接对齐“自动生成/持续学习 agent skills”的 benchmark。它不是简单问“给 skill 是否更好”，而是问：agent 能不能从工作经验里生成 skill，后续多实例复用时是否真的提升 outcome。官方说明为 20 verified skill-dependent tasks、100 instances、15 subdomains，并提供 skill quality、trajectory、outcome 三层评估。([arXiv][1])

### 哪些论文跑过

P02《SkillLearnBench》本身。暂未看到多篇外部论文正式把它作为横向 benchmark。

### 模型与规模

项目页称 controlled comparison 覆盖 4 methods、6 LLMs；arXiv abstract 说比较 one-shot、self/teacher feedback、skill creator 等 continual learning 方法。([arXiv][1])

### 普通 agent 做一题的 workflow

1. 读取任务说明和已有实例反馈。
2. 生成或更新一个 skill 文档。
3. 用该 skill 去做同类新 instance。
4. 执行环境/工具。
5. 记录轨迹、skill usage、最终 outcome。
6. 用失败反馈继续 refine skill。

### 数据规模与 split

20 tasks、100 instances；multi-instance testing 用来测 reusability。常规 train/dev/test split 需进一步读 repo/PDF 表格确认。([CXCSCMU][2])

### 评分方式

三层：skill quality、execution trajectory、task outcome。优点是能定位失败来自 skill 内容、轨迹使用，还是最终执行。缺点是中间层可能依赖 LLM judge。

### 为什么适合或不适合我的 SkillRL

非常适合。你的 critic 可以读失败轨迹输出“skill 哪部分缺失/错用/过窄/过宽”；actor 可以修改 skill 的 rules、tool allow list、阶段说明；re-eval 可以看 held-out instance outcome。它比 GAIA 更少 web/media/search 乱源。

### 工程落地风险

新 benchmark，外部 baseline 少；三层指标里的 LLM judge 需要固定模型和 prompt；需要先确认每个 task 的 verifier 是否足够 deterministic。

### 初步优先级

**P0。** 第一主线。

---

## B02. SkillsBench

### 基本定位

SkillsBench 是当前最核心的“Agent Skills 到底有没有用”的 benchmark。它以 skill package / SKILL.md 为中心，配 curated Skills 和 deterministic verifier。论文报告 86 tasks、11 domains；实际评估排除 2 个任务后用 84 个 tasks。([arXiv][25])

### 哪些论文跑过

P01 原论文；P02 复用/改编 SkillsBench 任务；P03 SkillFlow 种子任务中包含 SkillsBench；P05 realistic skill usage 在 SkillsBench 上做 retrieval/refinement；P07 EvoSkills 在 SkillsBench 上做 self-evolving multi-file skill packages。([arXiv][26])

### 模型与规模

SkillsBench 原论文评估 Claude Code、Codex CLI、Gemini CLI，模型包括 GPT-5.2、Claude Opus/Sonnet/Haiku 4.5/4.6、Gemini 3 Pro/Flash 等。([arXiv][25])

### 普通 agent 做一题的 workflow

1. 读取任务和环境文件。
2. 不加载 skill / 加载 curated skill / 自生成 skill。
3. 按 skill 指示执行脚本、分析数据或调用工具。
4. 生成输出文件或答案。
5. deterministic verifier 判定 pass/fail。
6. 记录 trajectory、steps、tokens。

### 数据规模与 split

86 tasks；84 evaluated；11 domains；difficulty 包括 core / extended / extreme。没有传统 train/dev/test，主要是三种 skill 条件对照。([arXiv][25])

### 评分方式

deterministic verifier；pass/fail。原论文主结果：No Skill 24.3%，Curated Skills 40.6%，Self-generated Skills 21.0%。([arXiv][25])

### 为什么适合或不适合我的 SkillRL

适合做**静态 skill 对照**，尤其是 baseline / bootstrap-only / actor-modified skill 的 pass rate 对比。不足是没有天然 lifelong split，critic/actor 迭代容易变成“在同一批任务上调 skill”。

### 工程落地风险

Harbor/containerized runner 需要配置；curated skill 有时可能非常贴题，论文也指出 realistic retrieval 条件下 skill benefit 会退化。

### 初步优先级

**P0 备用 / 对照。** 不建议单独作为唯一主线。

## B03. SkillFlow

### 基本定位

SkillFlow 是为 lifelong skill discovery/evolution 设计的 benchmark。它定义 Agentic Lifelong Learning：agent 从无 skills 开始，按 family 内固定顺序做任务，把经验外化为 skill patches，并把 library 带到后续任务。([arXiv][4])

### 哪些论文跑过

P03《SkillFlow》本身。暂未看到多篇后续论文使用。

### 模型与规模

论文摘要列出 Claude Opus 4.6、Kimi K2.5、Qwen-Coder-Next 等结果；正文线索还包括 Claude Code、Codex CLI、Qwen-Coder、Kimi-CLI harness。([arXiv][4])

### 普通 agent 做一题的 workflow

1. 在一个 task family 中接收第 k 个任务。
2. 查看当前 skill library。
3. 执行任务并产生完整 trajectory。
4. 根据 trajectory/rubric 生成 skill patch。
5. 更新 SKILL.md / helper scripts / references。
6. 后续任务复用或修补该 skill。

### 数据规模与 split

166 tasks、20 families；任务构造基于 Domain-Agnostic Execution Flow。它不是传统 train/dev/test，而是 family 内顺序 lifelong protocol。([arXiv][4])

### 评分方式

task success、efficiency、skill generation/reuse 等。论文报告 Claude Opus 4.6 lifelong skill evolution 从 62.65% 到 71.08%。([arXiv][4])

### 为什么适合或不适合我的 SkillRL

从方法叙事看最贴。你可以把 actor 的输出直接定义成 patch：改节点、边、rules、tool allow list、verification policy。critic 的 failure attribution 也有天然位置。

### 工程落地风险

新 benchmark，runner/repo 状态需要先 smoke；外部横向 baseline 少。

### 初步优先级

**P0.5 / 第二阶段主线。** 工程跑通后可升 P0。

---

## B04. SkillCraft

### 基本定位

SkillCraft 专门测 agent 是否能把 atomic tools 组合成高层 reusable skills。它有 126 tasks、21 task families、6 domains，强调 identify / compose / cache / reuse multi-step tool sequences。([SkillCraft][27])

### 哪些论文跑过

P04《SkillCraft》本身。

### 模型与规模

项目页列出 7 frontier models，包括 Kimi-K2-Thinking、DeepSeek-V3.2-EXP、DeepSeek-R1、GLM-4.7、MiniMax-M2.1、GPT-5.2、Gemini 3 Pro、Claude 4.5 Sonnet 等。([SkillCraft][27])

### 普通 agent 做一题的 workflow

1. 读任务，识别需要哪些 atomic tools。
2. 试探性调用工具。
3. 组合成多步 executable tool chain。
4. 验证 tool chain 是否成功。
5. 抽象为 reusable skill。
6. 在后续相似任务中直接复用。

### 数据规模与 split

126 tasks、21 families、6 domains；difficulty 为 Easy 63、Medium 42、Hard 21。([SkillCraft][27])

### 评分方式

success rate、skill execution、reuse factor、token/cost delta。项目页报告多模型在 Skill Mode 下成功率提高；GPT-5.2 token delta -79%。([SkillCraft][27])

### 为什么适合或不适合我的 SkillRL

适合测试 tool allow list 和“从原子工具到复合 skill”的抽象。但它比你的 graph/state-machine 更偏 tool-chain caching，未必能充分展示复杂 verification/repair policy。

### 工程落地风险

需要 Python、Node.js、MCP server、API key；部分任务可能依赖外部工具稳定性。([GitHub][28])

### 初步优先级

**P1。** 很适合做 tool-skill 支线。

---

## B05. SWE-Skills-Bench

### 基本定位

SWE-Skills-Bench 检验 public SWE skills 在真实 GitHub repo 任务上是否真的有边际收益。它用 fixed commits、acceptance criteria、execution-based tests / pytest verifier。([arXiv][8])

### 哪些论文跑过

P06 原论文；P19 Trace2Skill 用 spreadsheet/xlsx skill 方向时把它作为相关动机，不是直接主 benchmark。

### 模型与规模

模型表需进一步读 PDF；数据规模已核到 49 skills、约 565 task instances、6 SWE subdomains。([Hugging Face][29])

### 普通 agent 做一题的 workflow

1. clone fixed commit repo。
2. 读 requirement / acceptance criteria。
3. 加载某个 public SWE skill。
4. 修改代码或配置。
5. 运行 pytest / verifier。
6. pass/fail 统计。

### 数据规模与 split

49 public skills；565 task instances；6 domains：Deployment & DevOps、Analytics & Monitoring、API Development、Data Science & ML、Security & Testing、Developer Tools。([Hugging Face][29])

### 评分方式

execution-based deterministic tests。论文结论很重要：39/49 skills 没有改善，平均收益 +1.2%，token overhead 最高 451%。([arXiv][8])

### 为什么适合或不适合我的 SkillRL

适合证明“不是所有 skill 都有用”，能让 critic/actor 做 skill pruning/refinement。但如果目标是快速跑出正收益，风险较高。

### 工程落地风险

Docker、repo dependency、测试耗时；coding agent 成本较高。

### 初步优先级

**P1 / P2。** 更适合论文里的反例与 robustness 分析，不适合第一主线刷分。

---

## B06. ALFWorld

### 基本定位

ALFWorld 是经典 text embodied environment，agent 通过文本动作完成 household task，例如 find / pick / clean / heat / place。它在 2026 skill/procedural memory 论文中仍高频出现。SkillRL、SkillNet、ProcMEM、MemSkill、AutoRefine 都跑过或报告过它。([arXiv][6])

### 哪些论文跑过

P12 SkillRL、P13 SkillNet、P14 ProcMEM、P18 MemSkill、P20 AutoRefine。

### 模型与规模

包括 Qwen、Gemma、LLaMA、DeepSeek、Gemini、o4-mini 等。ProcMEM 明确报告 Gemma/Qwen/LLaMA 系列；SkillNet 报告 DeepSeek V3.2、Gemini 2.5 Pro、o4-mini。([arXiv][15])

### 普通 agent 做一题的 workflow

1. 读 household goal。
2. 观察当前位置和物品。
3. 搜索房间/容器。
4. pick / clean / heat / cool / place。
5. 检查目标是否满足。
6. 输出完成或继续探索。

### 数据规模与 split

官方有 train / seen / unseen 或 OOD split；seen 测训练布局中的泛化，unseen 测新房间/新组合。([arXiv][30])

### 评分方式

success rate；有时限制 step budget。

### 为什么适合或不适合我的 SkillRL

适合做横向 baseline，因为任务 family 清晰、规则可 proceduralize，critic 能从失败动作里归纳 skill。缺点是离你现在的 file/web/tool-rich SkillRL 形态有距离。

### 工程落地风险

环境比 WebArena 简单，但 task 长、动作空间规则多；小模型容易 stuck。

### 初步优先级

**P1。** 经典对齐组，不建议作为唯一主线。

---

## B07. WebShop

### 基本定位

WebShop 是模拟电商网页任务：给定产品需求，agent 搜索、浏览、选择、购买。它有真实产品库和 crowd-sourced instructions，适合测 web decision-making 和 strategy。原始 benchmark 有 1.18M products、12,087 instructions、1,600+ human demonstrations。([arXiv][31])

### 哪些论文跑过

P12 SkillRL、P13 SkillNet。

### 模型与规模

SkillRL 报告在 WebShop 上 score 85.2、success 72.7；SkillNet 报告跨模型 reward/steps 提升。([arXiv][6])

### 普通 agent 做一题的 workflow

1. 读商品约束。
2. reformulate search query。
3. 浏览候选商品。
4. 比较属性、价格、选项。
5. 选择商品规格。
6. purchase 并获得 reward/success。

### 数据规模与 split

原始 WebShop：1.18M products、12,087 instructions。具体 skill 论文采用的 train/test 设置需逐篇核。([arXiv][31])

### 评分方式

score/reward + success rate。原始 WebShop 还报告 human expert success 59%、best trained model 29%。([OpenReview][32])

### 为什么适合或不适合我的 SkillRL

适合把 skill 表达为“搜索策略、属性核查、候选比较、购买前验证”。比 GAIA 稳定一些，但仍有网页导航和 query formulation 噪声。

### 工程落地风险

模拟网页、产品文本噪声、reward 有时不如 deterministic pass/fail 直观。

### 初步优先级

**P1。** 作为经典对齐组保留。

---

## B08. WebArena / Mind2Web

### 基本定位

WebArena 是真实感 web environment，四类网站：e-commerce、social forum、collaborative software development、content management，并有 tools / knowledge bases / functional correctness tasks。Mind2Web 更偏离线网页导航动作数据。([arXiv][33])

### 哪些论文跑过

P09 SkillWeaver、P10 ASI、P11 AWM。AWM 还跑 Mind2Web。([arXiv][12])

### 模型与规模

P10/P11/P09 模型表需逐 PDF 核；关键是 WebArena 在 web skill/workflow 论文中反复出现。

### 普通 agent 做一题的 workflow

1. 读自然语言网页任务。
2. 打开对应网站。
3. 搜索/点击/填写表单/进入详情页。
4. 读页面反馈。
5. 调整计划。
6. 触发最终状态并由 evaluator 判定。

### 数据规模与 split

WebArena 官方环境 self-hostable，任务数和 split 需 repo 逐文件核；Mind2Web 与 WebArena 合计覆盖 1000+ tasks、200+ domains 的线索来自 AWM 摘要。([arXiv][13])

### 评分方式

WebArena：functional correctness / success；Mind2Web：动作匹配/导航指标。

### 为什么适合或不适合我的 SkillRL

适合研究 web workflow skills、programmatic skills、site transfer。不适合作第一主线，因为它会重新引入你在 GAIA 已经遇到的搜索/网页状态/执行噪声。

### 工程落地风险

browser service、自托管网站、账号、环境 reset、页面 edge cases。WebArena repo 也建议使用更新的 BrowserGym/AgentLab infrastructure。([GitHub][34])

### 初步优先级

**P2。** 论文叙事强，快速实验不优先。

## B09. AppWorld

### 基本定位

AppWorld 是 API/tool-use agent benchmark。agent 需要阅读数字生活任务，查询 API docs，用代码调用模拟应用 API，并由最终 environment state 判定任务完成。SAGE 特别强调 AppWorld 的 scenario structure 适合 Sequential Rollout。([arXiv][17])

### 哪些论文跑过

P15 SkillX、P16 SAGE。

### 模型与规模

SkillX 报告 Qwen3-32B、Kimi-K2、GLM-4.6；SAGE 模型细节需继续核 PDF。([arXiv][16])

### 普通 agent 做一题的 workflow

1. 读用户任务。
2. 查 API 文档。
3. 规划需要调用哪些 app/API。
4. 写代码执行 API call。
5. 检查返回和状态。
6. state evaluator 给 reward/completion。

### 数据规模与 split

750 tasks：Train 105、Dev 60、Test-Normal 168、Test-Challenge 417；9 apps、457 APIs、100+ simulated users。([arXiv][17])

### 评分方式

state-based completion reward，允许多路径完成。([arXiv][17])

### 为什么适合或不适合我的 SkillRL

很适合 tool allow list、API workflow、scenario-level reuse；不适合直接测文件型 SKILL.md 多阶段 repair，除非你把 skill 定义为 API 使用 policy。

### 工程落地风险

API environment、代码执行、长 context；训练成本高于 SkillLearnBench。

### 初步优先级

**P1/P2。** 如果你想和 SkillX/SAGE 对齐，可加入；否则不如 SkillLearnBench 快。

## B10. Terminal-Bench 2.0

### 基本定位

Terminal-Bench 2.0 是 terminal agent benchmark，89 个 hard realistic terminal tasks，覆盖 software engineering、ML、security、data science 等。([arXiv][35])

### 哪些论文跑过

P05 “How Well Do Agentic Skills Work in the Wild” 用它验证 skill retrieval/refinement 在非 skill-native benchmark 上也能提升。

### 模型与规模

P05 报告 Claude Opus 4.6；Terminal-Bench leaderboard 上有大量 agent/model 组合。([Terminal-Bench][36])

### 普通 agent 做一题的 workflow

1. inspect 当前目录。
2. 阅读 README / tests / logs。
3. 运行命令或脚本。
4. debug failure。
5. 修改文件或产出 artifact。
6. verifier/pass rate 判定。

### 数据规模与 split

Terminal-Bench 2.0：89 high-quality tasks。([Terminal-Bench][37])

### 评分方式

pass rate；通常是容器内任务完成判定。

### 为什么适合或不适合我的 SkillRL

适合看 skill retrieval/refinement 是否能跨出 skill-native benchmark。对你的 actor 来说，可以改“terminal debugging skill”“日志分析 skill”“测试修复 skill”。缺点是它不专门评估 skill generation，且成本较高。

### 工程落地风险

容器、依赖、长任务、高 token 成本；不建议第一轮上。

### 初步优先级

**P2。** 作为 paper robustness benchmark。

# 4. 三个排序

## A. 最适合横向对比分数的 benchmark

1. **ALFWorld**：SkillRL、SkillNet、ProcMEM、MemSkill、AutoRefine 都用；指标简单。
2. **WebShop**：SkillRL、SkillNet 使用；reward/success 常见。
3. **WebArena**：SkillWeaver、ASI、AWM 使用；web skill 论文生态强，但工程重。
4. **SkillsBench**：skill-native 里出现最多；2026 skill papers 已经开始围绕它做扩展。
5. **AppWorld**：SkillX、SAGE 使用；split 和 state evaluator 清楚。
6. **ScienceWorld**：SkillNet、AutoRefine 使用；适合作 ALFWorld 补充。
7. **Mind2Web**：AWM 等 workflow memory work 使用；离线稳定。
8. **Terminal-Bench 2.0**：非 skill-native，但 leaderboard/agent ecosystem 活跃。
9. **BFCL-v3**：tool/function calling 生态强，SkillX 使用。
10. **τ²-Bench**：tool-agent-user interaction 新生态，有业务流程感。

## B. 最贴近显式 skill 工件 / skill library 的 benchmark

1. **SkillLearnBench**：直接评估 continual skill generation。
2. **SkillFlow**：直接评估 skill discovery/evolution/patch/reuse。
3. **SkillsBench**：SKILL.md / skill package 效果基准。
4. **SWE-Skills-Bench**：public SWE skills + deterministic repo tests。
5. **SkillCraft**：executable skill composition / cache / reuse。
6. **AgentSkillOS benchmark**：skill selection + DAG orchestration，但 LLM judge。
7. **CUA-Skill / WindowsAgentArena**：execution/composition graph 明确，但工程重。
8. **EvoSkill’s OfficeQA/SealQA/BrowseComp setup**：failure-driven skill folder evolution，但 benchmark 公共性需核。
9. **Trace2Skill’s SpreadsheetBench-Verified**：SKILL.md patch 非常贴近，但单域。
10. **EffiBench-X**：优化 skill library 很清楚，但偏代码效率专项。

## C. 最适合从 GAIA 迁移并快速跑出结果的 benchmark

1. **SkillLearnBench**：最像你的 critic/actor 闭环，工程负担相对可控。
2. **SkillsBench**：最适合快速做 no-skill / bootstrap / actor-skill 对照。
3. **SkillCraft**：能测 tool allow list 和 skill reuse，结果指标直观。
4. **ALFWorld**：经典、稳定、低工程，但方法叙事不如 skill-native。
5. **WebShop**：经典 web shopping workflow，可做 skill 化策略。
6. **SWE-Skills-Bench**：deterministic，但提分风险高。
7. **SpreadsheetBench-Verified**：适合 SKILL.md patch，单域可控。
8. **SkillFlow**：方法最贴，但先做 smoke，确认 runner 稳定后再主推。
9. **AppWorld**：适合 tool/API skill，但环境比前几项复杂。
10. **Terminal-Bench 2.0**：适合 robustness，不适合第一阶段。

# 5. 缺口和二次核对清单

优先级最高的二次核对：

1. **SkillLearnBench PDF 表格**：需要确认每个 task 的 verifier、instance 划分、L1/L2 是否 LLM judge、最终 outcome 是否 deterministic。项目页已确认 20 tasks / 100 instances / 4 methods / 6 LLMs，但细分数值最好读 PDF 表格。([CXCSCMU][2])
2. **SkillFlow repo/runner 状态**：论文非常贴近你的方法，但需要确认是否已经公开完整 runner、tasks、patch evaluator、skill library format。当前已确认 166 tasks / 20 families / lifelong patch protocol。([arXiv][4])
3. **SkillsBench runner smoke**：需要确认 Harbor/containerized tasks 是否能在你的本地机器稳定跑，尤其是 step limit、tool logs、forced answer、verifier failure 的记录接口。([arXiv][25])
4. **AppWorld / BFCL-v3 / τ²-Bench 的训练成本**：SkillX/SAGE 方向很有价值，但要先核环境搭建、API docs 长度、并行跑法和 state reset。
5. **WebArena 是否值得重碰**：它和 GAIA 一样有 browser/env 噪声，但 web skill 论文太多，若写论文可能要至少做小规模 WebArena smoke。WebArena 官方 repo 自托管和 browser infrastructure 成本不低。([GitHub][34])
6. **SkillClaw / WildClawBench、SkillForge、AgentSkillOS 这些新工作**：叙事强，但 benchmark 公共性、可复现性、评分客观性不足，暂时不适合作主线。
7. **中文论文/中文文章线索**：本轮中文检索主要发现了 SkillClaw、EffiSkill、SkillsBench 等中文解读，但我没有把中文博客当主证据；正式结论仍基于 arXiv / OpenReview / GitHub / project page。

# 6. 最终建议

## 第一主线

**SkillLearnBench。**

理由很直接：它最接近你要证明的东西——不是“agent 会不会答题”，而是“agent 能不能从经验中生成可复用 skill，并在后续实例上真正提升”。你的方法可以自然落进去：

* bootstrap：用少量 instances / trajectories 初始化 skill；
* executor：用 skill 做 held-out instances；
* critic：读失败轨迹，定位 skill 缺失、规则过窄、工具策略错误、验证不足；
* actor：修改 SKILL.md / rules / graph / tool allow list；
* re-eval：看后续 instances outcome 和 trajectory alignment 是否改善。

## 备用 benchmark

**SkillsBench。**

它最适合做静态对照：No Skill / Curated Skill / Self-generated Skill / 你的 Actor-refined Skill。它不一定最适合作 lifelong，但能快速回答一个关键问题：你的 skill 工件是否比普通 prompt 或一次性 self-generated skills 更稳。

## 第二阶段主线

**SkillFlow。**

一旦 runner 稳定，它比 SkillLearnBench 更能体现你的“图结构 / 状态机 / patch / library evolution”。我建议把它作为第二阶段，不是因为不重要，而是因为它太新，先做工程 smoke 再押主线。

## 经典对齐组

保留 **ALFWorld + WebShop**。这组用来让论文读者知道你的方法不只是 skill-native benchmark 上有效，也能对齐 SkillRL / SkillNet / ProcMEM 这类经验/skill/procedural memory 工作。

## 只适合 smoke 或补充

* **SkillCraft**：适合 tool-composition skill 支线，尤其是 tool allow list / executable skill caching。
* **SWE-Skills-Bench**：适合 deterministic 反例分析，证明 skill 质量和 overhead 很关键。
* **SpreadsheetBench-Verified**：适合展示 SKILL.md patch 的细粒度改写，但单域。
* **Terminal-Bench 2.0**：适合最终 robustness，不适合第一阶段。
* **AppWorld**：适合 API workflow skill，但工程和训练成本更高。

## 暂时不建议碰

* **WebArena 作为第一主线**：太容易重现 GAIA 的 web/env 噪声问题。
* **WindowsAgentArena / CUA-Skill 作为第一主线**：叙事很强，但 GUI 工程成本过高。
* **WildClawBench / AgentSkillOS 30-task benchmark 作为主分数**：新且评分/复现不够稳，适合 related/new-paradigm discussion。
* **纯 RAG QA 组如 HotpotQA/NQ/PopQA 单独作为主线**：SkillRL 论文会用，但它们更容易退化成 retrieval/prompt 技巧，不足以突出你的状态机 skill 修改。

## 最推荐的论文实验组合

最稳的组合是：

**主实验：SkillLearnBench**
证明 critic/actor skill 修改能从经验中产生可迁移收益。

**静态 skill 对照：SkillsBench**
证明你的 skill 工件不是普通 self-generated prompt，且可以和 curated skills / no skills 对比。

**经典 agent 对齐：ALFWorld + WebShop**
证明方法不是只对新 benchmark 有效。

**方法特色补充：SkillFlow 或 SkillCraft 二选一**
如果想突出 graph/patch/lifelong，选 SkillFlow；如果想突出 tool allow list / executable skill composition，选 SkillCraft。

我的最终排序是：

1. **先跑 SkillLearnBench。**
2. **同时准备 SkillsBench baseline。**
3. **保留 ALFWorld/WebShop 作为经典对齐。**
4. **SkillFlow smoke 成功后，升级为第二主线。**
5. **WebArena、WindowsAgentArena、Terminal-Bench 先不要放进第一轮。**
