## 0. 这次筛选的硬约束

这轮目标是给接下来要定的 benchmark 提供可执行排序。核心目标是至少在三个 benchmark 上看到 `baseline -> boot skill -> 强化/actor-critic skill` 的可解释提升，候选数要多于三个，给失败和中途放弃留缓冲。

我把口头要求拆成 9 个原子条件，但权重分层处理。本轮真正的硬门槛只有两条：`R1 方法可完整接入` 和 `R4 冻结小模型可打`。其他条件用于排序、风险控制和落地顺序；`R9 任务不太窄` 只保留为叙事层面的低权重参考，不再影响首轮可行性判断。

1. `R1 方法可完整接入`：baseline 能用当前 ReAct/tool executor 跑；skill 能作为外部工件注入 executor；skill 能影响工具选择、阶段路由、验证和答案提交。
2. `R2 数据能支撑泛化`：有 train/dev/test、官方 split、family 顺序协议，或能用固定 seed 建立训练/验证/测试；训练和测试任务形态要足够接近。
3. `R3 端到端主分数清楚`：baseline 和 skill 版本最后能用一个官方或本机固定主分数直接对比；中间指标可以保留作诊断，但 headline 不依赖复杂人工拼装、LLM judge 或多指标临场解释。
4. `R4 冻结小模型可打`：Qwen3.5-9B thinking 作为 executor，且不做参数微调/SFT/RL 时有非零 baseline 和可调空间；允许用 ReAct、工具、检索、scaffold 和外部 skill，但不能把“7B/8B 微调后能做”直接等同为当前 training-free 方法可行。
5. `R5 依赖成本低`：优先离线、本地文件、程序化 scorer；搜索、浏览器、Docker、LLM judge、外部 API 越多，首轮优先级越低。
6. `R6 方便人调`：失败能归入少数清晰类别，人工和 critic 能看懂为什么错，prompt/skill 可以按 benchmark 单独调。
7. `R7 分数可信`：评分尽量是 deterministic verifier、exact/execution/state tests；LLM judge 只适合作补充诊断。
8. `R8 论文/社区对齐`：近期 skill/agent 论文实际跑过，方便和别人讨论，同时避免只依赖本机可跑性。
9. `R9 任务不太窄（低权重）`：只作为论文叙事和 benchmark 组合多样性的补充参考。若一个 benchmark 虽窄但 R1/R4 很稳、分数清楚、能快速闭环，仍应优先跑，例如 SQLBench/AgentBench DB。

评分标记：`Y` 满足，`P` 部分满足或需要工程补齐，`N` 当前不满足或风险高。

- `R1` 不满足：当前方法无法完整接入，默认不进首轮。
- `R4` 不满足：冻结 9B training-free 没有非零 baseline 或明显打不动，默认不进首轮；如果只有微调/SFT/RL 后小模型记录，只能算任务可学，不能作为本方法可行性证据。

- `R9` 不作为淘汰项。

## 1. 当前方法框架理解

当前方法的可迁移单元是：

- `baseline`：小模型 executor 用 ReAct/tool loop 做题，输出最终答案、动作轨迹、工具结果和错误诊断。
- `skill`：外部 `SKILL.md` 或等价 skill artifact 注入 executor；内容包括阶段职责、工具 allowlist、Next 边、短路径、验证规则、repair 规则、答案格式规则。
- `BOOT`：强模型或 Codex skill generator 读取 runtime contract 和训练任务快照，生成初始 skill。
- `critic`：读取一批训练轨迹，按失败族和成功锚点给 actor-facing reward 或修改建议。
- `actor`：改写 skill，可能锁图只改规则，也可能在 graph-unlocked 设置下改节点、边、阶段职责和 allowlist。
- `re-eval`：同一 executor 在 dev/test 或 held-out split 上重新评估，比较分数、步数、空答、max-step、工具失败和错误族。

因此，候选 benchmark 必须能被改造成以下闭环：

`task input -> executor + tools + optional skill -> trajectory -> deterministic/mostly deterministic single headline score -> critic row -> actor skill patch -> held-out re-eval`

当前最适合承接的 benchmark 通常有这些特征：任务可分 family、工具面有限、输入可控、scorer 稳定、失败轨迹能压成表格。纯网页开放搜索、大型 repo 修复、GUI 感知类任务会把大量误差放到 infra、检索、上下文和长程规划里，首轮风险更高。

按新优先级，首轮排序先看硬门槛：`R1 方法完整接入` 和 `R4 冻结 9B training-free 可打`。`R3 端到端主分数清楚`、`R2 split/泛化`、`R5 成本`、`R6 可调` 是第二层排序因素。`R9 任务宽窄` 只影响最后的 benchmark 组合叙事，不再压低 SQL/DB 这类窄但稳的候选。

### 第一批执行候选

1. `WebShop text/offline`
2. `SQLBench / AgentBench DB`
3. `tau2 hard subset`
4. `OfficeQA staged`
5. `SkillsBench small smoke`
6. `AppWorld simple subset`

这批覆盖购物检索、数据库执行、客服工具任务、文档检索与表格、显式 skill artifact、API 状态世界。按硬门槛重排后，WebShop/SQL/tau2 更靠前；OfficeQA、SkillsBench、AppWorld 仍保留在候选池，但必须先过 9B small smoke 或 staged 口径。Tau2 只建议先选 `DB / COMMUNICATE / ENV_ASSERTION` 这类硬口径任务；`NL_ASSERTION` 留作诊断或第二阶段。

### R4 training-free 小模型证据补充

这里把小模型证据分三档看：

- `A`：冻结 7B/8B/9B 或同量级模型在 prompt/tool/scaffold 条件下有非零公开或本机记录。
- `B`：小模型经过 SFT/RL/领域微调后有记录，只能说明任务可学，不能直接支撑当前 training-free 方法。
- `C`：公开主结果主要依赖 frontier model、大 agent harness 或商业闭源小模型；冻结 9B 可行性需要本机先验收。

| `OfficeQA`                 | `C + 本机低分` | 官方主结果面向 frontier agents；本机 `Qwen3.5-9B ReAct / full246 / evoskill_corpus / exact0` 只有 `8/246 = 3.25%`。主要瓶颈是 697 个文件里的路由和表格定位。R4 只能算 staged：先做 `oracle_source_files` 和 `retrieval_topk`，再谈 full corpus。 |
| `SQLBench / AgentBench DB` | `A+B`          | text-to-SQL 有大量 7B 级专用/微调模型记录；冻结通用 9B 也有机会靠 schema inspect、SQL 执行和 repair 拿到非零。任务域窄，工具反馈强，适合作工程保底。                                                                                                     |

### 条件候选

`tau2 / tau-bench retail+airline` 的方法适配度高，任务也像真实工具 agent。它的首轮风险集中在评估解释成本：full 口径里 reward 由多个 basis 乘起来，retail 里还常见 `NL_ASSERTION`。会议上建议把 Tau2 表述为“条件 P1：先跑硬子集，再决定 full 口径”。

`OfficeQA`、`SkillsBench`、`AppWorld` 的条件性来自 `R4`，不是来自方法接入。三者都能接 skill/executor，但 frozen 9B training-free 是否有足够非零 baseline 需要先验收：

- `OfficeQA`：先跑 `oracle_source_files` 和 `retrieval_topk`；full corpus 只有在路由 recall 和 9B 读表计算都过线后进入主线。
- `SkillsBench`：Docker/native verifier 修好后先跑少量 no-skill/with-skill smoke，确认 frozen 9B 能完成至少一部分任务族。
- `AppWorld`：先跑 difficulty-1 或 train/dev 简单子集，压缩 API docs，不直接把 457 个 API 全暴露给 9B。

### 当前暂缓候选

`BrowseComp`、`WebArena`、`Terminal-Bench`、`SWE-bench`、`WindowsAgentArena/OSWorld` 都有论文价值，但它们把主要风险集中到搜索/浏览器/Docker/长 repo/GUI 感知上。首轮用这些作为主线，会很难区分是方法问题、模型问题还是环境问题。

## 4. 主要候选详细分析

### 4.1 WebShop

**Benchmark 在做什么**

WebShop 是模拟电商购物任务。agent 根据用户需求搜索商品、筛选属性、打开候选、选择选项并提交购买。任务流程明确，技能空间也明确：需求解析、搜索关键词、候选过滤、属性核对、购买前验证。

**哪些论文或系统跑过**

- `WebShop: Towards Scalable Real-World Web Interaction with Grounded Language Agents`，2022，原始 benchmark。
- `SkillRL: Evolving Agents via Recursive Skill-Augmented Reinforcement Learning`，2026，这是当前最强的同类证据。SkillRL 把 WebShop 作为主实验之一，用 `Qwen2.5-7B-Instruct` 量级模型，先做 SFT，再做 GRPO + SkillBank；GitHub 里有 `examples/grpo_trainer/run_webshop_skills.sh`，配置包括 `env.env_name=Webshop`、`env.max_steps=15`、`top_k=6`、`enable_dynamic_update=True`、`update_threshold=0.4`、`max_new_skills=3`、`trainer.n_gpus_per_node=8`、`total_epochs=150`。这说明 WebShop 已经被“技能注入 + RL”范式正式跑过。
- SkillRL 仓库还提供 WebShop SFT/RL checkpoint 下载入口，并在环境准备里使用原生 WebShop 的 `./setup.sh -d all`，即完整商品库口径。
- `SkillNet` 和 `GraSP` 相关 skill/graph 工作也把 WebShop 列为经典 agent benchmark，但当前会议里优先引用 SkillRL，因为它和“skill + RL 提升”目标最贴近。

结论：WebShop 的优先级应该高于单纯“经典 web agent benchmark”。它有同类 skill-RL 论文证据、有自动 reward、有可落地动作空间。需要注意的是，SkillRL 的配置是完整 SFT/RL 训练链路和 8 卡训练，我们当前第一阶段只能把它作为“方法适配强证据”，不能直接承诺复现同等幅度。

**小模型 / training-free 证据**

WebShop 是 6 个主候选里小模型证据最稳的一类。公开记录里有 Qwen2.5-7B 量级 prompt/ReAct/Reflexion 非零结果，也有 SkillRL 这种 SFT/GRPO + SkillBank 训练后提升记录。当前 R4 判断只引用前者作为 training-free 可行性；后者只说明任务对 7B 级模型可学、skill/RL 空间存在。

对我们来说，第一阶段应以 frozen `Qwen3.5-9B + offline text env + tool ReAct + skill` 为准。如果 offline attr_small baseline 非零，WebShop 就可以进入 boot/actor；如果只在训练后模型上有效，就不能算当前方法的直接证据。

**普通 agent 工作流**

1. 读购物目标，抽取硬约束和软约束。
2. 生成搜索 query。
3. 浏览搜索结果和商品页。
4. 比较候选商品属性。
5. 选择颜色/尺寸/规格等选项。
6. buy now，并由环境给 reward/success。

**评估手段**

WebShop 的评分发生在 `buy now` 后。原生环境返回 `observation, reward, done`；本机 offline text env 用 `score_purchase(...)` 做确定性打分：

- `type_score`：是否买到目标 ASIN。
- `attribute_score`：商品文本是否覆盖任务要求的属性。
- `option_score`：颜色、尺寸、规格等 required options 是否选对。
- `price_score`：是否满足价格上界。
- 最终 reward 当前是 `0.45 * type + 0.25 * attribute + 0.20 * option + 0.10 * price`；`done && reward >= 0.999` 记为 success。

这里最终自然语言回复基本不参与评分，关键是动作轨迹是否买到了正确商品。建议同时报告 `mean reward` 和 `success rate`，因为小模型可能买到相近商品导致部分分。

**数据与 split**

原始 WebShop 有 1.18M products、12,087 instructions、1,600+ human demonstrations。本机当前已落地：

- 1000-product preview。
- human_small：13 题。
- attr_small：415 题。
- smoke：3 题，offline small text env 3/3。

**适配当前方法**

适配度高。当前 ReAct+skill executor 能自然接 search/click/select/buy action。skill 可以规定“先抽约束、再查属性、购买前必须核对每个硬约束、避免被标题相似商品骗走”。critic 能按 search miss、wrong candidate、wrong option、premature buy 分组。

**复现难度**

低到中。offline small text env 已经能跑，适合快速验证。原生 WebShop 需要 Pyserini/Lucene/spaCy/OpenJDK/faiss 和索引构建，作为第二阶段。

**建议用法**

第一轮用 `attr_small` 抽 100 题做 baseline/boot/actor，再扩大到 415。先用 offline text env 固定分数口径，拿到信号后再考虑 native WebShop。

### 4.2 OfficeQA

**Benchmark 在做什么**

OfficeQA 是企业文档 grounded reasoning benchmark。任务要求从 Treasury Bulletin 文档中检索证据、定位表格、做定量计算，并输出短答案。它有文档路由、表格读取、计算、单位/格式规范几类清晰失败点。

**哪些论文或系统跑过**

- `OfficeQA Pro: An Enterprise Benchmark for End-to-End Grounded Reasoning`，2026，提出 OfficeQA Pro，默认 frontier model 评测集为 133 题。
- `EvoSkill: Automated Skill Discovery for Multi-Agent Systems`，2026，把 OfficeQA full 246 作为主实验之一；文档记录的口径是 Claude Code + Opus 4.5，OfficeQA 60.6% -> 67.9%，train sizes 为 12/24/36，validation 17，其余 held-out test。

**小模型 / training-free 证据**

OfficeQA 的公开主结果主要面向 frontier agents。论文里有 GPT-5 Mini、Claude Haiku、Gemini Flash 等较小商业模型/agent ablation，但这些仍依赖强 agent harness、文件搜索和解析工具，不能直接代表本地 frozen 9B。

本机已经有最关键的负面先验：`Qwen3.5-9B-local ReAct / full246 / evoskill_corpus / exact0` 是 `8/246 = 3.25%`。这说明 full corpus 下，小模型主要卡在从 `697` 个 TXT 里找对 `1-2` 个 gold bulletin 文件，再定位表格和行列。R4 因此改成 `P/N`：OfficeQA 仍可做 staged benchmark，但首轮不能直接把 full-corpus 作为 9B 主实验。

**普通 agent 工作流**

1. 读问题，抽年份、月份、表名、字段、单位和计算类型。
2. 从 corpus 中路由到 1-2 个主要 Treasury Bulletin 文件。
3. 定位 page/section/table/line window。
4. 抽取数值并调用 calc/python。
5. 做单位、月份、财政年度和 rounding 检查。
6. 输出 scorer-friendly 短答案。

**评估手段**

OfficeQA 的主评分是“最终短答案 vs gold answer”。本机 adapter 已接 `external_refs/officeqa/reward.py` 里的 `score_answer(expected, prediction, tolerance)`：

- `exact`：`tolerance=0.0`，得分 1/0，适合最硬的 headline。
- `multi_tolerance`：按 `0.0 / 0.01 / 0.025 / 0.05 / 0.10` 多个 tolerance 加权平均，当前本机口径把 `score >= 0.8` 视为 passed。
- evidence、source file 命中、retrieval_topk、计算轨迹可以作为诊断指标；最终主分数仍由 answer scorer 给出。

因此 OfficeQA 会议口径建议写清：`split + evidence access + scorer`，例如 `OfficeQA full / retrieval_topk / exact0` 或 `OfficeQA Pro / oracle_source_files / multi_tolerance`。

**数据与 split**

本机已落地：

- `officeqa_full`：246 题。
- `officeqa_pro`：133 题。
- transformed TXT corpus：697 个 txt，383,162,413 bytes。
- 本地 EvoSkill-style split：full train 12/24/36，val 17，其余 test；pro 也有固定 seed split。
- official reward exact 和 multi-tolerance scorer 已接。

**适配当前方法**

适配度高，但要分阶段。full corpus 对 9B 直接太硬，remote132 c8 的 `Qwen3.5-9B ReAct` full/exact0/evoskill_corpus 只有 8/246。这个结果说明全量文档路由是瓶颈。合理路线是先做：

1. `oracle_source_files + 9B`：测读表/计算上限。
2. `retrieval_topk + 9B`：测路由和表格定位。
3. `evoskill_corpus + 9B agent`：最后对齐 headline。

skill 可以编码 router、table locator、calc、answer normalizer 和错误恢复规则。critic 的错误族也清楚：route miss、wrong table、wrong row/column、calendar/fiscal mix、calc、unit/format。

**复现难度**

中高。数据和 scorer 已准备好，主要难点在小模型路由。它适合作为“可调 benchmark”，首轮 headline 不宜直接拿 full-corpus exact0 硬比 Claude Code。

**建议用法**

把 OfficeQA 当作 staged benchmark：报告 `full/pro + exact/multi_tolerance + evidence_access + model/harness`。先追 retrieval_topk 和 oracle_source_files 的提升，再把方法迁回 evoskill_corpus。

### 4.3 SQLBench / AgentBench DB

**Benchmark 在做什么**

SQLBench / AgentBench DB 是数据库问答和 text-to-SQL 类 benchmark。任务给自然语言问题、数据库 schema 和可执行 SQLite/SQL 环境，agent 需要检查 schema、写 SQL、执行验证，并提交最终 SQL 或查询结果。它任务域偏窄，但端到端主分数最干净。

**哪些论文或系统跑过**

- `Spider: A Large-Scale Human-Labeled Dataset for Complex and Cross-Domain Semantic Parsing and Text-to-SQL Task`，2018，经典跨库 text-to-SQL benchmark。
- `BIRD: A Big Bench for Large-Scale Database Grounded Text-to-SQL Evaluation`，2023，强调真实数据库、外部知识和执行准确率。
- `AgentBench: Evaluating LLMs as Agents`，2023，把 DB 作为 agent 子任务之一，评估模型在交互式数据库环境中的执行能力。

**小模型 / training-free 证据**

SQL 是小模型可行性较高的工程保底项。text-to-SQL 社区有大量 7B 级专用/微调模型结果，说明任务可学；当前 training-free 口径还需要看 frozen 9B 在我们的 executor 里能否利用 schema inspect、SQL execution error、空结果和 repair 反馈。由于工具反馈强、上下文结构化、评分确定，R4 给 `Y/P`。

这里的风险是叙事偏窄：skill 很可能变成 SQL checklist。它适合证明 `baseline -> skill -> actor` 链路可以稳定提升，不适合单独支撑“通用 agent skill”故事。

**普通 agent 工作流**

1. 读问题和 database/schema 描述。
2. inspect tables、columns、foreign keys 和样例值。
3. 写 SQL 并执行。
4. 根据 execution error 或空结果修复。
5. 对比结果形态、排序、聚合和去重。
6. 提交最终 SQL 或答案。

**评估手段**

主评分是 execution accuracy：执行模型生成的 SQL，把结果集和 gold SQL 的结果集比较；SQL 执行错误、schema 不存在、结果集不匹配都记 0。对于 AgentBench DB 里非标准 SQL 输出或简单答案型任务，本机 adapter 会走 normalized answer / DB result comparison。中间可以看 SQL error rate、空结果率、repair 次数和执行步数，但 headline 只需要一个 accuracy。

**数据与 split**

本机已落地或可用：Spider dev 1034、Spider test 2147、BIRD Mini-Dev SQLite 500、AgentBench DB dev 60 / standard 300 / out-new 4803。Spider 和 AgentBench DB 的切分清楚；BIRD Mini-Dev 更适合先做小规模 smoke 和调试。

**适配当前方法**

适配度高。skill 可以写成 schema inspect、join path、aggregation、execution repair、answer normalization 的流程规则。critic 容易把失败分成 schema miss、join miss、aggregation、filter、排序/limit、SQL syntax、空结果和格式错误。actor patch 后可以直接看 execution accuracy 是否提升。

**复现难度**

低。依赖主要是本地 SQLite、数据文件和现有 adapter，评分便宜且可批量。主要短板是任务单域，方法故事容易变成“SQL checklist 优化”，所以它更适合作单分数验收和兜底，不适合单独承担全部方法叙事。

**建议用法**

首轮用 AgentBench DB dev 60 或 Spider dev 子集做 baseline/boot/actor 快速闭环；如果 WebShop/OfficeQA 短期被检索或环境卡住，用 SQLBench 提供一条确定的单分数对照曲线。最终论文里可作为保底实验或附表。

### 4.4 SkillsBench

**Benchmark 在做什么**

SkillsBench 是显式 skill artifact benchmark。它把 skill 作为一等输入变量，比较 no skill、curated skill、self-generated skill。任务跨多个专业领域，配 deterministic verifier。

**哪些论文或系统跑过**

- `SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks`，2026，官方站点写明 84 evaluated tasks、5 trials per task；Codex GPT-5.2、Claude Code、Gemini CLI 都有 without/with skill 对照。
- `SkillLearnBench`，2026，17 个 task 改自 SkillsBench。
- `How Well Do Agentic Skills Work in the Wild`，2026，在 SkillsBench 上研究 realistic skill retrieval/refinement。
- `Graph of Skills`，2026，把 SkillsBench 用于 structural skill retrieval。

**小模型 / training-free 证据**

SkillsBench 的公开主结果主要是 Codex/GPT-5.2、Claude Code、Gemini CLI 这类强 agent。它对我们的“skill 文件是否有用”非常贴合，但当前未核到 7B/9B frozen 主结果。R4 因此只能给 `P/N`：要先用本机 9B 跑少量 no-skill/with-skill smoke，确认至少一部分 task family 有非零 baseline 和可解释失败。

如果 9B 在 Docker/native verifier 下大量卡在文件编辑、依赖安装或长日志理解，SkillsBench 就会变成强 agent benchmark，首轮应降级到方法对照附表或少量精选任务。

**普通 agent 工作流**

1. 读任务说明和 workspace。
2. 选择 no skill / curated skill / generated skill 条件。
3. 执行文件处理、代码、科学计算、表单、数据分析等任务。
4. verifier 运行测试或检查输出。
5. 统计 pass rate、token、cost、skill usage。

**评估手段**

SkillsBench 的主评分来自每个任务自带的 deterministic verifier。典型流程是 agent 修改 workspace 产物后，Harbor/BenchFlow 在隔离环境里运行 `tests/test.sh` 或等价 verifier；verifier 会写 `/logs/verifier/reward.txt`，同时保留 `ctrf.json`、pytest 输出或任务自定义诊断。

- 多数任务是 0/1 pass/fail。
- 少量任务可能写连续 reward 或按 rubric 脚本折算分数；headline 建议统一报告 pass rate，同时保留 mean reward 作为补充。
- 这里评分对象是文件、脚本、表格、数据结果或程序状态，不是聊天最终答案。

最适合我们的对照口径是 `no skill / boot skill / actor skill` 三档固定模型、固定任务集、固定 verifier，比 pass rate、mean reward、token、步数和失败族。

**数据与 split**

论文口径：86 tasks，84 evaluated，11 domains。
本机当前 registry：94 tasks；metadata full eval 94/94。
当前没有自然 train/dev/test；更适合作静态 A/B 或按 domain/task family 自建 train/test。

**适配当前方法**

方法形态极高匹配：我们本来就要注入外部 skill，然后比较 baseline/with skill/actor-modified skill。它适合展示“skill 文件有没有用”。短板是 lifelong/held-out 泛化需要自建协议，或从 task family/domain 里切分。

**复现难度**

中高，主要卡 Docker。本机 BenchFlow venv 已准备，native smoke 因 `/var/run/docker.sock` 权限拒绝阻塞。Docker 权限解决后，它会变成最值得马上跑的显式 skill benchmark。

**建议用法**

Docker 修好后先锁 paper 版或本机 94 registry 版，避免版本漂移。实验分三档：no skill、boot skill、actor skill；再加 task-domain split 检查是否泛化。

### 4.5 AppWorld

**Benchmark 在做什么**

AppWorld 是 9 个日常应用、457 个 API、106 个虚拟用户组成的可控 app world。agent 要写代码或调用 API 来完成数字生活任务，最终由 state-based unit tests 和 execution tests 判定。

**哪些论文或系统跑过**

- `AppWorld: A Controllable World of Apps and People for Benchmarking Interactive Coding Agents`，ACL 2024 Best Resource Paper，官方 benchmark。
- `Reinforcement Learning for Self-Improving Agent with Skill Library` / SAGE，2025/2026，把 AppWorld 作为主实验，报告 Scenario Goal Completion 提升、步数和 token 降低。
- `SkillX: Automatically Constructing Skill Knowledge Bases for Agents`，2026，把 AppWorld、BFCL-v3、τ²-Bench 作为三组主实验之一；Deep Research 文档记录 Qwen3-32B、Kimi-K2、GLM-4.6 在 AppWorld 上有 skill KB 提升。

**小模型 / training-free 证据**

AppWorld 有直接的 frozen 8B 公开信号，但绝对值偏低。`Three Roles, One Model` 在同一个 Qwen3-8B 上做 inference-time scaffold，raw task goal completion 约 `5.4%`，三角色 scaffold 后约 `8.9%`；difficulty-1 子集从约 `15.8%` 到 `26.3%`。这符合 training-free 约束，也说明小模型有非零入口。

风险也很明确：9 个 app、457 个 API、代码执行、登录/credential、跨 app 状态更新和 collateral damage 检查都会压小模型。AppWorld 适合作第二批真实工具 agent benchmark；首轮需要先装本地 CLI 跑 train/dev 简单子集，确认我们的 9B + 压缩 API docs + skill workflow 能有非零 baseline。

**普通 agent 工作流**

1. 读任务和约束。
2. 查询相关 app/API docs。
3. 写短代码或调用工具读取状态。
4. 跨 app 组合数据、更新状态。
5. 运行 verifier 或看 state diff。
6. 修复参数、顺序、遗漏状态或 collateral damage。

**评估手段**

AppWorld 的评分主要看应用世界的最终状态。agent 通过 API/代码读取和更新多个 app 后，官方 evaluator 运行 state-based unit tests / execution tests，检查目标状态是否达成，以及是否造成不该有的副作用。

- 单题可看 `Task Goal Completion` 或等价 task-level success。
- 论文常报告 `Scenario Goal Completion`，适合看一组相关任务/场景是否完成。
- 多采样设置下可以看 `Avg@k` 或 best-of-k；首轮建议先用 pass^1/SGC，避免把采样收益和 skill 收益混在一起。

AppWorld 也不是按最后自然语言答案打分；最终回复主要用于结束任务，真正的分数来自 app state tests。

**数据与 split**

官方 benchmark：750 tasks。公开资料和调研文档记录的 split 为 Train 105、Dev 60、Test-Normal 168、Test-Challenge 417。

**适配当前方法**

适配度高。它很适合把 skill 写成 API workflow、read/write 隔离、验证节点、repair 策略和 collateral damage 检查。相比 OfficeQA，它更像工具 agent；相比 WebArena，它更稳定。9B 小模型可能吃力，但任务有 API docs 和 state tests，skill 有机会把规划空间压下来。

**复现难度**

中等。本机还没落地，但官方命令是 `pip install appworld && appworld install && appworld download data`。需要单独评估安装体量、数据下载和本机环境。它值得作为第二批安装目标。

**建议用法**

如果会议上要选一个“更像真实 agent 工作流”的 benchmark，AppWorld 比 WebArena/SWE 更合适。先装本地 CLI，抽 train/dev 小集跑 baseline，再判断 9B 是否有可调空间。

### 4.6 tau2 hard subset / tau-bench retail+airline

**Benchmark 在做什么**

tau-bench / tau2 是工具-用户-代理交互 benchmark。任务通常是客服场景，agent 要读 policy、查用户/订单/航班状态、调用读写工具、最后给用户回复。它比 SQL 更像 agent，又比 GAIA/WebArena 更可控。

**哪些论文或系统跑过**

- `τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains`，2024，benchmark 原始工作，报告 tool-calling、ReAct 等策略在 airline/retail 上的 pass^k。
- Deep Research 文档中的 `SkillX: Automatically Constructing Skill Knowledge Bases for Agents`，2026，把 `τ²-Bench` 作为 tool-agent benchmark 之一，和 AppWorld、BFCL-v3 一起验证 skill KB。

**小模型 / training-free 证据**

tau-bench/tau2 的冻结 7B/8B 公开证据比 WebShop/SQL 少，但它的动作空间比 AppWorld 更可控：domain policy、read/write tools、DB state 和 communication assertion 都能被 skill 压缩。已有 Qwen3-8B 类环境扩展/工具交互工作把 tau-bench 作为目标之一，可作为弱正向证据。

当前 R4 给 `P`。它的可行性应由本机 hard subset 决定：先避开 `NL_ASSERTION`，只跑 `DB / ENV_ASSERTION / ACTION / COMMUNICATE` 这类硬口径，看 frozen 9B 是否能通过 policy skill 提升 pass^1。

**普通 agent 工作流**

1. 读取用户目标和 domain policy。
2. 识别需要哪些状态：用户身份、订单/预订、限制条件。
3. 先调用 read-only 工具确认状态。
4. 按 policy 判断可执行、应拒绝、需澄清或需写入。
5. 调用 write 工具更新数据库状态。
6. 用 reward basis / assertion 检查 DB、ACTION、COMMUNICATE 是否满足。

**评估手段**

Tau2 的评分核心是 `reward_basis` 组合检查项；最后给用户回得像不像，主要通过 `COMMUNICATE` 或可选 `NL_ASSERTION` 影响分数。单轮 simulation 结束后，官方 evaluator 按任务里的 `reward_basis` 组合多个检查项，最终 reward 是这些检查项的乘积；`pass^1` 可以理解为 reward 是否达到 1.0，多次采样时再统计 `pass^k`。

- `DB / ENV_ASSERTION`：把 agent 实际调用工具后的最终环境状态，与按 gold actions 重放得到的目标状态比较；同时跑任务给出的环境断言。
- `ACTION`：检查轨迹里是否出现了任务要求的工具调用，主要比 tool name 和 arguments。
- `COMMUNICATE`：检查 agent 的 assistant 消息里是否包含 `communicate_info` 指定的信息；这是“最后给用户回复”的主要评分入口。当前实现偏字符串包含检查，大小写不敏感，并会去掉逗号。
- `NL_ASSERTION`：可选的自然语言断言，依赖 LLM judge；首轮建议单独报告，不把它混进主 headline。

所以 Tau2 的可靠 headline 应写成：`pass^1 / average reward / DB reward / ACTION reward / COMMUNICATE reward / 平均工具步数`。如果某题只要求状态更新，最后回复写得自然并不会自动得分；如果 reward_basis 包含 `COMMUNICATE`，回复里缺了指定信息会直接把最终 reward 乘成 0。

**数据与 split**

本机已落地：

- retail：base 114，train 74，test 40。
- airline：base 50，train 30，test 20。
- oracle smoke：retail 1/1，airline 1/1。

外部 tau2 版本还包含 telecom，但本机当前资产主要是 retail/airline。

**适配当前方法**

适配度高。skill 可以写成 policy skill：read/write 工具分层、拒绝规则、澄清规则、写入前复核、最后 communication 模板。critic 可以按失败类型归因：policy miss、wrong tool、missing read、wrong write、communication mismatch。actor 修改 skill 后，train/test split 能看泛化。

**复现难度**

中等。当前 oracle replay 已通；真 agent 评测还要接 user simulator/tool loop。full 口径如果包含 `NL_ASSERTION`，评分解释成本会上升。工程量比 SQL/WebShop 大，比 WebArena/SWE 小，适合作为条件候选。

**建议用法**

先筛 `reward_basis` 为 `DB / COMMUNICATE / ENV_ASSERTION` 的硬口径子集，优先 airline；`NL_ASSERTION` 只作诊断或第二阶段。首轮用 airline train 10-20 做 boot/critic，再在 airline test 20 或 hard subset held-out 上看 `pass^1`。指标同时记录 DB reward、ACTION reward、COMMUNICATE reward 和平均工具步数，但主 headline 只保留一个 `pass^1` 或 average reward。

## 5. SWE 独立分析

这里把 `SWE-bench` 和 `SWE-Skills-Bench` 分开看。

### 5.1 SWE-bench

**它在做什么**

SWE-bench 是真实 GitHub issue 修复 benchmark。每题给原始 issue 文本和 base commit 下的代码仓库，agent 需要提交 patch。评测时应用隐藏测试补丁，检查 fail-to-pass 和 pass-to-pass 测试。

公开信息：

- 原始论文：`SWE-bench: Can Language Models Resolve Real-world Github Issues?`，ICLR 2024。
- Full test split：2,294 issue-commit pairs，12 个 Python repositories。
- Lite：300 test tasks，另有 23 dev instances，偏更小、更自包含。
- Verified：500 human-verified solvable tasks。

**对当前方法的适配判断**

SWE-bench 是很标准的 coding-agent benchmark，而且小模型路线证明它“可学”。但它对当前 9B ReAct+skill 框架不适合作首轮主线，原因在迁移单元和工程瓶颈。

1. 原始小模型分数很低。ICLR 2024 原论文里，`SWE-Llama 7B/13B` 在 BM25 检索上下文下 Full 只有 `0.70% / 0.70%` resolved，Lite 约 `1.33% / 1.00%`；即使给 oracle 文件上下文，Full 也只有 `3.01% / 3.97%`。这说明裸小模型主要卡在 repo 定位、上下文筛选、patch 质量和测试反馈使用上。
2. 后续 7B/8B 能明显上来，但靠的是完整 coding-agent 训练和 scaffold。公开结果里，`Qwen2.5-Coder-7B-Instruct` 经 ADP/SWE-agent/OpenHands 类轨迹训练后可到约 `20%` Verified；`SWE-Dev-7B` model card 报 `23.4%` Verified。这个证据说明 SWE-bench 可学，但学习对象主要是代码代理行为、文件定位、补丁生成和测试循环，远多于文本 skill。
3. 上下文长度本身可通过工具规避，真正难点是 context acquisition。agent 需要从 issue、traceback、repo tree、`rg` 结果和测试输出中判断该看哪些文件。很多 issue 不直接给文件名；关键词会命中 docs/tests/多个模块；小模型容易打开错文件或被长日志带偏。
4. 当前方法的 skill 可以表达 coding workflow，例如“先找相关测试、最小修改、跑 targeted test、避免大改”。但 SWE-bench 的得分更依赖 file edit/apply patch、shell/test runner、Docker 环境、失败日志压缩、repo indexing 这些 coding-agent 工程能力。
5. 迁移性弱。issue fixing 是很宽的任务概念，12 个 repo 内部也有大量不同 API、测试风格和 bug 类型。训练集上沉淀的 skill 容易变成泛化的开发习惯，迁移到 held-out issue 的边际增益可能小；做成 repo-specific skill 又会引入过拟合和泄漏风险。
6. 数据口径容易被质疑。Lite/Verified 常被当作 test 口径；如果用同一批失败题反复生成 skill 再复测，会形成 test leakage。干净做法需要自己切 dev/held-out，但这样又降低官方 leaderboard 可比性。
7. 环境依赖重。每题要 Docker/镜像/依赖/测试超时，评估成本和失败排查成本远高于 WebShop/OfficeQA/SQL 这类单分数 benchmark。

**给对方的回应口径**

可以这样说：

> SWE-bench 我认可它的价值，它是标准的 repo-level issue fixing benchmark，主分数也很干净，就是 `% resolved`。而且小模型有可见上升空间，7B/8B 经过 SWE-agent/OpenHands 轨迹训练以后能从个位数甚至接近 0 提到 20% 左右，说明这个任务是可学的。
>
> 但它对我们当前这条 skill 方法迁移性差，主要瓶颈会落在 coding-agent scaffold：repo 定位、文件编辑、测试选择、Docker 环境、长日志压缩和 patch 生成。我们的 skill 能改善开发流程，但第一批实验很难把收益和这些工程因素分开。
>
> 如果你们已经有成熟 SWE-bench 跑法，可以作为单独 coding-agent 线保留；我们这边争取三组稳定提分时，先不把 SWE-bench 放进主候选。折中方案是拿 Lite/Verified 里单文件、短 patch、issue 关键词明确的小子集，自己切 dev/held-out，用 `% resolved` 做 exploratory result，别把它当第一批主结果。

### 5.2 SWE-Skills-Bench

**它在做什么**

`SWE-Skills-Bench: Do Agent Skills Actually Help in Real-World Software Engineering?`，2026-03-16 arXiv。它专门隔离“给 SWE agent 注入 skill 有没有边际收益”。数据包含 49 个 public SWE skills、约 565 task instances、6 个 SWE subdomains、fixed commits 和 execution-based tests。

**关键发现**

论文摘要报告：49 个 skill 里有 39 个零提升，平均收益只有 +1.2%；token overhead 最高到 451%；只有 7 个 specialized skills 有明显收益，3 个 skill 会因版本/上下文不匹配带来退化。

**对当前方法的适配判断**

它比 SWE-bench 更贴近“skill 是否有用”，但它的结论本身提示风险：公开通用 SWE skill 很容易变成 token overhead。当前方法如果上这个 benchmark，合理目标是证明 actor/critic 生成的 task-conditioned skill 比 public static skill 更有用。这个目标很有价值，工程成本也高。

**会议建议**

SWE-Skills-Bench 可作为后期“负压力测试”或回应对方的补充论据。首轮争取三组 benchmark 提升时，优先级低于 WebShop、OfficeQA、SQLBench/AgentBench DB、SkillsBench、AppWorld 和 tau2 hard subset。

## 6. 建议会议结论

建议直接给出三层方案，先按 `R1/R4` 硬门槛排序：

1. **硬门槛优先池**：`WebShop offline`、`SQLBench / AgentBench DB`、`tau2 hard subset`、`SealQA`。
2. **R4 待验收条件池**：`OfficeQA retrieval_topk/oracle_source_files`、`SkillsBench small smoke`、`AppWorld simple subset`。
3. **后补池**：`ALFWorld` 以及其他能快速证明 frozen 9B 非零的环境。

首轮落地顺序建议：

1. `WebShop offline attr_small`：最快验证 baseline/skill/actor 的完整链路。
2. `SQLBench / AgentBench DB`：单一主分数最干净，用 execution accuracy 快速验收方法链路。
3. `tau2 hard subset`：只把 `DB / COMMUNICATE / ENV_ASSERTION` 硬口径放进主 headline；`NL_ASSERTION` 作为诊断项或第二阶段。
4. `SealQA`：已有 9B baseline 非零，可作为补位单分数实验。
5. `OfficeQA staged`：先固定一个主 scorer，例如 `exact0` 或 `multi_tolerance`，再区分 oracle_source_files / retrieval_topk / full corpus；full corpus 只作为最终对齐档。
6. `SkillsBench native`：等 Docker 权限解决后先跑 9B small smoke，再决定是否进入主表。
7. `AppWorld`：单独安装和 smoke，作为第二批真实 app/API agent benchmark。

给会议的短结论可以这样说：

> 我们当前方法是 frozen 9B + tools + skill 的 training-free 路线，所以首轮硬门槛是两条：方法能完整接入，冻结小模型本身能打出非零 baseline。任务宽窄不是主要过滤项。按这个口径，WebShop 和 SQLBench/AgentBench DB 最稳，tau2 hard subset 可以补真实工具任务，SealQA 可作 9B 非零补位；OfficeQA、SkillsBench、AppWorld 都要先做 staged small smoke。OfficeQA 的主要问题是 697 个文件里的路由和表格定位，AppWorld 的主要问题是 457 个 API 和代码/状态更新，SkillsBench 的公开结果偏强 agent。SWE-bench 仍作为独立 coding-agent 线，先不计入三个提分主目标。
