## 可直接复制给 Deep Research 的提示词

我正在做一个 agent skill learning / SkillRL 方向的研究原型。当前方法可以理解为“外部 skill 工件 + 状态机式执行约束 + critic/actor 自动改 skill”的闭环。

当前 skill 工件类似一个 `SKILL.md`/skill package，但内容比普通提示词更结构化。它大致包含：

- `metadata`：skill 版本、适用 benchmark、来源、约束版本、是否允许最终作答等。
- `graph`：一张任务执行状态图，包含若干节点/阶段，以及允许的边/状态转移。例如 `INIT -> LOCAL_EVIDENCE / WEB_EVIDENCE / COMPUTE -> VERIFY -> REPAIR` 这类结构。
- `nodes / phases`：每个节点有自己的职责说明，例如读题、定位本地文件、搜索网页、解析媒体、计算、验证、修复、最终提交。
- `allowed_tools / tool allow list`：每个节点允许使用哪些工具，避免 executor 在错误阶段乱用工具或过早作答。
- `rules`：每个节点的执行规则、证据要求、停止条件、验证要求、修复策略、答案格式约束。
- `answer policy`：规定哪些阶段可以输出最终答案，是否采用 no-CONCLUDE / only-CONCLUDE / any-phase answer 等策略。
- `repair / verification policy`：当搜索失败、工具报错、证据不足、SQL/脚本执行失败或答案不确定时，如何重新定位错误并修复。

当前训练/迭代链路大致是：

- `bootstrap`：先看一批训练/dev 任务和执行轨迹，生成初始 skill 或初始图结构。
- `executor`：带着这个 skill 去真实环境里做题，产出完整轨迹、工具调用、最终答案、score、失败原因、步数、forced answer、missing answer 等指标。
- `critic`：读取真实执行结果，分析哪些题做对/做错、哪些节点或规则导致失败、工具 allow list 是否过窄/过宽、状态转移是否造成绕路或卡死、是否有过度验证/过度搜索/过早提交等问题。
- `actor`：根据 critic 的信号修改 skill。当前希望 actor 不只改普通提示词文本，还能改图结构、节点、边、每个节点的工具 allow list、rules、验证和修复策略。
- `re-eval`：用修改后的 skill 重跑 dev/test，观察 skill 是否真正带来可迁移收益。

当前已经在 GAIA 上做过多轮实验，包含 baseline、bootstrap-only、B1/B2 actor 修改、手工强模型改 skill、旧 skill 复跑等。观察到的主要现象：

- 有些 skill 能在 dev 上接近 baseline 或略有提升，但 test 不稳定。
- 旧版本某个 B 类 skill 曾出现较高 test 分数，复跑同 skill 后仍有明显波动，说明 benchmark/执行环境随机性较强。
- 更复杂的 skill 图和更严格的阶段约束，会让小模型 executor 更容易过度遵循流程，增加 step、max-step-hit 和 forced answer。
- GAIA 同时包含 web/search/file/media/multimodal/tool-use/final-answer 多种噪声，导致很难判断失败来自 skill 设计、executor 能力、搜索波动、工具失败、答案格式，还是任务本身不稳定。

现在我想换 benchmark。希望找到近一两年 skill 框架论文实际使用过、对比多、数据/代码相对完整、能展示 skill/状态机/经验迁移价值的 benchmark。尤其希望 benchmark 能支持以下研究问题：

- skill 是否能作为外部工件稳定提升 agent performance；
- critic 是否能从失败轨迹中产生有用的修改信号；
- actor 修改图结构、节点规则、工具 allow list 后，是否能在后续任务或 held-out test 上收益；
- 一个 skill 是否能跨 task family、benchmark split 或相近环境复用；
- 评分是否足够稳定，能区分方法收益和环境随机性。

请你做一次严格的 Deep Research 调研。重点不是泛泛介绍 agent benchmark，而是统计 **2025-2026 年涉及 agent skill / skill library / skill discovery / skill evolution / experience-to-skill / continual skill learning / self-evolving skills / procedural knowledge for agents** 的论文实际跑过哪些 benchmark。

请尽量查广，优先覆盖：

- 2025-2026 年正式论文、arXiv、OpenReview、项目页、官方 GitHub。
- 最近几个月的新 arXiv 也要覆盖。
- 明确提出 skill 框架、skill library、skill learning、skill evolution、skill refinement、skill reuse、experience-to-skill、lifelong skill discovery、self-improving agent skills 的工作。
- 论文中用于横向对比的方法和 baseline 的 benchmark 也要统计，不要只统计它提出的新 benchmark。

## 0. 一页结论

用 8-12 条 bullet 给最终判断，必须回答：

- 哪些 benchmark 是 2025-2026 skill 论文里出现最多、最适合横向对比分数的？
- 哪些 benchmark 最贴近“显式 skill 工件 / skill library / skill patch”？
- 哪些 benchmark 最适合我当前这个 SkillRL / 状态机 / critic-actor skill 修改框架快速迁移？
- 哪些 benchmark 虽然热门，但工程环境、数据许可、hidden test、LLM judge 或随机性会很麻烦？
- 如果只选 1 个主线 benchmark 和 1 个备用 benchmark，你建议选什么，为什么？

## 1. Paper-Centric Table：2025-2026 Skill 相关论文总表

请做一张表。每篇论文一行。至少包含这些列：

| Paper ID | 论文名 | 年份 | venue/status | 方法关键词 | 是否明确涉及 skill | 使用的 benchmark | benchmark 在论文中的角色 | 使用模型和规模 | 主要指标/分数 | 代码/数据是否公开 | 来源 |
|---|---|---:|---|---|---|---|---|---|---|---|---|

要求：

- `Paper ID` 用 `P01, P02, ...`。
- `方法关键词` 例如 skill library、skill discovery、skill evolution、experience replay、self-reflection、continual skill learning、web skill、computer-use skill 等。
- `是否明确涉及 skill` 要区分：
  - `explicit skill artifact`：明确有类似 skill 文件/skill package/skill library。
  - `experience-to-policy/trajectory memory`：更像经验检索或 in-context examples。
  - `tool/workflow policy`：更像流程策略或 tool-use policy。
  - `weakly related`：只和 skill 思想相关。
- `使用的 benchmark` 要列出全部，不要只列主 benchmark。
- `benchmark 在论文中的角色` 要写主实验 / 迁移实验 / 消融 / 补充 / baseline 对比。
- `使用模型和规模` 要写具体模型名和大概大小。比如 GPT-5.2、Claude Opus、Qwen-7B、Llama-8B、70B、frontier API 等。查不到写未查到。
- `主要指标/分数` 写论文里最关键的数字，最好带 baseline -> method。
- `来源` 必须给可点击链接，优先论文和官方 repo。

## 2. Benchmark-Centric Reverse Index：Benchmark 反向索引

请按 benchmark 汇总。每个 benchmark 一行。至少包含这些列：

| Benchmark ID | Benchmark | 类别 | 被哪些论文使用 | 出现次数 | 普通 agent 做一题的自然 workflow | train/dev/test 或官方 split | 评分方式 | 环境依赖 | 代码/数据状态 | 适合当前方法的理由 | 主要风险 |
|---|---|---|---|---:|---|---|---|---|---|---|---|

要求：

- `Benchmark ID` 用 `B01, B02, ...`。
- 按“出现次数 + 近期性 + 方法适配度”综合排序，不要按字母排序。
- `类别` 可选：web shopping、text environment、browser/web agent、document QA、search QA、coding/multi-file、computer-use GUI、DB/text-to-SQL、memory QA、embodied/game、explicit skill benchmark 等。
- `被哪些论文使用` 用 Paper ID 引用，例如 `P02, P05, P08`。
- `普通 agent 做一题的自然 workflow` 要写成 4-8 步，描述 benchmark 原生流程，不要硬套我的 GAIA 阶段。
- `train/dev/test 或官方 split` 必须尽量查清楚题数。没有固定 split 要写清官方协议，例如 hidden test、seen/unseen、family sequence、no-skill/with-skill paired eval 等。
- `评分方式` 要写 exact match、success rate、reward、execution accuracy、pass@k、deterministic verifier、LLM judge 等。
- `环境依赖` 要写 Docker/Harbor、browser service、website accounts、search API、SQLite、GUI/Windows、LLM judge、large corpus download 等。
- `代码/数据状态` 要写官方 repo、dataset、是否易复现。

## 3. Benchmark 详细 Block

请对排名前 10 的 benchmark 写详细 block。每个 block 必须使用完全相同的小标题：

### Bxx. Benchmark 名称

#### 基本定位

简述它测什么能力。

#### 哪些论文跑过

列 Paper ID + 论文名 + 该 benchmark 在论文中的角色。

#### 模型与规模

列论文里用过的模型和大概规模。API frontier 模型也要写清楚。

#### 普通 agent 做一题的 workflow

用 4-8 步描述一个普通 agent 怎么完成该 benchmark 的单题。

#### 数据规模与 split

写 train/dev/test/hidden test/seen-unseen/family split 的数量和协议。查不到写未查到。

#### 评分方式

写主要 metric 和 evaluator。

#### 为什么适合或不适合我的 SkillRL

从这几个角度判断：

- skill 是否能表达为可复用流程/规则/工具策略；
- 是否有跨任务 family 的迁移空间；
- 是否有稳定 verifier/reward；
- 是否能低成本跑 baseline vs skill；
- 是否适合 critic 从失败轨迹中生成修改信号；
- 是否适合 actor 修改 skill 文件、状态机、rules、tool allow list；

#### 工程落地风险

#### 初步优先级

给 `P0/P1/P2/P3`，并一句话说明。

## 4. 三个排序

请给出三个排序，每个排序至少 8 个 benchmark，并解释排序依据。

### A. 最适合横向对比分数的 benchmark

标准：多篇论文使用、指标常见、数据/代码公开、baseline 多。

### B. 最贴近显式 skill 工件/skill library 的 benchmark

标准：能直接评估 skill 文件/skill package/skill patch，或能清楚观察 skill reuse。

### C. 最适合我从 GAIA 迁移并快速跑出结果的 benchmark

标准：工程环境可控、评分稳定、训练/测试划分清楚、能体现状态机/critic-actor 修改 skill 的价值。

### 判断偏好

请按以下偏好做判断：

- 优先“很多论文用过 + 近两年仍活跃 + 数据/代码完整 + 评分稳定”的 benchmark。
- 然后看是否适合我的方法工作流。
- 新 benchmark 如果只有官方论文跑过，也可以列入，但要明确它的价值是“新范式对齐”，不是“已有多论文横比”。
- 旧 benchmark 如果很多新论文仍在跑，比如 WebShop/ALFWorld/ScienceWorld/HotpotQA/WebArena，也要认真列入。
- 不要因为我本地已经有 SQLBench/AgentBench DB adapter 就偏向它们。请根据论文生态和方法适配独立判断。
- 对每个推荐，都要说明它是“适合快速工程迁移”、“适合横向对比”、“适合方法叙事”中的哪一种。

### 严格质量要求

- 不要只看摘要。
- 不要把多个 benchmark 混成一个 block，除非先在表里分别列清。
- 不要只列一个论文用过的新 benchmark 就说它是主战场；要区分“新”和“共用多”。
- 不要漏掉论文里的 baseline benchmark。
- 不要把年份较早但 2025-2026 论文仍在使用的 benchmark 排除。
- 所有关键数字必须带来源链接。
- 结论要直接，允许指出某些 benchmark 不适合。
