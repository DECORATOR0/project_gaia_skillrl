## 1. 背景

当前 GAIA SkillRL 主线已有可参考的思路：

- phase skill：`INIT / ATTACHMENT_PARSE / WEB_RESEARCH / DIRECT_REASON / COMPUTE / VERIFY / REPAIR / CONCLUDE`
- runtime：逐 phase 注入 skill，限制工具白名单和 phase 转移边。
- executor：低成本模型按 `<CALL> / <NEXT> / <ANSWER>` 协议执行。
- critic / actor：从轨迹里归纳失败族，改写 `SKILL.md`。
- run 产物：每题 `state.json`、工具 trace、phase transition、action trace。

迁移项目目标是搭起独立的 “benchmark adapter + 数据下载 + smoke runner + skill 入口” 骨架。正式提分实验等 38B API 到位后再跑。当前只允许用 5.2 做最小冒烟，不能用 5.2 跑正式实验。

## 3. 独立项目结构

建议结构：

- `transfer_skillrl/`
  - `core/`
    - `base.py`：统一 `BenchmarkTask`、`BenchmarkAdapter`、`BenchmarkResult`、`BenchmarkRunner`。
    - `manifest.py`
    - `phases.py`
    - `runner.py`
  - `benchmarks/`
    - `agentbench.py`
    - `tau_bench.py`
    - `terminal_bench.py`
    - `browsergym_bench.py`
    - `sql_bench.py`
    - `webshop.py`
- `scripts/`
  - `prepare_<benchmark>_data.py`
  - `smoke_<benchmark>.py`
  - 可选统一入口：`run_benchmark_smoke.py`
- `data/benchmarks/<benchmark>/`
  - `raw/`
  - `processed/`
  - `manifest.json`
  - `tasks/`
- `external_refs/<repo_name>/`
  - 外部 benchmark repo clone 或 sparse checkout。
- `runs/benchmarks/<benchmark>/...`
- `runtime_state/handoffs/`
- `docs/`

统一 adapter 至少覆盖：

- `prepare()`：下载或校验数据和外部 repo。
- `load_tasks(split, limit, task_ids)`：读 manifest，返回统一 task 对象。
- `build_initial_prompt(task)`：生成类似 GAIA 的 task info。
- `run_task(task, skill, config)`：调用 phase executor 或 benchmark 原生交互环境。
- `score_task(task, trajectory)`：返回 `success`、`score`、`raw_score`、`diagnostics`。
- `write_manifest()`：记录数据来源、commit、依赖、样例数、smoke 命令。

统一初始 phase graph：

| phase | 职责 |
| --- | --- |
| `INIT` | 读任务说明、split、环境信息、答案/产物约束 |
| `INSPECT` | 查 schema、文件树、页面状态、policy、工具列表 |
| `PLAN` | 写出目标字段、操作步骤、验证点 |
| `EXECUTE` | 调 SQL、shell、browser/text env action、domain tool |
| `VERIFY` | 校验结果、状态、约束、格式、policy |
| `REPAIR` | 对一个 blocker 换策略重试 |
| `CONCLUDE` | 输出最终答案或提交产物 |

这版图只作为初始迁移骨架。后续可以为单个 benchmark 改图，但要保留统一接口。

## 7. 六个 benchmark 任务

### 7.1 Stage 01：AgentBench FC DB / OS

定位：第一迁移 smoke，验证统一 adapter、数据 manifest、phase skill 在结构化 SQL / shell 环境上能跑通。

要做：

- 拉取 `THUDM/AgentBench`，优先当前 FC 版。
- 固定 repo commit，写入 manifest。
- 只接 `dbbench` 和 `os_interaction`。
- DB 先支持读取 `data/dbbench/dev.jsonl` 和 `standard.jsonl`，统计 source、任务数、表规模。
- OS 先完成数据入口和 Docker 镜像/worker 启动说明；如 Docker 可用，跑 1-2 题。
- 设计 `AgentBenchAdapter`，把 DB / OS 任务映射到统一 `BenchmarkTask`。
- DB smoke 至少跑 3 题：schema inspect -> SQL plan -> execute -> verify -> answer。
- OS smoke 至少跑 dry-run；如 Docker 环境可用，跑 1 题真实 checker。
- 写 manifest 和 handoff。

注意：

- AgentBench DB 当前更像表格问答包装成 MySQL 环境，报告里要如实说明。
- Docker、MySQL、Redis、端口都要写清楚。

### 7.2 Stage 02：tau2 / tau3 retail + airline text

定位：policy + tool + user 状态迁移，验证 skill 的 policy gate 和状态校验能力。

要做：

- 拉取 `sierra-research/tau2-bench`。
- 使用项目推荐的 `uv` 环境，记录 Python 版本要求。
- 优先 text-mode，先接 `retail`，再接 `airline`。
- 支持读取 `base` split 和 train/test split 元信息。
- 设计 `TauBenchAdapter`，把 domain policy、tools、task 转成统一 task。
- smoke 只跑 1-3 个 text task；如需要 LLM 用户模拟器，使用 5.2 做最小 smoke。
- 记录每轮 user / agent / tool trace，并把最终数据库状态或 reward 写入 score。
- 写 handoff。

### 7.3 Stage 03：Terminal-Bench 2.0 小子集

定位：综合终端任务，验证 plan / execute / test / repair 迁移能力。

要做：

- 找到并拉取 Terminal-Bench 2.0 官方代码和任务 registry。
- 固定 commit 和数据来源。
- 选择 5 个中等或偏小任务作为 smoke 子集，优先依赖轻、时间短、验证确定的任务。
- 设计 `TerminalBenchAdapter`，每题暴露 instruction、workspace、test command、timeout。
- 先支持 dry-run：能列出任务、构建环境说明、生成执行目录。
- 如 Docker/Harbor/Daytona 本机可用，跑 1 个真实 task 到 checker。
- 记录 stdout/stderr、文件 diff、test result。
- 写 handoff。

### 7.4 Stage 04：BrowserGym 小子集

定位：web agent 统一接口。当前阶段以 MiniWoB++ 为 smoke，WebArena / WorkArena 留 skeleton。

要做：

- 拉取或安装 `ServiceNow/BrowserGym` 官方包。
- 优先 `browsergym-miniwob`，选择 3-5 个轻任务。
- 设计 `BrowserGymAdapter`，支持 Gymnasium reset/step、observation、action、reward、done。
- smoke 跑 MiniWoB text/DOM 观察链路，保存 trace。
- 为 WebArena / WorkArena 写 skeleton 和环境说明，暂不强行搭完整服务。
- 如 Playwright / Chromium 需要安装，记录命令和版本。
- 写 handoff。

### 7.5 Stage 05：BIRD / Spider SQL

定位：传统 text-to-SQL / database benchmark，弥补 AgentBench DB 偏表格问答的问题。

要做：

- 拉取 Spider 官方数据或脚本；拉取 BIRD dev / mini-dev 可公开部分。
- 若下载需要 Hugging Face，使用本文件里的 HF token。
- 设计 `SQLBenchAdapter`，统一读取 question、schema、db path、evidence、gold SQL 或 gold answer。
- 支持 SQLite 优先；BIRD 如有多数据库格式，先选最轻入口。
- 实现 execution accuracy smoke：模型生成 SQL 或用给定 SQL 跑通 scorer。
- smoke 选择 5 题，至少覆盖 simple select、join、aggregation。
- 写 handoff。

### 7.6 Stage 06：WebShop text mode

定位：搜索 / 筛选 / 购买动作链 microbench，优先级较低，但适合验证重复流程 skill。

要做：

- 拉取 `princeton-nlp/WebShop`。
- 先用 `simple` text environment。
- 优先小数据模式或 1000 product preview。
- 设计 `WebShopAdapter`，封装 `search[...]`、`click[...]`、`select[...]`、`buy now` 等动作。
- smoke 跑 1-3 个 instruction，保存 observation/action/reward。
- 如 standalone 环境过重，优先复用 AgentBench WS 数据入口，并写明差异。
- 写 handoff。
- 汇总六棒 handoff，生成最终报告。

## 8. 完成判定

每个 benchmark 完成的最低标准：

- 有 adapter 文件或脚本入口。
- 有数据 manifest。
- 有 smoke 命令。
- 有 smoke 日志或 dry-run 日志。
- 有 handoff 文档。
- 对未解决问题给出明确下一步。

六个完成的最低标准：

- 最终报告存在。
- README 或报告里能找到六个 smoke 的入口。
- 后续只改模型配置和并发参数，就能开始正式小批量实验。
