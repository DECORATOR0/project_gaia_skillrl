- 本地 direct 分数明显低于远端 direct baseline。

### 直接修法

1. 本地 vLLM Qwen3 使用 `chat_template_kwargs` 控制 thinking：

```json
"chat_template_kwargs": {"enable_thinking": true}
```

2. 远端 OpenAI-compatible Qwen API 继续使用顶层字段：

```json
"enable_thinking": true
```

3. 本地 stream 请求追加 usage：

```json
"stream_options": {"include_usage": true}
```

4. response 里记录流式拆分指标：

```json
"content_chunk_count": 95,
"reasoning_chunk_count": 819,
"first_content_chunk_index": 822,
"usage": {...}
```

5. 复现实验先用 `c20`，不要直接用 `c100` 判断模型能力。`c100` 会把本地 long reasoning、KV cache 压力、尾部超时一起放大。

6. hidden reasoning 只做统计，不追加回 executor messages。executor 历史继续只追加最终 `content`。

## 排查证据：排除项与根因定位

### 1. direct prompt 和上下文没有发现污染

两条 run 都是 direct baseline executor，执行模式一致：`direct-baseline` ReAct executor。

抽查同一道题的 step1 请求，旧远端和当前本地的 `messages` 完全一致：

- `3f57289b-8c60-48be-bd80-01f8099ca449`
- `50ec8903-b81f-4257-9450-1085afd2c319`

这说明当前 direct 分数下降，主要变量集中在本地 Qwen3 serving / streaming / thinking 适配层。

### 2. thinking 内容没有进入 executor 历史上下文

检查结果：

- 旧远端 run：`316` 个 response 中，`text` 里没有 `<think>` / `</think>`。
- 当前本地 run：`327+` 个 response 中，`text` 里也没有 `<think>` / `</think>`。
- 两边 request history 里都没有 `reasoning_content`。

executor 每一步只把 `result.text` 追加回 messages。当前 client 只从 `delta.content` 取文本，Qwen3 的 `delta.reasoning_content` 没有进入下一步 prompt。

结论：当前没有发现 hidden thinking 污染 executor 上下文。

### 3. max_tokens 请求层没有区别

旧远端和当前本地的 executor request keys 都是：

```text
messages, model, stream, temperature, enable_thinking
```

两边都没有显式发送 `max_tokens`。

旧远端 usage 统计：

- `completion_tokens` 平均 `955.9`，p90 `1589`，最大 `10916`
- `reasoning_tokens` 平均 `778.8`，p90 `1400`，最大 `8046`
- `finish_reason=length` 出现 `3` 次

当前本地 stream 没有返回 usage，因此看不到 token 统计。

结论：请求配置层面，`max_tokens` 没有差异。远端服务端是否存在隐式上限，需要服务端配置确认；从 `finish_reason=length` 看，旧远端至少存在某种停止或长度裁剪行为。

### 3.1 48K 是输入上下文字符限制，两边配置一致

旧远端和当前本地的 runtime 配置里都有：

```json
"max_context_chars": 48000
```

这项由 `_prepare_messages_for_call()` 使用，作用是裁剪 executor 每一步发给模型的历史 messages。它限制输入上下文字符数，单位是 Python 字符长度。

它不限制本次模型生成的 completion tokens，也不限制 hidden thinking / reasoning tokens。模型一旦开始生成，输出长度由 `max_tokens`、服务端默认策略、停止 token、超时共同控制。

direct 对比中，输入上下文没有触顶：

- 旧远端 request message chars：平均 `10412.6`，p90 `14195`，最大 `43137`，超过 `48000` 的请求为 `0`
- 当前本地 request message chars：平均 `10441.9`，p90 `15247`，最大 `31953`，超过 `48000` 的请求为 `0`

结论：这次 direct local 掉分，不能归因于 `max_context_chars=48000` 这项配置差异。两边该配置一致，且 direct 请求没有超过该上限。boot-v3 skill run 的上下文更长，那里需要单独看 48K 输入裁剪对题目的影响。

### 4. stream 开关没有区别，但 stream 形态差异很大

两边请求都是：

```json
"stream": true
```

`chunk_count` 是流式 SSE 返回片段数，可作为生成与流式拆包压力的近似观测。

“流式 reasoning 拆得很碎”的可观测含义是：同一轮模型回复，服务端没有一次性返回完整文本，而是切成大量很小的 `delta` 包持续返回。很多包里只有 hidden reasoning 的一小段，或只有控制信息；当前 client 只累计 `delta.content`，因此 hidden reasoning 包不会变成 executor 可见文本。

它和 token 的关系是近似关系：一个 chunk 可能包含 0 个、1 个或多个可见 token，也可能只包含 `reasoning_content`。所以 `chunk_count` 不能直接当 token 数，但 chunk 从几十变成几千、几万时，通常说明服务端正在长时间生成或传输大量中间 reasoning。

旧远端：

- 平均 chunks：`66.7`
- p90：`106`
- 最大：`688`

当前本地：

- 平均 chunks：`1464.6`
- p90：`1864`
- 最大：`58414`
- 多次出现 `720s` 超时，日志形态为 `2万到5万+ chunks` 且 `0 text fragments`

结论：stream 开关相同，流式协议行为差异极大。这是当前最明确的异常。

### 5. enable_thinking 的适配方式不同

旧远端请求发送：

```json
"enable_thinking": true
```

旧远端返回 usage 中包含 `reasoning_tokens`，说明远端 API 接受或兼容该字段。

当前本地 vLLM 日志反复提示：

```text
The following fields were present in the request but ignored: {'enable_thinking'}
```

这句话只说明“请求里的顶层字段没有被 vLLM 接收”。它不等价于“本地没有生成 thinking”。

从当前现象看，本地 Qwen3 实际很可能仍在默认 thinking 模式下生成：

- 本地启动了 `--reasoning-parser qwen3`
- stream 中出现大量 hidden reasoning chunks，也就是很多只携带 reasoning / 控制信息的小 `delta` 包
- 多次超时形态为 `2万到5万+ chunks` 且 `0 text fragments`

本地 Qwen3 tokenizer template 支持 `enable_thinking`，但 vLLM 需要通过 `chat_template_kwargs` 传入：

```json
"chat_template_kwargs": {"enable_thinking": true}
```

结论：当前本地请求里的顶层 `enable_thinking` 对 vLLM 没有效果。更准确地说，我们没有用 vLLM 认可的方式显式控制 thinking；本地实际表现像默认 thinking 开启，并且同一轮 reasoning 以大量很小的 SSE delta 包返回。

### 6. 本地 reasoning_parser 改变了流式输出结构

本地 vLLM 启动参数包含：

```text
--reasoning-parser qwen3
```

这个 parser 会把 Qwen3 的 `<think>...</think>` 拆成 `reasoning_content`，把最终答复放在 `content`。当前 client 只记录 `content`，所以 run 文件看不到 hidden thinking。

结论：本地没有把 thinking 放进 prompt，但 GPU 仍然在生成 thinking；client 也会一直等待 content。这解释了 `0 text fragments` 超时。

### 7. 并发差异需要纳入复现实验

旧远端 direct 基线是 `c20`。

当前本地 direct 诊断是 `c100`。

本地 vLLM 启动日志显示：

```text
max_model_len=40960
Maximum concurrency for 40,960 tokens per request: 3.45x
```

direct prompt 平均长度和旧远端接近，但本地 long thinking 会显著增加 decode 压力和 KV 占用。

结论：`c100` 结果不能作为干净的模型能力对照。干净复现实验应回到 `c20`。
