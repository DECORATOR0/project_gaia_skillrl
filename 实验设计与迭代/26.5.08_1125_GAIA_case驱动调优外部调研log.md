## 结论先行

当前 GAIA 9B B3/B3-2/B3-3 的调优已经进入 aggregate 分数低信噪比区间。外部资料的一致建议是：停止靠总分盲调，转为 case-level error analysis；prompt/actor 的每次修改都要绑定明确 failure cluster，并且用 success-anchor 做回归保护。

对本项目最有用的操作原则：

1. 先固定 anchor：把 `9b_bootv4_B3` 当作当前最强 anchor，不再把 B3-2/B3-3 线性迭代当成天然进步。
2. 建 case diff 表：对齐 baseline rerun / B3 / B3-2 / B3-3，每个 task_id 标成 win/loss/missing/max-step/tool-fail。
3. 只从 failure cluster 改：每个 prompt/actor 改动必须指向一个 cluster，例如 phase routing、web gather、local extract、compute check、answer format、max-step forced-answer、empty stream。
4. 防止 actor 改坏：critic/actor 输入里必须显式保留 B3 success anchors，actor 只能做 conservative patch，避免整块重写 skill。
5. 把 runtime noise 单列：empty stream、missing、GPU/vLLM、tail retry、工具失败和模型能力混在一个总分里，会把 prompt 质量判断污染掉。

## 来源与可迁移观点

### 1. OpenAI：eval 是改进 LLM 应用的工程入口

来源：[Evaluation best practices | OpenAI API](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

要点：

- 评估是针对具体应用设计的 structured tests，不是只看通用 leaderboard。
- 生成式模型有波动，传统单次测试不足以判断可靠性。
- 对我们来说，GAIA 的 `success/total` 只是第一层；还需要 task-level、trace-level、tool-level 指标。

迁移到 GAIA：

- 主表继续保留 aggregate score，但下一步主分析单位应改成 task_id。
- 每个 task 除 `success` 外，至少加 `phase_path`、`final_answer_nonempty`、`max_step_like`、`web_calls`、`tool_fail`、`empty_stream_fail6`、`missing`。

### 2. Anthropic：agent eval 要看 transcript/trajectory/outcome

来源：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

要点：

- Agent 评估比单轮输出更复杂，因为工具调用、状态和多轮决策会传播错误。
- 他们把 task、trial、grader、transcript、outcome、eval harness 分开定义。
- transcript/trajectory 是调 agent 的关键，不只看最终输出。

迁移到 GAIA：

- GAIA 当前有 state 和 executor_steps，刚好可以做 transcript analysis。
- 现在最该抽的是 `B3 win -> B3-2/B3-3 lose` 的 transcript diff，而不是继续改总 prompt。
- outcome 是最终 `task_success`，但 diagnosis 要回看：从哪一步开始偏离、是否用了错误工具、是否带错答案 contract。

### 3. “Better prompts can hurt”：通用更强 prompt 可能换来任务退化

来源：[When "Better" Prompts Hurt: Evaluation-Driven Iteration for LLM Applications](https://www.researchgate.net/publication/400237421_When_Better_Prompts_Hurt_Evaluation-Driven_Iteration_for_LLM_Applications) / [PDF](https://www.infiniteloopai.cloud/docs-dl/contam_2601.22025v1.When_Better_Prompts_Hurt_Evaluation_Driven_Iteration_for_LLM_Applications.pdf)

要点：

- 论文提出 Define / Test / Diagnose / Fix 的循环。
- 它强调 failure analysis over aggregate metrics：知道为什么失败比单一准确率更重要。
- 实验里“泛化更好看”的 prompt 会让某些结构化任务或 RAG compliance 下降。

迁移到 GAIA：

- B3-2/B3-3 很可能就是“看起来更完善的 skill 破坏了 B3 的任务特化路径”。
- 下一轮 actor prompt 应从“improve skill”改成“patch only diagnosed failure clusters; preserve success anchors”。

### 4. 自动 prompt optimizer 会误判失败原因

来源：[Are Large Language Models Good Prompt Optimizers?](https://arxiv.org/abs/2402.02101)

要点：

- 论文指出 LLM optimizer 在 reflection 中常常不能识别真实错误原因。
- 即便反思语义上合理，单步生成的 prompt 也未必适合目标模型。

迁移到 GAIA：

- 你现在的 offline critic/actor 本质上就是 LLM prompt optimizer。它可能会把随机失败、工具失败、尾部 missing 解释成 prompt 原因。
- critic 输入需要更硬的证据结构：每个建议必须引用若干 case、对应 trace 片段、同类失败模式，并标出可能的 non-prompt confounder。

### 5. Eugene Yan：先标小数据，重点攒失败样本

来源：[Product Evals in Three Simple Steps](https://eugeneyan.com/writing/product-evals/)

要点：

- 从小表格开始，列 input/output/metadata/label。
- 先用 binary pass/fail 或 win/lose/tie，减少主观打分噪声。
- 关键是攒足失败样本，尤其是 50-100 个 failure cases。

迁移到 GAIA：

- 不需要马上做复杂 dashboard。先用 CSV/Markdown 产出 `case_diff_b3_b32_b33.csv`。
- 对每个 task_id 给 binary label：`baseline/B3/B3-2/B3-3 = success|fail|missing|infra_fail`。
- 再人工看 30-50 个高价值失败/退化 case。

### 6. Hamel Husain 系列：error analysis 是核心技能

来源：[Why Your AI Product Needs Evals with Hamel Husain](https://humanloop.com/blog/why-your-product-needs-evals)、[Debugging AI Products: From Data Leakage to Evals with Hamel Husain](https://www.producttalk.org/debugging-ai-products-from-data-leakage-to-evals-with-hamel-husain/)

要点：

- AI 产品调优要反复看 logs、做 error analysis，并校准 human/LLM judge agreement。
- 如果 eval 说好但用户/开发者觉得坏，eval 本身会失去可信度。

迁移到 GAIA：

- 你现在的“看分数没法调”正是需要 error analysis 的信号。
- 先别让 GPT-5.4 actor 自己总结全部失败。先由脚本把 failure buckets 做硬分类，再让强模型解释每个 bucket。

### 7. 真实工程案例：不要指望换模型，先做观测和隔离

来源：[80 prompts, zero evals: fixing an LLM pipeline after launch](https://teotti.com/80-prompts-zero-evals-fixing-llm-pipeline-after-launch/)

要点：

- 案例里问题解决靠 instrumentation、audit trail、按字段分解错误、prompt architecture 隔离迭代。
- 更好的模型不是第一修复手段。

迁移到 GAIA：

- GAIA skill 也要按 phase/behavior 隔离修改，避免 actor 一次改很多东西。
- 例如只改 `WEB_GATHER` 的搜索 pivot，不碰 `LOCAL_EXTRACT` 和 `COMPUTE_CHECK`。

### 8. Anthropic：agentic eval 的基础设施噪声要单独控制

来源：[Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise)

要点：

- 小分差可能来自资源配置、环境噪声和运行条件。
- 资源配置要像 prompt 和 temperature 一样被记录和控制。

迁移到 GAIA：

- 你现在的 `empty stream`、`missing`、vLLM endpoint、GPU location、并发、tail policy 都必须进 case 表。
- `33/82 vs 34/82` 这种 1 分差不能单独解释为 prompt 改进。

### 9. 知乎中文材料：prompt 敏感，测试迭代不可省

来源：

- [Prompt Engineering(提示词工程)，看这一篇就够了 - 知乎](https://zhuanlan.zhihu.com/p/1945859590374818361)
- [自动生成prompt：Automatic prompt engineering - 知乎](https://zhuanlan.zhihu.com/p/672206721)
- [大语言模型生成内容评估用什么方法? - 知乎](https://www.zhihu.com/question/9667230918/answer/1980309800064685449)

要点：

- 中文材料普遍强调 prompt 高敏感性、需要测试再调优。
- 自动 prompt 工程的前提是有评价函数和候选比较。
- 大模型评估要按任务类型拆指标。

迁移到 GAIA：

- 小模型 9B 的 prompt 更敏感，actor 一次改太多会引起不可控回归。
- 自动 actor 迭代要配合固定 eval bank 和 regression buckets，否则只是在生成新 prompt。

## 调优决策树

### 情况 1：B3 成功，B3-2/B3-3 失败

结论：actor 过度改写或破坏 success anchor。

动作：

- 回滚到 B3 作为 base。
- actor prompt 改成 conservative patch。
- critic 必须列 success anchors，actor 禁止修改这些 anchor 覆盖的 phase/rule。

### 情况 2：B3 失败，B3-2/B3-3 成功

结论：迭代救了某个局部模式。

动作：

- 提取局部规则，merge 回 B3。
- 不整块采用 B3-2/B3-3。

### 情况 3：全版本失败

结论：优先怀疑能力、工具、搜索、文件解析、答案格式或 runtime。

动作：

- 按工具/phase 进一步分桶。
- 不用大 prompt 改所有阶段。
- 先修 deterministic bug 或工具路由。

### 情况 4：只有 1-2 分变化

结论：先按噪声处理。

动作：

- 检查 missing、empty stream、max-step、endpoint、并发、是否同题重复。
- 不据此调整 actor 范式。

## 对下一版 critic/actor 的修改方向

把 actor 从“生成更好的 skill”改成“带证据的补丁系统”。

建议给 critic 的输出 schema 加：

- `failure_cluster_id`
- `supporting_task_ids`
- `first_divergence_step`
- `phase_or_tool`
- `suspected_root_cause`
- `non_prompt_confounders`
- `success_anchor_to_preserve`
- `proposed_patch_scope`

建议给 actor 的约束加：

- 每次只 patch 1-3 个 failure clusters。
- 禁止重写没有证据支持的 phase。
- 对 B3 成功 case 涉及的 phase transition 做 preserve。
- 输出 patch diff / rationale / affected failure bucket。
- 若失败主要来自 missing/empty stream/tool error，actor 必须标注 `no prompt patch recommended`。

## 给当前 GAIA 的短结论

B3-2/B3-3 的总分说明：继续线性自举没有明显收益。下一步要用 case diff 找出 B3 的稳定收益来源，以及 actor 迭代破坏了哪些行为。只有当 failure cluster 清楚以后，才决定调 critical actor 范式、skill 局部规则、runtime/tooling，或停止该分支。
